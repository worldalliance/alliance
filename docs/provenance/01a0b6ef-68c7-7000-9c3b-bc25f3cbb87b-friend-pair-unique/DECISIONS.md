- The fix comes from a review of 890cfd771 ("Refuse a friend request to an existing friend"). That commit checks for a row in either direction before inserting. When A and B send each other a request at the same moment, both checks see no row, both inserts succeed, and the pair gets two rows. A temporary e2e test reproduced this in 10 of 10 rounds. The user asked for every review finding to be fixed.
- The database now enforces one row per pair. `Friend` has two stored generated columns, `lowUserId = LEAST(requesterId, addresseeId)` and `highUserId = GREATEST(...)`, with a unique constraint on the two. I picked these over an expression unique index because the e2e database is built with `synchronize`, which skips `synchronize: false` expression indexes, so the race test would run without the constraint. Generated columns also let `migration:generate` write the migration.
- On a unique violation, `createFriendRequest` runs once more instead of answering 409. The retry reads the row that won, so the loser of a crossed race accepts the other request, the same result as sending it a moment later. A review pointed out that a 409 there shows an error to someone whose request should have made them friends. One retry is enough because the winning row is committed by the time the violation comes back. A second violation propagates. The refused attempt's notification was saved in the same cascade transaction, so it rolls back and is never sent.
- The old unique constraint on `(requesterId, addresseeId)` is dropped. Any two rows equal on it are also equal on `(lowUserId, highUserId)`, so it only cost an index.
- I hand-edited the generated migration. TypeORM wrote this worktree's database name (`alliance_tanstack`) into its `typeorm_metadata` inserts and deletes. It reads those rows back filtered by the current database name, so any other database, prod included, would lose the generated-column expression, and its next `migration:generate` would drop and re-add both columns. The edit uses `current_database()` instead. Re-running `migration:generate` afterwards found no changes. `migration:revert` then `migration:run` both succeed.
- The migration doesn't clean up pairs that already have two rows. A fresh staging dump (988 rows, taken 2026-09-19) has 0 such pairs, and the migration's statements ran against it. Prod wasn't queried. If prod has one, adding the constraint fails and the migration rolls back instead of leaving the data half-changed.
- The commit comes right after 8b91d6491 ("Reuse a declined friend request when the other user sends one back"). Before that commit, sending back to someone who declined your request inserts a second row for the pair, which the constraint would now reject.
- The e2e test forces the race instead of firing two requests at once and hoping they overlap. A review found that version passed 20 of 20 runs with the constraint removed. The test stubs the friend repository's `findOne` to miss twice, so B's lookups don't see A's pending row, then checks that B's request returns 201 and leaves one accepted row. It fails without the constraint (two rows) and without the retry (409).
