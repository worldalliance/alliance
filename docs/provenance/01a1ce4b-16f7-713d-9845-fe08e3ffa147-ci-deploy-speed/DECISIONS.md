# Decisions

## Deferred to the implementing agent

- **How the work splits into PRs is undecided.** The proposal offered separate PRs per part, but the user didn't address that. Recommendation: one PR per independent part, in this order:
  1. Visual regression removal and the mobile bundle check.
  2. E2e sharding and instrumentation.
  3. Deploy concurrency.
  4. Runtime config for the web bundles.
  5. Promotion and the override.

  Promotion depends on both concurrency (its stale skip) and environment-neutral bundles, so it goes last. Each PR is its own provenance task naming this one.

- **The lock goes on the job in each entry point that calls the reusable deploy workflow.** Job-level concurrency on ordinary jobs locks each job separately, so one lock over deploy and smoke checks needs the calling job to hold it. GitHub allows `concurrency` on a job that calls a reusable workflow (EVIDENCE.md, "Deploy concurrency"). Origin: agent decision.
- **A production run waits for staging before it takes the production lock.** The wait is part of the promotion check, and checks run without any lock, so a queued override never waits behind it. If staging still isn't fully green when the wait ends, the run refuses as for a missing green run, naming what to push instead. Origin: agent decision.
- **The reusable deploy workflow takes the deployed commit as an input and passes it to every checkout and to `VITE_APP_GIT_SHA`.** Today these use `github.sha` (`.github/workflows/deploy.yaml:19,93`), which for the override's dispatched run is the dispatch ref, not the commit it deploys. Origin: every second-opinion reviewer named it; agent decision.
- **`publish-mobile-ota.yaml` tells a standalone dispatch from a call by its inputs, not `github.event_name`.** A called workflow sees its caller's event, so under the override its dispatch-only steps (`.github/workflows/publish-mobile-ota.yaml:49,70,85`) would run with `inputs.ref` empty, and Checkout Release would fall back to the dispatch ref. A call passes the environment and the commit; a standalone dispatch passes `ref`. Origin: second-opinion reviewers; agent decision.
- **Live state for each environment is recorded in one place both entry points write: a GitHub deployment per environment through the Deployments API.** The OTA dispatch guard reads the last successful production deployment instead of `deploy.yaml` runs with `branch=production&status=success` (`.github/workflows/publish-mobile-ota.yaml:62`), which misses an override run, whose branch is the dispatch ref, and counts a run whose deploy succeeded only if every later job did too. The staging guard reads the same record: it skips when the last successful staging deployment's commit is a descendant of the deployed commit other than the deployed commit itself. Origin: second-opinion reviewers proposed the Deployments API; agent decision.
- **"The current `production` branch" in the refusal requirement is the branch's tip.** A refused push has already moved it to the refused commit, and git accepts only a fast-forward from the tip, so the refusal names only descendants of that commit. The branch then names a commit that isn't live, as after a failed override deploy, and the deployment record says what is. It stays there until a fully green descendant is pushed. Deploying a commit older than the tip goes through the override, and the reconcile step stays for after an override. Origin: agent decision.
- **When no commit qualifies and no staging run is in progress for one, the refusal says so.** It names the pushed commit's staging run and its failed or skipped jobs, says a fix has to land on `main` and deploy fully green to staging before the next push, and mentions the override for urgent cases. A missing run or expired artifacts are named as such. After an override, the refusal names the reconcile step instead, per the entry below on every override blocking production pushes. Origin: agent decision.
- **"The newest for production" is the commit the `production` branch points at when the deploy acquires the lock.** A push sets it and so does the override, so a push run queued behind an override, or behind a later push, skips. Origin: agent decision.
- **The override moves the `production` branch when it acquires the lock, before deploying, with a lease on the value it read.** Moving it first makes git reject any `main:production` push lacking the fix from that moment, instead of letting a push that lands mid-override deploy after it and drop the fix. It is a forced update, since an override that rolls back moves the branch to an ancestor. A failed lease fails the run loudly. If the deploy then fails, the branch names a commit that isn't live; the deployment record says what is, and the next override or the reconcile step corrects it. The override needs `contents: write`. It moves the branch with `GITHUB_TOKEN`, whose pushes don't start workflow runs (EVIDENCE.md, "Deploy concurrency"), so moving the branch doesn't trigger `deploy.yaml`; a token of any other kind would start a promotion run that finds no green staging run. Origin: agent decision.
- **Every override, a rollback included, blocks production pushes until the reconcile step runs.** Each override marks its GitHub deployment as an override, and promotion refuses while the live production deployment carries that mark, naming the reconcile step. Git alone rejects only an off-`main` commit: after a rollback to a commit on `main`, the next `git push origin main:production` would fast-forward and redeploy the bad release from a `main` that may still hold it. The reconcile step's confirmation that `main` contains the fix covers a revert on `main` the same way. Origin: agent decision, for the rollback recovery the user asked to have decided.
- **A rollback doesn't revert migrations.** `scripts/deploy_backend.sh` only runs migrations forward, so rolled-back code runs against the newer schema. The override's dispatch form and run summary say to roll back only to a commit whose code works with the migrations already run; under the root `AGENTS.md` **Breaking changes**, an expand step keeps the previous release working, but a contract step doesn't. Origin: agent decision.
- **The reconcile step is a third thin workflow calling the reusable deploy workflow.** Its dispatch inputs are the destination commit, the expected `production` commit, the `main` commit or PR holding the override's fix, and a confirmation that must be ticked. Under the production lock it moves the branch with the lease and `GITHUB_TOKEN`, as the override does, then promotes the destination's staging artifacts, so the branch and the live deployment agree when it finishes. Both commits and the named fix go to its deployment record, Slack post and run summary. Origin: agent decision implementing the reconcile requirement.
- **The guidance for a rejected or refused production push** lives in the override's Slack post and run summary, the promotion refusal, and next to the documented `git push origin main:production` command, and says to run the reconcile step, not to force-push. Git prints its own non-fast-forward error, which the repo can't change. Origin: agent decision.
- **The override doesn't trigger the staging mobile build.** `build-staging-mobile.yaml:16-19` listens for completed runs of the workflow named `Deploy` on `main`; the override is a workflow under another name, so a dispatch from `main` doesn't match. Keep it named apart from `Deploy`. Origin: second-opinion reviewers found the trigger; agent decision.
- **The override publishes the production OTA update like every production deploy.** Origin: agent decision.
- **The hosts roles pin the reusable deploy workflow in place of `deploy.yaml`, and widen no further.** In a job of a called workflow, GitHub's token names the called file in `job_workflow_ref` and the caller's context in `ref` and `sub` (EVIDENCE.md, "Infrastructure changes"). Once the host deploy jobs move into the reusable workflow, today's pins to `deploy.yaml` (`terraform/ci-oidc.tf:79-92`) stop matching. `staging-hosts` keeps `refs/heads/main` and its branch rule, and its `job_workflow_ref` names the reusable workflow on `main`. `production-hosts` accepts `ref` `refs/heads/production` with the reusable workflow on `production`, for promotion, and `refs/heads/main` with the reusable workflow on `main`, for the override and the reconcile step, per the requirement that they start from `main`; its environment's branch rule adds `main`. A local reusable workflow is called at the caller's commit, so each `job_workflow_ref` carries the caller's branch, and no other file on `main` can assume the role. The trust change rolls out by expand and contract under the root `AGENTS.md` **Breaking changes**. Before the workflow change merges, the user applies a plan trusting both files and the coordinating agent adds `main` to the `production-hosts` branch rule; a later plan removes `deploy.yaml` once the change is live. Origin: agent decision, from review.
- **The production freeze check checks out the deployed commit by SHA in the reusable workflow, before any deploy job.** On staging the check runs in `exists` mode, which passes whatever `dirty.txt` holds, so a green staging run says nothing about the freeze. Origin: agent decision implementing the freeze requirement.
- **Each shard's per-file timings come from a JUnit report,** `bun test --reporter=junit --reporter-outfile=<file>`, not Bun's timings file (EVIDENCE.md, "E2e sharding and variance"). Origin: agent decision.
- **The production run must fail loudly when staging's artifacts are gone,** for example expired, never silently rebuild. Downloading another run's artifacts needs `actions: read` and that run's ID (EVIDENCE.md, "Promotion").

Origin: reconstructed from existing code.

## Consequences of the requirements

- **The shard-coverage check is dropped.** It was proposed to catch shards reading different timing files. Without timings, Bun's split by name is deterministic, so it has no job.
- **Admin's `index.html` needs a `Cache-Control` header** so browsers revalidate it after a deploy. Today it gets none (`deploy/nginx/alliance_admin.conf:34-40`).
- **The `server/package.json` e2e script carries `--concurrency 1`,** which isn't a Bun 1.4.4 `bun test` flag (absent from `bun test --help`). Remove it when the script changes for sharding.
- **Removing visual regression from Terraform touches:**
