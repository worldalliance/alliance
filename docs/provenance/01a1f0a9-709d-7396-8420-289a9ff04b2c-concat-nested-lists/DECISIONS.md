# Decisions

- **Fix the shared declaration, not only the expression check.** (agent decision) The issue offered a `concat` the expression check declares for itself. The older variable formula checker (`common/src/forms/variable-formula-check.ts`) reads the same `formula-lib.ts`, and its evaluator also calls native `concat` (`common/src/forms/variable-expression.ts`), so it had the same mismatch: `[[2]].concat([1])` was typed `number[][]` and ran as `[[2], 1]`. One declaration that matches how both runtimes run `concat` fixes both.
- **`concat(...items: (readonly T[] | (T extends readonly unknown[] ? never : T))[]): T[]`.** (agent decision) Native `concat` spreads every list argument, so a list argument has to hold items of the receiver's type, and only a value that isn't a list can be one item. The conditional distributes over a union item type, so `[1, [2]].concat([3], [[4]])` still types as `(number | number[])[]`, as it runs. `ConcatArray<T>` and `Exclude` aren't available, since the checkers run `tsc` with `noLib` and `formula-lib.ts` as the only library.
- **The rejection points at `tsc`'s own message.** (agent decision) `[[2]].concat([1])` reports "Type 'number' is not assignable to type 'number[]'." at the `1`, and an argument held in a variable reports that its list type isn't assignable to `readonly number[][]`. No extra wording was added, matching how the check reports other `tsc` type errors.
- **No stored formula breaks.** (agent decision) Tightening a type check is a breaking change for any stored formula that relied on the old typing. In the local database, a staging copy, no `form_snapshot.schema` and no `custom_validator.expression` contains `concat(`, checked 2026-11-18. Expressions in the new language aren't stored anywhere yet (ALL-2195).
