1. **Where the sync reads its values.** Its own keys live under `/alliance/staging/db-sync/`, and it reads the seven `DB_SYNC_KEYS` names from there, so a stray parameter under that path never reaches the sync or its children; from `/alliance/staging/server/` it reads only `DB_HOST`, `DB_USERNAME`, `DB_PASSWORD` and `ASSETS_BUCKET`. The staging login stays in one place, so rotating it can't silently break the sync, and the sync gets none of the server's other secrets. `scripts/secrets_run.sh` gains a `--path <prefix> [NAME...]` form for this; its no-argument form, which pm2 and the deploy use, is unchanged. (Codex proposal, agent decision.)
2. **The production login on the staging host.** The sync keeps the read-only production user it already used, stored under the staging path. Checked on 2026-11-14 (EVIDENCE.md): not superuser, member of `pg_read_all_data` only, no write privilege on any table, sessions read-only by default. Running the dump from the production host instead would remove the credential from staging but is a redesign of a working sync. (Agent decision.)
3. **No password rotation in this task.** Rotating the read-only user is a write to production and would mix two changes; the file was mode 600 on one host. The commented-out pair in `db-sync.env` was the production server's master login, already in `/alliance/prod/server/`; whether its old copies call for rotation belongs with ALL-2209's kind of review. Other choices:

- **The sync re-runs itself through the wrapper** instead of the systemd unit calling the wrapper, so the unit and the `systemd-run` command its Slack messages give for a manual run work unchanged. A failure to load stops it before it can post to Slack; the healthcheck's missing ping covers that, as it already covered a file that wouldn't source. (Agent decision.)
- **Database names come from committed config** through `scripts/deployed-db-name.ts`, since `DB_NAME` is committed and not in Parameter Store. A new script, rather than a line in `scripts/deployed-config.ts`, because the deploy's `deployed-config` action requires that script's output to match its own outputs exactly. The two share their argument handling through `scripts/deployed-config-arg.ts`. (Agent decision.)
- **Logins go to libpq through `PGHOST`/`PGUSER`/`PGPASSWORD`/`PGDATABASE`**, not `postgresql://user:password@…` URLs in argv, which any user on the host can read through `ps`. The sync built such URLs before this task; it changes here because the task moves those same credentials. The PostgreSQL docs advise against `PGPASSWORD` because some systems show a process's environment to other users through `ps`, and suggest a password file (vendor recommendation, [libpq environment variables](https://www.postgresql.org/docs/current/libpq-envars.html)); on the Linux staging host only the process's user and root can read `/proc/<pid>/environ` ([proc(5)](https://man7.org/linux/man-pages/man5/proc_pid_environ.5.html)), and the environment keeps the password off disk. (Codex finding, agent decision.)
- **`PROD_ASSETS_BUCKET` and `PROD_DB_HOST` are stored in `db-sync`**, since the server keeps its own `DB_HOST` and `ASSETS_BUCKET` in Parameter Store, and the staging role can't read production's path. (Agent decision, following `server/src/config/env.ts`.)
- **Rollout** follows requirement 4: the parameters and grant go in before merge so the first staging deploy's sync finds them, and `db-sync.env` stays untouched until then as the way back. Until this merges, `main`'s `parameter-drift` reports the seven parameters as under no known consumer; the PR's own run checks them with this branch's `DB_SYNC_KEYS`. (Agent decision.)
