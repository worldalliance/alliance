- `eventInEffectAt` moves from `server/src/actions/utils/action-event.ts` to `common/src/actionEvent.ts`, beside `hasTakenEffect`, and accepts serialized dates so clients can call it on DTOs. The server imports it from there.
- "Has the member-action phase started" had a server implementation (`findStartedMemberActionEvent` and `hasMemberActionStarted` in `server/src/utils/action-user.ts`) and three client copies: the admin dashboard and the legacy `viewer`-less fallbacks of `canCompleteAction` and `deadlineHasPassed`. Both functions move to `common/src/actionEvent.ts`, typed over `{ date: Date | string; newStatus: string }` so server entities and client DTOs both fit, and every copy calls them, as do the admin home placement's started check and its check that a follow-up's parent has opened. Common names the status as the `"member_action"` literal, as `common/src/taskBadge.ts` already does. The server spec that calls `hasMemberActionStarted` with `ActionStatus.MemberAction` keeps the literal tied to the enum.
- The admin home placement's `statusAt`, the dashboard's current event, and the admin action list's `getLastPastEventDate` go through `eventInEffectAt`. `getNextEvent` goes through `eventInEffectAt(...).nextEvent`, so it returns the earliest upcoming event instead of the first upcoming one in array order.
- The `date <= now` filters in `shared/lib/actionEventsPanel.ts` decide which action updates and timeline items are shown yet, a separate "don't show future items" rule, so they stay separate. `actionStatusReflectsPastEvents` in `shared/lib/useOnNextDeadline.ts` compares against the refetch timer's skewed timestamps, not the boundary itself, so it stays too.
- Choosing which member-action event opens the phase and which event closes it (first vs latest member-action event, `getDeadlineTimestamp`) is a separate design question and is filed as a follow-up.
