- These changes come from seven reviews of "Fail a friend query when the server refuses it". Each time the user asked for every finding to be fixed, including the nits, and asked that no REQUIREMENTS.md change; the fourth, fifth and sixth asked for `web-client-default` to be filed in Linear instead of fixed. There is no REQUIREMENTS.md here because nothing in this work came from the user beyond those instructions.
- Finding `body-status`: the retry rule read `statusCode` out of the body `@hey-api/client-fetch` throws, which is a NestJS convention and not anything HTTP guarantees. A refusal shaped by anything else fell through to the retry branch and still cost four requests: measured against `serveApi`, four attempts each for a 400 bodied `{ message, errors }`, a 401 with an empty body, and a 401 answered in plain text. The first is what NestJS returns for an exception built from an object literal, which drops `statusCode` — `tasks.service.ts:276` and `actions.service.ts:1340` do that today — and the other two are what a proxy in front of the API answers with. `registerErrorStatus` puts `response.status` on the error from the client's error interceptor, the one place that still holds the response, so the rule reads a status that is always there. It is the first commit of the task, ahead of the rule that reads it, so no deploy has the rule trusting a field that can be missing. The provenance directory starts here.
- This was ALL-1111's second half, "worth doing at the same time" as the `throwOnError` sweep. It is split off because it preserves object bodies and adds the response status. Non-object bodies stay under `body` for logging, which `errorMessage` ignores so a proxy's HTML error page leaves the caller's fallback intact. The sweep stays in ALL-1111, since it changes what 79 call sites return.
- Registered from each app root and from `serveApi`, rather than from `createClientConfig`. That function runs while `createClient` is still building the client, so there is no `interceptors` to register on yet. `serveApi` takes it so a test sees the error every app ships; four assertions on the old shape took the status code, in `serveApi.test.ts` and `useBackfillTimeZone.test.ts`.
- `useDeleteComment` and `useLoadComments` pass `throwOnError: false` to hold on to the response their `refusalMessage` call reads the status off, and say so in a comment. The interceptor makes that unnecessary, and they are left alone: rewriting them is a second change, and neither is part of the friend queries this task covers.
- Finding `retry-on-refusal`: a query that throws gets React Query's default of three retries, and the web `QueryClient`s set no `retry`, so a 401 or 404 was retried three times even though it cannot succeed. Measured: four requests per query. On web each 401 also re-enters the refresh wrapper in `shared/lib/hey-api.ts`, so a profile page reading all five friend queries made about twenty requests and as many refresh attempts. `retryUnlessRefused` in `shared/lib/retryQuery.ts` now holds the rule, and the three `QueryClient`s take it, mobile keeping the two retries it already asked for. The rule covers every query in each app rather than these five, so it is its own commit, the one ALL-1112 asked for. It reads the `statusCode` the commit before it leaves on every error the client throws.
- Finding `retry-storm`: that commit now comes first, ahead of the one that makes the five friend queries throw, so no deploy sits in the window where a refused friend read costs four requests and four refresh attempts. Nothing in the retry rule needs those queries to throw: mobile's client already threw on every refusal, and the web hooks that pass `throwOnError` per call already paid the retries. Leaving the order alone was the other option, on the argument that the branch ships whole, and it was rejected because a per-commit deploy is the thing the ordering is for. It sits second, behind the commit that gives an error its status code, since the rule reads that status.
- Finding `retryable-4xx`: the rule gave up on every status from 400 to 499, and 408 and 429 are the two a later attempt can still satisfy, since there the server is asking the caller to wait rather than settling the question. `RETRYABLE_REFUSALS` holds them. Nothing reaches it today: the only rate-limited read is `GET /link-preview`, and `useLinkPreview` already sets `retry: false`. It still matters, because this rule is now the default for every query in three apps, so the next throttled read would lose its retry with nothing in the diff to say so. Leaving the blanket and naming the choice in the comment was the other option, rejected because a comment does not stop the bug. The client drops the response, so a retried 429 falls back to React Query's backoff instead of the server's `Retry-After`; the error interceptor the commit before this one registers still holds the `Response`, and is where that header would have to come from. It carries the status code and nothing else, since no caller asks for `Retry-After` yet.
- Finding `two-checks`: `refusalStatus` returned a status or `undefined`, and the caller tested for `undefined` again before the range check. One `isRefused` predicate says the same thing in one place, and drops a parse that reports failure as `undefined`.
- Finding `weak-test`: the test for a request that never reached the server called the rule directly with a `TypeError`, which every error passes, since `failureCount` 0 is under 3 for anything the rule does not refuse. The route throws from inside the fetch now, so a real rejection reaches React Query and the attempt count is what the test reads. The refusal and retry cases are tables, 400, 401, 403 and 404 against 408, 429 and 500, so both edges of the window and both carve-outs are pinned. Checked by emptying `RETRYABLE_REFUSALS`: the 408 and 429 cases fail.
- Finding `unused-seam`: the file threw away what `serveApi` returned and passed `throwOnError` per call, a shape no app ships. It takes `throwingOnRefusal` now, which configures the client the way mobile configures it, and mobile is the client every query in this rule runs under.
- ALL-1112's closing comment described the rule as it stood before this round, down to the sha and the request counts its tests assert. It was rewritten in place rather than answered with a second comment: the issue is closed, so nobody is mid-conversation there, and a correction left standing beside the version it corrects keeps the wrong one readable.
