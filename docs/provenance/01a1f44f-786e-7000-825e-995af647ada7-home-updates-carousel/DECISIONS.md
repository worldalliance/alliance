# Decisions

- **Updates mean action updates.** The carousel holds the recent action updates the web "Updates" row showed. General updates keep their current places: listed below the carousel on web, and stepped through with tasks on mobile. (agent decision)
- **Five updates in the carousel, three in the sidebar**, through `HOME_UPDATES_LIMIT` in `shared/lib/useActionUpdates.ts`, which both apps read. The tasks route prefetches that query in place of the Alliance-wide feed it no longer shows. (agent decision)
- **Bounded, not looping.** Swiping stops at the first and last update, and the dots show the position. Web reuses `useBoundedIndex`. (agent decision)
- **Showing a card doesn't mark it read.** As with the old row, an update counts as read only once it's opened, so its unread dot doesn't disappear the moment the page loads. (agent decision, keeping existing behaviour) "New" is decided in one place, `useActionUpdateNewState` in `shared/lib/useActionUpdates.ts`: the update with the latest date (`newestUpdateId`), or one with an unread notification. Opening the newest update marks its notification read but it keeps "New" until a newer update is published. (agent decision)
- **Slide motion.** On web, a 300 ms ease-out CSS transform, within the 150–400 ms transition range in `ux-forms-platform`, with none under `prefers-reduced-motion`. Touch swipes of 50 px or more that are more horizontal than vertical change slide, and vertical page scrolling still works (`touch-pan-y`). On mobile, native horizontal paging with the dots following the drag; while a scroll started by the controls is in flight, the selection waits for it to land, so it doesn't snap back to the slide being left. Controls scroll without animation when Reduce Motion is on, and the dots' 150 ms width change follows Reanimated's default of respecting the system setting. Each slide's content is memoised, so changing slides re-renders only the thin wrappers. Off-screen slides are `inert` on web and hidden from screen readers on mobile. The slide area is `aria-live="polite"` and labelled "N of M", following the WAI-ARIA APG carousel pattern for a carousel that doesn't rotate automatically. (agent decision)
- **Dots only, on web too.** The Previous and Next buttons are gone from the mobile app, as required, and from web's narrow-window carousel, which is what mobile browsers show, so both platforms keep one control row: centred pill-shaped dots. Each dot is a button that jumps to its update, which keeps a single-pointer alternative to swiping for WCAG 2.5.1 (pointer gestures). The desktop sidebar has no carousel. (agent decision)
- **Narrow web screens.** The progress bars that sat above the tasks below 1150 px now come after the updates, so the task card opens the page as required. (agent decision)
- **Full list of updates.** Mobile had no list of all action updates, so `app/(app)/action-updates.tsx` mirrors web's `/action-updates` page. Both now render `HomeUpdateCard`: one column on mobile and narrow web, two from the `sm` breakpoint, so each card stays wide enough for its facepile. Unread state and marking read come from `useActionUpdateReadState` in `shared/lib/useActionUpdates.ts`, split out of `useHomeActionUpdates` so the tasks page and the list share it. The list no longer shows each update's full body, and an update counts as read once opened rather than once listed, as on the tasks page. With no caller left passing `onActionPageTimeline={false}`, that prop is removed from both `ActionUpdateCard`s. (agent decision, following `apps/AGENTS.md` web-mobile parity)
- **Mobile scroll-to-end.** With updates now below the task, the follow-up form's scroll-to-end measures the task body in both scroll branches instead of scrolling to the bottom of the content, so it doesn't scroll past the form into updates. (agent decision)
- **Mobile section heading.** The "Project updates" heading lives in `HomeUpdatesCarousel` at the default text size, semibold, `text-zinc-500`, matching "See all"'s size. With the activity heading gone, the `HomeSectionHeading` component had one caller left, so it is inlined and deleted. (agent decision)
- **Quoted font names on mobile web.** `resolveFontFamily` in `components/system/Text.tsx` quotes multi-word family names on web. CSS drops an unquoted name with a word starting with a digit, so every Source Sans 3 weight fell back to the system font at regular weight in the mobile web preview. Native is unchanged. This lets reviews in the preview show the real type, such as the semibold update title. (agent decision)
- **Links to the updates page.** Following REQUIREMENTS.md, the side navigation items this task had added are gone again, and the Information page entry (`InfoEntryId.ActionUpdates`) and the Actions page link, both older than this task, are removed. The admin panel keeps its own "Action updates" page, and `zoneLinks` still maps `/action-updates` between the member and admin apps for staff switching between them. (agent decision)
- **"See all" link style.** Web reuses the activity headline's project link classes, `font-medium text-green hover:underline`; mobile uses `text-green` at medium weight in a pressable at least 44 pt tall. The green, rgb(98, 161, 36), is about 3.2:1 against white, short of WCAG 1.4.3's 4.5:1 for text this size; the app's other green links share it, and the requirement asks for that style, so this departs from `ux-guidelines` at the user's request. (agent decision)
- **Card content.** The title is clamped to two lines and the excerpt, the first text block as plain text, to three. The project name above the title truncates to one line. "New" is a word in a green chip, so unread isn't shown by colour alone; the date chip is white at 90% opacity so it reads on any photo. The whole card is one link to its task page, and opening it marks its notification read; "Read" and the arrow are part of that link, not a separate control. On web the photos zoom by 3% on hover over 300 ms, and the card's shadow over 200 ms, both off under reduced motion. (agent decision)
- **Card image.** The photo list follows REQUIREMENTS.md: `updateCovers` in `shared/lib/actionUpdateCard.ts` lists the card image, then every image in the update's image blocks, skipping a body image whose upload key the card image was rendered from (`echoesStoredKey`), so a picked image doesn't appear twice. `useUpdateCardContent` turns that into at most three mosaic tiles plus the hidden count, and drops a photo that fails to load, falling back to the placeholder when none are left. The update's own card image lives in a nullable `action_update.cardImage` column holding an upload key, and members receive it as a URL through `getImageSource`, as project images are. The project's cover comes from an optional `actionImage` on `ActionUpdateDto`. Both are additive, so older clients ignore them, and the migration only adds a nullable column, so it can deploy ahead of the code. (agent decision)
- **Card image input.** `UpdateActionUpdateDto.cardImage` accepts an upload key or null and refuses anything else, so a card image is always one the admin uploaded or one already in the update. The admin field sits on the update's Details tab and saves with that tab's Save button rather than on its own, so saving it can't overwrite other unsaved details. It shows a 3:2 preview, an upload button, the update's own uploaded images to pick from (linked images can't be picked, since they aren't upload keys), and a remove button. The form sends the field only when it changed, so a save never writes back the URL the field was rendered from. (agent decision)
- **Local data for the image survey.** The image counts behind option 1a came from the local database, last loaded with data up to 4 November 2026; repulling staging failed because this machine's SSH key isn't authorized on the staging host. (agent decision)
- **Peeking carousel geometry.** On mobile each card takes 86% of the width minus a 16 px inset, leaving about 40 px of the next card visible on a 390 px screen. Phones snap to each card with `snapToInterval`; the mobile web preview uses `pagingEnabled`, which react-native-web turns into CSS scroll-snap on each card. Narrow web uses 82%-wide cards with a 12 px gap. The dots stay as the single-pointer alternative to swiping. (agent decision)
- **Alliance-wide feed removed from the tasks page.** With the sidebar now holding updates, the web-only `GlobalFeed`, `MemberFacepile`, `MembersModal`, `useFeedMembers` and `useGlobalFeed`, which nothing else used, are deleted. The server's global-feed endpoints stay, because open tabs on the previous bundle still call them; removing them is a later contract step once those bundles are gone. (agent decision)
- **Photos come from the update, not members' posts.** The mosaic shows the update's own images. Members' activity posts could hold photos too, but the local database, loaded with data up to 4 November 2026, had 10 activities with any post content among 8,703, so there was nothing to show. Revisit once members attach photos to their completions. (agent decision)
- **Who appears in the facepile.** `ActionUpdatesService.participantPicturesByAction` returns, for each project, the profile pictures of the three members who most recently completed it (`user_completed` activity), skipping anonymous and deleted members and members without a picture. Completions already appear to members in the Recent activity feed; anonymous members are left out because their accounts hide their identity. Only the member endpoints (`GET /actions/updates` and `/actions/allUpdates`) attach them, in one query for all the updates' projects. The count beside them is the project's cached `usersCompleted`, so a project nobody completed shows no footer label rather than "0 members participated". (agent decision)
- **Facepile style.** Profile pictures follow the app's existing stack in `LikeSummary`: `AvatarProfile` / `ProfileImage` at their small size, rounded squares, a 2 px white ring, overlapping. When the card is too narrow for the pictures, the participation label and "Read" on one line, the pictures give way: on web below a 20rem card width (the 288 px desktop sidebar), on mobile down to two pictures below a 340 px card and none below 300 px. (agent decision)
- **Mobile profile picture fallback.** `ProfileImage` on mobile now shows its default person icon when a picture fails to load, as web's `AvatarProfile` already did, instead of a blank square. (agent decision)
