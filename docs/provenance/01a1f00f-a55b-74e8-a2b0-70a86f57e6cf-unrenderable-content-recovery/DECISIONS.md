# Decisions

All agent decisions unless labelled otherwise.

## Telling "too old" from "broken"

- `formUnrenderable` (`common/src/forms/unrenderable.ts`) blames the client when `unknownKind` is set and the content otherwise. `variablesError` alone can't tell them apart: its strings mix authoring errors with this build not knowing a kind (EVIDENCE.md, Repository behaviour), so every kind evaluation can fail on is caught as `unknownKind` first (below).
- Display-only content: `readDisplayOnlySchemaForMember` blames the client for every parse failure. The server parses each display-only snapshot with its own build when serving it and serves an empty schema when that fails (`server/src/tasks/display-only-snapshot.ts`), and member clients are never newer than the server, so a schema the client rejects was written by a newer build. Splitting by zod issue code misread a widened type or relaxed bound as broken content.

## Kinds this build doesn't know

- `unknownKind` also covers the kinds that used to surface only through `variablesError`: unknown formula input kinds in variables and options formulas (`findUnknownVariableInputKind`) and unknown list sub-field kinds (`findUnknownFormElementKind` now looks inside lists). Member clients cast stored schemas rather than parse them, so these kinds do reach the renderer. An options formula's unknown input kind no longer throws while ordering the options formulas (`dependencies` in `formula-options.ts`), which crashed the form before the block could show.
- `unknownKind` also covers a variable or options formula this build can't compile (`findUncompilableFormula`): the server compiles every formula on save, so a compile failure on a member's screen is usually syntax or a function a newer build added. A formula saved before a stricter compiler rule (the `-x ** 2` rejection came two weeks after compiling on save) fails on every build and is mislabelled too; stored formulas weren't checked for one, and telling it apart would mean comparing the error against rules later builds tightened. Runtime evaluation failures stay content problems.
- Known gap, not addressed here: `readSourceHistory` drops a question of a kind this build doesn't know from another form's history before evaluation reads it, so a formula reading it computes without it rather than blocking. It predates this task; filed as ALL-2363.

## Reporting

- Every notice shown to a member is reported with `captureException`: `content_needs_newer_client` (not sent to Slack, since it's expected right after a release) and `content_unrenderable` (sent to Slack once per piece of content a day, REQUIREMENTS.md, since someone has to fix the content). Properties are the subject, the reason, the detail (what this build doesn't know, formula error, or the display-only schema's failing paths) and the content's ids (form, snapshot and action, or the action or general update), never answers. The ids are what lets staff find the content: mobile events carry no screen or URL, since autocapture is off. Each piece of content is reported once per app session for each reason and detail, so a broken update in a feed doesn't post to Slack once per card mount, while two forms failing the same way are both reported. That destination is PostHog's "Slack: broken content" (`01a1f620-a1e9-0000-ff8d-2b42ae5de350`), created through the API since PostHog sets a per-property repeat key only there (EVIDENCE.md, Alerts for broken content). It copies the main Slack destination's workspace and channel and takes `$exception` events whose `event` property is `content_unrenderable`. Its repeat key, kept 24 hours, is the subject with the form, action update or general update id, never the snapshot id, which can be null and changes on each republish. Its message names the member and lists the report's properties, since the main destination's text would only say `$exception`.

## Staff views

- Staff views (`showDetail` on admin form previews and response views, `staffView` on the admin's update list) show the detail under "This form can't be displayed" (or "update"). Content the admin build is too old for keeps "Reload page": the server serves only what it parses, so the tab is stale, and the admin, unlike the frontend, doesn't reload itself on a new build. Only the form builder's preview (`draft`) shows a formula error with no reload, since its schema is unsaved and no newer build fixes a mistyped formula; the response views show saved snapshots and keep it. A draft whose variable reads an input kind the tab doesn't know loses the reload too, though a newer tab would show it; the detail still names the kind, and telling the two apart would mean recording which check set `unknownKind`. They report nothing, so authoring broken content doesn't page Slack: `showDetail` (which `staffView` sets) skips the report, and every admin view that can show a notice sets it. The member apps never set it, so they have no prop for whether to report.
- The copy makes no claim that anyone was notified (REQUIREMENTS.md).

## Mobile tests

- Mobile component tests render through react-dom over happy-dom, loading the web packages' test preload (`shared/lib/testing/preload.ts`) so its cleanup, mock restores and compact failure output apply alike, with stand-ins in `apps/mobile/test-setup.ts` for the React Native and Expo modules a tested component uses, added with the first test that needs each, since Bun can't load React Native and per-file module mocks are lint-restricted (EVIDENCE.md, Mobile component tests). It departs from Expo's and React Native's Jest, jest-expo and React Native Testing Library, which would be a new test runner for the package; it is enough to check that `UnrenderableNotice` reports at the `captureException` boundary. Real component tests are ALL-2380. Agent judgement.

## Mobile recovery

- One search per moment, shared by every notice on screen (`shareInFlight`): download an OTA update first, then ask the server whether the store has a newer build (also when the OTA check failed, since a store build fixes the content either way), reusing the check `UpdateAvailableModal` already ran, now in `lib/storeUpdate.ts`. `OtaUpdateBanner` and the notice share `restartIntoUpdate` and `downloadUpdateNow`, which reports a failed check or download and joins one already under way (`shareInFlight`), so overlapping checks download once and report a failure once. A failed store request counts as a failed search ("Couldn’t check…"), never as "isn’t out yet".
- A failed OTA check, and separately a failed download, is reported at most once an hour (es-toolkit's leading-edge `throttle`, one per step, so a check failing offline doesn't hide a download failing once back online): offline every check fails, and checks run on returns to the foreground (up to one every 15 minutes, or on each return while a notice waits for an update, which then also checks every 5 minutes), and on each push.
- `restartIntoUpdate` saves the current route, query parameters included (expo-router's `useUnstableGlobalHref`, so `/messages/new?to=…` keeps its recipient), before `reloadAsync`; `ResumeAfterRestart` opens it with `router.navigate` (a push would stack a second home screen on a restart from home) once auth has loaded, waiting through a session restore that failed and may succeed on retry, for signed-in members only, if it was saved under two minutes ago and is an in-app path. The banner's restart returns to the same screen too. In-memory state (an open task flow) isn't restored: the member lands on the screen, not inside a sheet opened on it. expo-router marks that hook private and may add a hostname to it; `takeResumeRoute` then rejects the route as not in-app, so the restart lands on the home screen rather than anywhere unexpected. A failed save, read or drop of the route, and a saved entry that is unreadable or not an in-app path, is reported as `resume_route_failed` (not sent to Slack: the member still lands on the home screen). A failed reload drops the saved route, so a later launch from a push or link isn't sent back to it.
- Handled push taps are kept in AsyncStorage, the last 50 (`lib/pushTaps.ts`): on Android expo-notifications replays taps that arrived with no listener, the one that launched the app included, to each new listener, including after `reloadAsync`, so a restart would otherwise open a push's screen again on top of the resumed one (EVIDENCE.md, Dependency behaviour). A tap is kept once its action runs, or once a later tap replaces it while waiting for sign-in, not when it arrives, so the tap still waiting opens after a restart and the replaced one never does. A storage failure or an unreadable stored list is reported as `handled_push_taps_failed` (not sent to Slack) and falls back to this session's taps.
- Copy per state: "Getting the latest version…" with a spinner; "Restart Alliance to finish updating." + "Restart to update"; "Get it from the App Store." + "Open App Store" (Play Store on Android); "The version of Alliance this form needs isn’t out yet. Please try again later."; "Couldn’t check for an update. Check your connection and try again." + "Try again"; restart failure reuses the banner's "Couldn’t restart. Close and reopen Alliance to update."
- `updateRecoveryView` picks the message and button from the search outcome, apart from the component, so tests cover each state.
- Status changes are announced with `AccessibilityInfo.announceForAccessibility`, once per message across notices that mount or change within 2 seconds of each other, so a feed of cards the build can't show doesn't repeat it, while a notice on a screen opened later still announces.
- The notice rechecks every 5 minutes, the agent's reading of "every few minutes", and only while the app is active and the notice's screen is focused, since the navigation stack keeps covered screens mounted. A return to the foreground restarts the 5 minutes, so the two don't search seconds apart. One schedule (`createUpdateRechecks`) serves every notice on screen, so they share one search (`shareInFlight`) rather than each starting its own OTA check and store request. A notice brought back into view searches at once if its last search was 5 minutes or more ago, rather than waiting for the next tick; a return to the foreground while it was covered is otherwise caught by that tick. It also rechecks after "Couldn’t check for an update", which a dropped connection causes and a return to the foreground often fixes. A recheck runs without the "Getting the latest version…" spinner, and one that fails keeps the notice's last message rather than flipping "isn’t out yet" to an error.

## Getting updates to members sooner

- The new invite goal form counts as holding input (`newGoalDirty`) while its target is filled or a date differs from the default it mounted with. Creating a goal resets both dates and that default to fresh ones, on web too, so a form shown again, even on a later day, starts clean instead of keeping the last goal's dates and holding restarts off.
- Push checks: only a push the app shows triggers a check while open, not the silent task-badge push, which fires on every task change and would check on each. Pushes join the download already in flight (`downloadUpdateNow`), and pushes go through es-toolkit's `throttle` (`checkForUpdateOnPush`): the first checks at once, a steady stream checks about once a minute, and a check always follows the latest push, so a busy chat, with a push per message, doesn't poll, and an update published inside the minute is still found. This is the agent's reading of the requirement's "immediately". A launch from a tap checks once more right after expo-updates' own launch check; one extra request per such launch was judged cheaper than telling the launch tap apart.
- Restart on return: `startResumeRestarts` waits 1 s after the app comes back before restarting, and cancels the restart if the app leaves the active state first (iOS's inactive state included), since Expo calls reloading in the background experimental (EVIDENCE.md). The screen is live during that second, so a touch or press anywhere in the app (`memberActionHandlers` on the root view: `onTouchStart`, and `onClickCapture` for Android screen-reader and hardware-key presses, which arrive as clicks with no touch, EVIDENCE.md, Dependency behaviour) cancels the restart too, rather than cutting off what the member started; the update then applies on the next qualifying return. Counting those presses is agent judgement after a consult: the requirement never mentions touch, which was only this decision's way of not cutting off what the member started. A return after 30 minutes also starts the foreground check, and expo-updates runs a reload only after a check or download already queued (EVIDENCE.md, Dependency behaviour), so the restart first waits for the check under way, if one is (`downloadUpdateNow.current`), without starting another, and checks for a touch or press, the active state and `shouldResumeRestart` again once it ends. A check that takes over 5 seconds, such as a download on a slow network, drops the restart for that return rather than landing on a member who has started reading without touching anything. Timers left pending at suspension, such as the 300 ms local draft save in `useFormDraftState`, have earlier deadlines and so fire first, which keeps answers typed just before the app went to the background. The 1.5 s server draft sync may not run; the local draft restores the answers.
- The screen-reader skip (REQUIREMENTS.md) reads `AccessibilityInfo.isScreenReaderEnabled()` when the restart would fire, together with the settle wait and inside its 5 s deadline, rather than keeping a value current through the `screenReaderChanged` event: a read at the decision can't be stale after a screen reader was turned on while the app was in the background, and it costs one native call per qualifying return. The banner needs no change for it: it shows whenever an update is pending and its dismissal resets on every return, which announces a dismissed banner again.
- Screens holding unsaved input block the restart through `useBlockResumeRestart(active)` (REQUIREMENTS.md), CodePush's `disallowRestart` pattern (EVIDENCE.md). Places found besides those the requirement names: the comment reply and edit forms, the group info and group settings edits, the profile edit, settings until its autosave lands, the membership signing fields, the away ranges form, the invite goal form, the invite settings sheet and link labels, and the login screen. An edit form blocks only once its value differs from the saved one. The new-message screen doesn't count the recipient a `?to=` link picked, since the restart reopens the route with its query and picks it again; a recipient the member adds blocks. Search fields, the edit-goal target, which saves when it loses focus, and the invite group pick, a preference that stays after an invite is created and so would hold restarts off while the invites screen is mounted, don't block. The update then applies on the next qualifying return, a banner tap or a cold start.
- `shouldResumeRestart` also refuses while a text input is focused, a backstop for a screen added later without a blocker, per Shorebird's advice against restarting mid-task (EVIDENCE.md).
- The KORA review screen blocks the restart for as long as it is open (REQUIREMENTS.md). The review tool autosaves about 2 s after a change and when the page is hidden, so what a restart could lose is a note being typed or edited, a selection not yet marked, or a save that failed, which it keeps in memory only.
- No restart while a request that changes data, any method but GET, is in flight through the shared API client (`blockResumeRestartDuringWrites` wraps its `fetch`): a restart would cut it off, such as a push tap's mark-opened and mark-read requests, or one sent by an action the member took without a touch, such as a screen reader's adjust gesture. A request holds the restart off rather than counting as the member acting, since reads start by themselves on every return (the task badge refetch, queries past their stale time) and would cancel nearly every restart. Writes that also start by themselves, such as a device registration retry, hold off only the restarts due while they are in flight. Each block ends after 30 seconds even if its request hasn't settled: React Native's Android HTTP client sets no timeout, so a stalled request would otherwise hold off every restart for the rest of the process. Agent judgement, after a consult on the touch guard missing TalkBack presses.
- No restart while the write marking a push tap handled is in flight (`blockResumeRestartUntil` in `handledPushTaps`): a restart before it lands would replay the tap. The tap's mark-opened and mark-read requests are writes through the API client and so hold restarts off already.
- The 30-minute threshold has no source behind it; CodePush's `minimumBackgroundDuration` and Expo's "after inactivity" advice show the pattern, not a value.

## Deploy order

- The user deferred whether a failed OTA publish blocks the admin deploy, so how the ordering in REQUIREMENTS.md behaves on failure is the agent's choice: the admin deploy waits for `publish-mobile-ota` to finish and runs whether it succeeded or failed (`!cancelled()` plus the backend and frontend deploys' success, as GitHub recommends over `always()`; EVIDENCE.md, Deploy order). The OTA publish never failed in the deploy runs scanned, its job takes a few minutes, and blocking would supersede the OTA publish's place off the required list and as an alert only (`docs/provenance/01a1ce4b-16f7-713d-9845-fe08e3ffa147-ci-deploy-speed`, `docs/provenance/01a1ddf0-1ea9-7040-a575-80e716fde9ea-production-promotion`), which this keeps. During an Expo outage admins can use a new kind before a bundle that shows it exists; members see "isn't out yet" until it publishes.
- The smoke checks (`verify-*`) run on `!cancelled()` and the admin deploy's success. GitHub documents `failure()` as covering every ancestor job but doesn't say how the default `success()` treats them, so without the explicit condition a failed OTA publish, an ancestor through the admin deploy, may skip them.
- A deploy publishes the OTA without the fingerprint check (it runs only on manual dispatch), so for a commit that changes native code the bundle targets a runtime no installed app has, and the ordering gains nothing. Nothing in this task addresses that.
