# Decisions

## Research behind the requirements

Each requirement's option was checked against published practice before the user chose it.

- `/alliance/<env>/server/` scoped to the server: least privilege, NIST SP 800-53 AC-6 (formal), AWS's secrets best practices and the OWASP Secrets Management Cheat Sheet. Parameter Store scopes IAM access by path, so each role is granted only its own environment's path.
- No export fallback: the wrapper starts nothing when the fetch fails and sets fetched values over inherited ones of the same name, so exported values neither cover an outage nor prove the store complete. Validating before the running backend is stopped follows AWS's rollback-safety guidance and NIST CM-3(2).
- Split roles: NIST AC-6 and the AWS Well-Architected least-privilege practice. AWS's stronger recommendation, a separate account per environment, is out of scope.
- Human apply as non-root: HashiCorp recommends human review of production plans; AWS reserves the root user for tasks that need it.
- Parameter Store over Infisical: three independent agent brainstorms (two codex, one Claude) and a pricing check against vendor pages on 2026-11-05 compared hosted stores (Infisical, Doppler, 1Password, Bitwarden, Akeyless), self-hosted (Vault, OpenBao, Infisical), cloud stores (AWS Secrets Manager and Parameter Store, Google, Azure), encrypted files (SOPS, git-crypt) and GitHub secrets. For ten people with servers and CI signing in without stored keys, the AWS stores cost dollars a month and the hosted ones $210 or more (Doppler Team, https://www.doppler.com/pricing; Infisical Pro, https://infisical.com/pricing, which counts people and machines against Free's five identities); 1Password and Bitwarden are cheaper but authenticate machines only with static tokens. Two brainstorms preferred Secrets Manager and one Parameter Store; the user chose Parameter Store, free at this size (https://aws.amazon.com/systems-manager/pricing/). SOPS was ruled out because the repository is public.
- Committed CA bundle: NIST SP 800-57 treats a trust anchor's public key as non-secret.

## Implementation

- **`DB_CA_CERT` stays exported under `BACKCOMPAT(ALL-1963)`**, read from the release's committed bundle, because a release from before the server read that bundle has no fallback for it. Origin: agent decision.
- **The staging role gets `s3:DeleteObject` on the staging bucket.** The server deletes objects (`videos.service.ts`, `hosted-docs.service.ts`), and the old shared role granted delete on production's bucket but not staging's, so staging deletes were denied. Origin: agent decision.
- **The staging backend restarts right after the apply that gives staging its own role.** The apply moves the staging bucket's policy off the shared role, and a running backend keeps the shared role's credentials until they expire, so staging uploads and deletes fail until then. The setup steps given to the user include the restart. Origin: agent decision.
- **The production role drops the dev assets bucket.** The production server uses only its own bucket; the `alliance-dev` IAM user keeps dev bucket access. Origin: agent decision.
- **Workflows don't set `TF_VAR_db_password`.** No workflow runs Terraform, and set at workflow level it handed each job deploying to staging or production that environment's database password. Origin: agent decision.
- **Failures before the old backend is stopped leave it running instead of restarting it.** That covers unzip, install, entering the new release, the config check, installing the wrapper, reading the streak recognition removal state, an unrecognized state, and migrations that run with the old backend up. The old backend never stopped, so a restart there only adds downtime and another way to fail and another dependency on the secrets fetch, which in an outage can't start anything. The exception is an old backend that exited during the deploy: pm2 brings it back from its recorded path, which holds the new release by then, so a changed pid, or a pid where there was none because pm2 was between restarts as the deploy began, gets it restarted from the old release once that is moved back. `pm2 restart` reuses the process's recorded command and environment, so a backend from before this change restarts the way it ran. A backend that wasn't running when the deploy began and hasn't come up since stays stopped: after a failure that left it stopped, starting the old release could run old code against a schema not yet restored. A deploy that can't read the backend's pid from pm2 quits before touching anything, since an empty pid would pass for no backend running. A failure whose own pid read fails restarts nothing and says to check the backend by hand, since a restart there could take down a healthy old backend. Origin: agent decision.
- **The wrapper fetches with the AWS CLI and sets the variables in Python.** Both ship with Amazon Linux 2023, so hosts install nothing. Python reads the decrypted response from a pipe and execs the command, so values with newlines or quotes arrive intact and never pass through argv, a file or bash word splitting. Origin: agent decision.
- **Parameters use the AWS managed `aws/ssm` key, and each role may call `ssm:GetParametersByPath` on its own environment's path only.** That key's policy lets SSM decrypt for any caller in the account, so the IAM path grant is the whole boundary; a customer managed key per environment ($1 a month each) would add a second, independent boundary the team doesn't need yet. No role is granted a parent path such as `/alliance`, which would reach every environment. Each grant names both the path ARN (`…:parameter/alliance/<env>/server`) and `…/server/*`: AWS's IAM docs for Parameter Store don't say which one the call is authorized against, and neither reaches outside the environment's path. Origin: agent decision.
- **The parameters stay out of Terraform.** A Terraform-managed parameter would put its value in the state file; Terraform manages only who may read them. Origin: agent decision.
- **The wrapper lives outside the release, at `~/secrets_run.sh`.** `restore_old_release` restarts the previous release with the new deploy script's `start_backend`, so a rollback to a release from before this change also runs under the wrapper. The wrapper reads only `NODE_ENV`, so it serves any release. The deploy runs the config check through the new release's copy and installs it over `~/secrets_run.sh` only after the check passes, since the running backend restarts through the installed one. Origin: agent decision.
- **`/alliance/<env>/server/` holds the 20 secrets the deploy exported, under the server's names**, less `NOTIF_TEST_EMAIL`, which nothing reads, and `DB_CA_CERT`, now committed. Both environments' sets were checked against `validateServerEnv` before setup. Origin: agent decision, from the old export block.
- **The one-time copies are kept here, not in `scripts/`.** `infisical-server-folder.sh` gathered the secrets in Infisical's `/server` folders under the server's names, and `ssm-server-parameters.sh` copied those folders into Parameter Store. They are records of the setup, not tools: after setup the parameters are edited in Parameter Store directly, as `docs/backend-secrets.md` says, and a rerun would overwrite them with stale values. Origin: user asked to commit them for posterity; the agent chose the provenance directory.
- **pm2 restarts the backend with exponential backoff from 1 second.** Every start fetches the secrets first. With pm2's default zero-delay restarts, an unreachable Parameter Store at a host reboot or a `pm2 restart` uses up the 16 unstable restarts pm2 allows in 16 seconds and leaves `nest-app` errored until someone starts it by hand. The backoff grows to 15 seconds, so pm2 keeps retrying until the fetch succeeds. Origin: agent decision.
- **The health check retries up to 10 times, 3 seconds apart, after its 10-second wait.** Startup fetches the parameters before bun boots, so the fixed wait alone could roll back a healthy release. `--retry-connrefused` covers a backend not yet listening; curl's default retries cover timeouts and transient 5xx. Origin: agent decision.
