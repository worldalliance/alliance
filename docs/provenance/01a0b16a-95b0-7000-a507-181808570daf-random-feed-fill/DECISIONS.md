- Scoped the change to `ActionsService.homeFeed` (`GET /actions/homeFeed`), the endpoint whose doc comment describes "friends and group members" — the other feed endpoints (`activities/feed`, global feed, `timeline-feed`, `friendActivity`, `communityActivity`) use different, narrower filters and weren't in scope.
- The "set" the 10-person minimum applies to is friends ∪ group members, excluding the viewer themselves — the viewer's own id is still always added to `allUserIds` afterward, unchanged from prior behavior.
- Only friends and group members with an active contract count toward the minimum, the same check fillers must pass. Otherwise a group of 10 where 8 have left counts as full and gets no fillers. Inactive friends and group members still stay feed sources, as before; the count only decides how many fillers to draw (`UserService.countActiveUsers`).
- Renamed `findForumCommentsForFeed`'s `friendAndGroupMemberIds` param to `sourceUserIds`, since it now carries fillers too. Filler forum comments reach the feed on purpose: the request covers everything in the feed, not just action activity.
- Filler users are drawn only from users with an active/signed contract (`sqlUserHasActiveContractAt`), matching the existing convention for "real member" random-selection elsewhere in `user.service.ts` (`pickRandomUsersWithProfilePictures`, `getSignupSocialProof`). No explicit requirement covered this; existing code doesn't establish user intent per the provenance skill, so this is a judgment call to keep the fill from resembling account-less/unsigned users, which is the closest read of the request's intent that isn't contradicted by anything the user said.
- Filler selection via SQL `ORDER BY md5(u.id::text || :seed) LIMIT n`, seeded with the viewer's id. `ORDER BY RANDOM()` was tried first but re-drew the cohort on every request, and `homeFeed` is cursor-paginated: a scroll issues one request per page, so each page came from a different population and the client stopped early (measured: a friendless viewer reached 7-14 of 41 available activities before `hasNextPage` went false). Seeding by viewer keeps one cohort across a scroll. Nothing is persisted, so the change is still stateless; the cost is that a viewer's fillers only change when their friends or group change.
- New method `UserService.pickActiveUserIdsForSeed({ count, excludeIds, seed })` returns bare ids (not full `User` entities) since `homeFeed` only needs ids for its downstream `IN (:...userIds)` filters; kept public (unlike the private `pickRandomUsersWithProfilePictures`) since it's called cross-service from `ActionsService`.
- Threshold `10` pulled into a named constant `MIN_HOME_FEED_SOURCE_USERS` in `actions.service.ts`, following the file's existing pattern of named constants for feed tuning values (`GLOBAL_FEED_FACEPILE_LIMIT`, `GLOBAL_FEED_WINDOW_DAYS`).
- Added e2e coverage in `server/test/actions.e2e-spec.ts` (new "Home feed filler users" describe block): an end-to-end check that a filler user's completion reaches a friendless viewer's feed (the picker is stubbed to one id, so the assertion is about filler activity reaching the feed rather than about which members the shuffle lands on), a check that two pages of one scroll draw the same cohort and a second viewer draws a different one, a spy-based check that the fill asks for 0 when 10 active friends already meet the minimum, a check that 8 inactive friends out of 10 still leave 8 fillers to draw, a check that a viewer with 9 group-mates still draws 1 filler (the viewer is a member of their own group, so `communityMemberIds` includes them and has to be dropped before counting), a regression check that a friend's completion still surfaces, and a direct-call test of `pickActiveUserIdsForSeed`'s exclude/contract-status filtering. Skipped a unit-test file for `UserService` — its constructor takes 23 dependencies with no existing precedent for mocking it in isolation.
- The scroll-stability test seeds 40 active candidates first. Without them the test db held fewer active users than the fill asks for, so every draw returned all of them and the test passed against `ORDER BY RANDOM()` too; verified it now fails against `RANDOM()` and passes against the seeded ordering.
- The describe block restores mocks in `afterEach` rather than at the end of each test, so a failed assertion can't leave `pickActiveUserIdsForSeed` stubbed for later tests.
