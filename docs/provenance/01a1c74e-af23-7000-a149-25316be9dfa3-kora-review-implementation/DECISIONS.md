# Decisions

## Pulling in korabench-review

- **What was copied.** `src`, `test`, `samples`, the type generator and converter scripts, `LICENSE`, `README.md` and `CHANGELOG.md`, from tag `v0.1.0-alpha.0` (commit `62121ee04f876c726a4fd47ec3d4f4a9556d32f1`). Left out: the built `dist/` (consumers import the TypeScript source, as with `@alliance/common`), the example app and its own dependencies, the vitest config, `package-lock.json`, the GitHub workflow, and KORA's question list, which `docs/provenance/01a1c67a-0156-7000-a694-8fc78b1dd41b-kora-review-section-spec` answers. The first commit is the copy unchanged, so later diffs show every change made here. (agent decision)
- **Exports.** `.` (mount and types), `./schemas`, `./convert` and `./style.css`. The server imports only `./schemas` and `./convert`, so it never loads the DOM engine. Its CommonJS tsconfig maps those two paths to source, as it already does for `@alliance/common`. (agent decision)
- **Generated types renamed to `src/types.gen.ts`**, following the repo convention that the lint skips `*.gen.ts`. The generator no longer writes an `eslint-disable` header, which the lint flagged as unused. (agent decision)
- **Tests on `bun test`.** `vi.stubGlobal` became a saved and restored `globalThis.fetch`. `vi.advanceTimersByTimeAsync`, which Bun lacks, became `test/timers.ts`: it advances the clock in 10ms steps and lets promise callbacks run between steps. The package has its own DOM preload (`test/preload.ts`, happy-dom), so it doesn't depend on `@alliance/shared` for tests. (agent decision)
- **Workspace registration.** Added to the root workspaces, `scripts/test-all.sh`, the `ci.yaml` and `deploy.yaml` typecheck and unit-test matrices, the backend deploy zip (the server imports it at runtime), covercheck's shared packages, and `.jscpd.json`. Its dev dependencies are also declared in `apps/frontend/package.json`, per the root `AGENTS.md` dependency rule. The server declares `ajv` and `ajv-formats` itself. (agent decision)
- **Single ajv.** The lockfile held a stale nested `ajv@8.18.0` under `ajv-formats`, which made the two ajv type trees incompatible. It was removed, so `ajv-formats` resolves to the root `ajv@8.20.0`, which its `^8.0.0` range allows. (agent decision)
- **Converter as functions.** `readKoraPairs(text)` splits KORA's file into records numbered from 1, reporting a line that doesn't parse rather than stopping. `fromKoraPair(record)` maps one pair's fields and validates nothing, so the server reports every invalid line through `transcriptSchema`. The CLI script wraps the two. The script's duplicate-`pair_id` check moved to the server's upload, which checks `transcriptId` uniqueness across the whole file. (agent decision)
- **`engine.ts` waivers.** It carries an `alliance/max-lines 4300` waiver (about 1,700 lines as imported, 4,280 after Prettier) and an `eslint-disable` for `ban-ts-comment`, both naming the follow-up in REQUIREMENTS.md. One `prefer-const` warning in it was fixed. (agent decision)

## Closing sign-ups

- **Where the rule sits.** The participant service refuses a new participant at the three points one could be created: verifying a code for an unknown contact, finishing a signup, and a provider sign-in with no participant. Existing participants are never refused. A code is still sent to an unknown contact while Closed, because refusing at send time would reveal which contacts already have a participant. (agent decision)
- **Provider sign-in reuses `OAuthError.NoAccount`.** Kora's provider flow never produced it before, so it now means "no participant, and the project is closed", and `koraOAuthErrorMessage` shows the closed copy for it. That avoids adding a variant to the shared `OAuthError` that the member flow would have to handle. (agent decision)
- **The closed refusal goes back to contact entry,** like an expired code or signup, since the contact can't continue. (agent decision)
- **Closed page.** The sign-in under the thank-you starts collapsed behind its link, and starts open when the visitor is returning from a provider sign-in, so that refusal's message is visible. (agent decision)

## Notify waitlist

- **Who counts as notified.** Each participant has a `launchNotifiedAt` timestamp, set only once a message is delivered. The count shown to the admin, and each send, cover participants without one. (agent decision)
- **Sending.** Each participant is claimed (`launchNotifiedAt` set) under `FOR UPDATE SKIP LOCKED` before the message goes out, and the claim is cleared again if delivery fails. Two sends at once, even from different server processes, never message the same person. A failure is skipped for the rest of that run and retried on the next. (agent decision)
- **In the background.** The endpoint returns how many are waiting and sends after responding, so a long list can't time out the admin's request. A server restart mid-run loses nothing: unsent participants keep a null `launchNotifiedAt`, and the next send picks them up. (agent decision)
- **Only while Active.** The server refuses with "Make the project active before notifying the waitlist.", so nobody is told the reviews are open while they aren't. Until batch upload lands, Active can't be chosen, so the send can't be used yet. (agent decision)
- **Channel and delivery gate.** Email or SMS to the participant's one contact, through the same unrecorded senders as sign-in codes, so the existing delivery gate applies. The link is `APP_URL` plus the review path. (agent decision)
- **Migration.** Adding `kora_launch` to `EmailType` recreates the enum, as the `otp_code` migration did. The same unrelated `friend` generated-column drift as in the project-status migration was removed. A second `migration:generate` showed no Kora changes left. (agent decision)

## Batch upload

- **Storage.** `kora_batch` holds the batch's export schema, assignment size and review target. `kora_transcript` holds each converted transcript as jsonb, keyed by KORA's `transcriptId`, with its upload position and a content hash: `sha256:` plus the hex digest of `JSON.stringify(content)`. Exports echo the hash, so the server can tell which content was reviewed. (agent decision)
- **All or nothing.** `checkTranscripts` converts every line and reports every problem: unparseable JSON, a schema failure (ajv's messages), an id repeated within the file, or an id from an earlier batch. Nothing is stored unless every line passes. (agent decision, implementing REQUIREMENTS.md)
- **Export schema check.** The uploaded schema must parse, compile under ajv's strict 2020-12 mode, and accept the review tool's own sample export. A schema that would refuse every real save then fails at upload instead of mid-review. The sample export moved from `samples/export.json` into `kora-review/src/sample-export.ts`, because the server can't import JSON and its deploy ships only `kora-review/src`. (agent decision)
- **Active now needs a transcript.** `canActivate` is whether any transcript is stored. It replaces the placeholder that always returned false. (agent decision, implementing the project-status requirements)
- **Upload format.** Multipart, with both files and the two numbers in one request, following the hosted-docs upload. Files up to 50 MB. Assignment size is 1 to 100 and review target 1 to 50, checked by class-validator. (agent decision)
- **Admin file inputs aren't `required`.** A browser's required-file check gives a generic message. The form instead says "Choose both the transcripts file and the export schema." (agent decision)
- **Preview.** A full-page admin route outside the sidebar, `/kora-participants/preview/:batchId`, so the tool's fixed header and footer aren't offset by the sidebar. It mounts the real tool with a random transcript from the batch, an assignment id prefixed `preview-`, and a save that does nothing. A banner says nothing is saved and offers another transcript. (agent decision, implementing REQUIREMENTS.md)
- **Typing stored transcripts on the client.** `parseKoraTranscript` in `kora-review/src/parse.ts` builds a zod schema with `z.fromJSONSchema(transcriptSchema)`, so there is no hand-copied zod schema to drift. It doesn't enforce `contains` (at least one AI turn), which the server's ajv check already enforced at upload. Its one cast is commented. (agent decision)

## Review API

- **Reviewers.** `kora_reviewer` gives each member and each participant their own opaque id, and that id is all the tool and KORA see. A check constraint keeps exactly one of `userId` and `participantId` set. The row is created on first visit, and a member session wins, as on the project page. Reviewers and assignments carry `deletedAt`: the repo soft-deletes users, and its soft-delete cascade can't hard-delete a table other rows reference. Deleting a participant still removes their reviewer, assignments and exports through database cascades. The admin delete confirmation now says so. (agent decision)
- **Assignments.** A first assignment is created on the first visit while the project is Active. Extra ones come from "review more". Each assignment's id is the `batchId` the tool echoes. It's checked against the newest batch's export schema at the time it was created (`schemaBatchId`), because an assignment can span batches with different schemas. A per-reviewer advisory lock keeps two tabs from creating two assignments. An unfinished assignment is always resumed, even after the project closes. (agent decision)
- **Choosing transcripts.** `pickAssignment` is a pure function. It ranks candidates by reviews still needed, takes at most 3 per category, then relaxes the cap to fill the assignment, and orders by category group in random group order. A candidate's needed reviews is its batch's target, less finished reviews, less pending ones in unfinished assignments active within 7 days. Opted-out transcripts count as neither. A reviewer is never given a transcript they've had before. Two new reviewers at the same moment may get overlapping transcripts, which only means a transcript could pass its target. (agent decision)
- **Saving.** `checkExport` runs before anything is stored: the assignment's schema, the reviewer id, the assignment id, each transcript's content hash, and every assigned transcript present. A refusal is logged, and the response says why. Each transcript's status (done, opted out, or pending) is copied from the export, so counting reviews needs no jsonb scan. An assignment completes when no transcript is pending. The reviewer stops being asked the profile once any export carries one. (agent decision)
- **Redaction.** Annotation notes, `q3_text` and `exit_q6` are redacted before storing. Email addresses are found with markdown-it's linkify (non-fuzzy), and phone numbers with libphonenumber-js `findPhoneNumbersInText`. The `extended` option also catches unassigned numbers such as typos, and the default country is US, so a national-format number from another country without its `+` country code can be missed. (agent decision)
- **`reviewed` in the state.** Lets the page tell a reviewer who has finished something (thanks, plus review more or none left) from one who arrived when nothing was left (the none-left message only). (agent decision)

## Review page

- **Route and redirects.** `/projects/safer-chatbots-for-children/review`. Signed-out visitors go to the project page with `?next=review`, and the project page sends them back once they're signed in. NotActive goes to the project page. (agent decision, implementing REQUIREMENTS.md)
- **Active project page.** Signed-in participants and members see "Reviews are open." and a "Start reviewing" link in place of the "Reviews start" note. `KoraWelcome` takes the project status, so Pending, Active and Closed each have their own branch. (agent decision)
- **Mounting the tool.** Light theme, the site's body and display fonts, and a 78px top offset for the site header. `onComplete` refreshes the review state. The exit survey is asked on a first assignment only. Unmounting flushes pending changes first. A failed save shows "Your last change couldn't be saved." with "Try again", which flushes. (agent decision)
- **Typing server data for the tool.** Transcripts parse with a zod schema built from the transcript JSON Schema. The export schema's `if/then/else` rules are beyond `z.fromJSONSchema`, so `parseKoraExport` checks the fields the tool keys on (`schemaVersion`, `batchId`, `reviewer.id`, `results[].transcriptId`) and relies on the server's ajv check for the rest. Both go through `z.custom`, so no cast is needed, and both parse at the API boundary, as does the project status. (agent decision; replaces the earlier cast-based `parseKoraTranscript`)
- **Thank-you copy.** Placeholders in `REVIEW_COPY` in `copy.ts`, to be replaced by the user's copy. (agent decision, implementing REQUIREMENTS.md)

## Member action

- **Task kind.** `Action.taskKind` (`ActionTaskKind`: `form` or `kora_review`, default `form`) is a column with an admin "Task" select under Settings, and passes through create and update like the other picked fields. The web and mobile task panels branch on it exhaustively. A Kora review action shows "Start reviewing", which goes to the review page on the web and opens the review screen in the app. Once completed, it shows "Task complete" and "Review more transcripts". Copy shared by both apps lives in `shared/lib/koraAction.ts`. (agent decision, implementing REQUIREMENTS.md)
- **Completion by event.** When a member's first, non-extra assignment completes, the review service emits `kora.member.reviewed`, and a listener in the actions module calls `completeAction` for every live Kora review action. A refusal (already completed, not open to them) is expected and ignored, and anything else is logged. The event keeps the Kora module from importing the actions module. (agent decision)
- **Web handoff.** `POST /auth/web-handoff`, available to a signed-in member who isn't impersonating, returns a 32-byte random code. Only its sha256 is stored, valid for 60 seconds. `GET /auth/web-handoff/redeem` deletes the row as it reads it, so a code works once. It issues the normal web session cookies through the OAuth session service and redirects to `next` on the configured site URL for the request's host. `next` must be a site path, so `//host` and backslashes fall back to `/`. A spent or expired code still redirects, signed out, and the review page then asks to sign in. The mobile screen asks for a fresh code on each open (`useWebHandoffCode`, cache time 0) and loads the redeem URL on the API host, which shares the site's host in production and localhost's cookies in development. (agent decision, implementing REQUIREMENTS.md)
- **Returning from the review screen.** The mobile Kora task refetches the action when its screen regains focus after the review screen, so a completion shows at once. (agent decision)
- **No mobile component test.** The mobile app has no component-test setup. Its Kora panel shares its copy and its completed/can-start logic with the web panel, which is tested. (agent decision)
