# Decisions

- The link warning extends the worldalliance dialog's hook, renamed `useContentConfirm` (`apps/admin/src/components/useContentConfirm.tsx`), rather than adding a second hook, since the two share one dialog. `confirmSave(value, { siteLinksIn })` takes the text to check for site links separately from the text checked for worldalliance, so each editor names what can hold a path. (agent decision)
- "The site" is the web app's hosts as `isAllianceAppHostname` lists them (bare, `www.`, `staging.`, `www.staging.` on both domains), the same list `siteHref` turns into paths when links are shown. `admin.` links are a different app and aren't flagged. (agent decision)
- Within the covered editors, the link check skips fields where a path can't be saved or isn't a link. The action editor checks only an action's body, its one markdown field: its name, short description, stat label and thumbnail alt text render as plain text, its images are images, and its reviewer urls are made absolute with `ensureHttpProtocol` before saving. The staff directory checks only staff links, each as a whole url, since the web app uses one as an `href` as written; a staff member's title is plain text. The form builder checks exactly the strings it authors that the member apps' form renderers (web `sharedweb/forms`, mobile `apps/mobile/components/forms`) render as markdown or open as a link (`linkCheckedText` in `apps/admin/src/components/linkCheckedText.ts`): input field labels, except a contract field's, which shows the contract instead, and a custom component's, which is plain text; radio, multiselect and ranking option labels (a select's are plain text); a list's sub-fields, by the same rule; display blocks' text and quote text, markdown copy text and chat transcript messages, within accordions and output views too, and a big link's url, checked as a whole url rather than as markdown, which wouldn't read a protocol-relative url as a link; per-member content, resolved over its block as `resolveDisplayBlockForUser` resolves it for the member; and an output view field's label override where it renders as a field with its label shown, by its page field's rule with the override in place of the label, so a contract's or custom component's isn't checked. Everything else is plain text, media, HTML, answer data, formulas or not shown to members: descriptions (shown only as the share-info toggle's plain text), placeholders, headers, labels, captions, big link text, plain copy text (pasted elsewhere as typed, where a path has no site; markdown copy text turns paths into full urls as it is copied), page and form titles and descriptions, share text, option values, aggregate views, and a contract field's copy of a contract, which is edited on the contracts page. A row list value is checked as a whole url where its `#{row.<column>}` starts a link destination in a checked string or a big link's url, found by putting a stand-in url ending in a slash in place of each placeholder (common's `rowPlaceholderPattern`) and parsing the result as the string is parsed, so a suffix such as `?source=form` or `docs` and a bare placeholder the mobile app links are covered; each distinct url is listed once. Row values are checked only this way, as whole urls: a markdown link inside a row value, or a value filling part of a url such as its host, isn't asked about. Catching those means checking the form filled for each row (`schemaForRow`), whose strings aren't the stored ones the worldalliance check reads, so a worldalliance.org link from a row would be listed in both sections, against the requirement that each problem is listed once; rows are data the admin pastes in, and a template building a link from one usually takes it whole. A worldalliance.org url found this way is listed only in the link section, as each problem is listed once. The user deferred how rows are checked; this narrow check was the recommendation. HTML blocks aren't checked, though their anchors are links: app builds from before this change render them in a WebView with no base url, where a path doesn't open, so warning would push admins toward links that break there. This change passes the site url as that WebView's base url (next entry); ALL-2260 adds HTML anchors to the check once installed builds carry it, shown by a forced minimum version or no traffic from older builds. The user deferred how HTML blocks are handled; this was the recommendation. Per-kind lists are typed against the block and field schemas (`LINKED_DISPLAY_FIELDS`, an exhaustive switch over input kinds), so a new kind or a renamed field fails the build, and `linkCheckedText.test.tsx` renders a block and field of every kind with the web renderers and checks that the strings that come out as links are exactly the checked ones. Mobile is checked against the same list by reading its renderers, which the mobile unit tests can't load; it renders the same strings as markdown or links. Its default markdown parser also links a bare url, in display text, quotes, chat transcripts and a ranking field's options, so `linkCheckedText` returns those as `siteLinksIn`, parsed with GitHub's extensions; labels, a ranking field's included, other choice options and markdown copy text, which it renders with parsers that leave a bare url as text, as do the web form renderers everywhere, go in `siteLinksInCommonMark`, parsed as CommonMark, so a bare url there, which no app links, isn't asked about. This replaces per-field patches to a list that drew misjudged fields in every review round from the third to the ninth. The user left how the check chooses fields to the agent. Action update and general update details (title, notification texts) keep only the worldalliance check, since notification texts can go out as push or SMS text. (agent decision)
- The link check skips image sources and HTML attributes. It parses each checked string as markdown with GitHub's extensions (`mdast-util-from-markdown` with `micromark-extension-gfm`, the syntax `remark-gfm` gives the web app's markdown), and asks about a link node, a bare url GFM autolinks included, or a link reference definition a link uses (the first one for its label, as CommonMark resolves it) and no image does, when it points at the site over http or https, the schemes `siteHref` turns into paths. Text whose renderers don't link a bare url is passed apart (`siteLinksInCommonMark`) and parsed as CommonMark. A definition an image also uses isn't asked about, since a path there breaks the image in the mobile app. Images, image-only reference definitions and raw HTML aren't links to it; each caller passes only text that can hold a link, so image and video sources, quote pictures, HTML blocks and an action's square thumbnail never reach the check, which names no field itself. A path in those places doesn't load in the mobile app, which passes an image path to its image component or the upload resolver unchanged, and in app builds from before this change renders HTML blocks in a WebView with no base url. This replaces guessing a url's context from the characters before it, which drew new misreadings in every review round; parsing was chosen over narrowing the check to flag every site url, which would tell admins to turn image sources and HTML attributes into paths that break in the app. Where GFM itself reads text as a link, such as an unquoted HTML attribute it autolinks, the admin is asked and can confirm. A link to an image or video file on the site, such as `[Flyer](https://thealliance.org/api/images/<key>)`, is flagged like any other link: no string the check reads is used as an image source, so a link node there is only ever a link, and a path opens it on the site. A skipped url on the old domain is still flagged as a worldalliance mention, per the requirement that every mention stays flagged. (agent decision)
- The worldalliance section reads "This mentions worldalliance. Links should use thealliance.org; names that still use worldalliance, such as the GitHub organization, can stay:". The user deferred how the section words its advice on old-domain links. The hint is there because the reminder form, update details and the contract page don't check site links, so an old-domain link there shows only in this section, and without the hint its only advice reads as permission to keep it. In editors that check links, links to the site have already moved to the link section, so the hint is still correct. (agent decision)
- A worldalliance mention inside a flagged site link's url is listed only in the link section, but only when that same string was checked for site links. The link section's excerpt is the url with its context, so a mention in the link's text is listed in the worldalliance section, as text outside the link is. The url's span is the destination as the markdown parser marks it (`resourceDestination`, `definitionDestination`), so escapes, entities, angle brackets and a title don't move it; an autolink is its whole text. A string checked as a whole url, a row value's included, is its own span, so a mention in that string is listed only in the link section. Text outside the link check, such as an update's title, still lists it in the worldalliance section. (agent decision)
- The mobile HTML block (`apps/mobile/components/forms/HtmlBlock.tsx`) loads its document at `/html-block` on the site (`getSitePageUrl`), a path the site doesn't serve, as the WebView's `baseUrl`, so a relative anchor resolves against the site, as it does on the web, and reaches the link handler, which opens it in its app screen or the browser. The WebView loads only its own document, that url, `about:blank`, which an iframe with no `src` loads, and that url with a fragment, an anchor in the document, which `#faq` resolves to, though a tapped anchor doesn't scroll, since the WebView is as tall as its document and the screen isn't told to move (ALL-2284); every other url, the home page and `/#join` included, goes to the link handler. A path of its own replaces loading the document at the site's home page, where a link to the home page, or to an anchor on it, couldn't be told from the document's own load or an anchor in it: the platforms report a tap differently (Android never reports `click`), and a document-relative `#faq` and a root-relative `/#join` resolve to the same url. Android blocks http subresources on an https base url by default, so the WebView sets `mixedContentMode` to `compatibility`, which loads http images and media as the WebView did with no base url. iOS has no such setting: WebKit applies its mixed-content rules to the https document, the rules Safari applies to the web app's https pages, which render the same HTML, so an http image loads or fails there as it does on the web. That choice lives in `loadsInHtmlBlock` (`apps/mobile/lib/htmlBlockLoad.ts`), apart from the component, so a unit test covers it. It is its own commit, before the admin warning. The user deferred how HTML blocks are handled. (agent decision)
- `servedSchema` (`server/src/tasks/served-schema.ts`) sends image sources as stored. Clients already resolve a key: web and mobile image blocks have since the `images` block was added on 2026-08-25 (`resolveImageSrc`, `resolveImageSource`), and a mobile build older than that can't render an `images` block at all. Update schemas and response snapshots were already sent as stored. Web and mobile load a key through the api, which redirects to the environment's CloudFront distribution, as the next entry says. Serving keys removes the URL-to-key guessing on save, which drew review findings on hosts, environments and malformed URLs. (agent decision, following the user's choice to serve keys)
- Web (`resolveImageSrc`, `imageSrcFromKey`, the markdown resolvers) and mobile (`getImageSource`, `resolveImageSource`) resolve an upload key to the api's `/images/<key>`, as before this task, and in an environment that serves uploads through CloudFront that route redirects to `https://<CLOUDFRONT_DOMAIN>/<key>` (`cloudfrontSrc` in `server/src/images/images.service.ts`, the rule the server's `getImageSource` renders keys by), cached for a day since the domain can change; local and visual-test servers stream the object as before, and image downloads have their own route. Streaming every form image from S3 through the app server would leave it no edge cache. This replaced resolving keys to CloudFront in each client, which put both environments' deployed config in every web bundle (against committed-deployed-config's requirement that a bundle carries only its own environment's web values), needed every resolver, markdown's included, to take the origin, and left app builds already installed streaming through the api; the redirect covers every client and resolver from one place, at the cost of a small api request per uncached image. The user deferred how keys are resolved; the remaining alternative was serving urls again. (agent decision)
- A legacy submission is matched against two served shapes of each snapshot, current and historical, whole and narrowed to the member: as served now, and with page image sources rendered as URLs (`withImageUrls`, marked `BACKCOMPAT(served-image-urls)`, going with the `schemaSnapshot` branch it serves). The old shape is rendered from the stored snapshot rather than inferred from the echo, so a form holding both keys and stored URLs still matches. (agent decision)
- The admin users list (`GET /user/list`) returns `AdminUserListItemDto`, a `UserDto` with `storedProfilePicture`, the column value, as the admin action DTO returns `storedImage` beside the rendered `image`. The quote editor stores that value and shows the rendered URL. The web `AvatarProfile` resolves a key itself (`resolveImageSrc`), so the quote block and the quote editor's fallback avatar show a stored key; its other callers pass URLs, paths or data URIs, which `resolveImageSrc` leaves alone. The mobile `ProfileImage` has resolved a key since 2026-02; it now resolves one before picking the thumbnail, which only applies to rendered urls, so a quote picture stored as a key still loads as a thumbnail. That choice lives in `profileImageUri` (`apps/mobile/lib/profileImageUri.ts`), apart from the component, so a unit test covers it: the mobile unit tests can't load react-native's components or `lucide-react-native`. (agent decision)
- `browserUrlFor` lives in `apps/mobile/lib/config.ts` beside `getSitePageUrl`, and the link press logic in `openLink` (`apps/mobile/lib/openLink.ts`), which takes `router.push` and `Linking.openURL` as arguments, because `linkPress.ts` imports `expo-router`, which the mobile unit tests can't load. (agent decision)
- The web quote avatar's test stubs `window.Image` so the image the avatar preloads fires load, since the test DOM never loads images and the avatar shows its picture only after that event. (agent decision)
- Since admins can confirm absolute links, ALL-2219 doesn't stop absolute links from coming back after ALL-2220's migration; ALL-2220 is told so. (agent decision, following from the user's choice to warn rather than enforce)
