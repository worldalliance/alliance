# Decisions

- **Each action is a row in `mms_thread_event` (kind, `afterMmsId`, `markedById`, `createdAt`) that is only ever inserted, and each handled inbound text points at the event that handled it through `mms.handledEventId`.** This is the shape EVIDENCE.md §1 found in Intercom, Zendesk, Front and Help Scout: a current state for filtering beside an append-only history shown in the conversation. Needs reply stays one more condition on its existing per-text search (`handledEventId IS NULL`), and who and when come from the event, so the two can't disagree. Mark needs reply clears `handledEventId` and inserts its own event; the earlier event stays. A mark that changes no text inserts no event, so a repeated click or one racing another staff member leaves no misleading line: each mark locks the texts it reads, in id order, so a concurrent mark of the same kind on the same number waits and then finds nothing left to change, while one of the opposite kind changes the other texts. Deleting the staff member keeps `markedById`, a kept reference in `soft-delete.ts` like `Mms.sentBy`, so the history keeps who acted and a restore brings their name back; meanwhile the thread says "Deleted user". (agent decision)
- **Each event is anchored to the newest text the page showed (`afterMmsId`) and travels with that text in the thread response, so older pages carry their own history.** Both actions take that text as `throughId`, which is why Mark needs reply is `POST /mms-threads/:userId/needs-reply` with a body rather than a `DELETE`. Events are never deleted, so the history the requirements keep can't be lost: deleting their anchor text is refused (`ON DELETE RESTRICT`, which `softDeleteCascade` reports as `SoftDeleteRestrictedError`), and `soft-delete.e2e-spec.ts` lists `MmsThreadEvent` as never deleted rather than giving it a `deletedAt`. A soft-deletable event would instead vanish with its text, and its `SET NULL` on `mms.handledEventId` would put handled members back on Needs reply. No code deletes texts today. (agent decision)
- **Mark handled covers the member's unanswered texts up to the newest text the page shows (`throughId`), not every text on the server.** A member's text that arrives between the last 10 s poll and the click is one staff haven't read, so it stays on Needs reply. The server refuses a `throughId` from another number's thread with the existing "That text isn't in this thread." 400; the refusal formerly named `BeforeNotInThread` is now `TextNotInThread`, since it serves both. (agent decision implementing REQUIREMENTS.md: a handled member comes back when they text again)
- **Like a staff reply, handling applies to the phone number, so every member sharing it leaves the list.** This follows `01a1c8bb-…-member-sms-chat`'s per-number rule. (agent decision)
- **Mark needs reply clears the handled mark on every handled text no staff reply has followed.** Those are exactly the texts the mark took off the list, so the member comes back with their original "Waiting …" time and preview. Texts a later staff reply answered keep their mark and line, so undoing can't relist an answered conversation. (agent decision implementing REQUIREMENTS.md: mark needs reply undoes mark handled)
- **The thread reports `replyState`: `needs_reply` when some unanswered text isn't handled, `handled` when all are, `answered` when there are none.** The page shows "Mark handled" or "Mark needs reply" from it, and neither for `answered` or an opted-out member, whom Needs reply leaves off anyway. The server computes it, rather than the page reading the Needs reply list, so the thread and its control come from one response. (agent decision)
- **One button changes label in place, and stays focusable with `aria-disabled` while pending, so keyboard focus stays on it as "Mark handled" becomes "Mark needs reply"** (root ux-guidelines: focus never drops to `body`). Each mutation stays pending until the thread and the Needs reply list have refetched, so the label doesn't flip back for a moment. A failure raises a toast that stays until dismissed, as a failed opt-out does. (agent decision)
- **Each event's line goes under its anchor text, centred between the two sides of the thread**, since it records a staff action rather than either side's text. (agent decision)
- **The Needs reply page's explanation now mentions marking handled and texting again.** (agent decision)
