# Decisions

- **Rejected names.** "Block" names form display blocks across the admin app, which the same admins edit, and reads close to "blocked" in a feature that decides who gets what. "Cell" already names one square of the grid (part × action). "Segment" names a reusable, overlapping saved audience at the vendors checked, which this product calls a member list (`EVIDENCE.md`). "Branch" names the expression branches the preview reports.
- **Code names.** A bare `part` is avoided where it would read ambiguously, so the stored type is `PartitionPart` and ids are `partId`. A suite with a partition `isPartitioned` (on `ActionSuiteDto`, replacing `usesGroups`), and the viewer's optional reason is `partition_part`, replacing `split_group`. No installed app knows either reason, and unknown reasons fall back to the generic "optional for you" wording.
- **Migration.** `SuitePartitions` renames the four tables, their sequences, columns (`groups` → `parts`, `splitVersionId` → `partitionVersionId`, `groupId` → `partId`), primary keys, foreign keys, indexes and the unique constraint to the names TypeORM generates for the renamed entities, and rewrites each placement trace's `steps[].groupId` to `partId`. It started from a generated migration, which created new tables, and was rewritten as renames so staging's rows survive; `migration:generate` afterwards reports no changes, and it reverts and reapplies cleanly.
- **Deploy order and rollback.** A release from before `SuitePartitions` but after #1066 (`0368c48fde`) reads `suite_split` on every cohort decision and suite list, so it fails for every action against renamed tables. This is accepted for the moment staging deploys serve the old release (see `REQUIREMENTS.md`), with two constraints recorded rather than coded, since the deploy script would need a stop-before-migrating step for one rename. This PR merges to `main` before `main` next goes to `production`, so production, which ran `2c5eb2ec07` from before #1066 when this was written, gets both migrations in one deploy and never runs such a release. And a deploy of this release that rolls back after migrating, or a force-push of `staging` or `production` back to a commit between #1066 and this one, needs `migration:revert` of `SuitePartitions` before the old release serves again.
- **Earlier task files** keep "split" and "group" as written, including the `BACKCOMPAT(split-row-optional)` tag they name; the tag in code is now `BACKCOMPAT(partition-row-optional)`.
- **Unrelated uses** of the words stay: form-builder visibility groups ("Split group before …"), reminder groups, member groups, the variant split of experiments, `es-toolkit`'s `partition`, and `String.prototype.split`.
