# Implementation guidance

These are agent decisions, reconsiderable within REQUIREMENTS.md.

- Identify reinstatement in `ContractService.signContract`, which both the agreement page and task-form submission call: the effective contract event at signing time is a suspension. First signings and signings while active have no such event, so they never qualify.
- Key the transition's identity on the suspension it ends: a `Notification` row with a unique `reinstatedSuspensionId` is the durable claim. It is written in the same transaction as the signed event, after locking the suspension row and checking for an existing claim (soft-deleted rows included). Overlapping signings of the same return serialize on that lock, and the later one finds the claim and sends nothing. The unique index backs the check. A later pause creates a new suspension, so the next return qualifies again. No historical notification or preference backfill.
- The claim row is the in-app entry. Its visibility comes from the member's in-app preference when it is written, so it exists even with in-app off, and push still follows its own preference.
- Emit `contract.reinstated` right after the signed event commits, and deliver push, text, and email from `ContractReinstatedListener` as detached work. Group restoration and other signing follow-ups can still fail the request afterwards, but the member is reinstated by then, so the confirmation is accurate.
- Send push directly from the listener with `shouldPush: false` on the row, rather than through the notification push dispatcher, so one staleness check covers every external channel and the dispatcher needs no category-specific rule.
- Treat delivery as stale when the member's latest suspension is no longer the one the claim ended. Comparing against the latest effective event of any type would also skip delivery after a contract switch that follows the return, and the requirements invalidate pending delivery only on a later pause. In-app entries already written stay.
- Reinstatement is detected from the contract events `signContract` reads before its transaction, as `switchingContracts` already is. A suspension that commits during a signing can end unannounced; serializing contract writes per member is ALL-1850.
- Choose channels through `externalChannels` (via `NotificationPreferencesService.channelsFor`), which applies preferences, the active-agreement condition, and text reachability and unsubscribe. Each channel goes through the shared `sendBestEffort`, extracted from the suspension worker: a failure is logged, the remaining channels continue, and nothing retries.
- Render the email greeting with `nameParts(name).firstname`. Text and email link to `tasksUrl(true)`. The in-app entry and push open `/tasks`, which mobile's `notificationRoute` already maps to its home task list. Messages carry no click tracking, matching the suspension notice.
- The settings row is a new `NotificationKind.ContractReinstated` (Actions section, all four channels, not required). Web, mobile, and admin render kinds from the server, so they need only the regenerated client.
- Copy is approved text only. Signing listeners that resolve open-action cohorts stay as they are.
- Verification: `server/test/contract-reinstated.e2e-spec.ts` turns the acceptance checks into tests. The race test holds the suspension row until both signings wait on it, and the stale-delivery test holds the first delivery back until after the later pause. Unit tests cover the event helpers and the email copy. Admin suspensions take the same `suspendContract` path and event as voluntary pauses, so the voluntary-pause case covers them.
