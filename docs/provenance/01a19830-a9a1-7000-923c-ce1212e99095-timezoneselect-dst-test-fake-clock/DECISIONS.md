# Decisions

- **Cause.** Under bun 1.3.6, `jest.advanceTimersByTime` and `jest.runOnlyPendingTimers` discard the value set by `jest.setSystemTime`: afterwards `Date.now()` reads the real clock plus the advanced milliseconds. The minute tick therefore rebuilt the list for the real minute, and the assertion saw Los Angeles's real offset, -420 under PDT and -480 under PST. The host `TZ` has no effect since the offset is computed for the named zone. Bun's docs say `Date` and the timers read one clock, so this is a bun defect; no upstream issue was found.
- **Fix in the test, not the hook.** `useClockMinute` reading `Date.now()` on each tick is the behavior wanted in production, where the real clock is right. The test mocks the clock with `jest.spyOn(Date, "now")`, which bun's timer advance leaves in place and which the timer callback reads. Every instant downstream of the hook derives from that minute via `minuteStart`, so a `Date.now` spy covers the whole path; `new Date()` is not spied and is not on it. The preload restores spies after each test.
- **Not upgrading bun.** Whether a later bun fixes this was not verified, and an upgrade is a wider change than the issue asks for.
- **Other tests left as they are.** The remaining `setSystemTime` tests in the file either advance no timers or compute the boundary they cross from the fake clock itself, so they are deterministic.
