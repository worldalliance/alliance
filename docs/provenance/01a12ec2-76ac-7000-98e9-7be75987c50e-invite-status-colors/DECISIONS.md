## Decisions

- **Accepted green, pending amber.** The web one-time list was first written with pending green and accepted zinc; mobile one-time and web community lists copied that. Commit `a49dacaca` ("growth goal on invite page") then deliberately swapped the web one-time colors to accepted green and pending amber, alongside a goal that counts accepted invites. It is the most recent deliberate choice, and the copies that disagree predate it, so it wins over the majority.
- **Pending shades are one class.** Community `request_pending` was `text-amber-600` while one-time `request_pending` was `text-amber-500` under the same "Request pending" label; both use `text-amber-500` so a label has one color everywhere.
- **Records live in `shared/styles/inviteStatus.ts`.** Mobile's Tailwind build scans only `shared/styles` (`apps/mobile/global.css`), so class strings anywhere else in `shared/` would not be generated for mobile. The one-time labels move there from `shared/lib/copy.ts` so label and color sit in one record. Both sets draw on one tone→class map, so "Pending" in one set cannot drift from "Pending" in the other.
- **Admin invites page uses the one-time record.** It showed "Active" (green) for an unused link and "used" (gray) for every other status, including pending and rejected requests. It now shows the same labels and colors as the member-facing lists.
- **Mobile groups "pending invites" summary stays separate.** `apps/mobile/app/(app)/groups/index.tsx` lists only outstanding invites in muted zinc with "Pending"/"Link sent", a different view whose wording distinguishes a request from a sent link; it is not a status→color map.
