## Location: `agents/desktop`

The app lives at `agents/desktop`. `agents/` holds tooling for the coding agents that work on the repository, and `apps/AGENTS.md` covers the product apps (generated API client, web and mobile parity), none of which applies here. The root `package.json` lists its workspaces explicitly and `agents/` is not one, so the package installs from its own lockfile. Moving it in changes these things outside the folder: the root `eslint.config.mjs` ignores `agents/desktop/`, since `common`'s typecheck lints `../agents` with that config and ESLint drops a CLI `--ignore-pattern` that points above its working directory; `common/tsconfig.typecheck.json` excludes `../agents/desktop` from its tsc run, and its comment saying `agents/` has no `package.json` names the exception; the root `AGENTS.md` lists `agents/desktop/` as its own package and records it as an exception to the `apps/frontend` install rule, and `agents/README.md` describes it; `.prettierignore` lists the app's build and test output, which only its nested `.gitignore` names; `.vscode/settings.json` lists `agents/desktop` in `eslint.workingDirectories`, so the editor lints its files with its own config rather than the root one that ignores them; and `scripts/test-all.sh`'s header names `agents/desktop` as an exception. That script and the `test-unit` matrices of `ci.yaml` and `deploy.yaml`, which install only the root lockfile, keep listing `agents`: the app's tests are `*.e2e.ts`, which `bun test` doesn't discover, and narrowing the lists before then would silently drop any later test elsewhere in `agents/`, so the app's first test `bun test` discovers narrows them (agent decision). `.github/workflows/desktop.yaml` runs the app's typecheck and tests, path-filtered to the app, `eslint/`, the root `package.json` and `bun.lock`, and itself so other PRs skip its Electron download, and the app stays out of `bun run test` and `covercheck`. That workflow installs the root lockfile too, because the app's ESLint config imports `eslint/shared-rules.mjs` for the repo's shared rules, `alliance/max-lines` among them, and that file's own imports resolve from the root `node_modules`.

The app's tests drive the built app through Playwright Test's Electron support, one of the drivers Electron's testing docs describe (https://www.electronjs.org/docs/latest/tutorial/automated-testing). Playwright Test runs on Node, through the `playwright` bin's `node` shebang: Playwright 1.64's Electron launch timed out under Bun 1.3.6, the version installed when the app was built, and passes under the pinned Bun 1.4.4 on macOS but is unmeasured there on Linux. Node runs the tests whichever Bun a developer has installed; moving them to Bun, which would drop CI's Node setup, waits until they pass under Bun in the Linux CI job (agent decision). Electron has no headless mode on macOS, so the window opens with `show: false` and shows on `ready-to-show`, as Electron's `BrowserWindow` docs recommend to avoid a visual flash, and `playwright.config.ts` sets `ALLIANCE_AGENT_HEADLESS=1`, under which the app never shows its window or dock icon and a load failure skips its modal dialog. The files are named `*.e2e.ts` so `bun test`'s discovery never picks them up, and unit tests that need no Electron can use `bun test` beside them. CI runs on Ubuntu under `xvfb-run`, after lifting Ubuntu 24.04's AppArmor restriction on the unprivileged user namespaces Electron's sandbox needs; a macOS runner costs more and waits until a test depends on macOS behaviour (agent decision).

The app keeps its own copy of the `Result` helper rather than importing `common/`. The copy arrives with the first fallible operation that needs it, not with the skeleton, which has none (agent decision). The skeleton likewise has no preload script or IPC channel yet; the first PR whose renderer needs the main process (PR 3 or 7) adds them. The window refuses `window.open` and in-page navigation other than a reload of its own page, which Vite's dev full reload needs, and the renderer's Content Security Policy allows only the app's own scripts, per Electron's security checklist (https://www.electronjs.org/docs/latest/tutorial/security). The built renderer loads from a privileged `app://` scheme serving its build folder rather than `file://`, under which the policy's `'self'` admits every file on disk and the page can read local files, as the checklist's item on avoiding `file://` warns (agent decision). The main process reads the dev server's `ELECTRON_RENDERER_URL` only when unpackaged, as electron-vite's template reads it only in dev, so a packaged app's launch environment can't point its window at a remote page (agent decision).

## Agent processes

The Electron main process owns every child process; the renderer only draws and talks to it over IPC. Each backend has an adapter behind one interface (start a session in a worktree, send a message with optional images, resume, interrupt) that emits one event stream (assistant text, tool started, tool finished, turn ended, error), so the UI never sees vendor types.

- Claude runs as `claude -p --input-format stream-json --output-format stream-json --verbose --dangerously-skip-permissions` in the worktree. A `result` event ends a turn. Image input was verified on Claude Code 2.1.318: a base64 image content block in a stream-json user message was read correctly.
- Codex runs as `codex app-server` over JSON-RPC on stdio, with approvals and sandbox off. `turn/completed` ends a turn. `codex app-server generate-json-schema` on 0.163.0 shows `localImage` among `turn/start` inputs, and `codex exec -i` read a test image correctly. OpenAI documents `app-server` as the interface for rich clients, so it is preferred over `codex exec --json`.
- A turn ending, an error event, or the process exiting drives agent status and notifications. With permissions off, an agent never waits on approval, so the only "needs you" state is a finished turn.
- Bundled CLIs stay at the pinned version and send no telemetry, error reports or usage analytics, as REQUIREMENTS.md requires. Claude runs with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, which turns off auto-updates, telemetry, error reporting, `/feedback`, Claude-drafted feedback, release notes, PR status badge checks, availability checks and feature-flag fetching; `DISABLE_FEEDBACK_COMMAND=1`, which also covers `/bug` and `/share`; and `DISABLE_UPDATES=1`, which also blocks a manual `claude update` (https://code.claude.com/docs/en/env-vars, https://code.claude.com/docs/en/data-usage). The WebFetch hostname check stays on: it sends only the hostname, to check it against Anthropic's safety blocklist, and is part of the tool rather than analytics. Codex's private `config.toml` sets `analytics.enabled = false`, `feedback.enabled = false` and `check_for_update_on_startup = false`, the last because the app manages Codex's updates; these keys come from OpenAI's config reference and PR 4 confirms them on the pinned version. The app launches them by absolute path, which avoids macOS and Linux GUI apps not inheriting the shell's `PATH`, and builds the environment its agents run commands in deliberately: the tools they use (git, Bun, `gh`, Postgres clients) plus the bundled CLIs' directory first on `PATH`. The repo's subagents and review-loop skills spawn `claude -p` and `codex exec` by bare name, so Create PR works without a terminal install and its subagents run the pinned versions with the app's private config folders and sign-in. These variables, `CLAUDE_CONFIG_DIR` and `CODEX_HOME` therefore apply to everything the app's agents spawn; only a CLI started from the user's own terminal keeps its own settings and updates.
- A pinned exact version, not a minimum, because both CLIs' structured output changes between releases and Codex documents its protocol schema as matching the CLI version that generated it. A bot proposes version bumps so vendor fixes arrive with the next app release.

## Credentials

The CLIs start outside `infisical run`, and `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` are removed from their environment. Infisical's `dev` environment holds a shared `CLAUDE_CODE_OAUTH_TOKEN`; a `claude` process inheriting it would bill every employee's usage to one account, breaking the own-subscription requirement. Commands the agents run, such as dev servers, still get secrets through `scripts/with-env.sh`.

The app never collects or stores Claude or ChatGPT credentials; sign-in runs each CLI's own login flow inside the app's private config folders. Anthropic's legal and compliance page (https://code.claude.com/docs/en/legal-and-compliance) allows running the unmodified Claude Code binary in a product and allows end users to sign in to it with their own subscription, provided the organisation agrees to the Commercial Terms, the binary and its sign-in methods stay unmodified, no one intermediates Claude credentials or pays for usage on users' behalf, and the product's name and logo don't use Anthropic's marks. Releases are public GitHub Releases (see Release pipeline), and REQUIREMENTS.md accepts that anyone can download and use a build: anyone outside the Alliance gets a working Claude Code client, signed in with their own subscription, from a publicly distributed copy of the binary, which that page neither allows nor forbids. Whether the Alliance has agreed to the Commercial Terms, and whether they cover redistributing the binary in public release artifacts that anyone can use, is unconfirmed (assumption, agent decision to check both before the first employee build). PR 4 starts by getting both answers from the Alliance, since its approach depends on them. If redistribution isn't covered, PR 4 stops and asks the user how to proceed, since REQUIREMENTS.md requires the app to bundle the CLIs and no fallback is approved.

## Secrets migration

Until ALL-1964 (local dev on `infisical run`) lands, checkouts use hand-made `.env` files and `agents/chats/chats.ts` reads the bucket keys from `.env.devtools`. The app supports both paths, the env-file checks marked `BACKCOMPAT(ALL-1964)` and removed once ALL-1964's contract step lands, per the root `AGENTS.md` breaking-changes rule. Which path is in use is explicit; an expired Infisical sign-in shows as an error and never falls back to stale `.env` values. Per the Env Var Overhaul project, Linear and transcript-bucket keys will be in Infisical and PostHog keys are per user.

Transcript uploads and remote transcripts need the `alliance-agent-chats` keys, which `agents/chats/chats.ts` reads only from the gitignored `.env.devtools`, so a fresh clone has none; the repo's Linear skill reads its keys from the same file. No Env Var Overhaul issue moves them, so the plan does: they go in Infisical `dev`, and `chats.ts` reads them from its environment, falling back to `.env.devtools` under `BACKCOMPAT(ALL-1964)`. Its hooks run through `scripts/with-env.sh`, which gets them from Infisical once ALL-1964 lands, since the CLIs themselves start outside `infisical run`. Claude hooks already resolve `chats.ts` through `$CLAUDE_PROJECT_DIR`, the session's own checkout, so PR 19 wraps them with that checkout's `with-env.sh`. Codex hooks find `chats.ts` in the main checkout through the git common dir, but the main checkout's `with-env.sh` exits when run from a worktree, so they wrap with the session's own checkout's script, `$(git rev-parse --show-toplevel)/scripts/with-env.sh`. Codex loads a project's hooks only once the project and its hooks are trusted, which `agents/README.md` has terminal users do with `/hooks`, and a fresh private `CODEX_HOME` trusts nothing; the app has no TUI, so it writes that trust for the main checkout, whose `.codex/hooks.json` Codex runs in every worktree, into its private `config.toml`. PR 6 finds the keys the pinned version stores trust under and adds a test that starts `app-server` in a worktree with a fresh `CODEX_HOME` and sees the upload hook fire, and setup checks that trust like any other item, so PR 9 depends on PR 6. Setup checks the keys by fetching a missing transcript (`NoSuchKey` means they work); until ALL-1964 lands, its Fix session writes them to `.env.devtools` from Infisical `dev`. Every employee with `dev` access can then read every transcript, which the sharing design already assumes.

The repo's skills read keys from `.env.devtools` too: the Linear skill its client credentials and the PostHog skill `POSTHOG_API_KEY`, which Settings saves as an Infisical personal override. A value set in Settings reaches an agent only if the skill reads it from the environment, so PR 19 switches the Linear skill and PR 16 the PostHog skill to read their keys from the environment through `scripts/with-env.sh`, each falling back to `.env.devtools` under `BACKCOMPAT(ALL-1964)`. The PR that introduces a per-user key, PR 16 for the PostHog key, adds its placeholder shared secret in `dev` once; the app writes only personal overrides, so employees need no write access to shared secrets.

## Worktree records

The app does not parse the scripts' record files (`<git common dir>/alliance-worktrees/instances/<id>/record`). A new `scripts/list-worktrees` prints them as JSON (name, branch, path, ports, parent) with a `version` field, and a test fixes its shape. On a version the app doesn't know, it offers to pull the latest `main` instead of guessing, since the app and the checkout it drives update independently. New worktrees start from a freshly fetched `origin/main`. PR 10 runs the worktree scripts in the checkout PR 8 finds or clones, so it depends on PR 8.

## Transcript sharing

The user left the sharing mechanism to the agent. A "Copy link" button produces `alliance://transcript/<tool>/<session-id>`, which opens the transcript read-only in the app, and an "Open transcript" box accepts a bare id or bucket key (`<tool>/<session>.jsonl`). The `alliance` URL scheme follows the root `AGENTS.md` naming rule. REQUIREMENTS.md accepts that everyone with `dev` access reads every transcript, so sharing needs no permission model and the shared bucket keys suffice. Deleting a transcript hides it on that machine only. A remote transcript the user opens shows in the transcript view and is not added to the sidebar; the first version has no control that adds it, which REQUIREMENTS.md leaves open. The bucket's one IAM user can overwrite but not delete any object (`terraform/agent-chats.tf`), so read-only is the app's behaviour, not enforced by the bucket, and since no transcript is ever continued, an overwritten one can mislead a reader but never becomes an agent's history; an overwritten version stays recoverable for 7 days through bucket versioning.

## Release pipeline

electron-builder with electron-updater, publishing to GitHub Releases on tag. macOS builds are signed with a Developer ID, which auto-update requires, and notarized, which Gatekeeper requires to open a downloaded app. Linux ships as an AppImage, the format electron-updater has long supported; `.deb` support is checked before shipping one. The bundle identifier uses `alliance` per the root `AGENTS.md` naming rule, falling back to an existing prefix only if taken. The minimum supported version is published alongside releases and checked at launch.

## Not built on DeepSeek Harness

Considered and rejected (agent proposal, not put to the user as a question): DeepSeek Harness replaces the agent loop instead of running the CLIs, is a developer preview with breaking changes announced, and has telemetry on by default.
