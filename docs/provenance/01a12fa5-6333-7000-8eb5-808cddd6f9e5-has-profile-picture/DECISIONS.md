## Decisions

- **Definition: non-null and containing a non-whitespace character** (JS `trim()` in TS, `~ '\S'` in SQL, since Postgres `TRIM` strips only spaces). Three of the five server copies already required this, and form visibility's "profile picture has a value" (`userValuePropertyPresence` in `common/src/forms/user-properties.ts`) already used it. Staging held no empty or whitespace-only values, and the only write path (`ImagesService.resolvePhotoUpdate`) stores null or a fresh upload key, so no member's result changes today. The public directory, the facepile ordering, and the UploadedPhoto validator now also treat a blank value as no picture.
- **Location: `hasProfilePicture` in `common/src/profilePicture.ts`, `sqlUserHasProfilePicture` in `server/src/user/profile-picture.ts`.** The pair mirrors `isContractActiveAt` / `sqlUserHasActiveContractAt`. The TS form lives in common because form visibility's `userValuePropertyPresence` (common, run on the server) is also a copy of the rule: a form can gate a photo-upload step on that presence while the step's UploadedPhoto validator reads `hasProfilePicture`, so the two must change together. The SQL form stays server-only.
- **SQL matches TS on ASCII whitespace only.** Postgres `\S` follows the database ctype; non-ASCII whitespace (e.g. U+FEFF) can differ. Unreachable through the write path, so the JSDoc states the limit rather than adding locale-specific SQL.
- **SQL helper takes a column expression**, like `sqlUserHasActiveContractAt` takes a user-id expression, because callers alias the user table differently (`u`, `req`, `addr`, quoted `"user"`).
- **Left separate:** the DTO constructors' `profilePicture ? getImageSource(profilePicture) : null` map a stored key to a URL rather than deciding presence. The client apps' checks (`MemberFacepile`, `UserProfilePicRow`, `ActionActivityDetail`, navbars, admin `ForceGraph`) test whether a DTO carries an avatar URL, which the server has already nulled when the key is empty.
- **Tests:** e2e assertions pin that the UploadedPhoto validator rejects a whitespace-only picture and that the new-member facepile ranks blank pictures below a real one; a unit test (`common/src/profilePicture.test.ts`) pins `hasProfilePicture`; an e2e spec checks that `sqlUserHasProfilePicture` agrees with it on stored null, empty, space, tab/newline, and key values; an e2e test pins that `/user/members-public` excludes a member whose picture is blank.
