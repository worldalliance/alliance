## A fixer ends its run with its report

Agent decision on how; the user required the change and deferred how it is done (REQUIREMENTS.md). The fixer prompt tells the fixer to stop its background tasks, monitors and wakeups before its final message. The subagents skill runs `claude -p` with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` at two hours so a subagent's background checks can finish, and that same wait kept eight finished fixers alive for 2.6 hours (EVIDENCE.md, **Where review-loop time goes**). Lowering the ceiling instead would cut off fixers whose checks are still running. The review skill tells reviewers only to stop their background tasks, not monitors or wakeups; no reviewer was measured waiting this way, so reviewers are left as they are.

## At most four reviewers at a time

Agent decision on how; the user required the change and deferred how it is done (REQUIREMENTS.md). "A handful" left the number to each hub, and reviewers run end-to-end suites, typecheck and unit tests. Load averages of 800 and more on a 10-core machine appeared beside timing-test failures (EVIDENCE.md, **Where review-loop time goes**), recorded during fixer runs after that loop's own reviewers had finished, so the load came from other checkouts and the fixer's own checks, not from one loop's reviewers. Four is agent judgement: enough to keep reviews parallel on a branch's usual commit count while leaving cores for the fixer and other checkouts, and it bounds the worktree pool the next change keeps. Starting the next reviewer as one finishes, rather than in batches, keeps the slots full. This caps only one loop; loops on other branches still share the machine, and how much contention costs wasn't measured.

## Reviewer worktrees last the loop

Agent decision on how; the user required the change and deferred how it is done (REQUIREMENTS.md). Creating and removing a worktree per review cost 7.15 hours across the measured histories, removal more than creation (EVIDENCE.md, **Where review-loop time goes**). A reviewer worktree is now created when a reviewer needs one and none is free, and kept until the loop stops unless removed after a review; before each review the hub force-checks-out the worktree's own branch at the round's tip and runs `git clean -ffdx`, which also removes checkouts a reviewer nested inside it, keeping the root `node_modules`, `.worktree/` and every `.env*` file, including any a reviewer added or edited, then `bun install`, which is quick when the lockfile hasn't changed and relinks the workspaces' own small `node_modules` (0.53 s on 2026-11-12, bun 1.4.4). Nested `node_modules`, `agents/desktop`'s included, go with the clean, so a reviewer installs the desktop app against the tip's lockfile as in a new worktree. Every reviewer starts from the round's tip with nothing from the last reviewer but those kept files and any process it left running; reviewers have no reason to edit local config, and the review skill has them stop their background tasks. Findings files and a failed run's logs are copied out right after each review, before any removal, as before. Removing a worktree used to remove the worktrees its reviewer made of the base too, so the reviewer prompt now asks reviewers to remove them; any a reviewer leaves go with its worktree, after a failed review or when the loop stops. The ignored files in a worktree were checked on 2026-11-12: only `.env*` files, `.worktree/`, `.scratch/` and `node_modules`; the record id lives in git's admin directory, outside the tree. `scripts/rm-worktree.sh` deletes a branch the script created with `branch -D`, so moving it to each tip doesn't keep it from being deleted. The development database isn't reset between reviews: it starts as a copy of the main checkout's local data, so rows earlier reviewers add are the same kind of state, but a reviewer can migrate it, so a worktree is removed after any review at a tip where a commit since the base touches `server/migrations` or an entity, even one a later commit undoes, since a reviewer can check out any commit in the range. Keying the removal on the tip that review saw, at the same point as removal after a failure, needs no memory of each worktree's history; earlier rules missed migrations left behind, one by comparing the worktree's checkout, which shows only where the reviewer stopped, and one by testing the next tip, which a fixer dropping the branch's schema change makes quiet. On a branch where no commit touches either, `migration:generate` writes nothing, so a reviewer has no migration to run. Schema branches give up reuse. The test database needs nothing, since the e2e suite drops and rebuilds its schema. Lighter worktrees, skipping the database copy or install, would save less (install was 1.44 of the 7.15 hours) and would take away the isolated database reviewers use for integration tests.

## Deferred choices are simplified, not grown

Agent decision on how; the user required the change and deferred how it is done (REQUIREMENTS.md). The cut rule removes optional work that keeps drawing fix-now findings, but it excludes a choice the user deferred ("I don't care how"), so the fixer kept patching such choices to each reviewer's standard, and each patch gave the next review new text to find issues in (EVIDENCE.md, **What later rounds find**; **How others bound review loops** on drift and length bias). From a deferred choice's second round of fix-now findings, the fixer now answers them by simplifying or narrowing the choice where that fixes them, rather than adding a clause per finding. "Where that fixes them" is the only bound: a simplification that broke a requirement, a repo rule or an earlier fix would not fix anything, and a finding only an addition fixes still gets one. The trigger reuses the ledger column the cut rule already reads. Findings stay fix-now and every fix is still reviewed, so nothing the loop catches is waived; only the shape of the fix changes. Suppressing findings on `DECISIONS.md` entries outright was rejected: required behaviour is often implemented through agent decisions.
