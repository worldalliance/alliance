# Decisions

- "No custom stat" has one spelling: `CustomActionStat.NONE`. The column becomes `NOT NULL DEFAULT 'none'` and a migration turns the stored `NULL`s into `'none'`, so the property is `customStatType: CustomActionStat`. `NONE` stays over `NULL` because the admin select already offers "None" and the stats switch already handles it, while dropping it would need an enum migration and an admin change.
- `CreateActionDto` takes the type as optional, so a create that leaves it out gets the column default, as existing clients and specs do. It is validated with `skipNullProperties: false`, so an explicit `null` is a 400 rather than a `NOT NULL` violation. `@IsEnum` replaces the bare `@IsOptional`, which let any string through to a database error.
- The member action page shows the stat only for a type other than `none`. The stored value is not cleared when an admin switches the type to `none`, so the old truthiness check showed a stale value; the check lives in a small `ActionCustomStat` component so it can be tested without rendering the whole page. Which types track a stat is a `Record<CustomActionStat, boolean>` in `shared/lib/customActionStat.ts`, shared with admin's custom stat fields, so a new type is a compile error until it is opted in or out.
- The CI seed's action rows take `none` the same way the migration does, an edit to that one column rather than a full `reseed.sh`, whose dump also carries schema drift from unrelated migrations.
- Pasting an exported action stores a `null` type as `none`, so an export taken before the migration still imports.
