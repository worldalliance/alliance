# Decisions

- **Cause.** See `EVIDENCE.md`. Everything that grew with each deploy lived on the EC2 hosts, and nothing pruned it: the Bun install cache, the frontend build folder, the admin build folder and the pm2 logs.
- **Clear the Bun cache after each install** (frontend deploy script and `scripts/deploy_backend.sh`) with `bun pm cache rm`. Bun on Linux hardlinks installed packages out of the cache, so the installed `node_modules` survives. The cost is a cold download on the next install. A failure only prints a warning, because a cache that can't be cleared shouldn't fail or roll back a deploy.
- **Prune frontend and admin build files older than 7 days.** Both deploys extract over the previous build with `unzip -o`. They now add `-DD`, which dates every extracted file to the extraction time; without it, `unzip` keeps the zip's stored build time, so re-running a deploy job more than a week after its build would delete the build it just installed. A week still serves chunks to pages loaded before a deploy, as long as deploys are under a week apart; after a longer gap the previous build is pruned right away, and the frontend's chunk-load failure handling reloads the page. Production has not gone a week without a deploy in its last 400 deploys. The frontend prune runs after `pm2` starts the new server, so the old server is never missing files while it is still running.
- **Rotate pm2 logs with `pm2-logrotate`**, installed by the frontend deploy when it is missing. Both apps share one pm2 daemon per host, so one install covers both. The module's defaults (rotate at 10M, keep 30) cap each log, where before `client-ssr-error.log` alone had reached 376M on production.
- **Check free space before the upload.** `build-react-app` fails with a readable `::error::` when the host has under 3G or under 100k inodes free, before anything is deployed. Staging had run out of both. A full disk had shown up only as scp's `Process exited with status 1`. The 3G leaves room for the upload and for a Bun install with an empty cache.
- **journald is left alone.** It is capped by default (10% of the filesystem, so 3G on these 30G volumes) and held 1.8G.
- **Not in this change:** a Grafana alert on disk usage from the node_exporter metrics the monitoring instance already collects (`docs/legacy/monitoring.md`). That alert is configured in Grafana's UI, not in this repository.
