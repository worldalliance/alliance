# Seeded `random` variable input

[REQUIREMENTS.md](./REQUIREMENTS.md) defines the task. The choices below are agent-authored.

- The seed is `<randomizationKey>:<variableName>:<inputName>`, not just the variable name, so two `random` inputs in one variable pick independently instead of always being equal. Renaming the variable or the input re-rolls every member's pick, just as a variable-name-only seed would on a rename.
- `hashStringToSeed` moves to `common/src/random.ts` unchanged, and `uniformHash` there applies the murmur3 32-bit finalizer on top. `hashStringToSeed` itself is not changed: `shuffleWithSeed` and `commentsFilter` already depend on its output, so changing it would reshuffle every member's existing option order and comment order. Raw FNV-1a is unusable here because a product's low bits depend only on the operands' low bits: for `input % 2`, variables named `a` and `c` agreed for 1000 of 1000 members.
- `prepareFormula` takes the variable name as an optional `variableName`. Options formulas pass none, so a `random` input fails there. Validation rejects it in an options formula with `Input "<name>" picks a random number, which only a variable can use`, and the admin mode picker disables the option for options formulas. Options formulas have no variable name to seed with, and nothing asked for random options.
- Admin validation evaluates with the placeholder key `"validation"`. Without a key the unanswered evaluation fails, and every formula using a `random` input would be blocked from saving.
- Output views take the submitter's id (`submitterId` on `OutputSource`) from `activity.user.id` at the four activity call sites (web and mobile). The server builds an activity's output from that activity's own `taskFormResponse`, so the activity's user is the submitter. This avoids adding a user id to `FormResponseOutputDto`, which would need a regenerated API client. The key comes from `formRandomizationKey`, the pure function `useRandomizationKey` now wraps, so both surfaces share one key format.
- An output view with no submitter, such as the admin `OutputBuilder` preview, has no key, so the variable stays unresolved and shows `#{name}` as written. That is how shared output already treats variables it can't resolve.
- Anonymous members keep the existing randomization-key fallback (the persist key, else `form:<id>`). Their output views have no user id, so the variable stays unresolved there.
- The admin row for a `random` input replaces the form and question pickers with a sample-number box for the preview, defaulting to 0. The help text and example (`["A", "B", "C"][input1 % 3]`) live in `RandomInput.tsx`, because `VariableSamples.tsx` is at the line limit.
- `common/src/forms/formula-options.ts` was already past 500 lines and needed one more `case`. Following the repo's file-size rule, the saved-choices code (`FormulaChoices`, `readFormulaChoices`, `selectsFormulaChoice`, `selectedFormulaChoices`, `schemaWithSavedChoices`, `fieldWithSavedChoices`, `fieldsWithSavedChoices`) moves unchanged to `common/src/forms/formula-choices.ts`, and its importers are repointed. `codex` isn't installed here, so a read-only subagent given only the file name proposed the splits. This is the smallest of its options.
- `shared/useFormRenderer.ts`, `sharedweb/forms/FormRenderer.tsx` and `apps/mobile/components/forms/FormRenderer.tsx` are legacy files over the limit with `max-lines` waivers. They each gain a few lines of wiring and are not split here. Splitting them is separate work.
