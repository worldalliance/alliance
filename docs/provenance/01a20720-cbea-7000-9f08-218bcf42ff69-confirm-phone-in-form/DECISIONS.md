# Decisions

- **One confirm control, `apps/frontend/src/components/phone/PhoneConfirm.tsx`, serves the form and settings.** It shows "Confirmed" when the signed-in member's number is this one and verified; otherwise the unconfirmed note with "Send code", then the code box with "Confirm number" and "Send code again" (held until the server's `resendAvailableAt`). Confirmed state comes only from the signed-in member: after a confirm, `useVerifyPhoneCode` reloads the member and writes the confirmed number into its cache, so a failed reload still shows it confirmed, and no host keeps a record of its own that could drift from the server once the member switches numbers. Error copy is the server's (`otpRefusalException`), so it stays one set of messages with the endpoints. The code helpers it shares with the KORA sign-in card moved to `apps/frontend/src/lib/otpCode.ts`. The unconfirmed note is read in order, not announced: it appears beside the "Send code" button it explains as the member's own typing completes the number, where an announcement would interrupt them. REQUIREMENTS.md's announced status text is the code-sent, "Confirmed" and error lines: focus moves to the code box after every send, resends included, and the box is described by the code-sent line and any error, since a status region inserted already holding its text, or whose text a resend leaves unchanged, isn't reliably announced (MDN, ARIA live regions); focus moves to "Confirmed" too; errors are alerts. (agent decision interpreting the requirement)
- **The form reaches it through a context slot, `sharedweb/forms/phoneConfirmSlot.ts`.** `PhoneInputField` is shared with the admin panel and previews, so it renders the control only when a provider supplies one and the question fills the profile, can change, and holds a whole number. `TaskFlow` provides it only in a live flow for a signed-in member who is not being impersonated; an admin acting as a member doesn't text codes to them, matching settings, which already hides member-only prompts under impersonation. Other member form surfaces outside `TaskFlow` keep the plain field. Follows the existing `ShareLinkViewerProvider` pattern for app-specific behaviour in shared form parts. (agent decision)
- **Confirming is never automatic.** The member presses "Confirm number" (or Enter) after the code is filled, by hand, paste, Safari's one-time-code autofill or WebOTP; submitting on the sixth digit would change context on input, which WCAG 3.2.2 warns against, and KORA's code step works the same way. Enter in the code box confirms and is kept from submitting the task form around it. Busy buttons use `aria-disabled` rather than `disabled`, styled as disabled, so focus stays on them (ux-guidelines, focus). Focus moves to the code box once a code is sent and to "Confirmed" once confirmed. (agent decision)
- **The prefill seeds only phone questions with `autoExtractUserData`, in `useFormSchemaMaps`, shared with mobile.** That hook already seeds timezone fields from the member; the profile number replaces the field's own default, as the timezone does, and a draft's answer still wins, since defaults fill only empty answers. A draft in local storage leaves out an answer still equal to its default (`answersToStore`), so a number the member left alone is refilled on restore from the number on file then, not the one they had when they started; timezone fields get the same. The draft synced to the server carries every answer, since installed mobile builds, which an over-the-air update reaches only on a matching native fingerprint, keep their own value for an answer a synced draft leaves out; the profile phone answer goes as "" per the synced-draft requirement (`answersToSync`, `answersFromSync`), and a synced timezone comes back as it was saved, as before this task. Leaving answers at their default out of the synced draft waits for every installed build to reset such answers to their default (`BACKCOMPAT(sparse-synced-draft)`). Mobile gets the prefill in this PR because the hook is shared; its confirm control is ALL-2249. (agent decision)
- **Settings reads confirmed state from the signed-in member, so a saved phone change now reloads it** (`useUpdateProfileMutation`). Settings shows the control for the saved number, or for a number the server refused as held by another account, where it reads "Confirm it’s your number to move it to this account." Confirming a refused number calls `phoneNumberConfirmed` on the autosave hook, which clears the refusal and records the number as saved; without it, autosave would send the old number back over the one just confirmed. (agent decision)
- **Saving without a code is intended, so the `BACKCOMPAT(phone-verification)` markers in `UserService.update` and `FormProfileAnswersService.savePhoneNumber` are reworded to say so**, per REQUIREMENTS.md. ALL-2250 is closed with a note. (agent decision implementing the requirement)
- **The welcome text is unchanged.** It is the texting opt-in confirmation, telling the member to reply STOP to opt out, so it still goes on the first saved number, whether or not a code was also sent. (agent decision)
- **No hiding of "Send code" by country.** Twilio refuses UK numbers today, but REQUIREMENTS.md keeps a retry for every number; a send that fails shows the server's message with "Send code again". (agent decision implementing the requirement)
