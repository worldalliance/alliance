# Decisions

## Changes, one Linear issue each

Agent decision: the split of the work into independent changes, per the requirement that each becomes its own issue in one project. "Needs" names a change that must land first; everything else can proceed in parallel.

## Choices the user deferred

These are agent choices; drop any for an alternative once it adds more friction than it is worth. The user deferred how they are done, not whether.

- **Builder versus text for parts the builder can't show** (agent recommendation): the whole condition stays in text, with a note naming the unsupported part, and returns to the builder once that part is gone. This follows Jira's basic/advanced search (EVIDENCE.md, "How do products let non-engineers author conditional rules?"). The builder-first prototype's "Text only" rows are the alternative.
- **Preview refresh** (agent recommendation): sample-member results update live as the admin edits; population counts need an explicit "Run preview", with old counts marked out of date after edits.
- **Choice values in text**: show each value's label inline or on hover; an error for a wrong value lists the allowed labels.
- **TypeScript worker loading**: load the in-browser language service only when a text editor opens. Save-time checking stays on the server. The worker is about 1 MB gzipped on TypeScript 6, and TypeScript 7 has no browser checker (EVIDENCE.md, "Expression-language lab").
- **Builder visible under text**: show the builder below the text, with a "Hide" control.
- **Nesting depth**: no fixed limit; named conditions keep rules readable.
- **Type-check timing**: on save, plus autocomplete once the text editor is open.
- **Type-to-confirm** (agent decision; the user set when it's needed, not how): the admin types the suite's name, as `apps/admin/src/components/DeleteAccountModal.tsx` has the admin type the member's email. The server stores who confirmed, when, and the warnings they passed, beside the `member_action` event or split edit.
- **Builder fallback for visibility and required-if** (agent decision; the user deferred frontend details): when a visibility or required-if condition could be undecided, the builder shows a fallback choice worded for its consumer, "When there's no answer: Show / Hide" for visibility and "When there's no answer: Required / Not required" for required-if, printed as `?? true` / `?? false`, as split groups get "put them here" / "continue to the next group". Answer comparisons, which most conditions are (EVIDENCE.md, "Current usage volumes": 401 of 677 visibility conditions are `equals`), all need it, so leaving it to text mode would push routine conditions out of the builder.
- **Actions moving into or out of a live split suite** (agent decision; the user deferred the choice, and the majority of two second opinions recommended this): once a split suite has gone live, and after it finishes, no action moves into or out of it and none is created directly in it; new work goes in a new suite. The server refuses the change with an error naming the suite. A move in would give a pending member a same-suite read they can't satisfy, since they have no tasks for the suite until their group is fixed, and a source the group-fix capture lacks; a move out is treated the same. Should a grid column still be added after go-live, members already placed get "not assigned" decision rows for it (`included` false), so it affects only members decided afterwards. The fallback that shows an undecided action by live cohort eligibility (`server/src/actions/member-actions.service.ts`) doesn't apply to split suites. This is the reason REQUIREMENTS asks of a block it doesn't name. Alternative if this causes friction: allow a move while the action has no decision rows and no submissions.
- **Table versions a split suite's forms read** (agent decision; the user deferred the choice, and the agent's and a second opinion's recommendation): going live, and each later split edit, pins the version of every data table and the membership of every member list that the split or any of the suite's forms reads, directly or through named expressions, so a table only a form reads, such as a deadlines-by-state lookup, gets the same version for every member placed under the same pin, whenever their group is fixed. These are the versions REQUIREMENTS means by those a member's group was evaluated against. The save check for a form of a live split suite validates it against every table and list version its members use, those pinned at go-live and at each later split edit included, not only the latest, so a form can't start reading a column a pinned version lacks. Inputs set to "Refresh each time the form loads" keep their exception and read the current version on each load. Alternative if pinning keeps stale lookup data too long: capture form-only tables at the version current when the member's group is fixed.
- **Cutoff for members still pending** (agent decision; the user deferred the choice, and the agent's and a second opinion's recommendation): the suite's cutoff is the earliest member-action deadline among actions required in any group; when none of them has one, the earliest among actions optional in any group; otherwise the suite has no cutoff. Actions assigned to no group don't count. The REQUIREMENTS exclusion of members still pending happens at the cutoff, as do, for a member in "couldn't decide", the exclusion from the whole suite, the no-miss rule and alert escalation, and the earlier-action deadline warning compares against it. Without a cutoff nobody is excluded; saving the split or a suite form and "Begin launch process" show a type-to-confirm warning that pending members may wait indefinitely; and members in "couldn't decide" stay listed, keep retrying until a success places them, get no missed obligation and escalate after a set time instead of at a deadline. A cutoff from an optional action's deadline still excludes a pending member from the whole suite, later and deadline-free work included, so the earlier-action deadline warning says so. As REQUIREMENTS says, the exclusion doesn't wait for readiness. Alternative if early optional deadlines exclude members too often: block saving a split that waits on earlier actions while no assigned action has a deadline.
- **Default cell for a new action column**: "Not assigned"; a forgotten group is caught by the no-required-work tick.
- **Removing or renaming an input** (agent decision; the user deferred how): inputs have stable ids, so a rename is a label change. CI re-runs the save check over every stored expression of draft and scheduled suites and of current form versions against the declarations generated from the changed input list and functions, and fails the build on a break, so a removed, retyped or newly nullable input can't leave a split that fails at go-live or form rules that raise evaluation errors. Live and finished splits keep their pinned versions and aren't checked. An input change follows expand-migrate-contract (root `AGENTS.md`, "Breaking changes"). This replaces a CI test listing an input's users, which caught removals but not retyping. Alternative if the re-check proves too slow for CI: run it as a pre-deploy job.

## Interpretations and assumptions

- **Fill session** (agent decision): one server row per member per form attempt, kept alongside the draft. It holds the pinned input values, the earlier responses read, the server-computed values, and a record per load, each load naming the form version and the versions of the named expressions it used. A named-expression edit reaches a member like a new form version, on the next load and never while the member is looking at the form, since only the inputs are frozen; within a load, rules and the submission re-check use the expression versions that load recorded. A submission closes its session, so the next open of a follow-up form, which takes several responses, starts a new one. A `member_action` event marks a suite scheduled; a fill session pins a form's inputs. Neither is a separate "publish" state.
- **Split edits after the `member_action` event** (agent decision, within the requirement that a live split stays editable behind a warning): between saving the `member_action` event and go-live, an edit runs the same launch checks the event did: one failing a blocking check is refused, and one adding a warning-level failure needs a new type-to-confirm, so no suite reaches go-live with a split that skipped them. Braze locks the path order after launch (EVIDENCE.md, "How do audience-targeting products split an audience into groups?"); the user's requirement departs from that, while placed members staying put matches Braze keeping users in their group.
- **Which saves stay blocked** (agent decision, from the requirement that admins may do almost anything with warnings): REQUIREMENTS lists every block apart from the live-split action move, chosen above on a question the user deferred. They share one line: a static problem that means the saved rule couldn't be evaluated blocks, since a warning can't make it run, while a runtime problem, such as "couldn't decide" members in the preview, is a type-to-confirm warning.
- **One validation contract for splits** (agent decision): the expression core (1), the split editor (6) and the launch checks (7) run the same check for undecided group conditions and same-suite reads, so a split can't pass one and fail another. It follows named expressions transitively, so a group condition reading a named expression that reads a same-suite action or a value that can be `null` fails it, and it runs again when a named expression the split reads is saved and when suite membership changes, since adding an action to the suite can turn an existing read into a same-suite read. A group's own fallback satisfies the undecided requirement for that group, so the group condition needs no inline `??`. The preview over a configuration failing the contract, such as an unsaved edit in the split editor, shows "incomplete configuration" instead of counts, and never routes members whose result is undecided to "Everyone else".
- **Early-moved members at the deadline** (agent decision): a required task whose form is still waiting on an earlier action at its deadline gets no missed obligation, as a member still undecided because of an error gets none, since the member couldn't complete it. The copy for the waiting state is set in the staff-moves issue's PR.
- **Inputs captured at group fix** (agent decision for earlier answers, from EVIDENCE.md, "How do products handle changes to an answer that later steps depend on?" and "Earlier answers that later forms and groups read"; user requirement for settings and other inputs): a173's group and all four of its page conditions read the same earlier answers, so pinning at form open could show a required action with no pages. Capturing once per member when the group is fixed keeps group and content consistent for every form in the suite, including ones opened later. The user chose to have the group wait for every earlier action the suite's forms read, so form sources act as derived prerequisites and assignment can come later than the split alone would need; in exchange the capture is complete when the group is fixed, except for a pending member staff move early, whose capture completes as each source settles. The user then chose to capture settings and every other outside-form input at the same moment, so a setting changed mid-suite can't make two forms of one suite disagree; the change reaches the next suite, as the settings page says. Pinning at form open remains the rule outside split suites.
- **Form versions in a live split suite** (agent decision, within the user requirement that blocks such a version): the set of earlier actions the wait covers is taken from the forms published when the suite goes live, alongside the split's pinned versions; an edit to the split after go-live adds the earlier actions its conditions read for members decided after it, and those members' forms read the data-table and list versions that edit pinned, so their group and forms still read the same versions. The block exists because members already decided have no capture of a new input. Earlier answers can't be set to refresh in a split suite, so the refresh exception covers settings and other non-answer inputs only.
- **Outside inputs in visibility, against HL7 SDC** (agent judgement on a user requirement; EVIDENCE.md, the SDC entry under "How do form products handle definitions and inputs that change while someone is filling a form in?"): SDC says outside context SHOULD feed only initial and calculated values, with visibility driven off answers, even hidden ones populated once, so validation sees what the filler saw. A frozen input follows that pattern: the fill session holds its value like a hidden answer populated once. A refreshed input departs from it, because the user required "Refresh each time the form loads" for inputs that must stay current; the departure is narrowed by re-reading only on open and reload and by recording the table and list versions each load used, so a submission can be checked against what that load read.
- **Dynamic-page inputs in split suites** (agent decision): the requirement that a split suite captures every non-refreshed outside-form input at group fix outranks the later pin-on-page-open hook, so in a split suite only a refreshed input used only by a dynamic page is pinned when that page opens. A balancing count such as "times each page has been given out" therefore needs "Refresh each time the form loads" in a split suite, which is the use the user named for refresh there.
- **Writing decision rows** (agent decision): keeping `action_cohort_decision` and its readers reuses the freezing that already works and fits the old-suites-stay requirement. Readers switch from `action.optional` to the per-row field only for split suites. Old suites keep the action flag behind `BACKCOMPAT(split-row-optional)` until no unconverted suite remains.
- **Old cohort expressions** (agent decision): stay readable through the current resolver for existing suites only. New suites can't create them. That is the ratchet the breaking-changes rule asks for.
- **Same-suite reads** (agent decision for group conditions; user requirement for forms): blocking them follows from groups being decided before the suite's own actions are answered. Suite 32 does this today and stays on the old path (EVIDENCE.md, "Suite partitions"). A split-suite form reading a same-suite action would either hold the member's group until that action settles, which it can't before the member has the suite's tasks, or read an answer the capture can't hold, so the user chose to block it on save as group conditions are. The block covers new versions of a live suite's forms too.
- **Ordered groups rather than exclusive groups with overlap rejected** (agent decision, user-approved): EVIDENCE.md, "How do audience-targeting products split an audience into groups?", found ordered first-match with a locked catch-all to be the common practice. The empty and covered-group warnings, the preview counts and the fallbacks catch the mistakes rejecting overlaps would catch.
- **Restricted TypeScript over CEL** (agent decision, user-approved): `tsc` caught a misspelled field and an unhandled missing answer at save, where the CEL checker accepted both. AI models are expected to write TypeScript more reliably, since it is far more common than CEL (agent judgement; no source in EVIDENCE.md compares the two), and editor tooling comes free (EVIDENCE.md, "Which expression languages suit embedded admin rules, and how mature are their JS implementations?" and "Expression-language lab"). Storing the tree lets the checker be replaced later without migrating saved rules.
- **Three-valued unknowns** (agent decision, user-approved): plain TypeScript makes `null !== "CA"` true, so a forced `??` on split groups would never fire for negated conditions. Three-valued rules let unknowns reach the fallback (EVIDENCE.md, "How do rule engines and standards separate evaluation errors from unknown or missing values?" and "Errors versus unknowns today").
- **Checking three-valued conditions** (agent decision): `tsc` types `===`, `!==`, `&&`, `||` and `!` as plain `boolean`, so it can't see that a comparison with an unknown is undecided, and it rejects the required `(state === "CA") ?? false` as unreachable (EVIDENCE.md, "Expression-language lab"). The save check is therefore `tsc` plus a pass over the stored tree, as the builder-first prototype already paired `tsc` with custom checks (EVIDENCE.md, "Prototypes"). The pass marks each part that could be undecided (a comparison reading a value that can be `null`, and AND/OR/NOT over such a part by the three-valued rules), requires the `??` wherever the requirements do, and suppresses TS2869 on those `??`. It follows named expressions into their definitions, and covers ternary tests, list predicates (such as the callback of `some` or `filter`) and template values, not only top-level conditions. Under three-valued rules `x === null` is itself undecided when `x` is unknown, which is why "is unknown" has its own syntax, `isUnknown(x)`, with the rules REQUIREMENTS gives. The text keeps TypeScript's operators, and the interpreter evaluates comparisons and AND/OR/NOT by the three-valued rules, not JavaScript's. Function forms such as `is(state, "CA")` returning `boolean | null` would let stock `tsc` see the `null`, but `!`, `&&` and `||` would need function forms too, which makes text conditions harder to read. Drop the pass for function forms if it proves harder to keep correct.
- **Relational, arithmetic and method reads on an unknown** (agent decision, following the user requirements that a type error other than the required fallback's TS2869 blocks the save and that `tsc` runs with `strict`): under `strict`, `tsc` rejects `count > 5`, `count + 1` and `tags.includes("x")` on a value that can be `null` with TS18047, and those errors block, so such a read needs an `isUnknown` guard, or a guarded intermediate named expression, before it. Only `===` and `!==` can read an unknown unguarded, so "undecided" comes from them and from AND/OR/NOT over them. The builder's relational and list rows on an input that can be unknown print as `isUnknown(count) ? null : count > 5`, which `tsc` accepts and which stays undecided for an unknown, so the row still needs its fallback as REQUIREMENTS' comparison rule asks (EVIDENCE.md, "Expression-language lab"). Alternative if the printed guard reads badly: let the analysis, not `tsc`, judge nullable comparison operands, suppressing TS18047 and TS18048 there as it does TS2869, which needs the user's approval since it widens the exception they set.
- **Errors poison the whole condition** (agent decision, user-approved): this departs from CEL, where a decided half absorbs an error, so broken data shows up in the launch preview for every member rather than only some.
