## Authoring model

- Engineers define building blocks in code: inputs, functions, form components. Admins compose them. A new building block, once added, works in every consumer. (approved (agent))
- Admins may do almost anything, with a warning that says what the action will break, and type-to-confirm for very important actions. A blocked save shows an error saying why. Every block this file names is required; any other block is an exception that needs its own stated reason. (user)
- Forms stay typed schemas stored in the database and rendered natively on web and mobile, with sanitized rich text and engineer-written components for new interactions. Forms are not raw HTML. (approved (agent))
- Lookup data that formulas use today as large inline maps (deadlines by state, paragraphs by sector, company lists) lives in versioned data tables that admins edit like a spreadsheet and expressions look up by key. (approved (agent))

## Expression language

- One language for variables, visibility, required-if and suite split conditions: a restricted TypeScript expression subset: TypeScript syntax with three-valued semantics. The save check combines `tsc`, against declarations generated from the shared input list, with an analysis of the stored tree that requires a fallback wherever a result could be undecided; the analysis, not `tsc`, decides where a fallback belongs, so `tsc` objecting to a fallback the analysis requires (TS2869, since `tsc` types comparisons as plain yes/no) doesn't fail the check. A condition is an expression whose result is a yes/no value; a variable is a named expression of any declared type. Expressions can reference other named expressions. (approved (agent research); TypeScript syntax with three-valued semantics, and the save check's analysis: user)
- What is stored is a typed JSON tree, not the source text. One interpreter runs that tree on the server, web and mobile. The visual builder edits the same tree. The text shown to admins is printed from the tree in a canonical layout. Each expression has an optional Notes field for explanations. (approved (agent research, prototype))
- No sandboxing, metering or runtime limits beyond never using `eval`. Admins are trusted staff. (user)
- Conditions are edited in an All/Any builder that picks from the shared input list; formulas are edited as text; every condition can also be opened as text. (approved (agent)) A type error from the server check blocks the save, with the error shown at the offending expression; the TS2869 that a required fallback triggers is the exception, as the language entry says. (user)
- Reading a field that is not on an input's record is an evaluation error. Inputs always carry every declared field, `null` when missing. (approved (prototype))
- Saving a named expression that would break an expression depending on it is blocked, and the error lists each broken dependent with its reason. (approved (prototype)) Its dependents include, directly or through other named expressions, the split of every draft or scheduled suite that uses it and every form's rules. The save is blocked when it would leave such a split with a group that could be undecided and has no fallback, a group condition reading an action in its own suite, or a cycle across suites, or would break a form's rules, including a form of a live suite starting to read an input its group-fix capture doesn't hold. The error names each broken dependent (the suite and group, or the form) and the reason. Splits of live and finished suites are not checked, since they keep their pinned versions (below). The admin may instead save the expression together with fixed dependents in one save. (user)
- Deleting a data table or member list, or changing its shape (schema or columns), is blocked the same way when it would break, directly or through named expressions, any form's rules or the split of a draft or scheduled suite: the error names each broken dependent (the suite and group, or the form) and the reason, and the admin may instead make the change together with fixed dependents in one save. (user)
- A text template part whose value could be missing is rejected unless the author supplies a fallback (`?? "…"`); the error says what members would otherwise see. (approved (prototype))
- The shared input list has no tag input. (approved (agent))

## Unknown values and errors

- Unknown (a fact with no value: no answer, no setting) is `null`. Comparisons with an unknown give "undecided", and AND/OR/NOT follow SQL's three-valued rules: a known false still decides an All, a known true still decides an Any. (approved (agent research))
- Negative comparisons ("is not", "is none of") never treat an unknown as a match; including unknowns takes an explicit "is unknown" / "no answer" condition. (approved (prototype))
- "Is unknown" is written `isUnknown(x)` and is always true or false, never undecided. The declarations generated for `tsc` declare it as a type guard, `isUnknown(x: unknown): x is null | undefined`, so it also narrows the reads `tsc` types as possibly `undefined`, and the stored-tree analysis treats it the same way. `tsc` runs with `strict` and `noUncheckedIndexedAccess`. A generated built-in function parameter that accepts a missing value accepts both `null` and `undefined`. The same rule covers index reads, `.find`, `.findLast`, `.at`, optional chaining and a computed read repeated after its guard; where `tsc`'s narrowing doesn't carry over to the repeated read, the admin names the read as an intermediate named expression and guards that. The builder's "is unknown" / "no answer" row prints as `isUnknown(…)`. For a previous-answer input it is true both when the latest valid response left the question blank and when there is no valid response; telling those apart takes a separate input, such as "has responded". Pending and errors stay outside it. Each input defines what counts as blank; `0` and `false` are answers, for example. The save check rejects `=== null`, `!== null`, `== null`, `!= null`, `null` on either side of any other comparison, and an authored `undefined`, with an error suggesting `isUnknown`. An authored `undefined` stays banned: at runtime a missing lookup or index gives `null`, never `undefined`. (user)
- Every consumer of a yes/no value handles "undecided" explicitly: a suite split group through its fallback (below); visibility and required-if through a `??` the save check requires whenever the condition could be undecided. (user)
- Error (a failed read, an evaluation error) and pending (waiting on an earlier action) are separate from unknown, sit outside the language, and are never treated as unknown. An error anywhere in a condition makes the whole condition an error, even where the other side would have decided it. (approved (agent research))

## Previous answers

- "Previous answer" means the member's latest valid submitted response to that form, then the question read from it. If the question is blank in that response, older responses are not searched. "Ever answered X" and "full history" are separate named inputs. (approved (agent research))
- A valid response is submitted and is not one of the partial answers saved on withdrawal. "Latest" orders by submit time, then id. A session that already pinned a value keeps it if the source response is later deleted. (approved (agent judge))
- Partial answers saved on withdrawal are for admin viewing and analysis only; no logic in the new system reads them. The old system's readers, the cohort `FormFieldValue` leaf, visibility's previous-answer conditions (`sourceFormId`) and variables' `sourceField` and `sourceList` inputs, keep reading them as they do today. (user)
- Normal actions keep allowing one submission per member; follow-up forms keep allowing several. (user)
- Submitted responses to normal actions stay read-only for members; this work adds no answer editor. (approved (agent research))
- The server refuses a withdrawal from an action the member has already submitted, matching the app, which hides withdrawal once a form is submitted. Today `POST /tasks/optout/:id` accepts it. This is one of the project's issues. (user)

## Where rules run

- Admins never choose where a rule runs. Anything saved or access-controlling (group assignment, submit validation) is decided on the server. Visibility, variables and options run on the device when every input and literal they read may be shown to that member and the member's app supports every operation used; otherwise the server sends the computed value with the form, or recomputes it when answers it depends on change. Every submission is re-checked on the server. The editor shows the consequence ("Checked again on submit"), not a setting. A rule mixing a device-side input with a server-side one combines the server's computed value on the device. (approved (agent research))
- Each kind of form (member task, follow-up, public guest, onboarding) declares which inputs exist for it. Saving rejects a condition that uses an input the form's kind cannot have, for example the US setting on a public guest form. (approved (agent judge))

## Freezing what a member sees

- Once a member sees a form, its inputs stay fixed, except that anything derived from the member's own answers in that form reacts live: visibility reacting to an earlier answer in the same form, and which dynamic pages and content they get. A settings change, a staff action, or another member's activity does not reshape a form the member has open. (user)
- A fill session is created on the server when the member opens the form, before questions show. It pins every input that is not one of that form's answers; in a split suite it takes those values from the capture made when the member's group was fixed (below). Reopening, retrying or switching devices reuses it. (approved (agent research))
- A fill session pins the version of each data table and the membership of each member list it reads, not only the values looked up, so a changed answer looks up a different key in the same table version. An input set to "Refresh each time the form loads" records the versions each load used. In a split suite, a member's forms use the versions the member's group was evaluated against: those the split pinned at go-live, or at its latest edit before the group was fixed. A version still used by an open fill session or a live split is kept, even after the table or list is changed or deleted. (user)
- A fill session never expires, not even at the deadline, because some actions accept completion after it. Whether a submission is accepted is decided by the submission rules below. (user)
- Admins choose, per input a form reads, between frozen (default) and "Refresh each time the form loads". A refreshed input is re-read on open and reload, never while the member is looking at the form. Live updates while viewing may be added later; there is no websocket path for form content today. Named expressions built from a refreshed input recompute from it plus current answers. The setting is per form and input, shared by every expression in that form that reads the input. (user)
- Refreshed values may be used anywhere, including visibility; the editor warns "Questions may change between loads". (approved (agent))
- Each load gets a server-side id and records the values it used. A submission is checked against the exact load it came from, and a repeated submission does not create a second response. (approved (agent judge))
- When the source of a frozen input changes, a form the member has open is not updated and shows no notice of the change. In a split suite, the change reaches the forms of the member's next suite, not later forms of the current one. Outside split suites, it reaches the next form the member opens. (user)
- In a split suite, every input the suite's forms read from outside the form, earlier answers and settings included, is captured when the member's group is fixed, and every form in the suite reads that capture, so the forms agree with the member's group and with each other. The group waits for every earlier action any form in the suite reads, and a form can't read an action in its own suite (below), so the capture is complete when the group is fixed, except for a pending member a staff move placed early: their capture completes as each source settles (below). Settings are never pending, so capturing them adds no wait. An input the admin set to "Refresh each time the form loads" is left out of the capture and re-read on each load, as anywhere else; earlier answers cannot be set to refresh in a split suite. (approved (agent research); the wait for forms' reads, capturing settings and other inputs with earlier answers, and captures completing late after an early move: user)
- Members always get the latest published form version, so copy fixes reach everyone; only the inputs are frozen. (user) A new version replaces the old one on the next load, never while the member is looking at the form. Draft answers that still fit are kept, and the rest are cleared; when any answer was cleared, the form shows "This form was updated. Please check your answers." (approved (agent)) Outside a split suite, an input a newer version reads that the member's fill session hasn't pinned is pinned at the first load that reads it, since that version didn't exist when the session opened, and the session records it, as a refreshed input's load records its versions. (approved (agent))
- An older fill session or a changed input is never a reason to refuse a submission. Beyond the server's re-check of the answers and evaluation errors, a submission is refused only for the reasons that block completion today (`computeCompletionBlock`): the action has "prevent completion" set; the member is not in the action's group; the deadline has passed and the action does not allow completion after it; or, for onboarding actions, the contract is unsigned. A normal action, which allows one submission, also refuses a second one as today (`assertActionNotSubmitted`); a repeat of a submission already accepted from the same load is not refused and creates no second response (above). The rejection names the reason. In a split suite, a member's group changes only through a staff move. (approved (agent))
- The session is stored with the response so any submission can be explained later, and discarded with the draft if the member never submits. (approved (agent research))
- Opening a form needs a connection, and a dropped connection doesn't lose the open form. There is no offline mode, and this work adds none. As today, the form stays open while the connection is down, device-side rules keep reacting to answers, draft saves fail visibly, and submit fails until the connection returns. When something mid-form needs the server while the connection is down, such as a server-computed rule reacting to a new answer, or later a dynamic page being chosen as it opens, the form shows the existing "Try again" state at that point until the connection returns. (user)
- When the app cannot show a form (an unknown field type, input or function), it shows the existing message, the title "This form can't be displayed" over the body "Restarting the app or downloading the latest version may fix the issue." (`apps/mobile/components/forms/FormElements.tsx`). (user)
- When an input fails to load while a member fills a form, the form is blocked with a "Try again" banner. Visibility and variables never show default or blank values in place of an error. A visibility check that errors at submit rejects the whole submission. (approved (agent research))
- Draft syncing between two devices stays as it is today. (approved (agent))

## Suite splits

- A suite has one ordered split. Each member lands in the first group whose condition they match; the last group is a locked "Everyone else". (approved (agent research))
- Every action in a suite sits in the split; there are no overlay actions. The admin edits a grid of groups × actions; each cell is required, optional or not assigned. One action can be required for one group and optional for another, replacing duplicated "Optionally …" actions. (user proposed the all-in-split model; approved (agent research) for the grid and per-group cells)
- Each action has one form; actions with the same title but different forms stay separate columns. (approved (agent research))
- Combined groups (for example "A and B", "A only", "B only", "Everyone else") are written by hand from conditions defined once by name; there is no generator. (approved (agent research))
- A member list is one input, "is on list X", usable as a group's condition or inside other conditions; staff-picked lists are how hand-picked inclusions and exclusions are expressed. (approved (agent research, prototype, agent judge))
- A group whose condition could be undecided for some member carries a fallback, so the group matches when `groupCondition ?? fallback` is true; the admin picks the fallback: "put them here" (true) or "continue to the next group" (false). It applies only when the condition's whole result is undecided. It is required whenever a condition could be undecided, even if nobody is undecided today. (user, approved (prototype)) Every save of the split, draft or not, is blocked while such a group has no fallback picked, with an error naming the group. (user)
- A group condition that reads an action in the same suite is blocked on save, with an error naming the action. (approved (agent research, agent judge)) This blocks every save of the split, draft or not. (user) Saving a form in a split suite that reads an action in the same suite is blocked the same way, with an error naming the action, so nothing a form reads is missing from the capture. (user) A cycle across suites is rejected on save. (approved (agent research, agent judge)) For split suites, blocking same-suite group reads replaces sequencing inside one suite (A, then B1 or B2 by a condition on A), which `01a0fa28-8f25-7000-bdc8-a32ec135a380-prerequisite-equal-deadline` supports; such a sequence takes two suites. (approved (agent), a consequence of the blocks above)
- A member's group is fixed once per suite, where today's cohort decisions are made once per action: at go-live for members with nothing to wait for; once every earlier action that the split's conditions or any form in the suite read has settled for that member, who shows as pending, with no tasks for the suite, until then, or until the deadline exclusion below; and for a late joiner, once, when they join, with today's after-deadline treatment. A staff move can place a pending member sooner (below). An earlier action counts as settled for a member it excluded, as today. There is no separate prerequisite list; the wait comes from what the split and the suite's forms read, so an earlier action read only by a form still delays the member's group. For split suites, this replaces the explicitly configured prerequisites of `01a0d612-1fe1-7000-b1ea-5ac27d9ad6dd-stable-action-assignments`, and with them the equal-deadline prerequisites of `01a0fa28-8f25-7000-bdc8-a32ec135a380-prerequisite-equal-deadline`. A fixed group doesn't change when answers, settings or lists change later. (approved (agent research); the wait for forms' reads, and exclusion counting as settled: user)
- When the split's conditions or the suite's forms wait on an earlier action that has no member-action deadline, or whose deadline is on or after the earliest deadline of any action required in any group of the suite (an equal deadline included), saving the split or the form shows a warning naming each such action, which the admin passes with type-to-confirm; it doesn't block the save. An earlier action with no deadline gets its own warning, saying members may wait for it indefinitely. "Begin launch process" checks these again, and so does a change to a scheduled suite's dependencies or schedule. Whatever the warnings: at the earliest deadline of any action required in any group of the suite, members still pending for the suite, and members still in "couldn't decide" (below), are recorded as excluded from the whole suite, every action in it included, with no missed obligation, and for pending members the suite page names the earlier action or actions they were waiting on. This exclusion doesn't itself wait for those actions to settle, unlike today's after-deadline decision, which first keeps only members whose prerequisites are ready (`server/src/actions/cohort-decision.service.ts:278`). Late completion of tasks already assigned (`shouldCompleteAfterDeadline`) is unaffected, and whether an earlier action has settled is still judged by its own nominal deadline. (user)
- An earlier action completed late, after the member's group was fixed, does not change their group, even if the answer would now match a different group. The member can ask staff to move them. (approved (agent))
- In a split suite, a member can complete only the actions in their group's row. Today's rule that lets a member complete an unassigned action whose cohort they currently match, which `01a0d612-1fe1-7000-b1ea-5ac27d9ad6dd-stable-action-assignments` keeps, does not apply to split suites. (approved (agent))
- Groups may have required work, only optional work, or nothing. Any group without required work, including "Everyone else" and groups empty today, gets a tick, "This group intentionally has no required work"; saving a draft only warns, and launching with a group lacking the tick is a warning with type-to-confirm. The tick clears when the group's kind of work changes (required / optional only / nothing assigned). (approved (agent research, prototype); a warning rather than a blocker: user)
- Saving warns about groups that match nobody today and groups that earlier groups provably cover, found with an "empty today" count plus a simple structural check across named conditions; there is no general logical solver. (approved (agent research))
- The preview counts the suite's whole eligible population, split into required work, optional work only, nothing assigned, pending, and couldn't decide. It explains streak consequences: a member with only optional work neither gains a missed suite nor resets their streak, as today. (approved (agent research))
- Reminders keep today's behaviour for group-optional work: each reminder group's "include optional actions" setting decides, and late signers stay excluded through contract rules. Launch review shows the consequence. (approved (agent research))
- When the suite goes live (the `member_action` event's time), the exact versions of everything its split reads are pinned: named expressions, data tables, member list membership. Members decided later are evaluated against those versions with their own current facts, until an edit after go-live pins the versions current at that edit. (approved (agent)) Only an edit to the split itself re-pins; editing a named expression never re-pins a live split. At go-live the split's whole rule bundle is validated and pinned in one atomic step; saving the `member_action` event, which schedules the suite, is not go-live. (user)
- A member's resolved group writes the existing per-action decision rows (`action_cohort_decision`), one per action, from that group's grid row, plus a per-row required/optional field that readers use for these rows instead of the action-wide optional flag; rows written for existing suites keep the action flag, since those suites stay on the current code. The group and the evaluation trace are stored alongside. Existing readers (reminders, streaks, pills, assignment) keep reading those rows. (user)
- The trace stored when a group is fixed records each group tried, the facts read, the outcome, and any staff move. (approved (agent research))

## Launch and changes after launch

- Launch keeps the existing behaviour, and the split adapts if that behaviour changes. Today there is no stored launch flag: "Begin launch process" shows while the suite has no `member_action` or `office_action` event, completing it creates the `member_action` event (which may be in the future), and the suite's event list can also add that event directly. (user)
- Missing fallbacks and same-suite group reads are save blocks (above), not live warnings; the split editor shows the no-required-work tick as a live warning. "Begin launch process" checks the save blocks again, since a change outside the split's own save, such as an action joining the suite, can make a split saved clean fail them, and blocks launch with an error saying why; groups lacking the no-required-work tick, "couldn't decide" members in the preview and the earlier-action deadline warnings (above) are warnings the admin passes with type-to-confirm. The server refuses to save a `member_action` event, from any path, for a suite that fails a blocking check, or that fails a warning-level check without a recorded type-to-confirm override. (approved (agent); which checks block and which warn, and blocking missing fallbacks and same-suite reads on every save: user)
- While a suite is scheduled (its `member_action` event is saved and go-live hasn't come), the server blocks, beyond the save blocks above, which apply in every state, the changes that would leave its split unable to run: an action moving into or out of the suite where that creates a same-suite read or a cycle, through a group condition or a form. Deleting or reshaping a data table or member list the split reads is blocked as for any suite (above). The error names the suite and the reason, and the admin can make the change together with its fix in one save. Other changes, such as a table's rows, a list's membership and date changes, are allowed, with the warnings existing rules give. (user)
- If validation at go-live still fails, which only a bug allows, the whole suite does not go live, not just the affected groups, since groups are first-match: nothing is pinned, no decision rows are written, the failure is reported to PostHog, and the suite page shows "Launch failed" with the reason. Members get no tasks and no missed obligations for the suite, and the fallback that shows an undecided action by live cohort eligibility (`server/src/actions/member-actions.service.ts`) does not apply to it. Staff recover by fixing the split and running "Begin launch process" again with a new go-live time, so nothing becomes overdue or triggers reminders that have already expired. (user) Today "Begin launch process" hides once a `member_action` event exists; it must also show in the "Launch failed" state, and completing it there moves the existing `member_action` event to the new go-live time instead of adding a second one, so reminders and deadlines follow the new time. (approved (agent))
- After go-live, the split and its grid can still be edited, behind a warning with type-to-confirm that shows how many members are already placed. The edit applies to members decided after it; already-placed members don't change unless staff move them. An edit that would fail a blocking check stays blocked. (user)
- After go-live, saving a new version of one of the suite's forms that reads an input the group-fix capture doesn't hold is blocked, with an error naming the input, unless the input is set to "Refresh each time the form loads". (user)
- After launch, staff can move a member between existing groups, including a member who is still pending, which fixes their group early. Each move requires a free-text reason stored in the audit record. (approved (agent research))
- A move of a pending member places them and gives them the group's tasks immediately, creating their decision rows, which today's staff correction requires to exist already. Each answer the suite's forms read that is still pending is captured when its action settles; until then, a form reading it shows that it is waiting on an earlier action. Before a move that would break something, such as resetting progress, blocking a submission, or leaving forms waiting, the move shows a warning saying so. (user)
- A move resets the member's progress and blocks their earlier submission, or does whatever is easier in the code; admins only move members after telling them or at their request. (user)

## Runtime errors in splits

- A member whose group evaluation errors gets a visible "couldn't decide" state: no fallback, never placed in "Everyone else", recorded in the trace. Temporary failures retry with backoff from 5 minutes up to 1 hour; repeating errors retry daily and on demand. Each new error is reported to PostHog. The suite page lists these members with "Retry now" and "Move member". (approved (agent research))
- A member still in "couldn't decide" at the earliest deadline of any action required in any group of the suite is excluded from the whole suite with no missed obligation, as members still pending are (above), and the alert escalates. Retries after that point only update the trace; a later successful evaluation never places the member. Where the suite has no such deadline, members in "couldn't decide" keep retrying, and a successful retry places them. (approved (agent research); exclusion at the deadline and retries after it never placing the member: user)
- The launch preview shows "couldn't decide" counts next to the group counts. Launching with "couldn't decide" members is a warning with type-to-confirm; those members stay visibly unresolved, with the retries, exclusion and no-missed-obligation handling above. (approved (agent research); a warning rather than a blocker: user)

## Project assignment settings

- A "Project assignment" settings section chooses which projects get assigned to the member, and its wording makes that purpose clear. It holds a list of settings so more can be added later. (user)
- It has one setting now, a US / non-US choice that decides whether the member gets US or non-US projects; it might be a radio such as "I am based in the United States: ( ) Yes ( ) No". Assignment never reads location, in the old system included: from the day this setting ships, the old system's `USMember` and `NonUSMember` cohort rules, which existing suites keep using, read this setting instead of the member's location; this setting changes nothing else in the old code. This supersedes the location-based country predicates of `01a0d612-1fe1-7000-b1ea-5ac27d9ad6dd-stable-action-assignments`; their Boolean meaning stays.
