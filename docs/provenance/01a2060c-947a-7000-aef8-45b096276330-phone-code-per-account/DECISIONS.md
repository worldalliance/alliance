# Decisions

- **The owner is a nullable `userId` on `otp_challenge`, with a foreign key to `user` that cascades on delete.** `OtpService.start` takes a `requester` (`{ userId, holdsContact }`, or null for KORA sign-in) and scopes the resend wait and the replace-on-new-code delete to `(purpose, destination, userId)`. `verify` and `pending` take the `userId` and only find a challenge it owns, so a code sent to another account is refused as `CodeInvalid`, the same as an unknown token, and still counts against the per-IP verify limit. The index on `(purpose, destination)` becomes `(purpose, destination, userId)`, which still serves KORA's queries. (agent decision)
- **Codes pending at deploy fail rather than being honoured for one TTL.** A challenge written before the column existed has a null owner, so the requirement that codes pending at deploy stop working falls out of the owner check with no `BACKCOMPAT` branch. Between the migration and the server restart the old server writes null owners and queries by `(purpose, destination)`, which the new index covers. (agent decision)
- **Phone verification's per-number bucket is keyed with its purpose, `["send-contact", purpose, destination]`, and KORA keeps `["send-contact", destination]`.** KORA's rate events carry over unchanged, and the two purposes no longer draw on one bucket. The per-number limits reuse `SEND_LIMITS_PER_CONTACT` (5 an hour, 20 a day) and the new per-account limits are `SEND_LIMITS_PER_ACCOUNT`, included in `LONGEST_RATE_WINDOW_MS` so the hourly purge keeps their events for a day. (agent decision)
- **"The account that already holds the number" means the only live account whose `phoneNumber` equals it, verified or not.** Until the unique index on `phoneNumber` lands (ALL-2259), the `BACKCOMPAT(phone-verification)` profile update lets any number of accounts save one number without a code; exempting each of them would let N accounts send a number N times its limit. So while two or more live accounts hold a number, none skips its per-number limit. On production data, where no number has two live holders (EVIDENCE.md, **Production phone numbers**), this matches "the account holding it"; the gaps a deliberate duplicate opens are the ones REQUIREMENTS.md accepts. Once the index lands the check matches the plain "account holding it". `PhoneVerificationService.start` reads the holders before calling `OtpService.start`, outside the bucket locks: a number moving between that read and the send changes only which limits count one send. (agent decision)
- **Concurrent requests for one account stay serialised by the per-account bucket lock**, which every signed-in request takes, so its check-wait, delete and insert cannot interleave. Test phones still skip every limit and lock, as before. (agent decision)
