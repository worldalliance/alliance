# Decisions

- The deploy-order rule goes in the root `AGENTS.md` **Breaking changes** section, beside the rule that each step starts once the previous one is live everywhere, since that is the rule agents applied with staging alone in mind, and it holds for every repository task.
- The rule points at `.github/actions/deploy-guard/live-commit.sh`, which prints the commit production runs, because the `production` branch can be ahead of it (when this task was written the branch tip `86ffb5c` was ahead of the newest `production-live` deployment `c67ebad`) and only a `production-live` deployment whose newest status is `success` counts, which an agent can't tell without reading the deploy scripts. Squash-merge commits, reverts, failed rollbacks and mobile builds are left to the agent; a review loop had grown them into a command recipe in `docs/deploying.md`, which was cut as too specific.
- A PR waiting on production says so in its description, since a person merges it from GitHub, where an agent's handoff isn't visible.
- Agents leave pushing `production` to the user, since it releases everything merged to `main`, and the rule says so even where a skill waives asking before git writes, as review-base's **Applying fixes** does.
- Every agent acts in Linear as the one `Alliance agent` OAuth app user, so the assignee can't tell agents apart; the claim is the `In Progress` state plus a comment naming the branch and session id. Subagents, handoffs, closed issues and which state to restore are left to the agent.
- The claim is best effort: Linear has no compare-and-swap, so two agents that read an issue at the same moment can both claim it.
- The handoff file names the Linear issue the task claims, so the continuing session knows it holds the claim.
- An agent that finds an issue already claimed asks the user rather than judging the claim stale by when its transcript last uploaded: uploads run only on hook events, retry in later sessions and can be disabled, so the upload time doesn't show whether a session is still working.
- Linear's agent-session API (delegate plus `agentSessionCreateOnIssue`), Linear's documented path for agents, was offered and not chosen; a comment is enough for this workflow.
- The rule goes in `agents/skills/review/SKILL.md` rather than `review-base`, since `review` holds the review criteria and also governs reviews outside the loop. Judging against `writing-for-agents` also makes derivable or duplicated text a finding, so reviews can shrink an agent doc as well as grow it, as the research in EVIDENCE.md favours; the section doesn't restate those rules.
- The fixer's new class is `judgement`, and the ledger rule against reviving dropped issues covers it, so a later round's finding on the same case stays settled unless new evidence shows the call was wrong. It answers the fixer behaviour in EVIDENCE.md's review-round incident.
