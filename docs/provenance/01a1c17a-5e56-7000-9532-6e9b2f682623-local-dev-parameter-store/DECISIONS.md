# Decisions

Each is an agent decision unless labelled.

- **The wrapper is a bash script running inline Python, like `scripts/secrets_run.sh`.** `os.execvp` replaces the process, so signals and exit codes reach the command; Python handles values with any character. It stays separate from `secrets_run.sh`, which is installed alone on hosts and has no fallback, manifest or login handling. Its Python stays compatible with 3.9, the macOS system version.
- **A committed manifest, `scripts/dev-secrets.json`, names each consumer's secrets.** Injected values outrank `.env`, so without it a key missing from the store would still come silently from `server/.env`. The wrapper fails on a missing key. A stored key the manifest doesn't list gets a warning and stays out of the command, which keeps a stray `DB_NAME` or other per-checkout key out too: the store is shared, so failing on it would break every checkout whose manifest predates a new key, and the drift check reports undeclared keys. A server test ties the list to the schema.
- **Wrapping lives in `server/package.json`,** so `bun run dev` from `server/` and the root `server:dev` both get it, inside `with-env.sh` for the root script. Only `dev` and `repl` are wrapped. The `migration:*` scripts stay unwrapped because the TypeORM CLI reads only `DB_*` and `NODE_ENV`, so they need no login; `start:prod` and CI's direct `bunx typeorm` calls stay unwrapped because hosts use `secrets_run.sh` and CI has its own values.
- **This task supersedes the secrets plan in `docs/provenance/01a1a949-c8f1-7000-9631-5610045dff02-alliance-agent-desktop-app/DECISIONS.md` (Secrets migration), which that directory still records.** That plan put the Linear and transcript-bucket keys in Infisical `dev`, read through `scripts/with-env.sh` with a `.env.devtools` fallback. Here the Linear skill runs its calls through `scripts/with-secrets.sh devtools`, which reads `/alliance/dev/devtools/`, and transcript uploads use each person's `alliance-dev` login, so the shared bucket keys are not stored anywhere new and go with the `alliance-agent-chats` IAM user.
- **The fallback flag bypasses the store entirely** and restores the old path: it prints each listed key the consumer's env file sets and the shell leaves unset, naming the file, and exports it unless the manifest marks the consumer `loadsEnvFile`, whose keys may also come from the files Bun loads beside its env file. The server's bun and dotenv load `server/.env` themselves, and exporting would replace their parse with the wrapper's shell-style one, which treats backslashes and `$` differently. Nothing loads `.env.devtools` on its own, so the wrapper exports its keys, read by bash's `source`, which the Linear skill used on that file before, so a command in it that fails doesn't stop the read but an error bash reports fails it; a parser of its own would have to match bash's quoting and expansion. For such a consumer it fails when a listed key is set to a value neither in the shell nor by sourcing the env file, an empty shell value counting as unset, as `source` overwrote it for the Linear skill (an empty one would reach Linear as `invalid_client`, and the store holds no empty value), bash answering both which keys are set and their values, since nothing downstream would name the missing key; the server's schema does that for it, and a key the schema leaves optional may be absent from an existing `server/.env`.
- **Deployed paths' required keys come from `validateServerEnv({ NODE_ENV })`,** reading the `: missing` lines, so the drift check uses the schema's own rules. Dev paths use the manifest. A name under `/alliance/` outside every expected path and the CI paths (`/alliance/ci/` and `/alliance/staging/ci/`, the ones `terraform/ci-oidc.tf` grants) fails the check, so a key under a misspelt path such as `/alliance/production/server/` isn't silently left unread. The AWS CLI's paginator follows `NextToken`.
- **The drift check runs on PRs that change the schemas, the manifest, the check or what they load (`result.ts`, the RDS CA bundle, `bun.lock` for zod), and on every push to `main`.** The store is shared state, so running it on every PR would turn unrelated PRs red after any store edit; a dependency PR, which changes `bun.lock`, still runs it and goes red between a store edit and the PR that matches it; a push to `main` still shows drift a store edit causes. A deployed path may hold only the keys `inDeployedStore` in `server/src/config/env.ts` marks, a `Record` over every server key so a new key needs a choice: never `NODE_ENV`, which `secrets_run.sh` refuses to override, committed config, or dev and test keys such as `ADMIN_USER`, which would seed an admin on staging. Removing a key runs the other way from adding one: make it optional in the schema, until `bun scripts/check-parameter-drift.ts --required` stops listing it, and stop reading it, then deploy; delete the parameter; then remove it from the schema. Nothing reruns the check after a store edit, so the workflow takes `workflow_dispatch` and the docs say to dispatch it on `main` after one. A dev path may hold only the keys `scripts/dev-secrets.json` lists, with no allowed-but-not-required stage, so removing a dev secret turns the workflow red from the removal PR until the parameter is deleted, as `docs/local-secrets.md` says; such a stage, a `retiring` list per consumer, is filed as ALL-2159, since dev removals are rare and the check blocks no merge.
- **The drift check has its own CI role, `alliance-ci-parameter-drift`,** with `ssm:DescribeParameters`, which can't be limited by path, so it sees every parameter's name and metadata, including who last changed it, never a value. Names are already in this repo, but who last changed each can name a person, and any workflow on any branch can assume the review role, including agent jobs that could print it to public logs. Its trust takes `main` and same-repo pull requests and pins `job_workflow_ref` to `parameter-drift.yaml`, so other jobs on those refs can't assume it; a pull request that edits that workflow or its script still can.
- **No global `unhandledRejection` handler for the SDK refresh failure** (see `EVIDENCE.md`, Measurements). The failure needs a login that has ended, exits loudly with the login command, and a handler would hide unrelated bugs.
- **The daily login's group is named `alliance-dev`,** per the root `AGENTS.md` rule that new things carry the `alliance` identifier, and matching the permission set assigned to it (agent proposal, accepted by the user; see `REQUIREMENTS.md`). Terraform declares no `aws_identitystore_group_membership`, since membership stays in the console, and the group's description says so where an admin adds people.
- **Taking standing staging and production access off the daily login is left out, filed as ALL-2106.** The user left open whether this work happens at all, so it is optional. A version with a separate `alliance-deployed-secrets` permission set, assigned per user in Terraform with an end time, was cut in review: members who hold `AdministratorAccess`, assigned outside Terraform, reach staging and production through the same login anyway, so it gave no boundary, and making it one would take that standing access away too. The `alliance-dev` permission set reaches no staging or production secrets, so a member without `AdministratorAccess` has no path to them.
- **Transcript uploads read the `alliance-dev` login through `aws configure export-credentials`,** per the requirement that they upload with each person's own login, which Identity Center now makes possible. This supersedes, in `docs/provenance/01a19e0b-aa3d-7000-8fcd-136f2b217cd7-agent-chat-archive/DECISIONS.md`, the Credentials entry (the `alliance-agent-chats` IAM user's keys in `.env.devtools`, and per-person identities rejected for want of Identity Center), the Failure handling entry's missing-keys message, which becomes one message per login failure, and the AWS CLI half of the Bun S3 client entry, since the login needs the CLI; that directory still records them. `ALLIANCE_SECRETS_ENV_FALLBACK=1` restores the IAM user's keys until the rollout ends (ALL-1964).
- **The upload spool is `~/.alliance-agent-chats/`,** in the home directory because worktrees get deleted, holding `requests/<uuid>.json` (a transcript's key and absolute path), the `wake` marker, the `lock` file, which is never deleted, the worker's output in `worker.log`, and `worker-error`. Request files are written to a temp name and renamed, so a reader never sees a partial one. A failed upload is recorded by rewriting the key's newest captured request the same way with an `error` field and deleting its other captured ones, rather than in a second file, so the requests are the only state and a key whose uploads keep failing holds one request, not one per hook; once published, only the lock holder rewrites or deletes them. A temp file an interrupted write left behind is deleted by the next pass once it is a minute old. Transcripts upload whole, so a pass uploads each key once, from its newest request's path, however many requests it has (see `EVIDENCE.md`, Persisting and retrying uploads). The design review's import of the earlier queue's files is left out, as the user directed: that queue never shipped.
- **The worker lock is `scripts/lib/worktree-lock.sh`'s mechanism, perl's `flock`,** since Node and Bun expose no file locking. A short perl prologue opens the lock file, takes the lock, clears close-on-exec and execs `chats.ts worker`, which holds the inherited descriptor until it closes it or dies (see `EVIDENCE.md`, Hook output and kernel locks). A worker that finds the lock held exits at once, leaving the wakeup marker to the holder. The holder loops while the marker reappears during a pass; after closing the descriptor it starts a successor if the marker is set, so a request published between its last check and the release still gets a pass. A marker it can't clear or check while holding the lock makes the current pass its last, and that failure goes to `worker-error` before the release; one in the check after the release goes to `worker.log` and starts a successor instead, since another worker may by then hold the lock and have recorded a newer state, and the successor records the failure under the lock if it lasts. `retry` and `discard` wait for the lock instead; `discard` drains nothing, so after releasing it starts a worker if the marker is set. The lock file is not checked for replacement, as `worktree-lock.sh` does, because nothing retires it, and two workers after someone deletes the directory are safe under conditional PUTs.
- **Credentials are looked up once per pass, in the worker,** so a hook does only local work. An expired login records its message in every captured request. Nothing watches for `aws sso login`: the next session start or upload hook in any session starts the worker, as the design review proposed.
- **Uploads use `@aws-sdk/client-s3`, which the server already depends on,** for HEAD, the conditional PUT and `fetch`'s GET, because `Bun.S3Client` takes no conditional headers. It is declared in the root `package.json`, where the scripts' and agents' other dependencies are, and imported only when `chats.ts` uploads or fetches. A conflict (412, 409, or 404 under `If-Match`) starts over from the HEAD, up to five times. A HEAD error response has no body, so when a HEAD fails with anything but 404 a one-byte ranged GET supplies S3's error code and message for the recorded cause, when it fails with the HEAD's status; a GET failing otherwise, such as with 416 on an empty object, is about something else, so the HEAD's own status stays. The client always names S3's regional endpoint, since without one the SDK follows `AWS_ENDPOINT_URL_S3`, `AWS_ENDPOINT_URL` and a profile's `endpoint_url`, which point at local stand-ins on some machines and would get the transcripts and their signed requests. It also turns off FIPS and dual-stack endpoints, since the SDK rejects every request that pairs an explicit endpoint with `AWS_USE_FIPS_ENDPOINT`, `AWS_USE_DUALSTACK_ENDPOINT` or a profile's `use_fips_endpoint` or `use_dualstack_endpoint`. Connections time out after 5 seconds and go idle for at most 30, so a connection gone silent, as after a laptop sleeps, fails the upload instead of hanging. The SDK uses only the credentials it is given, so the relaunch that kept an ambient session token away from the fallback's static keys under `Bun.S3Client` is gone; this supersedes, in `docs/provenance/01a19e0b-aa3d-7000-8fcd-136f2b217cd7-agent-chat-archive/DECISIONS.md`, the Ambient AWS settings entry, the rest of the Bun S3 client entry, and the Overlapping uploads entry, whose stale snapshot landing last the conditional PUT now prevents; that directory still records them (see `EVIDENCE.md`, S3 conditional writes). `ALLIANCE_AGENT_CHATS_S3_ENDPOINT` points it at a local fake in tests, and the client fails unless it names a loopback host, so the variable can't send transcripts elsewhere either. The client makes three attempts per request, the SDK's default, whatever `AWS_MAX_ATTEMPTS` or a profile's `max_attempts` says, so on a silent connection the timeouts bound a request at about 90 seconds and an upload, a HEAD and then a PUT, at about three minutes. The handler's idle timeout stops once a response's headers arrive, so the client also wraps every response body in its own idle timer of the same length; without it a body that stalls after its headers, as on a `fetch` or the GET after a failed HEAD, hangs forever with the lock held (see `EVIDENCE.md`, Response timeouts and proxies under Bun). It bounds idleness, not total time, because transcripts reach tens of megabytes and a total deadline would cut off a slow link.
- **Uploads go through `HTTPS_PROXY` with `https-proxy-agent`, and `NO_PROXY` is matched as the AWS CLI matches it,** set as the S3 handler's `httpsAgent`, so the connect and idle timeouts stay as they are. Every request goes to one fixed host, the bucket's virtual-hosted S3 name, so the proxy is chosen once per client against that name; `proxy-agent`'s per-request choice, PAC files and SOCKS would be unused code loaded into every worker. The client looks for a proxy only when `HTTPS_PROXY` (or `https_proxy`) is set, the variables the AWS CLI documents, and ignores `ALL_PROXY`, which is often a SOCKS URL that `https-proxy-agent` can't speak. A value without a scheme, such as `proxy.corp:3128`, gets `http://`, as the AWS CLI gives it. A value with another scheme, such as `socks5://`, fails naming the variable and the scheme; the AWS CLI prefixes it with `http://` too and then fails naming that bogus proxy URL, and without the check the upload failed as a DNS error for the scheme's name. A `NO_PROXY` entry matches its host and every subdomain, leading dots ignored and case folded, and `*` alone matches everything, as Python's urllib, which the AWS CLI uses, does (see `EVIDENCE.md`, Response timeouts and proxies under Bun). `proxy-from-env` was used for `NO_PROXY` at first and dropped: it matches an entry without a leading `.` or `*` only exactly, so `NO_PROXY=amazonaws.com` sent uploads through a proxy the AWS CLI skips, it gives a scheme-less proxy `https://` and falls back to `ALL_PROXY`, so the client had already overridden it for both, and what remained is a few lines over one fixed host. `https-proxy-agent` is declared in the root `package.json` beside `@aws-sdk/client-s3`. Bun's own agent option `proxyEnv` was the alternative; the user chose a maintained package (see `REQUIREMENTS.md`, Developer tool credentials).
- **Claude Code's per-turn upload hooks run synchronously with a 10-second timeout.** They now only publish a request and start the worker, and only a synchronous hook's `systemMessage` reaches the user; an async one goes to the agent. So neither CLI's warning carries a "Tell the user" prefix. Warnings print at `Stop` and in `check` at session start; the `SubagentStop`, `PreCompact` and `SessionEnd` uploads print nothing.
- **The warning lists failed transcripts grouped by their last cause, naming at most three keys per group, requests an hour old with no recorded outcome as not confirmed, unreadable requests, at most three of them with each one's parse error on one line, and the worker's own last failure,** in one message with the `retry` command, which `retry` itself leaves out of what it prints, and an unreadable request no longer fails the hook. Grouping keeps the warning to one line per cause when every upload fails for one reason, such as a missing profile, which otherwise adds a key each session and repeats the cause at every Stop and session start; three keys is an agent choice that shows which transcripts without growing. `retry`, which runs on request, names every failed key, since `discard` takes one exact key and a backlog of deleted transcripts can run past three. The session-start check, which already states a failing login, names that login's group without repeating its cause. Once its own lookup succeeds, it leaves out failures an earlier lookup caused, which each request marks, since the worker it starts retries them and repeating "run `aws sso login`" right after one would send the user to log in again. The `Stop` hook doesn't look the login up, so it shows every failure as the last attempt's, followed by "retrying now", since it has just started the worker that retries them; a login that expires mid-session still shows there, and one the user has just renewed doesn't read as a current instruction. The hour is an agent choice: long past any upload, it catches a worker that never runs, such as one whose perl or bun can't start, without flagging requests a worker is about to take. `worker-error` holds a pass's failure outside any one request, such as a listing or a rewrite that failed, until a clean pass deletes it, and the worker's stderr goes to `worker.log`.
- **A hook that can't publish its request warns that the transcript won't retry, and starts one unlocked background upload of it.** Publishing first exists to keep transcripts, not to gate them. The design review had that upload wait for the lock, but the lock file lives in the spool that just failed, and conditional PUTs keep a concurrent upload from replacing newer content without the lock. Nothing records that upload's outcome, since the spool it would go in is the one that failed, so the warning names `chats.ts fetch <key>` to check it. A request recorded whose wakeup marker couldn't be set gets its own warning instead: it still uploads, but a worker mid-pass may leave it to the next session start or turn. The session-start check names a marker it can't set the same way and still starts its worker, rather than reporting that failure as the worker's.
- **A deleted transcript's requests stay, with an error naming `chats.ts discard <key>`,** which deletes them under the lock and fails for a key with none, pointing at `retry` for the keys, so a mistyped key doesn't read as done; restoring the file clears it on the next pass. Only a missing file counts as deleted: one the pass can't check still uploads, so the upload's own error is what gets recorded. The error names neither file nor key, so the warning's grouping by cause caps a backlog of deleted transcripts at three keys; the request file still holds the path. Hand-deleting request files isn't documented, since a worker could rewrite one it captured.
- **The worker runs from the checkout whose hook started it,** Claude Code's `$CLAUDE_PROJECT_DIR` or Codex's main checkout, instead of always from the main checkout as the design review proposed. Requests hold absolute transcript paths and the worker loads its code, the SDK included, as it starts, so deleting a worktree leaves pending uploads to the next worker, and running a worktree's own `chats.ts` keeps the hooks testable on a branch.
- **The Turnstile keys and `MEDIACONVERT_ROLE_ARN`, `ADMIN_SECRET`, `ADMIN_REFRESH_SECRET`, `SEND_DEV_NOTIFS` are left out** of both the store and the committed config: the schema doesn't require them.
- **Development's committed settings are `developmentEnv` in `common/src/deployed-config.ts`, beside `deployedConfig` rather than in it,** which is how this task reads the requirement's "development entry in the typed config". `deployedConfigFor(Development)` returning `undefined` is what `common/src/web-env-build.ts` and `scripts/deployed-config.ts` read as "not a deployed environment", and development lacks `DeployedConfig`'s domain and CloudFront keys. The object holds env-shaped strings, the form the server reads, and `server/src/config/env.ts` types it with a mapped type that fails the build on a key the server schema doesn't declare. Its Apple bundle IDs reuse production's list.
- **Rollout order: the PR opens before the AWS steps and merges after them.** The `parameter-drift` workflow fails until the `alliance-ci-parameter-drift` role from `terraform/ci-oidc.tf` exists and `/alliance/dev/` holds every key `scripts/dev-secrets.json` lists, and the wrapper needs the populated store anyway. So, after review: open the PR, expecting that check to fail; an admin runs `terraform apply` from this branch, copies the dev secrets into `/alliance/dev/`, reruns `bun scripts/check-parameter-drift.ts`, tests `bun run dev` with a real login; then the PR merges. (Agent decision, told to the user.)
