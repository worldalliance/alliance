- The count is the existing public `POST /user/nmembers` (`useAllianceMemberCount`), which counts users with an active contract, so a suspended member is not counted. Agent decision: it is the platform's one definition of a signed member, and every client already reads it.
- The count applies to every member-facing completion count on an onboarding action: the web and mobile completed bars and the web `ActionLink` preview. Admin stats and the stored `usersCompleted` keep counting completions. Agent interpretation.
- While the count is loading or has failed, nothing falls back to `usersCompleted`, which would show a number with a different meaning. A count already loaded stays on screen when a refetch fails, as `GrantmakingMemberProgress` does. Agent decision.
- The `ActionLink` hover preview uses the same "N members" wording as the completed bar, and non-onboarding labels keep "completed". Agent interpretation.
- The `ActionLink` preview prints the onboarding count as the bar does, through `withCount` and with no thousands separator, following the requirement's "1200 members" example. Agent interpretation.
- The web completed bar's info tooltip explains a denominator, so it renders only on a regular action's "N / M members completed" label. That also removes it from optional actions, whose label never had a denominator. Agent decision.
- Signing or suspending a contract and submitting a member's task form invalidate the count, so a member who signs sees it move. Every member form submission invalidates it because the client can't tell which forms signed a contract; only a mounted count refetches. Agent decision.
- `signedMembersCount` counts in SQL through `sqlUserHasActiveContractAt` instead of loading every user, because this task puts this public endpoint on each onboarding action's bar and preview, which call it on mount and window focus. The SQL commit lands first so that no deployed commit has them calling the full-table load. Agent decision.
