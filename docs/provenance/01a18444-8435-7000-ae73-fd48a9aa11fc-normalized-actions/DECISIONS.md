# Decisions

- Use Redux Toolkit for the action pilot. Its entity adapter provides an established normalized store; TanStack DB remains a beta alternative. This is an agent selection, not a user requirement for Redux throughout the repository.
- Normalize the complete member/public action responses used by the shared web/mobile hooks. Keep admin, feed summaries, and historical representations separate until their field authority is defined. Identical IDs alone do not make those payloads interchangeable. The member list endpoint does not load `authors`, `project`, `suite`, or `updates`, so those fields come from the newest detail response while the rest come from the newest response of either kind. `mergeOwned` (`shared/lib/ownedFields.ts`) holds this rule for every store whose responses leave field groups out: each group comes from the newest response that carries it.
- Scope each store to a QueryClient and clear it at session boundaries. Action and notification DTOs are viewer-specific. `shared/lib/sessionStores.ts` holds one session counter per QueryClient and a registry of stores created through `sessionStore`; `meCache` ends the session with `endSession`, which clears every registered store, so a new entity store cannot be left out of the reset. `sessionStore` keeps each store's `clear` off the store it hands out, so `endSession` is the only reset and a cleared store always rejects the previous session's loads. Mutation responses that resolve after a session boundary do not patch the new session's records: the stores' write methods take the session the write started in. The detail page's completion callbacks use the session of the render they come from, not the submission's.
- Each entity keeps its own Redux store rather than one combined store per QueryClient. The shared session registry already gives them one reset point, and separate stores keep a notification change from notifying action subscribers.
- Query caches retain IDs and list order; components obtain action records from Redux. Query lifecycle metadata remains in TanStack.
- Action queries share an invalidation prefix so writes affecting server-computed fields refresh details as well as list membership. Unread general updates retain their existing membership in that prefix.
- Reuse actionUtils for viewer-state patches. `sessionLoads` (in `sessionStores.ts`) wraps writesDuringLoads for every entity store: it numbers loads by request start so the newest wins, replays writes over loads in flight, and cancels aborted or prior-session loads. Revisions compare only within one `sessionLoads`, so a store routes every revision of its records through one instance. A write may carry its request as a confirmation; until that settles, the write also replays over loads that start after it, which may read the server before it applies the write. A refused write stops applying, including to loads already in flight, and a write stops replaying once its session ends. Loads in flight apply writes in the order they were made. A later load may already reflect the write and reads writes made after it from the server, so an update carrying a confirmation must be idempotent and commute with writes made after it until it settles. A confirmation must reject when the server refuses the write; SDK calls pass `throwOnError: true` for that. Both action list and detail loads participate in the same action write stream.
- Assess other entity families before broad migration. Unread totals remain server-authoritative when the client holds only a subset of the counted records.

## Notifications

- Records are keyed by `getNotificationIdentityKey` (`sourceType:id`); IDs alone collide across notifications and unread content. Each list query caches its ordered keys and the `loadedAt` header together (`NotificationList`), replacing the separate load-time query, so the cutoff cannot outlive or lag its list.
- Each list keeps the membership and order its own request returned (deferred choice). Deriving the bell from the newest full list would show new arrivals sooner but would tie the bell's read-all cutoff to a list it did not render.
- Optimistic state is best effort between a write and the refetch that follows it (deferred choice). A wrong record or count that outlasts that refetch, or that happens when no refetch follows, is a defect; one the refetch corrects is accepted. Making every interleaving exact kept adding replay and rollback code for states that last one round trip.
- Optimistic list writes (`markRead`, `markAllRead`) and read-all's count pass their request to `sessionLoads` as a confirmation, so a list load that starts before the server answers keeps them; with records shared across lists, one list's refetch would otherwise show the read undone in every list. `markRead`'s confirmation rejects when any of its reads is refused. Confirmed writes (action relations, content reads) replay only over loads in flight. Writes to list records must be idempotent. `markRead`'s count decrement is not, so it replays only over count loads in flight.
- A record's revision is the start of the load that last set it; writes do not change it. A load's value already holds the writes made while it was in flight, so a write during a load does not make the store discard the load's content, and an older load still loses to a newer one.
- The store keeps records until the session ends, after their lists are garbage-collected, so `markRead` treats a record as loaded only while a cached list holds it.
- The unread count stays a TanStack query holding the server total, loaded through the notification store's count loads so a read during a count load counts down its result. `markRead` subtracts the loaded records that were unread, clamped at zero, and refetches the count once its requests settle, because a count load in flight may already exclude the reads and still have the decrement applied, and one started before confirmation gets no decrement and may read the server before the read lands. It waits until no other read or read-all that lowered the count is pending, since a refetch then reads a count that does not yet reflect it and would undo it. Refetching the count first cancels a count load in flight: a query with no data yet would otherwise join that load instead of replacing it; a read for any notification no cached list holds refetches lists after the request settles and the count under the same wait as other reads, and a refusal refetches lists and count after it settles, so neither refetch can read the server before the read lands. A content read refetches the count, because the server marks unread content rows the client may not hold.
- Read-all marks immediately only what the server will mark: records sent and created through the list's `loadedAt` millisecond, mirroring `setReadAll` (deferred choice). The count becomes the loaded unread records, never more than the count it replaces, computed whenever it is applied so reads made while read-all is pending count down. That update does not commute with `markRead`'s decrement, which the `sessionLoads` contract asks of confirmed writes: a read during a count load that started while read-all was pending is counted twice until `markRead`'s count refetch, which this best-effort window accepts; the refetch after success adds any unloaded ones.
- A failed read-all restores the records it marked and the count it replaced, then refetches lists and count (deferred choice). Reads made while it was pending show unread again until that refetch (ALL-1934). Keeping them took per-record touch tracking whose interactions with replayed loads kept producing edge cases. Nothing is restored or refetched after a session change, and a read-all whose session ends before it starts sends nothing.
- `markCachedReadByContent` runs after its request and takes the session current at that time; a content read finishing just after a sign-in change can mark the new viewer's matching record read until the next refetch.
- The admin per-user notification view (`userNotifsAdmin`) stays separate: it is another viewer's data.

## Activities

- One store (`shared/lib/activityStore.ts`) holds activities and the forum comments the home and profile feeds interleave with them. Both arrive in the same feed responses, so one `sessionLoads` replays a write over either; the per-entity-store decision above was about keeping unrelated subscribers apart, and these render together.
- Activities are keyed by id, feed forum comments by comment id. Activity lists, the home and profile feeds, and `useActivity` cache ids and order; components read records through `select`. The lists go through `useEntityList` (`shared/lib/useEntityList.ts`), which holds the id-list query for any entity store; it was extracted from `usePostList` for the community lists. Each list or feed keeps the membership, order, and cursor its own request returned.
- The server sends `comments: []` unless the request asked for comments, and `formResponseOutput` only from the feeds that render cards in full (comment-carrying lists, the home and profile feeds) and the detail endpoint. Those two are field groups under `mergeOwned`, so a later list without them leaves the loaded ones in place.
- Every other activity field takes the newest response, so every endpoint must send it the same way. The profile feed did not load an activity's note (`editableContent`), and `fetchActivityFeed` did not select the author's `ambassador`; the server now sends both from every endpoint, which `server/test/activity-records.e2e-spec.ts` checks along with `isCommunityLeader`. A field one endpoint still sends differently would flip with whichever response is newest, so a new activity endpoint or a narrowed select needs a case there.
- Likes on activities and feed forum comments go through `useLikeActivity` and `useLikeForumComment` (`shared/lib/useFeedLikes.ts`), which every surface shares. The optimistic write sets the like rather than toggling it, so it is idempotent and passes its request to `sessionLoads` as a confirmation; the cancel-and-refetch around the detail load is gone because loads in flight replay the write. The activity like's response then sets likes, count, and liked-by-me. A refusal rejects. When the latest like or unlike of a target is refused, the target returns to the state the server last confirmed, not the opposite of the refused write, once every like or unlike of it has answered: an earlier one still out may yet succeed and change that state. Only the newest like or unlike of a target applies its answer, so two surfaces showing the same target cannot leave the earlier answer standing.
- A feed forum comment's like reaches only feed copies. The post's comment thread (`useLoadComments`) stays component state, per its own recorded reasoning.
- Activity list and feed requests pass `throwOnError: true`, so a failed refetch or next page keeps the loaded pages as a query error instead of replacing them with an empty page. After a failed next page the hooks report no next page until a refetch succeeds: the mobile home screen pulls the next page whenever none is loading, and with `hasNextPage` still true it would request the failed page in a loop. No surface renders the error yet; a failed first load still shows the empty state.
- The web activity detail reads `useActivity`, which shows a record a list already loaded while its own request is out; its outlet context carries only the action.
- Records stay until the session ends, as in the action and notification stores, so a long session keeps every activity it loaded after its queries are garbage-collected (deferred choice). Evicting records no cached query references belongs in `sessionStores.ts` for all three stores.
- The grouped global feed (`useGlobalFeed`) stays separate: its items summarize several activities rather than carrying records.

## Forum posts

- The forum index's and every user's post list's query keys share the `forumPostListsAll` prefix, so a new post refetches the index and every profile list (ALL-1585).
- One store (`shared/lib/forumPostStore.ts`) holds a record per post, keyed by id. The forum index (`useForumPosts`), each user's post list (`useUserForumPosts`), and the post page (`useForumPost`) cache ids and order; components read records through `select`. Their query keys share the `forumPosts` prefix. Each list keeps the membership and order its own request returned.
- `commentCount` and `lastComment` come only from the forum index, so they form a field group under `mergeOwned`. A profile list record keeps the index's values, so the web profile's post cards show neither (`showThread={false}`), as they did before, instead of a count that depends on whether the index loaded first. The profile endpoint did not send the likes facepile, and only the detail and update loaded tags. The server now loads both for the index and the profile list, each loading its to-many relations in a query apiece so likes, tags, and authors don't multiply each other's rows, and `server/test/forum-post-records.e2e-spec.ts` checks the index, profile list, detail, and update response agree. A new post endpoint, or a narrowed select, needs a case there. `findPostsByAction` has no client caller and is left as it is.
- Signed-out viewers of the profile list now receive the like facepile. Comment endpoints already send theirs to signed-out viewers.
- A saved edit enters the store as a load with a revision newer than any in flight, as the action store does with mutation responses, so a list or detail load that read the post before the save loses to it. It replaces the cancel-then-set the detail used, and reaches every list.
- A deletion drops the id from every cached list and detail and replays the drop over loads in flight, so a reload that read the post first keeps the rest of its content instead of being cancelled. The record then leaves the store, so the post page's placeholder cannot show a deleted post reopened after its detail query is collected. `forumPostStore.removed` does all of it, the cached ids first, since `selectPost` throws on a cached id the store lacks.
- A created post stays out of the store, as before: the create response lacks the action, authors, and tags the post page shows.
- Likes go through `sendLike` and `likeTurns` (`shared/lib/sendLike.ts`), moved out of `useFeedLikes.ts` and `activityStore.ts` for this second caller. The optimistic write sets the like rather than toggling it and replays over loads in flight and loads started before it is answered (ALL-1257). The like endpoints return nothing, so once a like answers the post page's query, captured when the like started, is invalidated for the facepile (ALL-1253).
- The post page shows a record a list already loaded while its own request is out. The edit form still waits for `isFetchedAfterMount` before filling. When that request answers 404 (deleted elsewhere, or no longer visible to the viewer), the page shows the loaded record until the answer and then "Post not found"; the answer drops the post through `forumPostStore.removed`, so lists and later opens stop showing it. The brief flash is the price of instant opens from a list.
- The `postTitle` that feed forum comments carry is a projection in the activity store and is not patched by an edit; it updates on the next feed load.
- Admin post views (`getPostsForAdmin`) stay separate.

## Communities

- One store (`shared/lib/communityStore.ts`) holds a record per community, keyed by id. The user's groups (`useMyCommunities`) and the public groups (`usePublicCommunities`) cache ids and order through `useCommunityList`, built on `useEntityList`, and read records from the store; their query keys share the `communitiesAll` prefix. Each list keeps the membership and order its own request returned. Both hooks back web and mobile alike.
- Both list endpoints send the same fields, so records have no field groups: the newest response wins whole. The public list, update, and join did not load members' contract events, so `ProfileDto.hasActiveContract` read false and `lastContractEvent` was missing there while the user's groups had them; a save then marked every member unsigned in the user's groups. `COMMUNITY_RECORD_RELATIONS` (`server/src/community/community.service.ts`) now loads members the same way for both lists, and create, update, join, and remove member reload the community with it before answering. `server/test/community-records.e2e-spec.ts` checks those six responses agree; a new member-facing community endpoint, or a narrowed select, needs a case there.
- Writes are not optimistic, as before. A write's response enters the store with a revision newer than any load in flight, as forum post edits do, so a list load that read the group before the write loses to it. Remove member now takes the server's group instead of patching the cached one.
- Saving settings refetches the public list, since a save can make the group public or private. Leaving drops the id from the user's groups only; deleting drops it from every list. Both refetch both lists, as before, so neither replays its drop over loads in flight: the refetch cancels and replaces an active list's load. Records stay until the session ends, as in the other stores.
- `usePublicCommunities` loads with `throwOnError: true`, so a refusal carries its status and `retryUnlessRefused` stops retrying it (ALL-1336).
- Admin community views (`useCommunitiesAdmin`) and the communities embedded in invites (`CommunityInviteDto`, `OnetimeInviteDto`) stay separate. Admin views are another scope, and invites load their community with other relations, so mixing them in would make fields flip with whichever response is newest.

## Conversations

- One store (`shared/lib/conversationStore.ts`) holds a record per conversation, keyed by id. The viewer's list (`useMyConversations`) caches ids through `useEntityList`, and a group's chat (`useCommunityConversation`) caches its conversation's id; both read records from the store, and their query keys share the `conversationsAll` prefix. The list's order comes from sorting its records with `sortConversations`, not from the order a request returned, so a new message re-sorts the list wherever it is shown.
- Every write goes to the record: write responses, mark-read responses (the Messages list used to discard its own), `conversation:updated` and `conversation:unread` from the sockets, and incoming messages. `useLiveConvoMessages` stores the last message and socket updates itself instead of taking per-screen callbacks, so the group's floating panel now updates the Messages list as well. Responses and socket payloads outrank loads in flight. A mark-read response sets only `unreadCount` and `hasUnread`, since the server may have built it before a newer message or rename the record or a load in flight holds. It and an incoming message patch the record and loads in flight without outranking those loads, so a load that read a newer message or title still lands. A mark-read answered before the conversation has a record stores nothing; a load in flight takes its read state, and a later load reads it from the server.
- Membership changes apply only to the viewer's list. A load's value says whether it is that list (`ConversationLoad.isViewerList`), because one `sessionLoads` carries both the list's and the group chats' loads. A chat the server returns from a create, or announces over `conversation:unread`, joins the list and any list load in flight; a declined or left chat leaves it. A decline now drops the chat from the list instead of storing the declined response, which the list's filters hid anyway. A socket announcement made before any list has loaded, with no load in flight, adds the record but no list; the list's first load brings the chat.
- A conversation open on any screen keeps `unreadCount` 0 when `conversation:unread` arrives, as before.
- Rename, add participant, and remove participant returned the conversation without `lastMessage` and with `unreadCount: 0` (ALL-1806); with one record per conversation, those responses would blank the preview and the badge everywhere. They now return `getConversationForUser`, as accept, mark-read, the sockets, and the group chat endpoint already did. Creating a direct or group chat builds its response the same way for consistency; a new chat has no messages, so its response is unchanged. An acting user removed before the response is built gets a 403, as every other non-participant does, though their write has gone through. `server/test/conversation-records.e2e-spec.ts` checks these agree with the list. A new conversation endpoint, or a narrowed select, needs a case there. A participant who removes themselves gets the old response, since they no longer have an unread count; no client offers that action. Decline and leave also keep theirs, since the client drops the chat.
- Records stay until the session ends, as in the other stores.
- Messages (`useConversationMessages`), the unread message total (`useUnreadMessageCount`), and admin conversation views stay separate, as listed under counts below.

# Further migrations

These are recommendations from the repository audit, not approved implementation scope.

| Priority | Entity                          | Evidence and proposed boundary                                                                                                                                                                                                                                                                                          |
| -------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Later    | Member profiles and friendships | `shared/lib/user.ts`, `useMembers.ts`, and `useMembersWithFriends.ts` expose overlapping profiles; messages and communities embed profiles too. Normalize public profile fields separately from private account data and viewer-specific relationships. A friend change also changes collection membership.             |
| Later    | Admin actions and form metadata | `shared/lib/useActionAdmin.ts` already coordinates list/detail invalidation. An admin-specific action table could share editable fields; list-only variant IDs and member-filtered forms cannot overwrite richer or differently scoped data. Normalize form index metadata separately from draft and published schemas. |
| Lower    | General/action updates          | The unread/all/recent lists overlap, but immutable content needs less synchronization than read/dismissed status and ordering. Reuse notification/content-read coordination where the server contracts overlap.                                                                                                         |

## Counts and intentionally separate state

- Notification unread count: see Notifications above.
- Task count is already derived from the complete member action list by `useTaskBadgeCount`; it now observes normalized action updates. Keep this derived rather than introducing a separately writable count.
- Message unread totals include server-specific request/message rules (`useUnreadMessageCount`). Preserve their endpoint and socket refresh contract until coverage and counting rules are explicitly equivalent.
- Preserve independent form drafts, published snapshots, historical feed representations, analytics aggregates, and search result membership. Their differing versions or scopes are part of their meaning, even when they reference the same underlying ID.
