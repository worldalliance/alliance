# Decisions

- **Page views are sent by hand, not by PostHog's history listener.** `capture_pageview: false`, and `useAnalytics`, under the admin root's `AuthProvider`, captures `$pageview` after React Router has matched the new route. PostHog's `history_change` mode fires on `pushState`, before the matched route and its params are known, so the route template (requirement 4) would lag a page behind. Time on page comes from PostHog's `$prev_pageview_duration` on the next page view and from `$pageleave`, sent on unload. (Agent decision.)
- **The route template comes from the matched params.** `routeTemplate` walks the leaf match's params from `useMatches` in path order, swapping for `:<name>` the first segment after the previous swap that equals the param, so `/projects/3/action/3` keeps both names. React Router decodes the matched pathname except `%2F`, which the param holds as `/`, so a segment is compared with `%2F` turned back into `/` and never decoded again. A param no segment holds makes the whole template `/[unknown]`, so an unforeseen encoding fails closed instead of leaving the value in. React Router matches regardless of case and a trailing slash, so the template drops a trailing slash and lowercases every segment but the param names, keeping `/members/` and `/MEMBERS` with `/members`. A static segment equal to an earlier param's value would still be swapped; admin's static segments are words and its params ids, so that is left alone. The route config in `routes.ts` is build-time data from `@react-router/dev`, kept out of the client bundle. (Agent decision.)
- **Every URL-like property is rewritten in `before_send`.** Each top-level key in `properties`, `$set` and `$set_once` that ends in `url`, `pathname` or `referrer` is rewritten to its route template. Admin paths are looked up in a map of the pathnames this tab has rendered, which covers `$prev_pageview_pathname`. Another site's URL is cut to its origin, and an admin path this tab never rendered, such as the session's entry URL after a reload, becomes `/[unknown]` instead of leaking. The `title` posthog-js adds to page views is dropped, since admin titles such as a text thread's name the member. A key-name rule is used rather than a list of PostHog property names because posthog-js adds such properties over time (`$session_entry_*`, `$initial_*`). posthog-js also copies campaign query parameters (`utm_*`, click ids) and a search engine referrer's keyword into event, session-entry and initial person properties (EVIDENCE.md, "Library behaviour read from source"); keys ending in those names, copied from posthog-js 1.364.6, are dropped at every level. A test reads the installed posthog-js bundle's lists, so an upgrade that adds a parameter fails until the list is updated. (Agent decision.)
- **Feature-flag requests are off** (`advanced_disable_flags`). The flags request sends person properties, including the raw `$initial_current_url`, and `before_send` never sees it (EVIDENCE.md, "Browser run against a production build"). Admin uses no flags. (Agent decision.)
- **Admin keeps its PostHog state in localStorage, under its own name** (`persistence: "localStorage"`, `persistence_name: "admin"`). Under the default `localStorage+cookie`, both apps name their cookie `ph_<key>_posthog`, and the member site's sits on the parent `thealliance.org` domain, so admin's first load would read the member site's distinct id and session. Where localStorage fails, posthog-js falls back to a cookie, which the name keeps apart from the member site's. Staff still end up as one person, because both apps identify by user id (requirement 3). (Agent decision.)
- **Events go out only under a staff member's own id, settled once per page load.** Once `/auth/me` settles, `syncStaff` resets a browser identified as anyone other than the signed-in staff member, since the shared session can change on the member site, then identifies the staff member. Only an admin signed in as themselves counts as staff: a signed-out visitor, a member who isn't an admin and an admin being impersonated (`isImpersonation` from `/auth/me`) are never identified from admin. `before_send` drops every event until a staff member is identified, so an event before `/auth/me` answers, or on a page load without staff, such as the login page's, goes unsent rather than out under a previous staff member's id or anonymously, and requirement 1's ranking counts staff visits only. Signing out clears the signed-in user but leaves PostHog's identity, so the `$pageleave` keeps the staff member's id, and the login page's load resets. (Agent decision.)
- **The `/events/` proxy drops the Cookie header** (`deploy/nginx/alliance.conf`). Admin's page-leave beacons go to the API host's `/events/` path, and a beacon carries that host's cookies, the staff session's `access_token` and `refresh_token` among them, which nginx forwarded to PostHog. The member site's own requests there already carried them. PostHog ingestion reads no cookies. (Agent decision.)
- **Super-properties are registered again after `reset()`**, which clears them, so events after a reset still carry `app: admin`. (Agent decision; seen in the browser run.)
- **Everything else posthog-js can capture is off**: autocapture, exceptions, rage clicks, dead clicks, heatmaps, performance and web vitals, surveys. That keeps the capture to requirement 4's page views and page leaves, whatever the project's remote config enables. (Agent decision.)
- **`defaults: "2025-05-24"`, matching the member site.** Later dates turn on network body capture for replay (EVIDENCE.md). Replay is off here, but pinning the member site's date keeps the two apps' behaviour the same. (Agent decision.)
- **The build super-properties (`git_sha`, `environment`) moved to `sharedweb/lib/posthogBuildProperties.ts`**, so admin and the member site tag builds by one rule. (Agent decision.)
- **No new PostHog project or key.** Admin already gets the production and staging keys through its runtime config (`common/src/web-runtime-config.ts`), and those environments already use separate projects (`common/src/deployed-config.ts`), so staging admin traffic stays out of production data. (Reconstructed from existing code.)
