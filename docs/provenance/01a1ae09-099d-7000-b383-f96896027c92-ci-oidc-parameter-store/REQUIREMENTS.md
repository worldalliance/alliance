## This task

- Three CI IAM roles, by trust level: a review role for workflows that run on any branch or same-repo pull request, a staging role, and a production role. Each trust policy pins the audience, the repository and owner by immutable ID, the `sub` claim, and the `ref` claim: the review role accepts any branch push, dispatch or same-repo pull request; the staging role accepts only `environment:staging` on `refs/heads/main`; the production role accepts only `environment:production` on `refs/heads/main` or `refs/heads/production`. Each role may read only the parameters it needs, granted by name, not by path. No CI role reads `/alliance/<env>/server/`. (agent-proposed after research, user-approved)
- `PR_SCREENSHOTS_GH_TOKEN`, the user token the PR screenshots workflow posts its comment with, sits behind a fourth role of its own, which only a dedicated GitHub environment can assume and which only the PR screenshots `post` job names. The review role no longer reads it, so code run by the screenshots `capture` job or `manual-review` can't reach it through the review role. The review role keeps the OpenAI key and the Slack webhooks, which those jobs may still read. (user-originated, choosing among agent-proposed options)
- The iOS visual regression workflow (`mobile-visual-regression-ios.yaml`), which runs code from whatever ref it is dispatched with, assumes a role of its own, `alliance-ci-visual-regression`, and names no GitHub environment. The role is trusted for `mobile-visual-regression-ios.yaml` on `main` and for `deploy.yaml` on `production`, each pinned by `job_workflow_ref`, so the production deploy's visual regression job uses it and its dependency code never holds the production role's Expo token. It holds only the visual regression access: the CI storage bucket, the dev assets bucket the screenshot server uses, and the Gemini, Anthropic and Slack bot keys. It gets no deploy parameter, no Run Command access and not the Expo token. (user-originated, choosing among agent-proposed options; the `production` trust agent-proposed, user-approved)
- Run Command on the hosts and the deploy artifacts bucket sit behind two roles of their own, `alliance-ci-staging-hosts` and `alliance-ci-production-hosts`, each trusted only for a GitHub environment of the same name (`staging-hosts`, `production-hosts`) that only the three jobs deploying to a host (`deploy-react-app`, `deploy-admin-app`, `deploy-nest-backend`) name. `staging-hosts` is pinned to `refs/heads/main`, `production-hosts` to `refs/heads/production`. `./.github/actions/run-on-host` assumes the hosts role; the staging and production roles hold neither Run Command nor the artifacts bucket, so jobs running third-party code under them can't get a shell on a server. (user-originated, choosing among agent-proposed options)
- The `staging` GitHub environment accepts deployments from the `main` branch only, and `production` from `main` and `production` (ALL-1325).
