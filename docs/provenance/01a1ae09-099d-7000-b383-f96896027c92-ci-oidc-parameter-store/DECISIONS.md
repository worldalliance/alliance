# Decisions

Research behind the requirements is in `EVIDENCE.md`.

## Roles and parameters

- **Parameter layout.** Values are stored once each, grouped by which roles read them: `/alliance/ci/review/` (Claude and OpenAI tokens, the CLA Slack webhook), `/alliance/ci/pr-screenshots/` (the screenshots GitHub token), `/alliance/ci/shared/` (the deploy Slack webhook, which PR CI also posts to), `/alliance/ci/visual-regression/` (Gemini and Anthropic keys, Slack bot token, which the visual regression role reads, and staging and production only the Slack bot token, for approving their baselines), `/alliance/ci/deploy/` (PostHog sourcemap key, Expo token), `/alliance/staging/ci/` (the App Store Connect and Play keys only staging builds use). Every CI value but those four was identical in Infisical's staging and prod, so per-environment copies would only add rotation work. Origin: agent decision.
- **Roles are named after the GitHub environments** (`alliance-ci-staging`, `alliance-ci-production`, `alliance-ci-staging-hosts`, `alliance-ci-production-hosts`), so a job passes its environment name as the role. Parameter paths keep the project's `prod` spelling. Origin: agent decision.
- **The review role trusts `sub` `ref:refs/heads/*` or `pull_request`, not `repo:…:*`,** which would also admit environment and tag subjects. A branch push, a dispatch from a branch, and a workflow_run from `main` all carry a `ref:refs/heads/…` subject. Each subject gets a trust statement of its own with the refs it carries: `refs/heads/*` for a branch subject, a pull request's `refs/pull/*/merge` for `pull_request`. A `pull_request_target` run, which a fork's pull request can trigger, carries the `pull_request` subject with the base branch's ref, so one statement checking both lists would admit it. Origin: agent decision, following the research; the pairing from review.
- **The roles can't tell one job from another beyond trust level, except for the screenshots token, visual regression and Run Command.** A job eligible for a role can read everything that role is granted, and `id-token: write` extends that to every step the job runs. Splitting by job (option 1b) was offered and not chosen; the screenshots token's role, the visual regression role and the hosts roles are the exceptions, per REQUIREMENTS.md. Any job on a branch that names no environment can assume the review role, the visual regression jobs included; that reaches nothing a pushed branch can't, and the PR screenshots capture and manual review jobs run the same dependencies under that role. Origin: user choice between options; the review role's reach from review.
- **The screenshots token's role is `alliance-ci-pr-screenshots`, trusted for `sub` `environment:pr-screenshots` on `ref` `refs/pull/*/merge`.** A job naming an environment gets an `environment:<name>` subject, and the `post` job runs only for a `pull_request` event, whose ref is the merge ref. A same-repo author who edits the workflow can still name the environment from another job, as they could read any repository secret before. Origin: agent decision.
- **The visual regression role alone gets the visual regression S3 policy** (`ci_visual_regression` in `terraform/ci-oidc.tf`: the CI storage and dev assets buckets) and the AI review keys. The staging and production roles get only the CI storage bucket and the Slack bot token, which `approve-visual-baseline.yaml` uses through them; its steps run no dependency code. Any branch's code dispatched from `main` can overwrite either environment's baselines, as the job itself does when it promotes one. Origin: agent decision.
- **`deploy.yaml`'s visual regression job, run only for production, assumes the visual regression role and names no GitHub environment,** so the role also trusts `sub` `ref:refs/heads/production`, per REQUIREMENTS.md. The job runs four `bun install`s, Playwright and the screenshot server with the role's credentials exported, and the production role would hand that code the Expo token, which publishes a production OTA. The visual regression role holds exactly the buckets and keys the job uses, and any branch's code already reaches it through an iOS dispatch, so trusting `production` exposes nothing new. The job uses no environment secret or variable; trusting `environment:production` instead would let every production-environment job assume it. Origin: agent decision, user-approved (REQUIREMENTS.md).
- **The visual regression role also pins `job_workflow_ref`:** `mobile-visual-regression-ios.yaml` on `main`, `deploy.yaml` on `production`. Any other job on either branch that names no environment carries the same `sub` and `ref`, such as `manual-review.yaml`'s agent on a `checkout_ref` of its choosing. For a job that calls no reusable workflow, the claim names the job's own workflow file, and AWS lists it among the GitHub claims STS checks (EVIDENCE.md). A trusted `sub` with no pin fails the plan, so a renamed key can't drop it silently. Origin: agent decision, from review.
- **The hosts roles pin `job_workflow_ref` to `deploy.yaml`,** `staging-hosts` on `main` and `production-hosts` on `production`, where the three host-deploy jobs run. A GitHub environment's branch rule checks only the ref, so without the pin any other workflow on that branch naming the environment, a `pull_request_target` one included, would get a root shell on the host. Origin: agent decision, from review.
- **The staging mobile build reads the App Store Connect and Play keys under the `staging` role,** so its dependency installs and native build can reach them through `id-token: write`. They could before too: `eas submit` evaluates the app config with the project's Expo CLI and config plugins from `node_modules`, with the keys in its environment, on the runner the install scripts already ran on. A submit job of its own would still need that `node_modules`; keeping the keys from the app's dependencies is ALL-2082. Origin: agent decision, from review.
- **Each environment role holds the mobile release, sourcemap upload and baseline approval powers its environment uses together.** The Expo token is shared, so the staging role can publish a production OTA, as any staging job could before. Origin: agent decision; separate Expo tokens per environment would close it.
- **The hosts get a custom SSM agent policy, not `AmazonSSMManagedInstanceCore`.** The managed policy grants `ssm:GetParameter` and `ssm:GetParameters` on every parameter, and the `aws/ssm` key decrypts for any caller in the account, so attaching it would let the staging host read production's secrets and undo ALL-1963's boundary. The custom policy allows `ssm:UpdateInstanceInformation` and the `ec2messages`/`ssmmessages` calls the agent needs. It omits association and inventory calls, which Run Command doesn't use; the agent logs errors for those. Origin: agent decision.
- **The OIDC provider lists GitHub's two published thumbprints** because AWS provider 4.x requires `thumbprint_list`; AWS validates GitHub's certificate against its own CA library and ignores them. Origin: agent decision.
- **The CI roles replace the `alliance-dev` IAM user's keys in CI** with direct S3 grants: read/write on the CI storage bucket (visual regression), through the policy document the dev user already uses, and read/write on the dev assets bucket, which the screenshot run's server uses as `ASSETS_BUCKET`. The dev user keeps its own policies, since people may use its keys locally; ALL-1965 decides that. Origin: agent decision, following the research.

## Workflows

- **`./.github/actions/aws`** is the one place a job assumes a role. It uses `aws-actions/configure-aws-credentials` pinned to v6.3.0's commit with `output-env-credentials: false`, so the role's credentials stay inside the action unless the job sets `export-credentials`. Jobs that run untrusted code, such as the screenshot and manual review agents, get no AWS credentials in their environment. That stops a leak, not an attack: `id-token: write` lets any step in the job request an OIDC token and assume the job's role, reading everything the role is granted. Origin: agent decision.
- **Secrets come back as one JSON output**, used as `fromJSON(steps.aws.outputs.secrets).NAME`, because a composite action declares its outputs statically. Each step that uses a secret names it in its own `env`, as with `secrets.NAME` before, rather than the action exporting every secret to the whole job. Origin: agent decision.
- **Multi-line values are masked line by line** (`read-parameters.sh`), so lines with no letter or digit, like a JSON brace, can be skipped: they hold no key material, and since the runner masks every line of a multi-line mask, masking them would hide that punctuation in every later log line. A single-line value is masked whole, whatever it holds. Each mask escapes `%` and carriage returns as `@actions/core`'s `setSecret` does, because the runner unescapes a command's data before masking it. Origin: agent decision; the punctuation exception and the escaping from review.
- **Two requested names sharing a last segment fail the step**, since the output keys values by that segment and one would silently replace the other. Origin: agent decision, from review.
- **The action loads `.github/ci.env` into the job's environment.** Every job that reads a committed CI value also assumes a role, so one step covers both. Origin: agent decision.
- **Jobs that set `id-token: write` list every permission they use**, since naming any permission sets the rest to none, and the repo's default token is read/write. Callers of the reusable `mobile-fingerprint-check` and `publish-mobile-ota` workflows grant `id-token: write` too, which caps what the called job can have. Origin: agent decision.
- **The PR screenshots `post` job runs the action from the run's own ref**, the pull request's merge ref, which its workflow file also comes from and which has the action whenever that file uses it. Checking out another ref protects nothing: whoever can change the action there can change the job's steps. Origin: agent decision, from review; it replaces a default-branch checkout whose stated security reason didn't hold.
- **The fingerprint check posts its Slack message from a job of its own**, the only one holding `id-token: write`, so the check's dependency install and fingerprint run can't assume the review role and read its Claude and OpenAI keys. The post skips reading the webhook for a fork's pull request, which gets no OIDC token, and keeps its existing skip when the webhook is empty. Origin: agent decision; the separate job from review.
- **`manual-review` reads the action from its `review-tools` checkout**, the dispatched branch, not the reviewed `checkout_ref`. Origin: agent decision.
- **The iOS visual regression job assumes its role just before taking screenshots, for three hours.** Taking screenshots builds the app first, and a cold build, the capture and the uploads after it can outlast an hour, so the visual regression role allows three-hour sessions; the setup before it (installs, CocoaPods, prebuild) needs no credentials. A dispatch from a branch other than `main`, which the role doesn't trust, fails in the job's first step. It runs the action from a sparse checkout of the workflow's own commit, since the workspace holds the tested ref, which may predate the action. The staging mobile build does the same, since it runs from main's tip but builds the Deploy run's commit, and so does the PR screenshots `capture` job, whose workspace holds the PR head. Each checks it out under `.scratch/`, which git ignores, so EAS doesn't copy it into a build as an untracked file. Origin: agent decision, from review.
- **The deploy's React build assumes no role; `upload-react-sourcemaps` uploads its source maps.** The upload job and the build's artifact upload continue on error, as the single source-map step did, so source maps never block a deploy or turn a deployed run red, which `publish-mobile-ota` reads as not live. The build injects PostHog's chunk ids, which needs no token, and hands the assets over as an artifact. The upload job names the environment and holds `id-token: write`, but runs only the checkout, this repo's actions and PostHog's CLI. Under the environment role, the frontend's build dependencies could read the Expo token, which no build step could reach as a GitHub secret. PostHog's CLI, which already holds the sourcemap key, still can; `./.github/actions/posthog-cli` installs it from its release tarball, checked against a committed sha256, because its npm package's install script downloads that tarball from a GitHub release unchecked. Origin: agent decision, from review.
- **The no-GitHub-secrets check is `.github/scripts/reject-github-secrets.sh`, run by a step in `actionlint.yaml`,** which both `ci.yaml` and `deploy.yaml` call, and lands in a commit of its own right after the deploy stops reading `EC2_SSH_KEY` and `INSTANCE_IP`, the first commit where it holds. It reads only `.yml` and `.yaml` files, the only ones under `.github` where GitHub evaluates the context, so a script or test there may name `secrets` freely. It greps, ignoring case as GitHub's expressions do, for the `secrets` context followed by `.NAME`, `.*`, `[`, `)`, `}`, a comparison or `&&`/`||`, for `secrets` between `(` or `,` and a comma, as in `join(secrets, ',')` or `format('{0}{1}', secrets, 'x')`, and for `secrets: inherit`, quoted or spaced around its colon too, but not preceded by a word character, hyphen or dot, so a path like `docs/ci-secrets.md` or a step output named `secrets` doesn't trip it. The name must follow the dot directly, so a sentence ending in "secrets." doesn't trip it either, at the cost of missing a space after the dot, as in `secrets. NAME`, which no one writes by accident, and an expression split across lines. A comma after `secrets` counts only after `(` or another comma, so a comment's "secrets, …" doesn't trip it, though "keys, secrets, …" does. A grep that errors, or a missing directory, fails the step rather than reading as no match. `reject-github-secrets.test.ts` holds a case for each of these behaviors. It carries no `BACKCOMPAT` marker: it is the ratchet, not a fallback awaiting removal. Origin: agent decision, following REQUIREMENTS.md.
- **A missing parameter or an AWS failure fails the job.** Before, an unset GitHub secret silently became an empty string in several steps. Origin: agent decision, following the repo's fail-loudly rule.

## Deploying through Run Command

- **`./.github/actions/run-on-host`** uploads the script and files to `s3://<deploy-artifacts>/<environment>/<run>-<attempt>/<job>/<random>/`, a prefix per call so a second call in a job can't overwrite the first's files, runs `AWS-RunShellScript` on the environment's instance, polls the invocation, then prints the output Run Command wrote to the same prefix. A failed or timed-out command fails the step. Origin: agent decision.
- **Scripts run as `ec2-user` in a login shell (`sudo -iu ec2-user`) from `~/`, with the files copied into `~/`,** matching what the SSH steps did, so the existing scripts run unchanged: `~/react-build.zip`, `~/alliance.conf` and `~/nest-build.zip` land where they did, and pm2 talks to ec2-user's daemon. The login shell `exec`s the script's bash, so timeout's SIGTERM reaches the script's trap whatever ec2-user's dotfiles set. Origin: agent decision.
- **Output arrives when the command ends, not streamed.** Run Command writes full output to S3 at the end; the step falls back to the invocation's first 24,000 characters when S3 has none. Streaming through CloudWatch Logs would add a log group and polling for little gain. Origin: agent decision.
- **`run-on-host` assumes its environment's hosts role itself, for three hours** (`role-duration-seconds: 10800`), and the hosts roles allow that much. The duration follows from its own wait arithmetic, so callers don't repeat it. `run-on-host` polls one invocation for up to its lock wait, timeout and recovery window plus delivery, about 2h15m for the backend, and an expired session would fail the poll without the host's output while the script kept running. A `timeout-minutes` whose wait, plus ten minutes for the uploads before it and the output download after it, would outlast the session fails before sending the command. The other roles, but visual regression, keep a one-hour maximum.
- **The host-deploy jobs name the `staging-hosts` or `production-hosts` environment in place of `staging` or `production`,** since a job names one environment and the hosts role trusts only its own. They use no environment secret or variable. Origin: agent decision, following REQUIREMENTS.md. Origin: agent decision, from review.
- **The backend step gets 45 minutes, the frontend and admin 30.** The SSH steps had appleboy's default 10 minutes, and migrations run inside the backend step. A timeout's SIGTERM ends in `deploy_backend.sh`'s recovery only on its stop-first path; its ordinary path traps no signal, so a timeout there leaves the new release in place as an ended SSH session did (ALL-2052). Origin: agent decision.
- **A script that reaches its timeout gets SIGTERM from `timeout`, then 15 minutes before `timeout` sends SIGKILL.** `timeout` runs the script in a process group of its own, so the agent's SIGKILL of a cancelled or timed-out command, sent to the command's own group, doesn't reach it, and it keeps the host lock until it ends. The script's shell traps TERM to exit only after the command it's running, so `deploy_backend.sh` finishes any recovery first. Not yet tried on a host. Origin: agent decision, from review.
- **Cancelling the GitHub job doesn't stop the host script.** With SSH, cancelling hung up the session, which `deploy_backend.sh`'s HUP trap recovered from only on its stop-first path. Run Command keeps the script running to completion, which the rollback logic handles better than an interruption. One job may have one call in flight at a time, since parallel calls, such as matrix legs, would wait on and then refuse each other. A lock per job name on the host makes the next run's same job wait for it before copying files, for up to its own timeout and recovery window plus two minutes for the earlier command's downloads, then fail. `flock` wakes waiters in no set order, so each command appends the time the runner sent it to a queue file on the host before waiting, and once it holds the lock exits without copying files if the queue holds a later send: that command's run started only because this one's job was cancelled, and deploying now would overwrite its newer files. Commands are ordered by send time, not by when they reach the host, because an agent that was offline receives several at once and runs them in parallel. The send times come from different runners' clocks, which would have to disagree by more than the minutes between two runs of one job to misorder them. A re-run of an older run, as a rollback, is sent last and so still deploys. `aws ssm cancel-command` doesn't stop the script either, and `docs/ci-secrets.md` says how to. The script writes its output to a file on the host, which the command prints once it ends, because on cancel the agent closes the pipe it reads output from, and a script writing to it would die of SIGPIPE. Origin: agent decision; the lock and the queue from review.
- **The React build moves from scp in `build-react-app` to an artifact** that `deploy-react-app` downloads and hands to Run Command, like the admin build already did. Origin: agent decision.
- **The deploy artifacts bucket expires objects after a day**, the shortest lifecycle S3 allows, and blocks public access. Each hosts CI role writes only its environment's prefix; each host's instance role reads that prefix and writes Run Command's output there. The hosts roles' `ssm:SendCommand` grant names the bucket too, which AWS's service authorization reference lists among that action's resources. Origin: agent decision, from the user's requirement of a private bucket with short expiry.
- **The hosts' instance ids are committed in `.github/ci.env`**, replacing `INSTANCE_IP`; Run Command targets instances by id. Origin: agent decision.

## Rollout

- **Setup, in order**: `terraform apply` by an admin (the CI roles, the OIDC provider, the bucket, the hosts' agent policy); confirm both hosts show as online managed nodes; run `ssm-ci-parameters.sh`; the coordinating agent, with the user's go-ahead, creates the `pr-screenshots`, `staging-hosts` and `production-hosts` environments and sets the branch rules of those and of `staging` and `production` through the GitHub API; merge. Review workflows prove out on the branch itself, staging on merge, production on the next production push. GitHub secrets stay until ALL-1965. Origin: agent proposal, user-approved as one PR.
- **The `pr-screenshots` environment** must exist before the `screenshots` label posts anything; without it, the post job's assume-role fails. Create it with deployment branches set to "Selected branches and tags" and one branch rule, `refs/pull/*/merge`: GitHub matches the rule against the run's `GITHUB_REF`, which for a `pull_request` run is the merge ref, so `main` or "Protected branches only" would block every run ([GitHub docs](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). It needs no secrets or reviewers. Origin: agent decision.
- **The `staging-hosts` and `production-hosts` environments** must exist before the deploy reaches a host; without one, its hosts role's assume-role fails. Create each with deployment branches set to "Selected branches and tags" and one branch rule: `main` for `staging-hosts`, `production` for `production-hosts`. Give each the reviewers or wait timer, if any, its `staging` or `production` counterpart has, since the host-deploy jobs no longer name those. The coordinating agent creates them through the GitHub API once the user gives the go-ahead. Origin: agent decision.
- **If `ssm-ci-parameters.sh` ran before its paths last changed**, move `PR_SCREENSHOTS_GH_TOKEN` from `/alliance/ci/review/` to `/alliance/ci/pr-screenshots/`, and `GEMINI_API_KEY`, `ANTHROPIC_API_KEY` and `SLACK_BOT_TOKEN` from `/alliance/ci/deploy/` to `/alliance/ci/visual-regression/`, deleting the old parameters. Origin: agent decision.
- **Before the deploy switches to Run Command, on the staging host**, the coordinating agent checks that `timeout`'s signals reach the script through `sudo -iu ec2-user`: `sudo -V` and `sudo -l` for whether `use_pty` is set, under which `timeout`'s SIGKILL reaches `sudo` but not the script; a command with `timeout-minutes: 1` and a script `trap '' HUP TERM; sleep 1200`, then `ps -eo pid,pgid,args` and `flock -n /run/lock/run-on-host-<job> true` to confirm the sleep doesn't outlive `timeout` with the lock free; and a command cancelled mid-script whose script keeps writing output, as `for i in $(seq 120); do echo $i; sleep 1; done; touch /tmp/done`, to confirm script and lock survive. If `use_pty` breaks it, the script runs through `runuser -l ec2-user -c` instead. Origin: agent decision, from review.
- **The one-time copy script is kept here, not in `scripts/`,** as ALL-1963 did, because a rerun would overwrite rotated values with stale ones. Values come from Infisical, which imported them from GitHub; a secret rotated in GitHub after that import would arrive stale. Origin: agent decision.
