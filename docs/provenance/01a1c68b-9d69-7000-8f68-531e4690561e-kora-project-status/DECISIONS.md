# Decisions

- **One-row table.** The status lives in a `kora_project` table with a check constraint that allows only `id = 1`. The migration inserts that row, and the service reads it with `findOneByOrFail`, so a missing row fails loudly. No existing table holds site-wide settings like this one. (agent decision)
- **Server-side Active guard.** `PUT /kora/admin/project` refuses Active with "Upload transcripts before making the project active.", the same copy the admin control shows (`KORA_ACTIVE_NEEDS_TRANSCRIPTS` in `common/src/kora.ts`). `canActivate()` returns `false` until the batch upload PR replaces it with a check for uploaded transcripts. (agent decision, implementing the user's choice in REQUIREMENTS.md)
- **Public read.** `GET /kora/project` is public, because signed-out visitors need it. It uses `@UseGuards(AuthOptionalGuard)` and `@Public()`, as `GET /kora/participants/count` on `main` does. (agent decision)
- **Confirm before every status change.** Changing the status changes what every visitor sees, so the control asks for confirmation and names the effect before saving, following the ux-guidelines item on consequential actions. The radio stays on the saved status until the change is confirmed. (agent decision)
- **Closed copy.** The thank-you heading is "Thank you for taking part". For signed-out visitors, it replaces the sign-up form, and the hero headline stays. For signed-in participants and members, it replaces the page heading, the "Reviews start" note and the reminder toggle, and the subtitle and category carousel stay. (agent decision; the message text is from REQUIREMENTS.md)
- **A failed status load blocks the project page.** If `GET /kora/project` fails after one retry, the page shows "Couldn't load the project. Reload to try again." rather than guessing a status, per the root `AGENTS.md` fail-loudly rule. (agent decision)
- **Migration hand edit.** `migration:generate` also produced statements recreating the `friend` table's generated columns `lowUserId` and `highUserId`. That's drift between this worktree's database metadata and the entities, unrelated to Kora. Those statements were removed, and `INSERT INTO "kora_project" ("id") VALUES (1)` was added. A second `migration:generate` after running the migration showed only the same `friend` drift. (agent decision)
