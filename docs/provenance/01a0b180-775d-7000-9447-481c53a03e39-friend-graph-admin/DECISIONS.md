- Modeled the new feature closely on the existing invite graph (`server/src/user/user.controller.ts`'s `list-graph`/`onetimeInvites/graphEdges` endpoints, `UserService.findOnetimeInviteEdges`, and `apps/admin/src/pages/InviteGraphPage.tsx`'s hand-rolled d3 force-directed graph), per the user's own suggestion to reuse that code.
- New edge type named `{ userAId, userBId }` (`FriendGraphEdgeDto`, `server/src/user/dto/friend-graph.dto.ts`) rather than reusing the invite graph's directional `invitingUserId`/`invitedUserId` naming, since friendship is symmetric and that naming would imply a direction that doesn't exist.
- "Restrict to members with an active contract" enforced in the backend query (`UserService.findFriendGraphEdges`, `server/src/user/user.service.ts`): both `requester` and `addressee` must satisfy `sqlUserHasActiveContractAt` for a `Friend` row to appear as an edge. This makes it a hard server-side restriction, not a client-side toggle. The node list (`/user/list-graph`, unchanged) still returns all users; the frontend filters it to `hasActiveContract === true` before building nodes, so an edge can never reference a node that wasn't rendered.
- Dropped several invite-graph-specific concepts that don't map onto an undirected friend graph: the campaign node kind and campaign fetch (no marketing attribution for friendships), the "Unattributed" hub node (exists there to keep a directed attribution tree in one connected component; friendship has no root to hang orphans off), the contract-status filter dropdown (now a hard restriction, not a toggle), and arrow markers/directional link styling. Edge dedup uses a sorted-pair key instead of the invite graph's directional `"src->tgt"` key.
- Click-to-highlight: the invite graph highlights a node's full ancestor chain and descendant subtree (a lineage). For an undirected graph that distinction doesn't exist, so clicking a node highlights just its direct friends (one hop) instead of walking a whole connected component, which could be most of the graph and make "isolate subgraph" useless.
- Kept the role/community/tag filter dropdowns and the "isolate subgraph" (renamed "isolate on click") interaction from the invite graph, since they're still useful ways to slice a member graph and weren't specific to invites.
- Route `/friends/graph` (paralleling `/invites/graph`) added to `apps/admin/src/routes.ts`. Unlike the invite graph (reached only via a link on `InvitesPage.tsx`), the user asked for a new admin-panel "extra," so this got a proper entry in the sidebar's "Extras" section (`apps/admin/src/sidebar.tsx`) with a `lucide-react` `Waypoints` icon (chosen over the already-used `Network`, which represents Clusters, to avoid a duplicate icon for a different graph).
- Regenerated `shared/client/types.gen.ts`/`shared/client/sdk.gen.ts` via `bun run gen-api` against a locally started dev server, per `apps/AGENTS.md`. The local server failed to boot beforehand on a missing `MAIL_FROM` env var; copied the placeholder value from `server/.env.example` into the gitignored, uncommitted `server/.env` to unblock this — not part of this feature's diff.
- Added e2e coverage in `server/test/users.e2e-spec.ts` ("friend graph edges (admin)"): an accepted friendship between two active-contract users appears as an edge; a friendship is excluded when the addressee lacks an active contract, when the requester does, and while it's still a pending request; a non-admin gets 401 (AdminGuard throws UnauthorizedException). Each of the query's three filters fails exactly one test when removed. Did not add a unit test file for `UserService` (no precedent exists — its constructor takes too many dependencies to mock reasonably).
- Manual browser verification (Playwright/Chrome) wasn't completed: the Claude-in-Chrome extension wasn't connected in this environment, and a manually-minted admin JWT for a direct `curl` check got a 401 from a running local dev server for reasons not fully diagnosed (the auto-mode permission classifier also began blocking further token-bearing `curl` calls as "credential materialization" mid-investigation, so this path was abandoned rather than worked around). Confidence instead comes from: `bun run typecheck` clean in both `server/` and `apps/admin/`, the full server e2e suite passing (812 passed, same as before this change, plus 2 new passing tests that exercise the new endpoint through the real `AdminGuard` path via the test harness's own token-signing helper), and the new page reusing the invite graph's already-working d3/rendering code paths nearly verbatim.
- Removed "isolate on click" per the user's follow-up request: it used to drop non-neighbor nodes/links to opacity 0 on click. `applyHighlight` now only adds blue stroke/link coloring to the selected node and its direct friends; every other node and link keeps its normal opacity regardless of selection. Opacity dimming from the role/community/tag filter dropdowns is untouched — that's a separate, still-live feature.
- Added a "Spread" range control (`spread` state, `MIN_SPREAD`/`MAX_SPREAD`/`DEFAULT_SPREAD` = 20/800/120) driving `forceManyBody().strength(-spread)`. Stored as a positive magnitude and negated at the force call so the slider reads intuitively (higher = more spread out) despite d3 charge strength being negative for repulsion. Changing it swaps the charge force on the running simulation and reheats it, so nodes move to the new layout while zoom and the selected node stay. Rebuilding the graph per slider step cost about 180ms each and reset both.
- Fixed a pre-existing bug the user hit clicking a node in the live app: the highlight effect's dependency array was `[filteredUserIds, hasActiveFilters]` only. On mount it bails early (`if (!graph) return;`) since data is still loading and `graphRef.current` is null, and it never got a reason to re-run once the graph actually finished building (that happens on `loading`/`activeUsers`/`friendEdges`/`spread` changes, none of which were in its deps) — so the `graph-selection-change` listener was never attached and clicks were dispatching an event nobody heard. Added those four to the dependency array so the highlight effect re-syncs with `graphRef.current` every time the graph is rebuilt. Also route `/friends/graph` → `/friend-graph`: the user pointed out `/invites/graph` nests under an actual `/invites` page, but there's no `/friends` page, so the invite graph's nested-route convention didn't apply here; flattened it and matched this file's hyphenated multi-word style (`/invite-feed`, `/general-updates`).
