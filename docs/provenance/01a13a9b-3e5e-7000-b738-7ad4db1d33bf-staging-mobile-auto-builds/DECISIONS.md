## Decisions

- Modeled on Bluesky's `social-app` (`bundle-deploy-eas-update.yml`, `build-submit-ios.yml`, `build-submit-android.yml`): fingerprint check on push, `eas build --local` on GitHub runners, then `eas submit --path`. It is the closest public setup that builds locally on GitHub runners rather than on EAS. Expo's `continuous-deploy-fingerprint` action has the same flow but builds on EAS cloud, which the requirements rule out.
- A separate workflow, `.github/workflows/build-staging-mobile.yaml`, triggered by `workflow_run` on Deploy completing for `main`. It isn't a job inside `deploy.yaml` because Deploy's per-environment concurrency group would make every later push to `main` queue behind a 60-minute iOS build. Its first job, `source`, reads the Deploy run's jobs and builds only when `deploy-nest-backend` concluded `success`, and fails when the run has no such job unless Deploy's concurrency group cancelled it before any job started, so a deploy that fails later (in `verify-*` or `notify`) still builds, and one cancelled before the backend shipped does not. It builds the Deploy run's `head_sha`, and names the run `Staging build of <sha>` with it, since a `workflow_run` run's own `head_sha` is `main`'s tip when the run started. It also takes `workflow_dispatch` with a platform input (`both`, `ios`, `android`); a dispatch from any ref other than `main` fails at the start, and builds `main`'s HEAD. A dispatch reads the newest Deploy run for that commit and fails unless its `deploy-nest-backend` succeeded, so a retry never ships ahead of the backend; and since Deploy runs one at a time, every older Deploy has finished by then, so none can trigger a later build of an older fingerprint over the dispatched one.
- The fingerprint comes from `APP_VARIANT=staging node scripts/fingerprint.mjs` in `apps/mobile`, after `bunx expo config --type public`. That's the hash EAS resolves during the build (it matched for the hand-made builds of `3fc25ec…` and `bf5e011…`), and the config step fails loudly where `@expo/fingerprint` would hash a config it couldn't load, as `publish-mobile-ota.yaml` does. Before submitting, the build job reads the fingerprint embedded in the artifact with `node scripts/fingerprint.mjs artifact` and fails if it differs from the planned one, so a tag never marks a runtime that wasn't built.
- Which platforms to build is a jq filter, `.github/scripts/staging-build-plan.jq`, tested in `.github/scripts/jq-filters.test.ts` like the repo's other workflow filters. It takes the requested platforms, whether the run is forced, the raw text of `fingerprint.mjs` and of each platform's newest tag, and every job of this workflow's other queued and in-progress runs, each marked by whether the commit its run builds, read from the run name, descends from this run's (GitHub's compare API), so the parsing and the choice of which jobs count as in flight are tested too, and emits the build job's matrix with each platform's runner, timeout, and artifact extension. A missing fingerprint for a requested platform is an error rather than an empty plan. The plan job reads the filter from the workflow's own commit (`github.workflow_sha`), not the deployed one: a `workflow_run` run takes its workflow file from `main`'s tip, and a Deploy that finishes after a newer push deploys an older commit, whose filter might not exist or might expect a different input. That checkout comes after the fingerprint step, so its files can't change the hash.
- The plan job fetches the `staging-build/*` tags and takes each platform's newest by creation date as the fingerprint testers run, and builds when the current fingerprint differs. Each tag is annotated and points at the commit that was built. A separate `tag` job writes it through the REST API once that platform's build job succeeded, dated with that build job's completion time, since the tag job waits for every platform, and moves an existing tag, so rebuilding an older fingerprint after a revert makes its tag the newest. That job alone has `contents: write`, and it checks out and installs nothing, so the write token never shares a runner with dependency code. Tags written with `GITHUB_TOKEN` don't trigger workflows, and no ruleset covers tags. If the tag write fails after a successful submit, the next push rebuilds and resubmits that fingerprint, which does no harm, and the failure goes to Slack.
- Superseding without starvation. `main` can see dozens of pushes a day, and builds take 30–60 minutes. A per-platform concurrency group with `cancel-in-progress: true` alone would let each same-fingerprint push cancel the running build, so nothing would ever finish. So:
  - Before building, the plan job lists the build jobs of this workflow's other queued and in-progress runs that are unfinished, or that succeeded and wait on their run's tag job, which needs every build leg. Build jobs are named `Build <platform> <fingerprint>`, so if one is already building or tagging this fingerprint, the plan leaves that platform out. If one from a newer commit is building or tagging this platform, the plan leaves it out too, even when forced, since superseding it would ship the older fingerprint over the newer one; a Deploy that finishes after a dispatch of a later `main` reaches this. If one from an older or the same commit is building a different fingerprint, the plan builds even when the current fingerprint is the newest tag, since the running build would otherwise become the newest. A forced run that leaves out a requested platform says so in a notice.
  - Otherwise its build job joins the per-platform group `staging-build-<platform>` with `cancel-in-progress: true`, which cancels only a build of a different fingerprint.
  - A re-run attempt skips the build job, and its tag job fails, which posts to Slack, naming the dispatch that retries. A re-run would build its original commit, and its build would join the concurrency group and cancel a newer build, then tag a stale fingerprint as the newest. Retrying goes through `workflow_dispatch`, which plans from `main`'s HEAD.
  - The plan sees only build jobs that exist, and a run creates its build jobs only after its plan finishes, so plan jobs share the concurrency group `staging-build-plan` without `cancel-in-progress`. A run whose backend deploy didn't succeed stops at `source` and never enters the group. Two plans running at once would each miss the other's build, and the one that finished last would win the platform's build group whichever commit is newer. GitHub keeps one pending job per group, so a third run's plan replaces a waiting one. That drops a deployed commit or a dispatch, so a cancelled plan posts to Slack.
  - Known gap: `eas submit` hands the build to EAS servers and waits, so a cancellation that lands during the Submit step still delivers the superseded build, untagged. The newer build lands after it. If the newer build fails, testers stay on the untagged build until a later run builds the current fingerprint, whose plan sees an older tag as the newest.
  - The `notify` job runs when any job failed or was cancelled. It posts for jobs that concluded `failure` or `timed_out`, and for `cancelled` jobs whose check-run annotations say the job exceeded its maximum execution time or can't be read, and for every cancelled `plan`. Other cancellations, a newer fingerprint superseding the build, post nothing.
- Runners:
  - Android on `ubuntu-latest`, with `actions/setup-java` (Temurin 17) and the runner's preinstalled Android SDK.
  - iOS on `macos-26` with its default Xcode, the image `mobile-visual-regression-ios.yaml` already uses. The CocoaPods cache follows that workflow's key scheme.
  - Both use Bun `1.3.6` and the runner's preinstalled Node. The `node` in `eas.json` applies only to EAS cloud builds, and local builds with Node 25 succeed.
- `eas-cli` is pinned to `18.5.0`, the version that made today's successful local builds. `publish-mobile-ota.yaml`'s `16.5.0` stays as it is.
- Builds use `eas build --platform <p> --profile staging --local --non-interactive --output <file>`. Signing comes from EAS remote credentials via `EXPO_TOKEN` (the existing `EXPO_ACCESS_TOKEN` repo secret), as on the developer's machine. The staging profile's `autoIncrement` gives each build a new versionCode or buildNumber.
- Submission uses `eas submit --platform <p> --profile staging --path <file> --non-interactive`. `submit.staging` in `eas.json` holds `ios.ascAppId: "6819396166"`, `android.track: "internal"`, and `android.releaseStatus: "completed"`. The fingerprint hashes `eas.json` without its staging profiles, so this changes neither variant's runtime version.
- `eas submit` reads credentials only from the submit profile, and `@expo/eas-json` expands `$VAR` in `ascApiKeyPath`, `ascApiKeyId`, `ascApiKeyIssuerId`, and `serviceAccountKeyPath`. So the profile names `$ASC_API_KEY_PATH`, `$ASC_API_KEY_ID`, `$ASC_API_ISSUER_ID`, and `$PLAY_SERVICE_ACCOUNT_KEY_PATH`, and no key ID or path is committed. A local `eas submit --profile staging` without those variables fails.
- Secrets on the `staging` environment: `ASC_API_KEY_ID`, `ASC_API_ISSUER_ID`, `ASC_API_KEY_P8_BASE64` (the `.p8` file, base64-encoded), and `PLAY_SERVICE_ACCOUNT_JSON`. The submit step writes only its platform's key file, under `$RUNNER_TEMP` with `umask 077`, and removes it with an `EXIT` trap. Hosted runners are discarded after the job, so a killed step leaves nothing behind.
- The build step pipes `eas build` output through `sed`, replacing the argument after `eas-cli-local-build-plugin@<version>` with `[redacted]`. A failed local build prints that argument, a base64 job that includes the keystore and certificate passwords, and this repository's Actions logs are public.
- Slack failure posts reuse `.github/scripts/slack.sh` (`slack_post`, `slack_commit_subject`) and `.github/actions/slack-mention` with `github.actor`, matching `deploy.yaml`'s `notify` job.
- The seed tags for the hand-uploaded builds point at `3ef960936` on `origin/main`, whose tree is identical to the commit they were built from.
