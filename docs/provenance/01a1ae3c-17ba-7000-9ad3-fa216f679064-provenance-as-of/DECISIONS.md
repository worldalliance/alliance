# Decisions

- A later task that supersedes an earlier requirement or decision names the earlier task's directory in its own entry. Rationale: an earlier file stays unchanged, so a reader determining provenance finds what superseded it only by searching for that directory name. (agent decision)
- The skill's REQUIREMENTS.md and DECISIONS.md sections scope "state" and "replace superseded ... in place" to the owning task while it is in progress, and a later agent that reconsiders a decision records its choice in its own task's files. Rationale: an agent that jumps to one section would otherwise read "current" and "replace in place" as license to edit an earlier task's files. (agent decision)
- The skill's opening tells a reader to search `docs/provenance` for a task's directory name before relying on its files, since the earlier files carry no pointer forward. (agent decision)
- `agents/README.md`, which points at the desktop app's provenance for the edits its removal reverts, also counts the removal edits recorded by later tasks naming that directory, since that task's files stop changing once it ends. No other file outside `docs/provenance/` treats provenance files as current rules (`git grep docs/provenance`). (agent decision)
- The skill's opening says an `AGENTS.md` or skill rule added or changed after a task wins over a conflicting entry of that task. Rationale: such a rule supersedes entries without naming their directory, as the newer skill did to `responses-table-view`'s icons-over-text entry per REQUIREMENTS.md, so the directory search alone misses it. "Added or changed after" rather than "current" keeps a task's explicit exception to an older, unchanged general rule standing. A later rule is itself a later task's change, which REQUIREMENTS.md lets supersede an earlier requirement, so this doesn't conflict with root `AGENTS.md`'s "a requirement later agents must keep", which binds agents acting on their own. (agent decision)
- The skill's When paragraph tests whether a task has merged by its directory being on `main`, read from `FETCH_HEAD` in the same command as the fetch. Rationale: `main` squash-merges, so the obvious test, whether the branch's commits are ancestors of `origin/main`, says a merged task is still in progress, and the directory test needs no PR or `gh`. `FETCH_HEAD` is set only by a fetch that succeeded, so a missing remote or failed fetch stops the command instead of printing `unmerged` from a stale or absent `origin/main`. (agent decision)
- `writing-for-agents`' rule that renaming a file or heading updates every reference to it excepts earlier tasks' provenance, and `.prettierignore` lists `docs/provenance`. Rationale: REQUIREMENTS.md lets a later task edit an earlier task's files only to redact, so a renamed path or a Prettier upgrade that reflows markdown must not require editing them. Ignoring the whole directory leaves a task's own provenance unformatted too, which costs nothing a reader needs. (agent decision)
- The root `AGENTS.md` "Secrets and personal information" section opens with the open-source reason, keeps REQUIREMENTS.md's "information anyone viewing the repository can already see needs none" with examples (contributors' names and handles on their commits, identifying information deliberately used for authorship, credit, or project responsibility), and says committing secrets or incidental personal information doesn't exempt them, so they still get redacted. It keeps redacting in ignored files and `.scratch/`. Rationale: read literally, "already visible" covers everything on public `main`, which would cancel the redaction exception REQUIREMENTS.md grants for earlier tasks' files and let an agent copy a leaked secret into new files; the user's answer granting that exception rules out that reading. Working files stay in scope because anything written in the repository may become public. (agent decision)
- The skill states the open-source reason for its redaction exception and points at the root `AGENTS.md` section for what it covers, rather than repeating that section's wording. Rationale: one source for the rule, so the two can't drift. (agent decision)
- The skill's When paragraph makes each PR its own task, so a plan's next PR gets its own directory even while the earlier PR is unmerged. Rationale: REQUIREMENTS.md gives a later PR of a plan its own directory; tying the new directory to the earlier PR's merge would have a stacked PR keep revising the earlier PR's files, and those edits would land on `main` after that task ended. (agent decision)
- The skill's When paragraph exempts from needing a directory only a change that redacts earlier tasks' provenance, not every change touching only `docs/provenance/`. Rationale: a later task may not edit an earlier task's files except to redact, so a provenance-only change that supersedes an earlier entry needs its own directory to record it in. (agent decision)
