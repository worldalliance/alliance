# Decisions

- Action writes go through a `written` reducer that replaces the record's value and keeps its revision and group revisions, as the notification store does. A record's revision stays the start of the load that last set it, and that load's value already holds writes made while it was in flight, so no separate touch revision is needed, unlike ALL-1935's suggested fix. Keeping the group revisions leaves `mergeOwned`'s detail-group ownership unchanged; the write patches the current value, detail fields included. Mutation responses still enter through `receive` with a fresh revision.
- ALL-1931 takes the issue's second fix: `useAction` no longer writes the relation (`markCompleted`/`markDeclined` are gone), and the detail page's `onCompleteAction`/`onOptOutAction` only reload tasks. Every form that reaches them already writes the relation with the session its submission started in: `recordCompleted` before `onCompleteAction` on web and mobile, and `optOut` before `onOptOutAction`. The detail page's write was a duplicate for members. For non-members it changed nothing: web guest mode passes a no-op `onCompleteAction`, a signed-out web completion reloads the page to `/actions/completed`, and the mobile action page runs as a member. Threading the submission's session through `onCompleteAction` would have changed five callback layers in two apps to keep a duplicate write.
