## Chat

- The message history is a `role="log"` region with an accessible name, so appended messages are announced politely. **Formal standard**: [WCAG technique ARIA23](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA23), whose Example 1 is a chat log.
- A message being streamed carries `aria-busy="true"` until done. The attribute's meaning is formal; its use for streaming is **common practice** ([MDN aria-busy](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-busy), [APG feed pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/)).
- Products render answers as Markdown and show tool calls as compact rows with a status, details one level down, and completed groups collapsed. **Common practice**: VS Code ([review agent changes](https://code.visualstudio.com/docs/agents/run/review-code-edits), [AI settings](https://code.visualstudio.com/docs/agents/reference/ai-settings)), [Cursor](https://cursor.com/docs/agent/overview), [Zed](https://zed.dev/docs/ai/agent-panel), [Claude desktop](https://code.claude.com/docs/en/desktop).
- A message sent mid-turn: [VS Code](https://code.visualstudio.com/docs/copilot/copilot-chat) steers by default, [Cursor](https://cursor.com/docs/agent/overview) and [Zed](https://zed.dev/docs/ai/agent-panel) queue, [Warp](https://docs.warp.dev/agents/local-agents/interacting-with-agents/prompt-queueing) interrupts by default, with queueing as an option, and [Claude Code](https://code.claude.com/docs/en/interactive-mode) delivers at the next tool boundary. None blocks the composer. **Common practice**, with products disagreeing.
- [Warp](https://docs.warp.dev/agents/local-agents/interacting-with-agents/prompt-queueing) pauses its prompt queue when a response errors or is stopped, and resumes it by itself after the next clean response. It names no Resume action, but a row's "Send now" and Enter on an empty input send a queued prompt at once, with no exception documented for a paused queue. It is the only product found that documents resuming. **Vendor recommendation**, for its own product.
- Specific, clickable prompt suggestions near the input help with a blank prompt. **Research-backed** (Nielsen Norman Group: [prompt suggestions](https://www.nngroup.com/articles/prompt-suggestions/), [use-case prompt suggestions](https://www.nngroup.com/articles/designing-use-case-prompt-suggestions/)); Microsoft's [HAX guideline G1](https://www.microsoft.com/en-us/haxtoolkit/library/), "make clear what the system can do", is a **vendor recommendation**.
- Review of edits after the fact, with a diff and undo, is how products with permission prompts off let users review changes. **Common practice** ([VS Code](https://code.visualstudio.com/learn/foundations/reviewing-and-controlling-agent-changes), [Zed](https://zed.dev/docs/ai/agent-panel)).

## Worktrees

- Archiving preserves uncommitted work or asks first, and only one product keeps the folder. [VS Code](https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions) commits uncommitted changes and then removes the worktree folder, [Codex](https://learn.chatgpt.com/docs/environments/git-worktrees) snapshots and then deletes its worktree, and [Claude Desktop](https://code.claude.com/docs/en/desktop) asks or keeps the folder. Codex keeps the newest 15 worktrees ([Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)) and Cursor 25 per machine ([Cursor worktrees](https://cursor.com/docs/configuration/worktrees)) when cleaning up. **Common practice**, with products disagreeing on what archive keeps.
- `git worktree remove` refuses a dirty worktree without `--force` (**vendor recommendation**: [git-worktree](https://git-scm.com/docs/git-worktree#Documentation/git-worktree.txt-remove)).
- Products that clean up worktrees automatically limit it to the ones they created ([Claude Code](https://code.claude.com/docs/en/worktrees), by a marker it writes; [VS Code](https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions), which excludes external worktrees), except [Cursor](https://cursor.com/docs/configuration/worktrees), which can delete worktrees made outside its manager. None documents what deleting a worktree does to worktrees nested under it. **Common practice**, with products disagreeing.
- Products create a task's worktree on an explicit New action ([Conductor](https://conductor.build/docs/concepts/workspaces-and-branches)) or when the first prompt is submitted ([Codex](https://learn.chatgpt.com/docs/environments/local-environment)); none found creates it while the prompt is typed. **Common practice**.
- Slow environment setup is prepared before it's needed. **Vendor recommendation**: [GitHub Codespaces prebuilds](https://docs.github.com/en/codespaces/prebuilding-your-codespaces/about-github-codespaces-prebuilds). Applying it to worktrees is agent judgement.
- Ambient in-app status interrupts less than notifications. **Research-backed**: [Iqbal and Horvitz](https://www.microsoft.com/en-us/research/publication/notifications-and-awareness-a-field-study-of-alert-usage-and-preferences/), [Iqbal and Bailey](https://interruptions.net/literature/Iqbal-CHI08.pdf) and [Mark et al.](https://ics.uci.edu/~gmark/chi08-mark.pdf) on interruption cost. Separately, in the [ParallelPilot study](https://arxiv.org/abs/2609.33113) an ambient dashboard for parallel coding agents lowered tracking effort and context switching; it doesn't compare ambient status with notifications. Apple counts only unread items in a badge (**vendor recommendation**, [Human Interface Guidelines, Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications)).

## Setup

- Each problem is shown beside its specific fix. **Common practice**: [Expo Doctor](https://docs.expo.dev/develop/tools/), [mise](https://mise.jdx.dev/cli/doctor.html), [1Password Watchtower](https://support.1password.com/watchtower/).
- On fixing, products split three ways: diagnose only ([Homebrew](https://docs.brew.sh/Manpage), [mise](https://mise.jdx.dev/cli/doctor.html)), fix after confirmation ([Claude Code `/doctor`](https://code.claude.com/docs/en/troubleshooting)), and fix without asking ([`expo install --fix`](https://docs.expo.dev/more/expo-cli/)). Each is a **vendor recommendation** for its own tool.
- A destructive repair is a separate, named action. **Vendor recommendation**: [Docker Desktop's Troubleshoot menu](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/), which also offers a diagnostics ID to hand to support.
- A check passes on its re-run, never on a remembered checkmark. **Common practice**: doctor tools that re-test every run ([`brew doctor`](https://docs.brew.sh/Manpage), [`mise doctor`](https://mise.jdx.dev/cli/doctor.html)), and fix flows that end by re-running the check ([Expo](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/)).
- Check only what the workflow needs, and postpone nonessential setup until the feature that needs it. **Vendor recommendations**: Homebrew's own guidance on `brew doctor` warnings ([manpage](https://docs.brew.sh/Manpage)); [Apple Human Interface Guidelines, Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding). Contextual help over up-front tutorials is **research-backed** (Nielsen Norman Group: [mobile app onboarding](https://www.nngroup.com/articles/mobile-app-onboarding/), [onboarding tutorials](https://www.nngroup.com/articles/onboarding-tutorials/)).
- Homebrew can't pin arbitrary versions, so brew-installed tools are checked against a range. **Vendor recommendation**: [Homebrew Bundle](https://docs.brew.sh/Brew-Bundle-and-Brewfile).
- One entry point that installs dependencies and prepares a project. **Common practice**: [GitHub's "Scripts to rule them all"](https://github.blog/engineering/engineering-principles/scripts-to-rule-them-all/) (2015).
- AWS CLI v2 separates refreshable `sso-session` configuration from legacy configuration, and keeps its token cache under `~/.aws/sso/cache`. **Vendor recommendation**: [Configuring IAM Identity Center authentication](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html).
- PostgreSQL major upgrades need a migration procedure, unlike minor ones. **Vendor recommendation**: [PostgreSQL 17, pg_upgrade](https://www.postgresql.org/docs/17/pgupgrade.html).

## Signing in to GitHub

- Native apps send authorization requests through the system browser and "MUST NOT use embedded user-agents". **Formal standard**: [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) (BCP 212), §8.12.
- The device grant is for devices without a browser or with limited input, not a replacement for browser OAuth on capable devices, and its client must display the user code; §5.4 warns of remote phishing with an emailed code. **Formal standard**: [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628), §3.3.1.
- GitHub's device codes expire after 15 minutes. **Vendor recommendation**: [Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps).
- `gh auth login --web` opens a browser flow that shows a one-time code; `--git-protocol` sets the protocol, and the token goes to the system credential store, falling back to plain text. **Vendor recommendation**: [gh auth login](https://cli.github.com/manual/gh_auth_login). When not interactive, `gh` prints the URL without waiting for Enter ([GitHub CLI source, `internal/authflow/flow.go`](https://github.com/cli/cli/blob/trunk/internal/authflow/flow.go)).
- `gh auth status` exits 1 on an auth problem in any checked account, always exits 0 with `--json`, and `--active` limits it to the active account. **Vendor recommendation**: [gh auth status](https://cli.github.com/manual/gh_auth_status).
- `gh auth switch` changes the active account for a host; `gh auth refresh --scopes` widens an existing token through the browser flow; `gh`'s minimum scopes are `repo`, `read:org` and `gist`, and adding or updating workflow files needs `workflow`. **Vendor recommendation**: [gh auth switch](https://cli.github.com/manual/gh_auth_switch), [gh auth refresh](https://cli.github.com/manual/gh_auth_refresh), [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps).
- `gh auth setup-git` makes git use `gh` as its credential helper, a separate step from API authentication. **Vendor recommendation**: [gh auth setup-git](https://cli.github.com/manual/gh_auth_setup-git), [Caching your GitHub credentials in Git](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).
- `GH_TOKEN` and `GITHUB_TOKEN` take precedence over stored credentials. **Vendor recommendation**: [gh environment](https://cli.github.com/manual/gh_help_environment).
- Desktop tools sign in with a button that opens the system browser and returns to the app. **Common practice**: [GitHub Desktop](https://docs.github.com/en/desktop/installing-and-authenticating-to-github-desktop/authenticating-to-github-in-github-desktop), [VS Code](https://code.visualstudio.com/docs/sourcecontrol/github), [Cursor](https://cursor.com/docs/integrations/github).
- A user without write access is offered a fork. **Common practice**: [GitHub Desktop](https://docs.github.com/en/desktop/adding-and-cloning-repositories/cloning-and-forking-repositories-from-github-desktop), [VS Code](https://code.visualstudio.com/docs/sourcecontrol/github); [`gh pr create`](https://cli.github.com/manual/gh_pr_create) forks automatically unless given `--head`.
- In an organization, Write is the role for contributors who push, and only repository admins and organization owners manage access. **Vendor recommendation**: [Repository roles for an organization](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization).

## Planning

- Work items are independent, valuable, small and testable, sliced vertically through the layers. **Common practice**: [INVEST](https://www.agilealliance.org/glossary/invest/), [Wake 2003](https://xp123.com/invest-in-good-stories-and-smart-tasks/), [Humanizing Work's splitting guide](https://www.humanizingwork.com/the-humanizing-work-guide-to-splitting-user-stories/).
- Build one small piece end to end, the one with the most unknowns, before refinement and visual styling. **Common practice**: Shape Up, ["Get one piece done"](https://basecamp.com/shapeup/3.2-chapter-10) and ["Show progress"](https://basecamp.com/shapeup/3.4-chapter-12).
- A reviewable change is one self-contained change with its tests. **Common practice**: [Google engineering practices, small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html). Small changes get first feedback faster, under an hour against about 5 hours for very large ones. **Research-backed**, observational: Sadowski et al., ["Modern Code Review: A Case Study at Google"](https://research.google/pubs/modern-code-review-a-case-study-at-google/), ICSE-SEIP 2018.
- An issue describes a task with a clear outcome; projects run 1–3 weeks, and sub-issues fit work too large for one issue but too small for a project. **Vendor recommendation**: [Linear Method](https://linear.app/method/write-issues-not-user-stories), [scoping projects](https://linear.app/method/scope-projects), [sub-issues](https://linear.app/docs/parent-and-sub-issues).
- Abandoned work closes in a state distinct from done. **Common practice**: Linear's canceled state ([delete and archive issues](https://linear.app/docs/delete-archive-issues)), GitHub's "not planned" ([closing an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/closing-an-issue)).
