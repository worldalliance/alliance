# Decisions

Agent decisions unless labelled otherwise. The spec's own decisions this builds on are in `01a1c8da-8f1b-7459-9652-87f613c8693c-variable-framework-spec/DECISIONS.md` ("Writing decision rows", "One validation contract for splits", "Cutoff for members still pending", "Type-to-confirm").

## Storage

- **Four tables.** `suite_split` marks a suite as split and holds the "Launch failed" state. `suite_split_version` holds immutable saves of the groups and grid as JSON, read through a zod schema, and the latest version is current. `suite_split_pin` records the split version and the formula and list versions a split reads, as of go-live. `suite_split_placement` holds each member's group, the pin it was placed against and the trace, unique per suite and member. Versions follow formulas and member lists (`01a1f4f1-c0d1-7100-ae2a-42c26b35cfee-store-named-expressions`, "Versions"), so a later edit after go-live (ALL-2178) can add a pin without migrating anything.
- **Groups as JSON, not rows.** A group's condition is an expression tree, and its cells are a short list. One JSON document per version keeps each save atomic and each version immutable, at the cost of no foreign key from a cell to its action. A cell naming an action that left the suite is ignored by readers and left out of the split the editor loads, so the next save drops it; a save naming an action not in the suite is refused with 409. Group ids come from the client; a save repeating one, or not ending in a lone "Everyone else", is refused with 400.
- **The tick stores the kind of work it was ticked for** (`optional_only` or `nothing`). It counts only while the group's work is still that kind, so changing the work clears it without the editor having to track history. The save drops a tick that no longer matches, and the split as loaded leaves one out, so an action leaving the suite lapses it too.
- **Per-row optional.** `action_cohort_decision.optional` is nullable: true or false on rows a split writes, null on every other row, whose readers keep the action's flag. It is marked `BACKCOMPAT(split-row-optional)` for removal once no suite without a split is still read.

## Deciding members

- **One decision path.** Split-suite actions go through `CohortDecisionService`, with the same triggers (launch pass, signing, catch-up), admissibility, settling and late-decision rules. Only the question "is this member in the cohort?" changes, through `DecidingCohort` (`server/src/actions/deciding-cohort.ts`): for a split action it is the member's placement and grid cell, otherwise the cohort rule. A second, parallel path would have had to repeat the contract and away rules that already work, as the spec's "Writing decision rows" decision says.
- **Go-live pinning happens in the first pass after the `member_action` time,** inside a transaction that locks the `suite_split` row. It takes the split's, and each formula's and list's, latest version saved by the event's time, of those not deleted by then, not the versions current when the pass runs. A pass reads the pin, or the launch failure, without a lock and takes the lock only to pin. This follows the requirement that the suite goes live at the event's time. There is no launch flag to hook a job onto, and a pass may run minutes late. Validation and pinning are one transaction. On failure the transaction writes "Launch failed" and its reason instead, no pin and no rows, and reports to PostHog (`split_launch_failed`, sent to Slack).
- **A member whose evaluation errors is left unplaced** and gets no rows, logged with a count and the distinct errors. The visible "couldn't decide" state, retries and per-member PostHog reports are ALL-2180. Leaving them unplaced keeps them out of "Everyone else", as the spec requires.
- **The old path can't touch split actions.** A split suite's actions keep no cohort rule and no prerequisites, so every live-cohort reader, the live-eligibility fallback included, evaluates them to nobody. The spec's "no live-eligibility fallback" and "completion limited to the row" then follow from the saved decisions alone, with no branch in those readers.

## Saves and checks

- **One check for undecided groups.** `Undecided.NeedsGroupFallback` in `common/src/expression/check.ts` refuses a condition that can be undecided when its group has no fallback picked, with a message naming the two choices. The split save, the formula save's dependents and go-live validation all use it, following the spec's "One validation contract for splits". The save drops a fallback the condition can't need, so a stored fallback always means something.
- **Only lists and formulas, for now.** Every group condition, directly or through formulas, may read only member lists and formulas, checked at split save, formula save, list delete and go-live (`outsideReads`). This is the guard the user approved for deferring the waits and captures. Since the catalog has no inputs yet, nothing trips it today; each issue that adds an input lifts it only after building its part of the deferred work.
- **Covered groups** are found structurally, never by a solver: a later group is covered by an earlier one whose condition is literally `true` (through formulas), or which is one of the conditions the later one joins with `&&`. An earlier group counts only if it can't send undecided members on, that is, it has no fallback or puts them here.
- **"Empty today" warnings** come from running the preview after the save commits, outside the lock, over members holding a contract now.
- **Formula saves check draft splits.** A split whose suite hasn't gone live, that is has no `member_action` event at or before now, is a dependent of every formula save and list delete. Deciding by the event's time rather than by the pin keeps a save between go-live and the first pass from writing a fix the pin ignores. Its id is `split:<suiteId>:<groupId>`, and the refusal names the suite, group and version, so the formula editor can show it and fix it. A fix carries the group's text and fallback plus the split version it started from, and the save writes a new split version in the same transaction, unless the fixes leave the groups as they were. Like a split save, it stores a fix's fallback only when the condition can be undecided. A fix of a group with no condition, or a second fix of one group, is refused with 400. Splits and formulas take the same advisory lock (`formulas`), since each check reads the other.
- **Converting** a suite refuses while any of its actions has its own cohort rule or prerequisites, naming those actions, rather than clearing them silently. The first version has only "Everyone else", assigned nothing, following the spec's deferred choice that a new action column starts as "Not assigned".
- **The action-wide optional flag** is written from the grid on every split save (user requirement). Editing an action's optional flag, cohort rule or prerequisites so it no longer matches its split is refused in the writing transaction, as is creating, importing or moving an action into a split suite with a cohort rule or prerequisites. An action created, imported or moved into a split suite takes the optional flag its cells imply instead, since the grid derives that flag and the admin form doesn't show it there.

## Refusals until launch is allowed

- **Launch.** `assertNoSplitLaunch` runs inside every transaction that writes action events or an action's suite: adding a suite event, editing one, scheduling a project action's release, updating an action, importing one. It refuses any state in which a split suite's action has a `member_action` event. A database-level check would be more airtight, but the event table has no suite column to check against. It and the other split guards first lock the actions' suites `FOR SHARE`, which conflicts with the suite lock convert and save take, so a writer and a concurrent convert or save can't each pass on the other's uncommitted state. The admin suite page shows why "Begin launch process" is missing.
- **Staff corrections** of one action's decision are refused on split suites, since the spec moves members between whole groups. Moves are ALL-2179.

## Readers of optional

- **The viewer's own status** treats an action as optional when the row says so (`ViewerCohort.optionalRow`), with reason `ViewerOptionalReason.SplitGroup`, since the field's contract asks a new reason for every widening of `optional`. Installed apps fold a reason they don't know into the generic "optional for you" wording, and the shared client maps `split_group` to that wording too until group-specific copy is written. `findUncompletedTasks` keeps or drops a task by its reason through a `Record`: a contract-gap task goes, as its old expression meant, and a task optional for the member's group stays for reminder groups to filter.
- **Leader and admin pills** read the row too, so a member whose group has the action as optional work shows the optional pill, not a missed deadline.
- **Reminders** that exclude optional actions read each member's rows (`loadOptionalRowMemberIds`), in recipient selection and in the reminder worker's task list.
- **Missed deadlines and suspension.** The old cohort rules' missed-deadline leaf, on both the population and single-member paths, and the suspension planner treat a member whose row is optional as unable to miss the action. The planner skips that member for the action entirely, so optional work neither misses the suite nor satisfies it. This follows the spec's streak rule: only-optional work neither gains a missed suite nor resets the streak.
- **Analytics.** `findBaseUsersForEvents` takes `requiredOnly`, which retention (when leaving out optional actions), tenure and missed-actions analytics pass. This is the one place their denominators are built, so the per-row rule has one implementation.

## Admin

- **The editor** sits on the suite page under "Groups". Groups are ordered with Move up and Move down buttons rather than drag and drop, since every action must work from the keyboard and with a single pointer (ux-guidelines). "Everyone else" stays last and can't be moved, renamed or removed. Conditions are edited as text, as formulas are; the All/Any builder is ALL-2383. A refetch replaces the groups only while they hold no unsaved edits; otherwise the editor says they were saved elsewhere and offers "Load latest", and a save is still refused with 409. A refused save's problems show only while the groups are as they were sent. A save that goes through adopts the groups as stored, unless they were edited while it ran, in which case the edits stay, now unsaved against the stored version.
- **The fallback choice is always shown,** with a note that it is needed only when a condition can have no answer. Whether it is needed is known only after the server check, and the save drops one that isn't.
- **The preview runs on demand** ("Run preview"), on the groups as edited, saved or not, and is marked out of date after an edit. This follows the spec's deferred choice on preview refresh, minus live per-member results, which need sample members the editor doesn't pick yet. It omits "pending", since nothing can wait yet.
- **`ActionSuiteDto.usesGroups`** tells the action form to hide the optional checkbox, prerequisites and participants, with a link to the suite's groups. It is loaded through a `split` relation on `ActionSuite`, and the DTO throws when that relation wasn't loaded, rather than reporting a suite as not using groups. The optional checkbox is hidden there, since the server sets it from the grid, and an update leaves the flag out, so a grid saved since the form loaded doesn't get the save refused. Prerequisites and participants stay shown while they hold a value, with a note to clear them, so an action moved into the suite isn't refused for fields the admin can't see. Clearing them on the move instead would drop the admin's rule without a word. While the suites load, the form shows none of the three, since whether the suite uses groups is still unknown.

## Refactors made along the way

- `CohortDecisionStore` took the decision-row reads and the insert out of `CohortDecisionService`, which was past its line ceiling, before the split path was added. The ceiling went from 750 to 650, and choosing between a split's groups and a cohort rule lives in `DecidingCohortService` so the service stays under it. A read-only subagent ranked splitting the service four ways first. That would have touched every caller, so it was left for separate work.
- `setPriorities` moved into `priority-order.ts` beside its sibling, so `actions.service.ts` stays under 500 lines with the split guards. It gained an e2e test, since none covered the endpoint.
- `FormulaPage.test.tsx` went past 500 lines with the `groupFixes` expectations. Following a read-only subagent's ranking, its save-outcome tests (problems a save would cause, conflicts, refused saves) moved to `FormulaPage.saveOutcomes.test.tsx`, and the fixtures and mocked API moved to `FormulaPage.testHarness.tsx`.
