- The fix comes from the review of "Leave notifications that aren't due yet unread on mark-all-read", finding `unseen-due-race`. The user asked for it to be fixed. Mark-all-read used the server's clock at request time, so a reminder that came due between loading the list and tapping "mark all as read" was marked read without being seen, and the push worker then skipped it.
- `POST /notifs/read-all` takes an optional `loadedAt` query param and marks only rows whose `sendTime` and `createdAt` are both at or before it. Without `loadedAt` it marks every due row, so older clients keep working and the server change deploys before the clients send it.
- `GET /notifs` sends the time it read the list at in an `x-notifs-loaded-at` header (exposed through CORS), for clients to send back as `loadedAt`. A header keeps the response an array, so current clients keep parsing it. The server takes the stamp from Postgres with `SELECT now()` before it queries the list, and the list's own `sendTime` filter uses that stamp, so the list and the bound share the clock `createdAt` uses, not the app host's. Every row within the bound existed and was due when the list loaded, so it was either shown or sorts below the shown page (the web dropdown loads 20), and marking it matches what the user asked for.
- A `sendTime` bound alone isn't enough: some rows are inserted with a `sendTime` already in the past (an action update's unread content takes the update's `date`, which can be days before an admin notifies; the ambassador halfway notif is backdated up to its 1h lookback), so such a row arriving after the load would be marked read. A `createdAt` bound alone isn't enough either: a reminder scheduled before the load that came due after it would be marked read. The same stamp bounds both.
- One param replaced an earlier pair, `before` (the newest loaded `sendTime`, computed by the client) and `createdBefore` (the header). The review of this commit, finding `one-bound`, showed that the header alone covers both, and that the pair left gaps: a client with an empty list had no `before` to send and marked everything, and a row the list hides (deleted content) that was due after the newest loaded row could never be cleared. The user asked for it to be fixed.
- The server caps the `sendTime` bound at now, so a client sending a future `loadedAt` can't mark reminders that aren't due yet. The `createdAt` bound is not capped: rows can't be created in the future, so a future bound marks nothing extra.
- `loadedAt` is an RFC 3339 date-time in the query, converted to a `Date` only when `isRFC3339` and strict `isISO8601` both pass, then checked with `@IsDate()`; anything else is a 400. `@Type(() => Date)` handed every string to `new Date`, which accepts `1` (2001-01-01), `March 7`, offset-less times read in the server's zone, and `2026-02-30` rolled to March 2, each returning 201 while marking little or nothing. `@IsISO8601` alone passes week dates (`2026-W39-3`) that `new Date` can't parse. The OpenAPI type is `string` with `format: "date-time"`, which is RFC 3339.
- The bound includes its whole millisecond (`sendTime < loadedAt + 1ms`, same for `createdAt`). Timestamps are stored to the microsecond but serialized to the millisecond, so an inclusive `<= loadedAt` would miss a row that falls later in the same millisecond, such as one whose `sendTime` and `createdAt` came from the column default. `GET /notifs` filters `sendTime` by the same bound, so a row due within the stamp's millisecond is both listed and marked; the review of this commit, finding `due-edge-mismatch`, showed the list's plain `< loadedAt` left such a row off the list but marked it read, and the user asked for it to be fixed.
- `createdAt` is the start of the inserting transaction, so a row from a write still in progress when the list loads carries a `createdAt` before the stamp and is marked read unseen; so is a likes notification re-armed by a write in progress, since re-arming keeps its old `createdAt`. Both need a write to overlap the list load, and each costs one notification the same fate every notification had before this change. The window lasts as long as that write: an action update's notify inserts its whole audience in one transaction, which took 46 ms for 1,000 recipients and 262 ms for 10,000 against a local database, and runs longer against a remote one. The review of this commit, finding `fanout-window`, measured it; the user asked for this wording to be fixed, not the window. The review of this commit, finding `pre-write-transaction-race`, showed that stepping the stamp back to the oldest open write through `pg_stat_activity` still missed a transaction that hadn't written yet; the user judged that machinery too much for the window and chose plain `now()`. Rows shown on the page with a `createdAt` past the stamp stay unread after mark-all.
- The OpenAPI `description` on `loadedAt` says it is inclusive to the millisecond and that the due bound is capped at now, since the generated client carries no other hint.
- The unread count counts only unread-content rows the list can show, by running them through `hydrateUnreadContentDtos`, the same filter `findAll` uses. Rows whose content is gone (a deleted forum reply, an action update deleted directly or by cascade from its action, a reply whose author was deleted) never render, so counting them left the badge above zero with nothing to tap, and one created after the list loaded stays unread through a bounded mark-all-read. Deleting those rows at each deletion path was the alternative, but content disappears through several cascades as well as service calls, and rows already orphaned would need a migration; one shared filter covers every path. The count now loads the unread rows and their content rather than a `COUNT`, which is bounded by what the user hasn't read.
- Web and mobile send the list's `x-notifs-loaded-at` header back as `loadedAt`, unchanged, so client clock skew can't shift it. When the header is missing they send no bound and read-all marks every due row, as it did before. Mobile keeps the header in the query cache beside the list, not in the screen, since a screen that mounts again over a cached list doesn't refetch it for the five-minute `staleTime`; the screen observes that cache entry so it isn't collected while the list is still shown. Once read-all returns, both refetch the list, not only the count: a row left unread otherwise shows in the badge with no row to tap, and the next mark-all resends the old stamp and leaves it unread again. Web refetches at the limit of the load it shows, so the full notifications page isn't cut to the dropdown's 20. It records that limit when a load lands, not when it starts: a direct load of the notifications page starts the page's full load and the provider's 20-row load together, and the one started last isn't the one shown. Until a load lands, the limit is the provider's first-load 20: the dropdown's mark-all button shows before any load has landed or after one failed, and refetching with no limit would put the whole history in the dropdown. The review of this commit, finding `stale-last-limit`, showed the page cut to 20 after mark-all; the user asked for it to be fixed.
- The mobile notifications screen hands the cached list to `buildNotificationRenderItems` as is, without sorting it first. The server already sorts by `sendTime || createdAt`, newest first, the builder sorts its rows by the same time, and the sort ran in place on the React Query cache. The review of "Show every listed notification on mobile, whatever the phone's clock", finding `sort-mutates-cache`, found this; the user asked for it to be fixed.
- Mobile and web show a notification's time as no later than the device's clock, through `formatNotificationTime`, so a row the server listed as due but the device's slower clock doesn't reach yet reads "less than a minute ago" instead of "in 2 minutes". The clamp sits in a notification helper, not `formatTime`, since `formatTime` also shows future event times. The review of "Show every listed notification on mobile, whatever the phone's clock", finding `future-relative-time`, found this; the user asked for it to be fixed. The review of "Show a notification due by the server's clock as just past on mobile", finding `web-uncapped-time`, found web still read "in 2 minutes"; the user asked for it to be fixed.
- The mobile notifications screen shows every row the list returns, with no filter against the phone's clock. The server already lists only rows due by its `loadedAt`, and a bounded read-all marks all of them read, so a phone clock running behind the server's would otherwise hide a row that had just come due and still mark it read. The review of the commit that sends `loadedAt`, finding `client-clock-filter`, found this; the user asked for it to be fixed.
- On web, a 20-row load is dropped, list and unread count both, when a whole list is shown while it is in flight. A direct load of the notifications page starts both, the provider's and the page's, and the 20-row one landing last cut the page to 20. The review of "Send the list's load time when marking all notifications read", finding `mount-load-race`, showed it; the user asked for it to be fixed. The whole list covers the dropped rows. Dropping the 20-row load's unread count too keeps the count from the same load as the list. A 20-row load that lands first shows until the whole list replaces it, and a whole-list load that fails drops nothing, so the page keeps the first 20 and the server's unread count rather than an empty list and a zero badge. The review of "Keep the whole notifications list when the navbar's load lands after it", finding `failed-whole-list`, found the empty list; the user asked for it to be fixed. Every `refreshNotifications` call, such as mark-all's or the dropdown's after marking a likes bucket read, loads the whole list when a whole-list load is in flight as it starts, since that load may predate the write and would otherwise drop a 20-row refresh that reflects it, and a whole list that lands after a newer one is dropped. The provider's first load skips that upgrade: the page's effect runs before the provider's, so the navbar would otherwise wait on the whole list for its first rows. The review of "Keep the whole notifications list when the navbar's load lands after it", finding `stale-whole-list`, found this for mark-all, and finding `stale-whole-wins` of a later review of the same commit found it for the other dropdown refreshes; the user asked for both to be fixed.
