- `hasTakenEffect(date, at)` and `eventInEffectAt(events, at)` in `server/src/actions/utils/action-event.ts` are the shared definition. `hasTakenEffect` takes a date rather than an event so `hasMemberActionDeadlinePassed` can use it for deadlines that come from suites and prerequisites as well as events: a deadline is the date the next event takes effect.
- `actionStatusAt` changes from `date < at` to the shared `date <= at`, so `action.status` turns over at the event's own instant. `checkActionShowsWhenEntriesArrive` no longer adds a millisecond to work around the old boundary.
- `findActionEventWindowAt` in `action-user.ts` took the first event in array order rather than the latest, so its window depended on load order. Away status now takes its window's start from the member-action event and its end from `eventInEffectAt`.
- The action stats analytics and `findParticipantIdsForActions` read `action.memberActionPhase`. They differed from it only for actions with several member-action events, which the `UQ_action_event_one_member_action` index rules out.
- The SQL in `ActionsService.findAllSorted` ordering (`e.date > NOW()` for upcoming events) already matches `[a, b)`. It is the only SQL boundary on action events and cannot share the TypeScript helper, so it stays.
- The admin's `statusAt` in `apps/admin/src/lib/homePlacement.ts` recomputes the server's `Action.status`, so it moves to `<=` with it and drops its own extra millisecond. Other client checks of the boundary are separate implementations the server cannot share, and are filed as a follow-up.
- `action-user.spec.ts` was already past 500 lines, so its `computeIsAssignedFromCohortSet` tests move to `action-user-population.spec.ts` in a preceding commit before this change adds tests to it.
