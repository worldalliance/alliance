- `apps/admin/src/lib/useGroupAssignmentAdmin.ts` owns the queue under `queryKeys.groupAssignmentMembersAdmin()`. `useGroupAssignmentMembersAdmin` reads it, and `useAssignGroupsAdmin` moves there from `useCommunitiesAdmin.ts`, since assigning is the admin write that empties the queue. `GroupAssignmentContext` and its provider go: the sidebar badge and `GroupsPage` read the query directly, as the sidebar already does for outreach responses, and `GroupAssignmentPanel` drops its `assignMembers` prop because the mutation updates the queue itself.
- A successful assignment drops the assigned members from the cached queue, which keeps the panel's immediate update. A failed assignment refetches the queue. `GroupAssignmentService.assignGroupsAdmin` refuses a batch before its first write, but it writes member by member outside a transaction, so a batch that fails part-way, or whose response is lost, can leave some members assigned. Both outcomes still refetch the communities, as before.
- The queue used to load once, when the admin app mounted, and a failed load left it silently empty. It now loads where the sidebar and `GroupsPage` render, refetches on mount and focus like the other admin queries, and `GroupsPage` shows "Unable to load members awaiting group assignment. Please try again." (or the server's refusal through `adminRefusalMessage`) when the first load fails. The provider's Storybook stub goes with it; the admin app has no Storybook.
- Adding a member to a group or moving one through `useCommunitiesAdmin` also clears that member's queue flag on the server, but those mutations don't refresh the queue, and they didn't before this change either. `GroupsPage` refetches the queue on mount, so the panel catches up when the admin returns to it.
