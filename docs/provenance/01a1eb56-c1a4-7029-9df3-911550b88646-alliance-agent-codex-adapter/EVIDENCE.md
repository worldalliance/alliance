## Research: generated protocol types, PR sequencing, Codex sign-in and trust

Question: what established practice exists for keeping a client's view of `codex app-server`'s protocol in step with the CLI, for landing a second agent backend apart from its UI, for signing GUI users in to Codex, and for writing Codex project and hook trust from a client? A research agent (Claude) answered from vendor docs and open-source code, a brainstorming agent proposed options without research, and a Codex agent gave a second opinion on both, all on 2026-11-17. No formal standard covers any of the questions.

## Measurements on Codex 0.167.0

Run on 2026-11-17 on macOS (arm64) with Codex 0.167.0 from npm (`@openai/codex`), from this repository's `desktop` worktree, through probe scripts that used the adapter's `RpcConnection`, `trustRepositoryHooks` and `codexEnvironment`, and through the capture run.

- **Trust from a worktree.** With a fresh `CODEX_HOME`, app-server logs that project hooks are disabled until the *main checkout* is trusted, and `hooks/list` for the worktree lists none. Once `projects."<main checkout>".trust_level = "trusted"` is written, `hooks/list` lists the six hooks of the main checkout's `.codex/hooks.json` (source path in the main checkout), each `untrusted` with a `key` and `currentHash`. A `config/batchWrite` upsert of `hooks.state` with each `trusted_hash` turns them `trusted` in the same process; writing project trust through `config/batchWrite` with `reloadUserConfig` also takes effect in the same process. Changing `hooks.json` makes the changed hook untrusted again until rewritten.
- **Traffic settings.** `codex app-server --strict-config` rejects an unknown `-c` key and accepts `analytics.enabled=false`, `feedback.enabled=false` and `check_for_update_on_startup=false`. Rechecked on 2026-11-18 (round 13 of the review loop) with `~/.bun/bin/codex` 0.167.0 and a `CODEX_HOME` whose `config.toml` held project trust and a `hooks.state` entry: with the three overrides it answered `initialize`, and with `-c bogus.key=1` added it exited with `unknown configuration field \`bogus\` in -c/--config override`.
- **Turns.** A turn sends `turn/started`, `item/started` and `item/completed` per item (`userMessage`, `agentMessage` with phase `commentary` or `final_answer`, `commandExecution`), `item/agentMessage/delta` per text fragment, and `turn/completed`. The trusted hooks run and report `hook/started` and `hook/completed`: `sessionStart` before the first turn, `preToolUse` before each command, `stop` after each turn.
- **Interrupt.** `turn/interrupt` answers `{}` and `turn/completed` follows with status `interrupted` and no error, within 50 ms.
- **A second `turn/start` mid-turn** answers with the running turn's id and adds its message to that turn rather than starting another.
- **Failure.** A turn with an unsupported model sends an `error` notification (`willRetry: false`) and then `turn/completed` with status `failed` and the same error message.
- **Missing thread.** `thread/resume` of an unknown id fails with `no rollout found for thread id <id>`.
- **Images.** A `localImage` input is read and answered correctly, and the thread's rollout stores the image inline as a `data:image/png;base64` URL, alongside the path in the `userMessage` item.
- **Resume.** `thread/resume` in a new app-server process continues the thread with its history.
- **Close.** Ending app-server's stdin exits it with code 0, idle or mid-turn. Mid-turn it sends no `turn/completed` and runs no `stop` hook. Either way it runs the `sessionEnd` hooks first and waits for them: with a `sessionEnd` hook sleeping 2 seconds, it exited about 2,050 ms after stdin closed, against about 50 ms with a fast hook.
- **Sign-in.** `codex login status` prints `Logged in using ChatGPT` and exits 0 when signed in through ChatGPT, and `Not logged in` and exits 1 when signed out, on stderr. With an API key saved through `codex login --with-api-key` it prints `API key configured - sk-proj-***<last five characters>` and exits 0, and `codex login` still starts the ChatGPT browser sign-in (round 11 of the review loop). `codex login` opens the browser, runs a local callback, and exits 0 on success or 1 with `Error logging in: Login cancelled`. The binary also holds the statuses `Logged in using access token`, `Logged in using personal access token` and `Logged in using workload identity` (found with `strings` by round 12's reviewer; not produced live).
- **Overlapping launches.** Each round created a fresh `CODEX_HOME` and four repositories, each with a `.codex/hooks.json`, started a session in each through four overlapping `start`s of one backend, then listed each session's hooks and read `config.toml`. With each launch setting itself up independently, 6 rounds gave 22 failures: launches exiting with `failed to initialize sqlite state runtime` while the first created the home's state, and trust lost from `config.toml`. With the backend running each launch's spawn, `initialize` and trust one at a time, 6 rounds gave none: every session started, every hook listed as trusted, and every repository was in `config.toml`.
- **Trust layouts** (2026-11-17, round 6 of the review loop). With a fresh `CODEX_HOME` per case and a repository whose `.codex/hooks.json` defines one hook, trust written for `dirname(git-common-dir)` made `hooks/list` list that hook as trusted from a plain repository, a linked worktree, a symlink to either and a subfolder. From a bare repository's worktree (`git clone --bare`, `git worktree add`) and from a submodule, Codex wanted the checkout itself trusted (its startup `configWarning` names the folder), so the written trust didn't take and `hooks/list` returned no hooks with no warning or error, the same answer as a repository without hooks. So did a linked worktree whose branch has `.codex/hooks.json` while the main checkout's branch doesn't. A submodule's git common directory is `<superproject>/.git/modules/<name>` and a bare repository's worktree's is the bare repository, so neither is named `.git`, which the trust tests confirm; trusting a submodule's own top level instead made Codex list its hook (observed by round 12's reviewer).
- **Empty hooks files** (2026-11-17, round 10 of the review loop). With a fresh `CODEX_HOME` and a new repository per case, after the adapter trusted it, `hooks/list` on `~/.bun/bin/codex` 0.167.0 returned no hooks, warnings or errors for a `.codex/hooks.json` of `{}`, `{"hooks":{}}`, `{"hooks":{"Stop":[]}}`, `{"hooks":{"Stop":[{"hooks":[]}]}}`, `{"hooks":[]}` and one defining a hook under an unknown event; with one `Stop` hook it listed that hook as trusted, and an unknown top-level key gave a `failed to parse hooks config` warning.
- **Hook counts** (2026-11-17, round 11 of the review loop). Same setup as Empty hooks files. `hooks/list` listed one hook per handler, keyed by event, group index and handler index, so two identical handlers in one group, the same handler in two groups, and two matcher groups each listed as two. A file with a `Stop` hook and a hook under an unknown event listed only the `Stop` hook, with no warning, and the adapter's trust then passed; under Claude Code's `Notification` event Codex likewise skipped the hook without a warning. A `prompt` hook was skipped with the warning `prompt hooks are not supported yet`. The repository's own `.codex/hooks.json` passed the count check.
- **Hook sources** (round 12 of the review loop, observed by its reviewer). `hooks/list` gives each hook's `source`. With a `Stop` hook in the private `CODEX_HOME`'s `hooks.json` and a repository file defining a `Stop` hook and one under an unknown event, it listed a `user` and a `project` `Stop` hook, so counting hooks of every source passed though the repository's second hook was skipped. The captures list the repository's hooks with source `project`.
- **Session folders** (2026-11-18, round 13 of the review loop, observed by its reviewer on 0.167.0). A linked worktree whose main checkout's `.git/worktrees` was deleted makes `git rev-parse --git-common-dir` fail with `fatal: not a git repository`, the message a folder outside any repository gives, so the adapter then treated it as outside a repository and Codex listed none of its hooks. A session started in a subfolder holding its own `.codex/hooks.json` listed the project hooks of both that file and the checkout's, and a hook under an unsupported event in either was skipped without a warning while the total still matched the checkout's file.
- **thread/start and config.toml** (same day). Once the checkout was trusted, `thread/start` left `config.toml` untouched (same modification time and inode, from the main checkout and from a worktree). In a folder no trust had been written for, `thread/start` with `sandbox: "danger-full-access"` wrote the folder's project trust to `config.toml` itself (observed by the round's reviewer).
- **Worktree hooks files** (2026-11-18, round 14 of the review loop, on `~/.bun/bin/codex` 0.167.0 with a fresh `CODEX_HOME` per case). From a linked worktree whose branch edited `.codex/hooks.json`, `hooks/list` listed only the main checkout's file's hooks, keyed by its path. With the main checkout defining a `Stop` hook and one under an unknown event and the worktree only the `Stop` hook, trust that counted the worktree's file passed; counting the main checkout's file failed it. The reviewer saw the same, and saw a hooks file only in the worktree listed nothing.
- **config.toml hooks** (2026-11-18, round 16 of the review loop, on `~/.bun/bin/codex` 0.167.0 with a fresh `CODEX_HOME` per case; the round's reviewer saw the first case too). A checkout whose only hooks were a hook under an unknown event in `.codex/config.toml` passed trust, and `hooks/list` then listed nothing, with no warning or error. A `Stop` hook there was listed with `source` `project` and `sourcePath` that `config.toml`. `config/read` with `includeLayers` and the folder as `cwd` returned a `project` layer, naming its `.codex` folder, whose config held each file's `hooks` table, an empty `[hooks]` included, and no `hooks` key for a `config.toml` without one, which passed trust.
- **Separate git directories** (2026-11-18, round 17 of the review loop, on `~/.bun/bin/codex` 0.167.0 with a fresh `CODEX_HOME` per case; the round's reviewer saw the first case too). For a checkout made with `git init --separate-git-dir <store>/.git <repo>`, git reports `<store>/.git` as the common directory, so the earlier rule trusted `<store>`, and `hooks/list` for `<repo>` then listed none of its `.codex/hooks.json` hooks, with no warning, while trust passed. Git run in `<store>` reports `<store>` as a work tree top, so only the session folder's own top tells it from a main checkout. From a linked worktree of that checkout, trust passed with `<store>` trusted, and `hooks/list` listed none of the worktree's own `.codex/hooks.json` hooks, as for any worktree (Worktree hooks files); the round's reviewer saw Codex key that worktree's trust by `<store>`. From a linked worktree of a plain checkout whose main checkout's `.codex/config.toml` defined a `Stop` hook and whose own `config.toml` defined none, `config/read` reported the project layer's `dotCodexFolder` as the worktree's `.codex` but its `hooks` as the main checkout's, and `hooks/list` keyed the hook by the main checkout's `config.toml`.
- **Root certificate** (same day). The 0.167.0 binary's strings list `CODEX_CA_CERTIFICATE` first in its CA lookup, before `SSL_CERT_FILE`, and its TLS error says "If you set CODEX_CA_CERTIFICATE or SSL_CERT_FILE, ensure it points to a PEM file".
- **Generated types.** `codex app-server generate-ts` writes 761 files (about 3 MB) and gives identical output on repeated runs.
