## Adapter

- **One app-server per session.** Each session runs its own `codex app-server`, as each Claude session runs its own CLI, so close and quit end one process and wait for its SessionEnd hooks, and a crash takes down one session (agent decision). The session's id is the thread id `thread/start` returns.
- **Handshake.** `initialize` (client name `alliance_agent`), `initialized`, hook trust, then `thread/start` or `thread/resume` with `approvalPolicy: "never"` and `sandbox: "danger-full-access"`. Any failure ends the process and fails `start` or `resume`, so a missing thread fails `resume` at once with Codex's `no rollout found` (EVIDENCE.md, Measurements), rather than on the next send as Claude's missing session does. A backend runs each launch's version check, spawn, `initialize` and hook trust one launch at a time, since every app-server shares the private `CODEX_HOME`: overlapping first launches race to create its sqlite state, and overlapping trust writes overwrite each other's `config.toml`, which can leave a session running with its hooks untrusted (EVIDENCE.md, Overlapping launches). `thread/start` and `thread/resume` run in that queue too, as the handshake's last step, and answer quickly; with the checkout trusted first, `thread/start` leaves `config.toml` alone (EVIDENCE.md, thread/start and config.toml). Since a later launch waits on the one ahead, the handshake must finish within 30 seconds, and trust's `git rev-parse` within the 10-second query timeout, or the launch fails naming the timeout; 30 seconds leaves room for a fresh `CODEX_HOME`'s first launch, which creates its sqlite state (agent decision). A launch whose handshake failed returns its failure without waiting for its app-server to close, since close may wait 17 seconds for one that hangs; a resume of its thread waits out that close (Live set).
- **Mapping.** `item/agentMessage/delta` becomes AssistantTextDelta, a completed `agentMessage` AssistantText, a started `commandExecution`, `fileChange`, `mcpToolCall` or `dynamicToolCall` ToolStarted, and its completion ToolFinished, and `turn/completed` ends the turn, with an Error first when its status is `failed`, or `interrupted` without the user's interrupt, such as by Codex itself, which would otherwise stop the reply unexplained (round 15 of the review loop). Commentary and final answers are both AssistantText. Other item types (reasoning, plans, web searches and the rest) and other methods map to nothing, as Claude's thinking blocks do, so a later Codex can add them. The `error` notification is ignored, since `turn/completed` repeats its message (EVIDENCE.md). Notifications about another thread, such as a subagent's, are left out, as Claude's subagent messages are. ToolStarted's names are `command`, `edit`, `<server>.<tool>` and the dynamic tool's name, for generic display (agent decision).
- **One turn at a time.** A second `turn/start` mid-turn joins the running turn (EVIDENCE.md), so `send` keeps refusing mid-turn, as `session.ts` requires; steering stays behind the requirement that both CLIs support it.
- **Interrupt.** `turn/interrupt` needs the turn id, which `turn/started` or the `turn/start` response gives, whichever arrives first. An interrupt before `turn/start` goes out, such as one in the same tick as `send`, ends the turn without sending it, so Codex never starts a turn already stopped. One after it goes out waits for the id, and each turn sends at most one, since a second could land on the next turn. Found when a replay test failed one run in three.
- **Images.** Each turn's images are written, mode 600, to a fresh folder in the system temporary folder and sent as `localImage` paths; the folder is removed when the turn ends, since the rollout keeps the image inline (EVIDENCE.md). A temporary folder rather than the app's data folder, since nothing needs the files after the turn (agent decision).
- **Requests from app-server.** With approvals off none is expected; one that comes is answered with a JSON-RPC error and reported as an Error during an uninterrupted turn, per the root `AGENTS.md` fail-loudly rule.
- **Close.** Close ends stdin, which stops a running turn, runs the SessionEnd hooks and exits (EVIDENCE.md), so there is no immediate SIGTERM as Claude's mid-turn close needs. SIGTERM follows after 15 seconds, past the repository's 3-second SessionEnd upload timeout, and SIGKILL 2 seconds later. A running turn ends with TurnEnded and no Error.
- **Live set.** The registry shared with the Claude backend (Shared code): concurrent resumes share one process, a resume waits out a closing process, and a stale handle's close changes nothing. A new session joins the set once `thread/start` has given its id, and an exit or close it reports before then takes effect once it has joined.
- **First message read.** Resolves when `turn/start` answers, which is when Codex has accepted the message into the thread.

## Environment and version

- `codexEnvironment` drops every variable starting with `CODEX` or `OPENAI_`, Codex's own namespaces for credentials, endpoints, its home and a parent session's markers, but `CODEX_CA_CERTIFICATE`, the custom root certificate Codex trusts ahead of `SSL_CERT_FILE`, which a TLS-intercepting proxy needs (EVIDENCE.md, Root certificate; round 14 of the review loop), plus, per the desktop-app task's Credentials decision, every `ANTHROPIC_` variable, Anthropic's namespace for credentials such as `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`, dropped by prefix as `claudeEnvironment` does so a credential the list missed can't pass (round 15 of the review loop), and `CLAUDE_CODE_OAUTH_TOKEN`, then sets `CODEX_HOME`, the same namespace approach and rationale as `claudeEnvironment` (agent decision).
- Every Codex command but `codex --version` runs with `-c analytics.enabled=false -c feedback.enabled=false -c check_for_update_on_startup=false`, the settings the desktop-app task's "Agent processes" section names, confirmed on 0.167.0 (EVIDENCE.md). app-server runs with `--strict-config`, so a later version that no longer knows one of these keys fails every launch rather than quietly sending what the key turned off; `codex login` refuses the flag, so sign-in relies on the sessions failing first (agent decision, round 13 of the review loop). Passing them as overrides rather than writing them to the private `config.toml` keeps that file to the trust the adapter writes (agent decision).
- Each Codex run and app-server launch first creates `CODEX_HOME`, mode 700 since it holds the sign-in, because Codex 0.167.0 refuses every command but `--version` when the folder is missing, as on a fresh install (verified against the real binary). Creating it where Codex runs, rather than where the app builds the `CodexCli`, leaves no caller to remember it (agent decision).
- `CODEX_VERSION` is 0.167.0, the installed version the captures came from; each backend checks `codex --version` before its first launch and refuses any other version, as Claude's does.
- The development `CODEX_HOME` is `Alliance agent (dev)/codex` in Electron's appData, beside the Claude config folder.

## Sign-in

`signInToCodex` runs `codex login` and `isSignedInToCodex` reads `codex login status`, through the same runner as Claude's sign-in. Only `Logged in using ChatGPT` counts as signed in, since each employee uses their own subscription. Any other credential counts as signed out, `API key configured` or another `Logged in using` mode such as an access token, so the app offers the ChatGPT sign-in, which `codex login` starts even with a key configured (EVIDENCE.md, Sign-in; for the other modes assumed, not tried), rather than failing with output that quotes part of the key (agent decision, rounds 11 and 12 of the review loop); any other status fails with the output. When the browser can't open, `codex login` prints a URL or device code that the app doesn't relay until the CLI exits, the gap Claude's sign-in has (ALL-2112).

## Hook trust

Before each session, `trustRepositoryHooks` finds the main checkout through `git rev-parse --git-common-dir`, upserts its project trust, lists the hooks Codex then finds, failing the launch when Codex reports any problem with them, such as a hooks file it couldn't read or a hook type it doesn't support (it then leaves out what it couldn't load, so the session would run without it; failing tells whoever changed the hooks file why, per the root `AGENTS.md` fail-loudly rule, agent decision), upserts the hash of each not yet trusted or managed, and lists again, failing the launch, naming the hooks, unless every hook that listing holds is trusted or managed, one the first listing lacked included (round 15 of the review loop). This follows OpenAI's TUI and codex-acp (EVIDENCE.md). The session's folder must be the top of the main checkout or of a linked worktree of it, which is where the app starts sessions, since the desktop-app task starts each in a worktree. The main checkout is confirmed rather than other layouts refused: it is the parent of git's common directory, which must be its `.git`, and git run there must report that folder as its top, which a main checkout whose `core.worktree` points elsewhere doesn't (round 18 of the review loop; git run in a folder holding a `.git` directory reports that directory as its git directory, so that isn't checked); anything else fails the launch before any trust is written (agent decision, round 17 of the review loop, after a `--separate-git-dir` checkout passed the earlier rule). That replaces the cases rounds 6, 12, 13 and 17 of the review loop each found another of: a folder outside any repository, and a worktree whose main checkout was moved or pruned, fail because git does, rather than starting with no hooks; a subfolder fails, since Codex also runs the hooks of each `.codex` folder between the checkout's top and the session's folder, which could hide a hook it skipped from the count below; and a submodule, a bare repository's worktree, and a checkout made with `git init --separate-git-dir` fail, since Codex keys their trust by a folder other than their git directory's parent, so the trust wouldn't take (EVIDENCE.md, Trust layouts, Session folders and Separate git directories). A linked worktree of a `--separate-git-dir` checkout passes: git takes the separate directory's parent for its main checkout, and Codex keys the worktree's trust by it, so the trust and the count use that folder and its hooks file, and the worktree's own file isn't counted, as for any worktree. The launch fails too when Codex lists fewer project hooks than the main checkout's `.codex/hooks.json` defines, naming both counts, or when the app can't read that file as event groups of hooks, which fails loudly rather than pass. Only hooks whose `source` is `project` count, since the user's, managed and plugin hooks Codex also lists would hide a skipped one (EVIDENCE.md, Hook sources). That file is the one Codex runs in every worktree, as the Hook trust requirement says, so a worktree's own `.codex/hooks.json` isn't counted: counting it compared Codex's listing of one file with another file's hooks, which let a skipped hook in the main checkout's file pass (round 14 of the review loop; EVIDENCE.md, Worktree hooks files). Codex leaves out without a warning a hook under an event it doesn't support, such as Claude Code's `Notification` (EVIDENCE.md, Hook counts), which the count catches. It does the same in a project's `.codex/config.toml`, which Codex also reads hooks from, so the launch fails, naming the main checkout's `config.toml`, which a worktree's project layer holds too (round 17), when `config/read` shows a project `config.toml` defining a `hooks` table, an empty one included, rather than counting a second format: the requirement and this repository use `.codex/hooks.json` (round 16 of the review loop; EVIDENCE.md, config.toml hooks; agent decision). Comparing counts replaces separate rules for each case, which rounds 2, 3, 6, 10 and 11 of the review loop each found missing one (agent decision, round 11): a hooks file defining none, such as `{}` or an event whose group lists no hooks, passes, since its count is 0 (EVIDENCE.md, Empty hooks files). The `git` call drops inherited `GIT_*` variables through `gitEnvironment`, since one set by a git hook or rebase would answer for another repository; a test run under `git rebase --exec` showed the same leak in the test's own setup, which then wrote to the repository running it, so the tests' `git` calls use it too. Trust is upserted through `config/batchWrite`, so the app writes no TOML itself.

## Generated protocol types

The user deferred this. `scripts/codex-protocol.ts generate` runs `bunx @openai/codex@<CODEX_VERSION> app-server generate-ts`, renames each file to `*.gen.ts`, which the max-lines lint and Prettier skip, rewrites relative imports to match, and replaces `codex/protocol/`. `check` regenerates and fails on any difference; the desktop CI workflow runs it, which is the real-path-first task's schema comparison. Every request the adapter sends is checked against its generated params type with `satisfies`. The adapter validates with zod only the messages it reads, and a `Fits` type check makes the build fail when a generated type stops being assignable to its schema's input type, as a version bump that changes a read field would (agent decision, following the committed-and-checked practice in EVIDENCE.md); `fits.test.ts` typechecks, with bun's `expectTypeOf` rather than hand-written helpers (round 16 of the review loop), that it gives exactly `false` for each drift it lists, a union with one drifted member included, and for `never`, which an `Extract` of a variant a Codex version dropped gives (round 15 of the review loop). That check proves assignability to the schema's input type, not runtime acceptance: refinements, a strict object's rejection of unknown keys and a schema whose input is unknown don't constrain it, so the replay tests cover the captured shapes.
