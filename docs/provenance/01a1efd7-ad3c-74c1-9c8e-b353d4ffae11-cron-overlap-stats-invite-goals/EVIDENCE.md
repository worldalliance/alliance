# Evidence

## Research: at-most-once inserts, guarded upserts and testing races

Done by a research subagent and checked by a codex second opinion, 2026-11-18. Labels follow root `AGENTS.md` **Established practice**.

- **Transaction-scoped advisory locks.** `pg_advisory_xact_lock` is released at the end of the transaction, and the application must use advisory locks consistently, since the system does not enforce them. [PostgreSQL: explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS) (vendor documentation). PgBouncer's transaction pooling lists session-level advisory locks as unsupported; a transaction-scoped lock doesn't outlive its transaction. [PgBouncer features](https://www.pgbouncer.org/features.html) (vendor documentation).
- **Unique index plus `ON CONFLICT DO NOTHING`.** At Read Committed, an insert may not proceed because of another transaction's not-yet-visible row, so two overlapping inserts can't both land. `CREATE UNIQUE INDEX` fails while duplicates exist. [PostgreSQL: transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [INSERT](https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT), [CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html) (vendor documentation).
- **Conditional claim.** A blocked `UPDATE … WHERE claimed IS NULL` re-checks its condition against the committed row at Read Committed, so it suits rows that already exist. [PostgreSQL: transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (vendor documentation).
- **Guarded upsert.** `ON CONFLICT DO UPDATE` gives an atomic insert-or-update outcome under concurrency, and its `WHERE` leaves a conflicting row unchanged when false. [PostgreSQL: INSERT](https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT) (vendor documentation).
- **TypeORM 0.3.28.** `EntityManager.upsert`, which `Repository.upsert` calls, passes on only `skipUpdateIfNoValuesChanged`, `indexPredicate` and `upsertType`, dropping `overwriteCondition`; `InsertQueryBuilder.orUpdate` carries it. Checked in the installed source, `node_modules/typeorm/entity-manager/EntityManager.js`. [TypeORM insert query builder](https://typeorm.io/docs/query-builder/insert-query-builder/) (vendor documentation).
- **Testing races.** Hold both actors at the race window with a test barrier, release them together, and check the test fails without the fix; `Promise.all` or sleeps alone are flaky. [lirbank: Harnessing Postgres race conditions](https://www.lirbank.com/harnessing-postgres-race-conditions), [Doppler: Reliably testing race conditions](https://doppler.com/blog/reliably-testing-race-conditions) (common practice). PostgreSQL's own isolation tester runs sessions through fixed step orders. [isolation README](https://github.com/postgres/postgres/blob/master/src/test/isolation/README) (vendor reference practice).

## Measurements

- **TypeORM omits generated columns from inserts that name no columns.** `InsertQueryBuilder.getInsertedColumns` (TypeORM 0.3.28, `node_modules/typeorm/query-builder/InsertQueryBuilder.js:448-472`) returns the columns passed to `into(target, columns)` when there are any; otherwise it skips a column with `generationStrategy === "increment"` on Postgres, whatever value the row carries. The per-action ordering test, run against a query-builder upsert with `overwriteCondition` and no column list, failed: the older run's insert took a fresh, larger number and overwrote the newer run's row. With the column list it passes. Bun 1.4.4, PostgreSQL 18.3 test database, 2026-11-18.
