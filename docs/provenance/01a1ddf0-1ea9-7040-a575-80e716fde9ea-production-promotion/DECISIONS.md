# Decisions

Decisions carried from `docs/provenance/01a1ce4b-16f7-713d-9845-fe08e3ffa147-ci-deploy-speed/DECISIONS.md` and implemented here: the freeze check checks out the deployed commit by SHA before any deploy job. That task's entries on waiting for staging, refusals, the override and the reconcile step are superseded by REQUIREMENTS.md "Any push to production deploys".

## Shape

- **The checks and builds moved from `deploy.yaml` into `deploy-checks.yaml`.** Staging, and a production push that builds itself, call it, and its `passed` job is the one place the checks-and-builds part of the required list is defined. This also advances ALL-2012's split of `deploy.yaml`. Its `dirty-check` always runs in `exists` mode: production's `empty` check moved into the deploy. Origin: agent decision.
- **`deployed-config` and `upload-react-sourcemaps` moved into `deploy-environment.yaml`.** A promoted deploy uploads the staging run's source maps, which `deploy-environment.yaml` selects by id as it does the builds, and a deploy the guard skips uploads nothing. They run under the lock. The guard waits for `deployed-config`, so a config failure deploys nothing and opens no record, as when `deploy` needed it; that adds its run, about a `bun install`, to every deploy. The source map upload waits for the guard and runs alongside the deploys. A hung job would otherwise hold the lock, so `deployed-config` times out after 10 minutes and the upload after 15. Every step of the upload continues on error, not the job, and each step has a timeout, 13 minutes together, within the job's 15: GitHub doesn't document whether a failed job inside a called workflow fails the calling job, which would make Deploy alert on a deploy that succeeded. A failed upload shows as an annotation on the run. This supersedes the deploy-lock task's decision that `deploy.yaml` keeps them. Origin: agent decision.
- **`deploy-environment.yaml` downloads another run's artifacts by the ids its caller passes, not by name.** A name reads the newest artifact of that name, which a re-run of the other run after its ids were checked may have replaced; by id, a replaced artifact fails the download. Origin: agent decision.
- **A deploy's details go in its deployment record's payload.** The record already belongs to the deploy, so the details stay with it without another store. Origin: agent decision implementing "records the artifact IDs".
- **One `deploy` job in `deploy.yaml` serves staging and both kinds of production push.** It needs `checks` and `promote`, and deploys once the checks passed or promotion named a staging run. Origin: agent decision.
- **The required list lives in `promote.sh` as `checks / passed` plus the three deploys and three smoke checks.** `passed`, the gate job in `deploy-checks.yaml`, needs every check and build, so its `needs` list is the single definition of the checks-and-builds part, and the staging deploy gates on the same workflow. The deploys and smoke checks are the jobs `deploy-environment.yaml`'s `record` needs, which already decide a deploy's success; `promote-contract.test.ts` fails when the list and those jobs, by the names the jobs API reports, differ. Origin: agent decision implementing "the list is defined once".
- **A promotion's details are its staging run and the ids of the artifacts it deploys**, recorded in the deployment's payload and the run summary, and the deploy downloads those ids. A run that lists a name twice builds in the production run, since failing would fail every re-run the same way: artifact ids don't follow upload order (a re-run's earlier upload was seen with the higher id), so nothing tells which copy a download by name reads, and re-runs seen so far list each name once. A deploy that builds itself records no details. Origin: agent decision implementing "records the artifact IDs".
- **Promotion requires the frontend and admin builds but not the `react-assets` source maps.** Their upload is best-effort (`continue-on-error`), as is their upload to PostHog, which fails without them; requiring them would let a failed best-effort upload block reuse. Origin: agent decision.
- **A production push builds itself whenever promotion finds nothing to reuse:** no staging run, one that isn't fully green, or a fully green one lacking an unexpired frontend or admin build. REQUIREMENTS.md names the first two; the user's "with unexpired artifacts" leaves the third, and building beats refusing a push the requirements say deploys. Origin: agent decision.
- **Building production's own artifacts departs from build once, promote everywhere,** which is vendor and common practice (EVIDENCE.md, "Build once and promote"). The user chose it for speed, the project's goal, after the measurements in EVIDENCE.md, "Production pushes during staging": waiting for a staging run in progress costs up to about 12 minutes against about 9 for building. A self-built deploy still runs every check before deploying. Origin: user requirement; this entry records the departure.
- **Only a definite "nothing to reuse" builds; a promotion that can't tell fails.** Each API read gets three tries, 10 and 20 seconds apart, as the deploy's `record` step does, so a one-off 5xx doesn't hold up a deploy. An error that outlasts them fails the `promote` job, which skips `checks` and `deploy`, and Deploy alerts. `checks` runs on production only when `promote` succeeded without naming a run. Deploy's alert fires whenever `deploy` didn't succeed, with no exception for promotion: superseding is the guard's call under the lock, where a skip succeeds, so a self-built run whose checks failed can't read as superseded. Origin: agent decision, from a Codex second opinion that the earlier exception for a promotion without a run would hide a failed fallback.
- **Promotion leaves the freeze and superseding to `deploy-environment.yaml`.** Its `deployed-config` job checks the freeze and its guard job superseding, under the lock for promoted and self-built deploys alike, so a frozen or superseded commit that builds itself spends its checks before the deploy stops or skips it. Hosted runners cost this public repository nothing (EVIDENCE.md, "Waiting for staging versus building"), and one check in one place can't disagree with another. Origin: agent decision.

## Rollout

- **This PR leaves the CI environments' settings, such as `production-hosts`' deployment branch rule, manual; ALL-2294 moves the five CI environments into `terraform/`.** The user chose to manage them with the GitHub provider, branch rules derived from `local.ci_roles[*].trust`, applied by hand and never from CI, as separate work, so that choice is ALL-2294's requirement rather than this PR's. Never from CI because environment and branch-policy writes need repository Administration write, which `GITHUB_TOKEN` can't be granted. Origin: user choice, asked in review.
- **Production pushes build themselves until a commit has a staging run of the new pipeline.** Staging runs from before it name the gate `checks`, not `checks / passed`, so promotion finds them not fully green. The merge commit's own staging run qualifies. Origin: agent decision.
- **Nothing runs the new workflows before merge.** Local checks cover syntax (actionlint, shellcheck) and the guard's and promotion check's decisions (unit tests with a stand-in `gh`). Origin: agent decision, as in the deploy-lock task.
