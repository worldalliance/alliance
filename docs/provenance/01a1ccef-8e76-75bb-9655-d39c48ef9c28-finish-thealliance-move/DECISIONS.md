# Decisions

- Members who haven't opted in are signed out by the cutover, because session cookies are host-only. They see a notice on arrival instead of a cross-domain session handoff. The user deferred how this is done. The notice needs no new auth code, matches what the 163 opted-in accounts already went through, and with about 200 actual users affects few people. Drop it for a one-time token handoff if the sign-outs cause real friction. (agent decision)
- Notice copy: title "We've moved to thealliance.org", body "Sign in again to continue. Your account hasn't changed. If you sign in with a password, your browser may not fill in one it saved for worldalliance.org." The body covers members who sign in with Google or Apple and have no password. It shows on the sign-in screen, only to a visitor who arrived through the legacy redirect, marked by a query parameter nginx adds and the app strips on load and keeps in `sessionStorage`, so the sign-in screen shows it whenever the member reaches it in that tab, whichever page they landed on. Signup and the public pages show none: invite links and outside links bring people with no account there, whom "Sign in again" would mislead. A signed-out member is not always sent to sign-in: an action page or the landing page at `/` leaves them where they are until they choose to sign in (`EVIDENCE.md`, code paths), which is why the marker outlives the first page. Referer can't mark it, since a redirect keeps the referrer of the original navigation (`EVIDENCE.md`, outside sources). (agent decision)
- Everyone moves as soon as the production cutover deploys, and the opt-in modal is removed in the same change. The user deferred the date. The November 2 date in the modal had passed, and opt-ins had fallen to about one a week (`EVIDENCE.md`, opt-in counts), so waiting longer would move few people. (agent decision)
- The `302` redirects become `301` two weeks after the production cutover deploys with no rollback. The user deferred the timing and asked for it to be an issue. Two weeks catches a broken flow while a revert is cheap, since browsers may cache a `301` (`EVIDENCE.md`, outside sources). (agent decision)
- Each environment's cutover makes thealliance.org its `DOMAIN_NAME` and keeps worldalliance.org as the legacy domain, rather than swapping the two values alone. nginx's redirects, the admin vhost's included, and the server's link building all depend on which is primary, so swapping only the values would reverse them (`EVIDENCE.md`, code paths). (agent decision)
- Staging's cutover builds the mechanism and turns it on for staging; production's cutover turns it on for production and removes the opt-in modal. The modal is code shared by both environments, so removing it with staging would drop it from production before production moves. (agent decision)
- TLS certificate lineages named for the thealliance.org hosts, the app's and `admin.`'s on each server, are a manual prerequisite of both cutovers, with DNS and OAuth callback registrations, because both nginx vhosts name their certificates after `DOMAIN_NAME` and a missing lineage fails the frontend deploy's `nginx -t` and every reload after it (`EVIDENCE.md`, code paths). (agent decision)
- Stored-link inventory is its own issue before the ratchet, since which columns hold authored links in production decides which writes to normalize and what the migration rewrites. Form snapshots record what a member saw, so the inventory decides whether they count as authored content. (agent decision)
- Removing `switchedDomainAt` waits for the removal of the legacy-host sign-in block, the only server logic that reads it. Dropping it from response DTOs needs no client release. The web app's other reader, `DomainMigrationModal`, goes with the production cutover. The mobile app, the only installed client, reads it only as a presence flag for form conditions, which it evaluates with a default that reads a missing key as unset; it also receives the timestamp on `UserDto` without reading it, and the generated client doesn't validate responses, and once saved form conditions are migrated off it none refers to it (`EVIDENCE.md`, code paths). The migration covers every stored form schema, form snapshots included, not only live forms: removing the enum member makes an element whose condition names it fail to parse, and readers of a snapshot then drop that question or read it by its current definition (`EVIDENCE.md`, code paths). The contract issue confirms both. (agent decision)
- The `switchedDomainAt` ratchet blocks new conditions on the server as well as dropping the property from the admin form builder: the server rejects a form save that adds a `SwitchedDomainAt` condition the form's current snapshot doesn't have. Otherwise a stale admin tab or a direct API call could add one after the migration, since the server parses any `UserValueProperty` (`EVIDENCE.md`, code paths). Forms that already have one stay editable until the migration. (agent decision)
- After the cutover the legacy hosts keep answering `/api`, `/events`, `/socket.io/` and `/.well-known/` instead of redirecting them. The user deferred which paths keep answering (how the cutover treats them, not whether it happens). Installed apps call the API and events there and open their websocket-only messaging socket there (`EVIDENCE.md`, code paths), so answering keeps them working without depending on how each client handles a redirect, and Apple fetches each host's association file without following redirects (`EVIDENCE.md`, outside sources). `/api`, `/events` and `/socket.io/` stop answering together, once no traffic comes from older builds. (agent decision)
- Legacy `/.well-known/` serving and the worldalliance.org entries in the app's associated domains are removed together after the legacy API, once no older builds call it. After that, a worldalliance.org link opens in the browser, which redirects, instead of the app. (agent decision, following the approved removal of the legacy `/.well-known/` exception)
- The existing ALL-2110 ("move metrics over to thealliance") joins the project instead of being duplicated. (agent decision)
- ALL-1892 ("Complete the migration from worldalliance.org to thealliance.org"), the older umbrella issue whose ordered list the project's issues and blocking relations supersede, sits outside the project, open and related to each of the project's issues. Inside the project it looked like an unblocked step with no PR of its own. A person filed it, so it is left for them to close. (agent decision)
- The cutover's catch-all `302` replaces the invite redirect, which is a `301` today (`EVIDENCE.md`, code paths). That `301` already points at the domain that becomes primary, so the browsers that cached it need nothing. (agent decision)
- Legacy `/api` stops answering only after the Twilio and Mailgun webhooks have moved off it, as well as the mobile app. Until then they post to worldalliance.org, and their inbound messages and mail events would be lost. (agent decision)
- The Twilio check drops the worldalliance.org URL only after the production cutover as well as the console change. Dropping it returns the check to the single URL derived from `APP_URL` (`twilioWebhookUrl()`), which is worldalliance.org until each environment's cutover, so returning to it earlier would reject every MMS Twilio signs for thealliance.org once the console points there. (agent decision)
- ALL-2110 ("move metrics over to thealliance") has no description. Web analytics already follow the domain the app is served from (`apps/frontend/src/lib/config.ts`), and ALL-2142 moves the mobile analytics host, so the code side is covered. The graph keeps ALL-2110 for what lives in PostHog: dashboards, insights and authorized URLs that filter on or point at worldalliance.org, checked once both web and mobile send events from thealliance.org. It stays open, so its creator can correct this reading. (agent decision)
- The local `server/.env` `SMTP_USER` contains the legacy domain. It's a login, not the sender (`MAIL_FROM` already uses thealliance.org), so no issue covers it. (agent decision)
