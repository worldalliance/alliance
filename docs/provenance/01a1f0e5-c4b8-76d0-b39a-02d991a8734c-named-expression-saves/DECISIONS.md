# Decisions

All entries are agent decisions. Spec references are to `docs/provenance/01a1c8da-8f1b-7459-9652-87f613c8693c-variable-framework-spec`.

## API

- **One call for a save.** `checkNamedSave` in `common/src/expression/named.ts` takes the stored named expressions, the dependents outside them, the named expressions saved and the ids deleted, and returns the saved expressions and fixed dependents as trees, so callers store what was checked without rebuilding the save's scope, or every problem. Saving fixed named dependents together is passing them in the same `save`, so the save is checked as a whole, as the requirement for fixed dependents in one save asks. ALL-2195 names this function as what its save and delete go through.
- **Dependents are opaque to the core.** A `Dependent` is an id, a source and the `ResultRule` its consumer checks it under, such as a split group's `Undecided.Allowed` or a form condition's `NeedsFallback`. Splits (ALL-2177) and forms (ALL-2184) supply their own, and own the checks that need suites or forms, such as same-suite reads, cross-suite cycles and the group-fix capture. Each dependent says whether it is `stored` or `fixed` in this save, rather than the core inferring it from its source, since the visual builder edits fixes as trees. A stored dependent is passed as its tree. A fixed one is passed as the admin's text, parsed against the save's scope like a saved named expression, or as the builder's tree: its consumer can't parse text reading a name the save introduces or renames, and text's diagnostics are then located in what the admin typed.
- **Saved text or trees.** A saved named expression may be the admin's text, so its own problems are located in what the admin typed, as `checkExpression` does for text. The parser reads only names from the scope, so text is parsed against the saved names before any saved tree exists. Each problem with diagnostics carries the text they are located in: the admin's, or the tree printed with the names as they are after the save, since a save can rename what an unchanged reader reads and its stored text would then no longer fit. A reference to a named expression the save deletes prints with the name it had, which `checkExpression` takes as `deletedNames`, so the admin reads the name they deleted rather than its id; wherever the scope's name rule (`nameRuleBreak`) rejects that name beside the scope's names and the function parameters around the reference, such as one the same save renames another named expression to, the reference prints as its id, since the name would read as something else. `checkNamedSave` prints with `printNames`, the rule `checkExpression` prints with, rather than a copy that could drift from the spans.
- **Names typed by an admin get messages, not throws.** `checkScope` throws for a bad or clashing name, which is right for engineer-defined inputs and functions; a saved name is admin input, so `checkNamedSave` reports it first, through the scope check's own `nameRuleBreak`, saying what already uses the name. One rule function and one list of the scope's names (`scopeNames`) serve both, with the `__` prefix rule `checkExpression` once checked apart folded in, so the admin is never told a name is fine that the scope check then rejects.

## Checking

- **Saved expressions first, then dependents.** Each saved expression is checked on its own, as a named expression with no result type and undecided allowed, the rule its readers rely on. Dependents are checked only once every saved expression passes, so the admin fixes the save before seeing what it breaks, and a saved expression's problem is never shown in another's printed text.
- **One problem, at its cause.** A diagnostic `checkExpression` places in a named expression is listed under that named expression, not under the expression being checked, and repeats are dropped, so a dependent failing only through a named expression it reads isn't listed. Each loop is listed at the named expressions on it, each found by whether it reaches itself, not at the saved, stored or fixed expressions reading into it: one of those reaching a loop it isn't on is checked through the stored expressions on that loop, unless a saved one is on it, since the saved ones on it are checked anyway, and every other expression is still checked. One on a loop is checked with the loops it only reads into cut out, so it is told its own loop, and those loops are checked through their stored members as for any other. This applies the spec's "one error at its cause" requirement across a save.
- **Which dependents are checked.** Every fixed dependent, since it is saved with the save, and every stored named expression and stored dependent that reads a saved or deleted id, directly or through other named expressions (`reads`). A stored one reading nothing changed can't be broken by the save, so it isn't checked. A checked dependent that was already broken, such as by an input change before ALL-2195's re-check exists, is listed too, and so is an already broken named expression a checked one reads, though it isn't checked itself: the checked one can't be checked while what it reads is broken, the save can't be told apart from its cause without checking every dependent twice, and the admin can fix it in the same save.
- **Needless fallbacks left out where they arise.** `checkExpression` takes which expressions are stored, and the analysis doesn't report a needless fallback in those, rather than `checkNamedSave` filtering the diagnostics after: `checkExpression` stops checking a reader once a named expression it reads has a diagnostic, so a filtered one would still hide its readers' real problems. A fallback an `isUnknown` guard makes needless is left out too: the requirement's "A fallback a save makes needless doesn't block it" covers it, as a save that makes a named expression known can make a stored expression's guarded fallback needless.
- **Cost.** Each checked expression builds its own `tsc` program, so a save costs one check per affected expression. Nothing stores expressions yet; if saves with many dependents prove slow, checking them in one program is the next step.
