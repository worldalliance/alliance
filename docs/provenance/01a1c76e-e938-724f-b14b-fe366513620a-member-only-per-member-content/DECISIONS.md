# Decisions

- The approach follows Linear ALL-2114's proposed fix, which the user handed over as the task without approving point by point (forwarded source, agent decision): the server narrows each `manualPerUser` block's `manualUserContent` to the one member's entry, or drops it when there is no member, in `memberSchema` (`common/src/forms/row-list.ts`), which every member-facing schema already goes through. Admin paths (`adminForm`, create and update) keep the full map, since the builder's preview switches between members.
- Narrowing keeps a one-entry map instead of merging the entry into the block (agent decision). Installed web and mobile clients already read `manualUserContent[activeUserKey]`, so they render the same content with no client change, and the shape stays valid against `formSchema`.
- Whose entry each path keeps (agent decision):
  - `GET /tasks/slug/:id`: the signed-in member; none for a guest.
  - A response (`FormResponseDto`): its respondent, since the member's own completed-form view renders the response's snapshot with their key. A guest's response keeps none. A guest draft linked to a member keeps the member's, as they are the one continuing it. The admin response endpoints also keep the respondent's, which is no more than the respondent's own content.
  - Response history: the member whose history it is.
  - `FormResponseOutputDto` in the activity feed: none, since other members read it and output views never apply per-member content (only form pages call `resolveDisplayBlockForUser`).
- A legacy client that submits the schema it was served instead of `formSnapshotId` now echoes the narrowed schema, so `resolveSubmissionSnapshot` also matches the hash of the snapshot as served to that member (`memberSnapshot`), alongside the stored one (agent decision). `snapshotForRow` became `memberSnapshot`, taking the member's row and id together. When the echo is of an earlier version, because the form changed after the client loaded it, `findHistoricalBySchemaOrThrow` also matches each history version as `memberSchema` serves it to that member. The service remembers which snapshots `memberSchema` changes, by id only, and a miss reloads just those to hash them as served to that member, so the cache holds no schemas (agent decision, review round 3). This also lets an echo of an earlier version of a row-list form match, which it could not before.
- Display-only schemas (action and general updates) need no change: their schema omits `manualPerUser` and `manualUserContent` (reconstructed from existing code, `common/src/forms/display-only-schema.ts`).
