- `memberActionPhase` and its `MemberActionPhase` type move from `server/src/actions/utils/action-event.ts` to `common/src/actionEvent.ts`, generic over `{ date: Date | string; newStatus: string }` so server entities and client DTOs both fit. The deadline event is `eventInEffectAt(events, event.date).nextEvent`, the earliest event dated after the member_action event, whatever the array order.
- The phase's opening event is the first member_action event in the array (`find`), as `findStartedMemberActionEvent` already picks it, instead of the server's latest by date. `UQ_action_event_one_member_action` allows one live member_action event per action, so the two pick the same event.
- Clients compute the phase from `action.events` with the common function rather than reading the server-computed deadline. The home-page comparator also sorts `AdminActionListItemDto` (admin PriorityPage), `ActionDto` without `viewer` (guests), and test fixtures, which carry no `viewer.deadlineAt`; the reminder tab and timeline need the deadline event per member_action event of an action they hold. The events are present on every one of these payloads, so one call covers them all and stays the same definition the server uses.
- `getDeadlineTimestamp` in `shared/lib/actionUtils.ts` had no caller besides `actionPriority`, so it goes; `actionPriority` takes both start and deadline from one `memberActionPhase` call.
- `apps/admin/src/lib/actionTimelineData.ts` held a fourth copy (`nextEventsById`, the next event in date order after each event), used for `from_deadline` reminders on the timeline. It reads the deadline from `memberActionPhase` per action too. `eventsByDate` stays: the phase segments still need the sorted list.
- Client behavior: the server loads `action.events` without an `ORDER BY` and serializes them in load order, so clients previously took the deadline from Postgres row order. Where that order is not date order, or another event shares the member_action event's instant, the home ordering and the reminder previews now show the server's deadline instead of a different one. The local database (staging data) had no action whose events' id order differs from date order and no two events of one action at the same instant, so on that data nothing changes.
