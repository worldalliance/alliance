# Formula choice options

[REQUIREMENTS.md](REQUIREMENTS.md) records the user's request and approvals. The design below is agent-authored. It was written as a specification and then revised during implementation; [Implementation choices](#implementation-choices) records how it was built and where it departs from the specification.

## Authoring and result contract

Offer fixed options or an options formula in the admin editor for `select` and `multiselect`, including list sub-fields. Reuse the existing formula input picker, expression editor, type feedback, and sample evaluation. Show evaluated choices in the preview so authors can inspect labels, values, and deduplication.

An options formula returns an array of `{ label: string, value: string }` records. This matches existing choice inputs and avoids converting a list to display text and parsing it back. Check this result type in the builder and validate the actual result at runtime. `[]` is a valid empty result; `undefined`, scalar results, nested arrays, and malformed records are errors. Authors explicitly supply empty fallbacks where inputs may be unanswered.

Keep text variables' existing output contract. Reuse the formula engine with a separate options result contract rather than permitting array-valued text interpolation. An options formula has its own inputs and expression; it does not require a named text variable.

Reuse existing input semantics, including source lists and local inputs. Prior-response inputs expose submitted history in its existing order and preserve labels from each response's form snapshot. Source drafts are excluded. Formula expressions choose submissions, flatten lists, concatenate sources, transform values, or add literal choices. There is no separate latest/all selector, union configuration, or implicit addition of the fixed option list.

For a multiselect history input named `input1`, the authoring help should include:

| Purpose                           | Expression                                          |
| --------------------------------- | --------------------------------------------------- |
| Latest submission's selections    | `input1.at(-1) ?? []`                               |
| Selections across all submissions | `input1.flatMap(answer => answer ?? [])`            |
| Latest selections from two inputs | `(input1.at(-1) ?? []).concat(input2.at(-1) ?? [])` |

These are examples, not a default history policy. Source history already supplies snapshot labels; formulas may replace them deliberately. A later request added source categories; see [Option categories](#implementation-choices). Fixed options retain their category behavior.

## Resolution and interaction

Deduplicate by exact stored value, preserving the first label and position. Case differences remain distinct. Equal labels with different values remain separate. Apply existing option randomization after deduplication; search and multiselect selection limits operate on the resolved choices.

Resolve the same choices for rendering, answer cleanup, required checks, submission validation, and choice inputs consumed by other formulas. Evaluate dependencies consistently; reject self-dependencies and cycles as configuration errors rather than oscillating between option sets. List sub-fields use the existing formula input scope, without introducing a new implicit current-row variable.

Load prior history once for the open form and member. Local-input formulas recompute when their inputs change, using that fixed history. Reopening or reloading fetches fresh history. Changing the preview member discards the previous member's context. A guest or preview without a selected member inherits the existing empty-history behavior.

Loading is distinct from an empty result: gate the form until its sources resolve. Source retrieval errors offer retry; invalid formulas, malformed results, and deleted or incompatible sources block the form with a visible error. Never replace an error with an empty list or fall back to fixed options.

For an empty list, disable the field and display “No options available.” Existing visibility and conditional-required rules determine whether an unanswered field prevents submission; hidden fields do not acquire a new requirement. A field with an options formula has no default, and the sole available option is never selected automatically.

On draft restoration, resolve options before checking saved answers. Clear an unavailable select value; for a multiselect, remove only unavailable values. Apply the same cleanup when local inputs change the available choices. A selection is cleared when its choice is offered neither against every answer, hidden ones included, nor against the visible answers; once cleared it stays cleared if the choice returns. When either fails, nothing is cleared. Otherwise hiding an input a formula reads only leaves its selections out of the rendered and submitted answers until the input shows again. Repeat this behavior for list sub-fields.

## Submission and saved responses

Validate submitted selections on the server against the formula's resolved options for the submitting member. Reject forged values and malformed formula results. Enforce required and maximum-selection rules after existing hidden-answer handling, including list sub-fields.

Keep source history fixed through submission as well as display: the server needs a verifiable reference to the history used by the open form, not a client-provided option list it blindly trusts. Additional source submissions must not silently replace that context. If the original context can no longer be verified, return an explicit refresh error rather than substituting current history. The transport and storage mechanism is an implementation choice.

Persist the selected values and their resolved labels with the destination response, including enough field/row identity for repeating lists. Keep the existing scalar/array answer shapes so answer consumers retain their value contract. Response-specific label metadata belongs with the response, not in the shared form definition. Persist only selected choices, avoiding disclosure of unselected private source answers.

Use saved labels for completed form display, admin review, shared output, and subsequent formula reads of these answers. These paths must not depend on refetching the original source history or on the viewer's identity. Existing answer visibility rules govern access. Later source edits, new submissions, or deletion must not relabel a completed destination answer.

Existing fixed-option schemas and responses require no backfill. Add formula configuration compatibly, and add response metadata with an empty/absent legacy state. A schema migration may be needed for that metadata; choose the exact shape during implementation. Legacy responses continue resolving labels through their saved form snapshots.

## Boundaries

Authoring remains admin-only. Member rendering covers web and mobile, and admin preview uses the selected member. This feature does not add cross-member computations, guest history retrieval, live history polling, or radio/ranking destinations. Existing previous-answer display and visibility-condition history policies remain separate.

## Acceptance checks

These behaviors were the acceptance bar, along with the affected packages' required checks. Each has a focused test except those listed under Unverified:

- Builder configuration, sample preview, save/load, invalid result types, and invalid references work for both destination kinds and list sub-fields; fixed-option forms retain their behavior.
- Latest and all-submission formulas produce the expected choices for zero, one, and multiple submissions, including unanswered fields, unions across forms, source lists, and literal choices.
- Duplicate values keep the first label and position; different values sharing a label remain distinct; transformed values can prevent a collision. Search, randomization, and selection limits use resolved choices.
- Web and mobile distinguish loading, empty, failed, and ready states; optional/required and hidden-field behavior matches the contract. Retry and preview-member switches do not leak stale choices.
- Local-input changes and reopened drafts clear invalid selections without dropping valid multiselect values or restoring selections cleanup removed. Dependency cycles fail visibly.
- Server checks reject out-of-set submissions and enforce limits and required fields, including required fields in repeating lists; a list sub-field's selection limit is enforced only by the renderer (see List sub-field limits). A new source submission during an open form does not change its validation context.
- Completed responses retain chosen labels through source changes or deletion, in member display, admin review, shared output, and downstream formulas. Shared output exposes only permitted selected answers and needs no private source-history request.

Spec completion requires all approved choices to be represented, agent decisions to remain distinguishable from user-origin requirements, and both documents to pass formatting and sensitive-data review.

## Implementation choices

- **Stored shape:** `select` and `multiselect` take an optional `optionsFormula: { inputs, formula }`, the inputs and expression of a variable without a name. The schema rejects such a field with any fixed option, category, or default, so what the formula offers is never mixed with a fixed list. Schema parsing on server writes and in the admin's merge path rejects the key in a build predating it. Older member renderers and the older builder cast the schema unparsed, so they show the field with no options, and the server refuses a member's submission from them that selects a formula choice reading another form, since it names no source form, or a choice the formula doesn't offer.
- **Option categories:** a choice record read from a field with categories carries its category's name as `category`, so a formula can keep, filter on, or set it; an uncategorized choice has no `category` key. An options formula's result may give each item a text `category`; a blank one is none, and names equal once trimmed and ignoring case take the first's spelling, meeting the fixed-option rule that category names be nonblank and unique. Anything else in `category` fails the formula. The resolved and saved fields turn the names into the field's `categories`, in first-offered order, with each name as its own id, so the existing grouping renders them on web and mobile and the builder's result preview prefixes each choice with its category. `formulaChoices` saves each choice's category; the jsonb column needs no migration, but #279 put a reader on `main` that rejects unknown keys, so a separate earlier commit widens the reader before any build saves the key. Installed mobile bundles are the exposure, since web and server deploy together; ALL-1258 tracks keeping the writer out of `production` until no bundle with the strict reader remains.
- **No default:** the builder sets defaults by ticking fixed options, and a formula field has none to tick. Rather than add a typed default that could name a choice the formula rarely offers, a formula field has no default.
- **Result validation:** each item needs a string `label` and a non-empty string `value`, and may have a text `category`; other keys are dropped, matching TypeScript's structural typing, so a city record's extra keys don't fail a formula. An empty value would read as unanswered wherever answers are read, so it fails the formula. The builder checks the result type with the TypeScript checker. Saving also evaluates the formula with nothing answered and no submissions, which catches `input1.at(-1)` without `?? []`, since strict null checks are off and the type check can't.
- **Resolution order:** `resolveFormulaOptions` orders formula fields by the local answers their formulas read, so a formula reading another formula field gets that field's resolved labels and its answer without dropped choices. A list input depends on the formulas of its list's sub-fields, so a sub-field reading its own list is a loop. Loops fail at save and at runtime.
- **Cleanup:** the renderer resolves against the visible answers and drops unavailable selections from the answers it validates, renders, and submits. Which answers are visible is decided without the dropped selections, since dropping one can show or hide a question. An effect also writes cleaned answers back to form state, which keeps a cleared selection cleared. It runs only once the histories and every visibility input have loaded: the visibility context, the sign-in, previous answers, and a verdict for each validator the form's conditions reference. A signed-in member's form whose formulas read another form also waits while the sign-in is still resolving rather than read the histories as a guest with no submissions. The effect works out what's offered from the answers it edits, so a draft restored in the same render is checked against its own answers. A selection stays while either every answer, hidden ones included, or only the visible ones offer it, so hiding an answer a formula reads keeps the selections it offered, showing it again brings them back, and a choice offered only while an input is hidden can be picked. When a hidden answer makes a formula fail, nothing is cleared; the rendered answers still leave out what the visible answers don't offer. A multiselect left with nothing loses its key, which is safe because formula fields have no default to restore. A cleared select's empty answer is no selection, so it is neither dropped nor refused. The draft-restore filter that drops unknown multiselect values skips formula fields, whose options aren't known until they resolve.
- **Submission reference:** a submission names, for each source form an options formula reads, the ids of the responses the open form loaded, oldest first. When the answers select a formula choice, the server loads the member's history and refuses with 409 unless it starts with exactly those ids, then resolves against that prefix. A response submitted since the form opened is left out. A deleted source form also answers 409. Otherwise, a submission that doesn't name every source form is refused with 400, and a history the server can't read answers 500. A client can send a shorter prefix, but only to resolve against fewer of the member's own submissions. That seemed an acceptable trade for a reference that needs no storage; ALL-1152 tracks bounding it. Web forms show the reload instruction for a 409 that carries it rather than a generic failure, and don't report it as an error. Mobile, which has no reload and often shows the form inline, refetches the histories in place, keeping the answers, and asks the member to check them and submit again.
- **Guests and withdrawals:** a guest submission resolves against no submissions. Its choices are checked against the visible answers, as a member's are, with visibility decided from the validator verdicts it sends, and it skips the required and selection-limit checks, as guest submissions already did. A withdrawal saves partial answers unchecked, as it did before. It names the responses its formulas read, as a submission does, and saves the labels of the choices they still offer. A withdrawal whose history can't be matched or parsed, or whose formulas fail, saves no labels, and so does one that doesn't name a form its formulas read, or whose formula sources are malformed. An error loading a history fails the withdrawal. The admin responses table and history reads then show those answers' stored values, and read-only form views show them unselected.
- **Stored labels:** `form_response.formulaChoices` is jsonb, NOT NULL, default `{}`. For each answered formula field it holds the selected choices, in the order offered. A list sub-field's rows share one offer, so its entry covers every row; no row identity is needed, departing from the specification's field/row identity. Existing responses read as `{}`.
- **Reading saved labels:** `schemaWithSavedChoices`, and its field-level forms `fieldWithSavedChoices` and `fieldsWithSavedChoices`, turn each formula field into a fixed-option field offering its saved choices. The read-only renderer, the admin responses table, the Questions tab, the HTML export, previous-answer blocks and history reads apply them. The stats tab counts every choice any response saved, under the first label saved. A read-only form with a saved response loads no history for options formulas. The CSV export keeps stored values, as it does for fixed options. The response filter's summary names a formula choice by the first label saved, as the stats tab does. The Questions tab, stats tab and filter summary read the field's current configuration, so once a field is switched back to fixed options they label values by its current options, showing any other value raw or, in stats, as an unknown option; ALL-1205 tracks it.
- **Shared output:** the server reads labels from the saved choices, then ships each drawn formula field as fixed options holding only the choices the output's answers select. The formula itself is not shipped.
- **List sub-field limits:** departing from the specification, the server doesn't enforce a list sub-field's selection limit, for formula or fixed options; the renderer does. ALL-1153 tracks it.
- **Aggregate inputs:** an options formula can't read an aggregate input, which counts members' answers. Saving rejects one, and the builder won't switch an options formula's input to counts, since neither the renderer nor the submission check loads counts for an options formula.
- **Deleting a source form:** the delete guard also refuses while the current version of any form has an options formula reading it. A read-only form still draws past a deleted source form, and an options formula reading it resolves as if it had no submissions, which saving checks every formula can take. An editable form reading it shows an error instead, and keeps its draft's selections.
- **Builder:** the variable card's inputs, samples, help and preview became `FormulaEditor`, which both variables and choice fields use. Switching a field with fixed options or option categories to a formula asks first, and so does switching a formula other than the empty starting one back to a fixed list. The options editor, like the Variables tab, says when the list of forms fails to load. A local input reading another formula field has no sample options to pick, since its options exist only at runtime; ALL-1201 tracks typed samples. For the same reason a show/hide condition on a formula choice field takes a typed value, and a new one on a formula multiselect starts as any option selected.
- **Unverified:** these acceptance checks have no focused test and are accepted as gaps: search and randomization over resolved choices, and the renderer's selection limit on them; builder sample preview for a multiselect destination, and for a list sub-field; invalid result types and references for a multiselect destination, tested only on selects; the retry path with an options formula, whose gate is tested through a variable; saved labels surviving an edit to or deletion of the source form; invalid references for a list sub-field, tested only at top level; builder save/load, tested only through the server API; preview-member switches, tested only at the hook level; dependency cycles, tested only in common; a required formula field left blank while choices are offered, on web or server; a hidden required formula field acquiring no requirement; the sole available option never being selected automatically; choices resolved from another form's list through a source list input; the server's required check on a formula sub-field in list rows; the web form's loading state while an options formula's history loads, tested only for the sign-in wait; a deleted source form hiding the web form's fields, tested only for its error; the web renderer dropping a hidden formula field's answer, tested in the shared logic but not through the renderer; shared output needing no private source-history request; and the mobile renderer, which is covered only by typecheck and the shared logic's tests and was not run on a device.
