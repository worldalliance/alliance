# Preservation policy

The user deferred whether work is archived at all, what an archive contains, and its retention period. Omit archival and restoration in the first implementation: its purpose is removing temporary environments, and recovery was not considered valuable enough to require it. This is an agent choice that may be replaced if it causes friction.

Per the Removal requirements, cleanup discards staged and unstaged edits, untracked and ignored files, and local database changes in the selected worktrees, and deletes the branches created for them. Remote branches and pull requests remain untouched. Document this behavior in command help so callers understand the operation they invoke.

Neither merge detection nor squash-merge recognition gates cleanup. The agents' merge strategies vary, and retaining environments until incorporation can be proved defeats unattended cleanup. No archive directory, expiration mechanism, or recovery command is needed under the chosen policy.

# Creation and ownership

- Preserve full environment provisioning and the existing sibling-directory layout. Parentage expresses lifecycle ownership, not filesystem nesting.
- Resolve the creating checkout from the invocation directory when it belongs to this repository; otherwise use the checkout containing the invoked script. Resolve the default code revision there, and continue honoring an explicit `--from`. Read copied configuration and source database settings from the main checkout as required.
- Persist parentage and which branch the script created alongside worktree metadata. Use checkout identity rather than the current branch name for parentage, so switching branches does not move a child between parents.
- An existing branch supplied to `--branch` remains user-owned. Cleanup removes its checkout but retains that branch. Delete only explicitly owned branches, not branches selected by a naming pattern or newly discovered during cleanup.
- Apply parent tracking to newly created worktrees. Older worktrees retain direct named removal; infer no historical parentage from Git ancestry or directory names.

# Cleanup contract

- Extend `rm-worktree.sh <name>` to remove that worktree and its recorded descendants. The main checkout has no name and is never a removal target.
- Remove descendants before their parents. Unrelated worktrees, including the named worktree's own ancestors and siblings, remain outside the removal set.
- The caller stops and waits for its agents and development processes before cleanup. A planned desktop app can own this sequence; these scripts do not launch or supervise Claude or Codex. Preserve existing current-directory and Git worktree-lock protections rather than deleting the checkout running the caller or bypassing a lock.
- Coordinate creation with cleanup so a parent cannot acquire new children while its removal is underway. Keep ownership metadata until the corresponding resources are gone, allowing cleanup to resume after an interruption or partially failed creation.
- A failure to validate ownership or remove a resource produces a nonzero exit and a report naming what remains. Retain a parent while a descendant is unresolved; continue cleaning independent siblings. Retrying an interrupted cleanup treats already removed resources as complete.
- Preserve existing checks against deleting the main checkout or its database. Cleanup targets owned resources even when their names resemble another task's resources; uncertain ownership is an error.
- The commands run without interactive prompts once invoked. Report completion only when the selected resources are removed, and report retained pre-existing branches separately from incomplete cleanup.

# Implementation boundaries

- Keep Git, local environment setup, and cleanup usable directly from the command line. Desktop UI, provider integration, conversation storage, S3 synchronization, and agent orchestration belong to a future feature.
- Update the generated worktree instructions and script documentation to describe child creation, ownership, and the destructive cleanup contract.
- Keep the Bash-based macOS/Linux approach. Do not add a native Windows installer or substitute shell as part of this feature.

# Acceptance checks

Use disposable repositories, synthetic configuration, and disposable or stubbed database resources. The implementation is complete when these cases pass on macOS and Linux:

1. Create a child from a worktree and a grandchild from that child. Each records the correct parent, starts at its creator's committed revision by default, honors `--from`, receives its own ports and databases, and copies environment inputs from the main checkout.
2. Remove a child that has a child of its own. Remove both generations and their owned resources; preserve the child's parent and an unrelated sibling task.
3. Remove a parent from outside its subtree. Remove its descendants first and then the parent, including owned branches with unpublished commits and directories containing staged, unstaged, untracked, and ignored files.
4. Remove a child using a pre-existing branch. Preserve that branch and its commits while removing the child's environment. No remote ref or pull request is changed by either removal mode.
5. Fail a database deletion or filesystem removal midway through cleanup. Report incomplete cleanup, retain the metadata needed to retry, clean independent siblings, and complete successfully after the failure is resolved.
6. Interrupt creation and race child creation against parent cleanup. Leave no unregistered resource that cleanup cannot identify, and never add a child to a parent being removed.
7. Run simultaneous creations with distinct names and with conflicting names. Successful creations own distinct resources; failed calls leave other calls' resources intact. Run overlapping removals and reuse a removed name while an earlier removal is still finishing; preserve the replacement worktree and its resources.
8. Reject malformed or foreign ownership, a locked removal target, the main checkout as a removal target, and a removal set containing the caller's checkout. Do not remove unrelated resources while reporting these failures.
9. Remove a worktree created before parent tracking by its existing name, without treating unrelated legacy worktrees as descendants.

# Implementation

- Creation checks the worktree directory before the databases. A worktree from before records owns databases no record names, and refusing its name over them would point at dropping a live worktree's data.
- Records live in `.git/alliance-worktrees/instances/<uuidv7>/record`, under the shared Git directory. Every checkout reads the same registry, and the records survive deletion of the worktree directory, so a retry can still find them. A worktree's Git admin directory holds its record id in `.git/worktrees/<dir>/alliance-instance`, which is its checkout identity. A file inside the checkout would not do: `git clean -fdx` deletes ignored files, and removal would then refuse a worktree it created. `git worktree prune`, and `git worktree add -f` over a missing registration, delete the admin directory with the marker, so a tree made by hand at the path later never inherits it.
- Records are the claims. Name, databases, created branch, and slot are checked and recorded under one registry lock (`.git/alliance-worktrees/lock`), which replaces the per-slot `alliance-slot-locks` directories. Records are deleted under the same lock, so a scan never sees half a record. A record exists before its resources and is deleted after them, which covers interrupted creation (acceptance check 6). A record is staged in `instances/.new-<id>` and moved into place, and deleted by moving it to `instances/.deleted-<id>-<pid>` first; both scripts sweep what stopped runs left of these under the registry lock, keeping a graveyard while its remover runs.
- Locks are `flock` locks, taken through perl because macOS ships no `flock(1)`. The kernel releases a lock when every descriptor on it closes, so a killed run leaves no stale lock and no clearing step can race. Bash 3.2 cannot allocate descriptors, so the registry lock uses descriptor 8 and a record's lock descriptor 9. Child processes inherit the descriptor; `git worktree add` and `bun install` run with descriptor 9 closed, so a daemon they leave behind cannot hold a creation's lock forever. A creation takes its record's lock in the staging directory, before the record becomes visible.
- Removal resolves `<name>` to a record under the registry lock. A record seen before taking the lock and gone or replaced by another id under it was removed by a concurrent run, and the removal reports that and exits 0. A replacement belongs to a creation that reused the name, so it is never removed for the name the run was asked about earlier. Neither is a record that appears under the lock when none was seen before it: the removal keeps it and fails, telling the caller to rerun, rather than delete a worktree created after it started.
- Removal waits while a live process holds a record's lock: a creation in progress or an overlapping removal. A record that disappears while the removal waits was completed by the other run. Creating a name whose earlier instance is still being removed waits for that removal and then proceeds. If the removal stops without finishing, creation fails and points to `rm-worktree.sh <name>`.
- Removing a worktree flags every selected record as `removing`, under the registry lock, before any removal begins. The flag is a symlink to the remover's pid and start time, so a flag left by a dead remover reads as stale and pid reuse cannot pass for a live one. `ps` reports the start time in the caller's locale and time zone, so the stamp pins `LC_ALL=C` and `TZ=UTC0`. Creation checks its parent's flag under that same lock, so a child is either recorded in time to be removed or refused. A failed or killed removal leaves the flag; creation then refuses the child and names `rm-worktree.sh <name>` to finish the removal.
- Database ownership is proved by the database comment `alliance-worktree:<id>`. Removal drops a database under its real name only when the comment matches, so even a name collision cannot drop another worktree's database. Creation makes each database under a staging name derived from the record id (`alliance_wt_<id hex>`, plus `_test` for the test database), sets the comment, and only then renames it to its real name with `ALTER DATABASE ... RENAME TO`. Removal drops a staging name only when it carries this record's comment or none, since a worktree named `wt-<id hex>` holds the same name under its own comment. A stop at any point, including a kill during the slow template copy that Postgres still finishes server-side, therefore leaves only databases removal can identify. This replaces recording `db_creating` after `createdb` returned, which left a database stranded when creation was stopped during `createdb`. A name someone else takes after the registry-lock check fails the rename, so it is never claimed. Such a database, or a directory at the recorded path that the record does not own, keeps the record and fails every rerun until someone renames or moves it, which the error says; releasing the record instead would settle uncertain ownership silently. Creation fails when a database already exists, replacing the old reuse. Reuse would have tagged a database of unknown origin as owned. `restore_staging_data.sh` recreates a checkout's database with its comment, so loading staging data into a worktree keeps that database removable.
- A directory counts as owned when its `alliance-instance` marker matches, or when no instance file exists yet, the record has `dir_added=1`, and the directory is empty or holds only a `.git` pointing into this repository. Creation runs `git worktree add --no-checkout`, writes the instance file, and only then checks the tree out, so a stopped creation without an instance file leaves nothing more, and deleting that loses nothing. Accepting any tree whose `.git` points here would delete a worktree someone checked out by hand into the empty directory of a creation stopped before its `git worktree add`, with its uncommitted work. `dir_added` is written after creation's `mkdir` of the path succeeds, so a path someone else took first is never claimed, and is cleared once the instance file is written, or when the add fails and the directory is still empty. A creation stopped between that `mkdir` and writing `dir_added` leaves an empty directory, which removal deletes with `rmdir`, since `rmdir` fails on anything that has appeared in it. Without `dir_added`, a worktree someone else later made at the path of a creation that stopped before checkout would read as owned, and keeping it set once the instance file exists would claim one made after a finished worktree was deleted by hand. Removal clears `dir_added`, renames the tree to `<dir>.removing-<id>`, and only then runs `rm -rf` on that name, which a rerun finishes. A failed rename restores `dir_added`, so a rerun still owns a tree claimed only through it. The rename frees the path at once, so a checkout someone makes there while the delete runs, after it fails, or after a later step fails is never taken for this one. Flagging the record before deleting in place was rejected: the flag would claim whatever later stood at the path.
- Every record claims its branch, created or not, and creation refuses a branch any record holds: a worktree that switched to another branch still owns the one it was created with. `branch_created=1` is recorded before the branch exists. Creation records `branch_from=<commit --from names>`, resolved after the database copy since `--from` can move during it, makes the branch from `--from` with `git branch`, records `branch_added=1`, and only then runs the slow `git worktree add`. Branching from `--from` rather than the commit leaves the upstream to `branch.autoSetupMerge`, as `git worktree add -b` did. A `--from` that moves between the two steps leaves the branch off `branch_from`, so a creation killed before `branch_added` then has its branch kept and reported rather than deleted. Removal deletes the branch with `git branch -D` when `branch_added=1`, and otherwise only while it still points at `branch_from`, with `git update-ref -d` given that commit as the old value. A creation killed between `git branch` and that write therefore leaves no branch for a later creation of the name to adopt as one that existed before and keep on every removal. A `git branch` that fails, because someone else made the branch since the claim, clears `branch_from`, so removal never takes that branch for this creation's. `update-ref` does not refuse a checked-out branch the way `git branch -D` does, so removal keeps a branch checked out in another worktree, which covers a creation killed before `git branch` or before clearing `branch_from`. A same-named branch at any other commit is kept and reported, as not made by the creation when `branch_from` is empty and as moved otherwise, since deleting another's commits cannot be undone. A `--branch` that already exists is recorded as `branch_created=0` and is reported as kept.
- Creating a child from a worktree with no record fails. A child of a worktree with no record could not be removed along with its parent, and a silent orphan is worse than an explicit refusal. The error points to the main checkout instead.
- Before removing anything, removal rejects the whole run if any selected record is malformed, any selected worktree is locked, or the selection includes the caller's checkout or the checkout holding the running script, which `--list` also leaves out with its ancestors. It also rejects the run when any record's parent is unreadable, since that record might be a descendant. A lock on a tree claimed only through `dir_added` is the one `git worktree add` writes while it runs and leaves behind when killed, not a user's lock, so removal unlocks that tree instead of refusing it. `git worktree prune` keeps a locked registration, which would refuse the name to the next creation. Two records naming the target also reject the run, since the target is ambiguous. Failures removing a resource stay per worktree: siblings continue, and ancestors are kept.
- Worktrees without a record keep the previous removal: by name, using `.worktree/ports.json`, deleting their branch only when it is merged. That code lives in `scripts/lib/rm-worktree-by-name.sh`, which refuses a worktree carrying an `alliance-instance` marker.
- Tests run the real scripts in a temporary repository whose `scripts/` is a symlink to this one. `psql`, `createdb`, `dropdb`, `pg_dump`, and `bun install` are stubbed with files in place of databases. Hold and fail files in the stub state stage interruptions, races, and failed drops deterministically.
