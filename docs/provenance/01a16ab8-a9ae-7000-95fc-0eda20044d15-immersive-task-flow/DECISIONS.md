## Decisions

- **Static chunking.** Form pages are split into screens once, from the schema, by a pure function in `shared/forms/flowScreens.ts`. The web renderer reuses it. Hidden elements are skipped at runtime, so screens don't reshuffle while the member types.
- **Display blocks follow the next input.** Display blocks that come after a screen's 2nd input move to the next screen together with the input they introduce. Instructions then sit beside the field they describe.
- **Shared form state.** The flow uses the same answer state, draft, visibility and submission logic as the inline form, extracted from `FormRenderer.tsx` into a hook. Drafts, autosave, row-filled forms and variables then behave identically. It also keeps `FormRenderer.tsx`, already well past 500 lines, from growing.
- **Resuming.** The draft keeps storing `currentPageIndex`. The flow resumes at the first screen of that page, so the draft stays compatible with the inline form.
- **Modal, not route.** The flow is a full-screen RN `Modal` opened from the action page. That keeps it inside the authenticated app shell without showing the tab bar.
- **Mobile motion.** The modal is transparent and draws its own motion, so mobile uses the same durations and curve as web: the panel slides up with `flowMotion.expand` and down with `flowMotion.collapse`. The slide starts on the panel's first layout, because the modal shows its content a few frames after it opens and the curve's fastest frames would otherwise play unseen. Closing the completion screen follows web's order: the green fades with `flowMotion.recolor`, the panel slides away, and only then is the action completed. Reanimated's timings follow the system's reduced-motion setting.
- **Completion waits for the member.** A successful submit shows the completion screen first. Recording the "completed" relation and `onCompleteAction` run only when the member leaves that screen. Either one flips the panel (or the home card) to its completed state, which would unmount the flow before the completion screen shows.
- **Holding the page behind the completion screen.** The server records the completion when the form is submitted. Any later refetch would then bring the completed state in and unmount the flow, at a moment that looks random to the member: a window refocus, the Tasks badge's one-minute poll of the task list, or an event boundary. So `useTaskFlow` marks its action as completing in `TaskFlowCompletionContext`, from the start of the submit until the flow closes. While that mark is set, `useActionHandlers` (the action page, both platforms) and `useHomePageActions` (the home task list, both platforms) keep the data they had when the mark was set. Holding at those two hooks, rather than at the queries, leaves every other reader of the same data live. `markCompleted` skips the optimistic count for an action the server already reports as completed, since a held refetch may already have counted the member.
- **Next stays pressable.** Next is muted while a visible input on the screen fails validation, as in the designs. It can still be pressed, so the errors appear and say why rather than leaving the member stuck.
- **Labels.** The last screen's button reads "Submit". Authors are labelled "Staff" and reviewers "Expert", following the designs. The completion screen has no task-specific subtext, because the schema has nowhere to store it.
- **Response card.** The completion card renders the form's output views with the existing `OutputRenderer`, using the answers just submitted, under the member's avatar, name and city.
- **Shared form pieces.** The inline form and the flow share `useMobileFormState`, `FormElements` and `WithdrawalModal`, and submit through `useSubmitTaskForm`. Splitting mobile `FormRenderer.tsx` into these is recorded in [split-mobile-form-renderer](../01a17969-2f3f-7000-8faa-7d077a283e32-split-mobile-form-renderer/DECISIONS.md).
- **Project background page.** It takes over the first visible screen when that screen shows no inputs: a question a visibility rule hides counts as none. It counts as the first step of the progress bar. Back from the first question screen returns to it.
- **Screen titles.** A screen's H1 is the header block that opens it. A screen split off by the 2-input cap repeats that header. Headers stacked directly under the opening one stay on its screen as subheadings, and a header that ends a page joins that page's last screen, so no header an author wrote is dropped. A screen with no header gets a fallback title: "Answer the questions below" when it has inputs, "Read this before you continue" when it doesn't. The active wording itself comes from each form's headers, which admins write.
- **Scenario accordions are content, not code.** The existing accordion block is collapsed by default, so collapsing scenarios means wrapping each scenario's description in an accordion in the form. Action 139's forms were edited this way by a one-off script kept outside the repository.
- **Own answers on the card.** `useOutputItems` takes `ownView`, which treats every answer as shown. Output views otherwise show only public answers, so a member who keeps answers private would get an empty card.
- **One progress bar for the whole flow.** `TaskFlow` renders a single bar under the background page and question screens, so it animates across every step. `ProgressBar` animates only changes after its first value, so its other uses look the same as before.
- **Resume position.** The last screen shown is kept per form on the device, tagged with the form version, so an edited form falls back to resuming by page from the draft. It's cleared on submit or withdraw.
- **Leaving and returning.** The flow closes when its screen loses focus, and records the task in `TaskFlowReturnContext`. The task page reopens the flow at the saved screen when it regains focus, for example through the back gesture. Only the task's own page reopens it; a home-screen card for the same task doesn't. Both platforms reopen through `useReopenLeftTask`, and only work out whether they're on the task's page.
- **Pinned accordion title.** The accordion sits deep inside the form content, so the scroll view's built-in sticky headers can't reach it. Instead, open sections report their position to `StickyAccordionScrollView` (flow screens only), which overlays a copy of the title bar while the member is scrolled inside a section. Tapping it collapses the section and scrolls back to where it starts. Chevrons swap between up and down icons instead of rotating, because rotated icons disappear in the web build.
- **One flow, two renderers.** The stage machine and screen navigation live in `shared/forms/useTaskFlow.ts` and run over a narrow `TaskFlowFormState` that both platforms' form-state hooks satisfy. Each platform keeps only its UI. The same applies to the resume position (`shared/forms/useFlowPosition.ts`, with AsyncStorage on mobile and localStorage on web), the leaving-and-returning context, the screen title, the background split, the contributor labels, the dev warning and the copy. Behaviour changes once and both platforms follow.
- **Web form state.** The web inline form and the flow share `sharedweb/forms/useWebFormState.ts`, `FormElements` and `WithdrawalMenu`. Web and mobile state stay separate, because their draft storage and public-answer models differ.
- **Web screen validation.** Both platforms check a screen through `useFormValidation`'s `validateScreen`. Next on a web screen runs the screen's own checks and then the browser's validity check, as the inline form's page Next does. That way format errors such as email syntax also block it.
- **Web panel, not modal.** The web flow is a non-modal Base UI Dialog panel. It fills the content area beside the side nav and below the top bar from `md` up, and the whole screen below `md`. Being non-modal keeps the collapsed nav clickable. Following a nav icon unmounts the flow mid-task, which is the same "leave and return" path the browser's Back takes. Only Escape dismisses the panel, unless a list inside it, such as city suggestions or the withdraw menu, closes on that key first; an outside press doesn't, so that clicking the nav doesn't close the flow before the navigation records the task. Content sits in a centred column of at most 640px.
- **Nav collapse.** The flow sets an `immersive` navbar option (`useImmersiveNavbar`) while it's shown.
  - `NavbarVertical` animates its width to a 4.75rem icon rail. Labels fade but stay readable to screen readers, each item gets a hover title, and badges become dots.
  - The logo doesn't wrap and overflows the rail into the grey top band.
  - The rail's stroke starts below the top band, so it never crosses the logo. The top band gets a bottom stroke that meets the rail's in one line.
  - `NavbarTopBar` fades out and inerts search and notifications. The profile button stays.
  - While immersive, the root drops its reserved scrollbar gutter and stops scrolling. A fixed panel can't extend into that gutter, which otherwise shows as a white strip on the right.
  - `--nav-width` follows the rail through a `ResizeObserver`, so the content and the panel track the animation frame by frame.
- **Expanding from the task container.** `useExpandingPanel` animates the panel's `clip-path` from the container's rectangle to the full panel, so nothing reflows mid-animation. The container is the nearest ancestor marked `TASK_FLOW_ORIGIN` (the homepage task card), falling back to the panel's parent on the action page. Closing reverses the clip and fades out, and the nav stays collapsed until the panel has shrunk back. Re-expanding the nav earlier would move the card out from under the shrinking clip. Reduced motion skips every step.
- **Closing the completion screen.** The close runs in steps:
  1. The completion screen fades out to the panel's white while the nav and top band turn back from green.
  2. The empty panel shrinks into the container.
  3. The nav widens.
  4. The action is completed.

  Completing re-renders the task panel or the home list, and that took about 100ms of main thread in testing. It waits for step 3 because a stall during the nav's width transition makes the nav jump. Each wait counts from the frame after the change that starts it, so a slow commit can't cut a step short. The Begin button stays hidden while the flow is on its completion stage, so it doesn't show through the shrinking panel.

- **Motion in one place.** Every duration and easing curve in the flow, on both platforms, is in `shared/forms/flowStyle.ts`, with each curve as cubic-bezier control points: the panel's expand and collapse, the recolor, the nav's width, the label and icon fades, and the progress bar. Web's `flowMotion.ts` turns them into CSS transitions and mobile's into Reanimated timings. `NavbarVertical` and `NavbarTopBar` read them through inline `transition` styles, because Tailwind classes can't take runtime values. Mobile's `ProgressBar` takes the flow's timing as `fillTiming`, and web's as `fillTransition`; their other uses keep their own.
- **One page frame.** On each platform, the background page, the question screens and the blocked view share one `TaskFlowPage` frame and `TaskFlowTitle`: the close button and any header control, the scrolling content and the footer. The blocked view is titled with the action's name.
- **One button treatment.** Every control in the flow, on both platforms, is a `FlowButton`: filled, borderless, `rounded-md`, `h-11` and medium weight. There are four kinds: primary (green), secondary (solid `zinc-200`), inverse (white, on the green completion screen) and icon (a filled `bg-zinc-100` circle with a zinc-600 glyph, a shade darker on hover on web). The kinds are the shared `FlowButtonKind` in `shared/forms/flowStyle.ts`, and each platform styles them in a `Record`, so a new kind fails both builds until both draw it. The close and withdraw circles sit flush with the text column's left and right edges, as in the designs. Web `BaseButton`'s `Light` and `White` variants and mobile `Button`'s draw a visible stroke while `Green` doesn't, which made neighbouring buttons inconsistent. Submit shows a spinner while submitting on both, and keeps its label for screen readers. The completion title has regular weight on both, matching the other screen titles and the design.
- **Same tokens, each app's scale.** Both flows use the same type and spacing tokens: `text-3xl` screen titles, `text-4xl` on the completion screen, `text-base` body and buttons, blocks 24px apart (`gap-y-6` on mobile, which `FormElements` takes as a `className`; the inline form keeps its 16px), and a `px-4` gutter for the content, the footer and the progress bar. Each app maps the tokens to its own scale, web's root being 15px and mobile's `text-base` 17px, so the mobile flow reads about an eighth larger. That scale is app-wide and stays as it is.
- **Shared copy.** Every label in the flow, including Next, Back and Submit, comes from `taskFlow` in `shared/lib/copy.ts`.
- **Web pinned accordion title.** It is CSS `position: sticky` on the accordion header, switched on by the `StickyAccordionTitles` context that only the flow provides. The header sticks within its own section, so it unpins once the member scrolls past that section.
- **Web leaving and returning.** Links inside form content open in a new tab on web, so following one leaves the flow open. The flow closes when it unmounts while open after the path has changed, for example on the browser's Back or a nav icon, and records the task. Reopening follows mobile: coming back to the task's own page reopens the flow at the saved screen, and nothing else does.
- **Web completion.** `ActionTaskPanelForm` splits submission (`submitTaskForm`) from completion (`completeAction`). Completion records the relation, calls `onSubmitted`, refreshes the user and calls `onCompleteAction`, and in the flow it runs when the member leaves the completion card.
- **No flow for public actions on web.** Guests on a public action are redirected to `/actions/completed` after submitting, so the web flow is off when `publicAction` is set.
- **Web withdraw.** The background page's `…` icon button opens the inline form's withdrawal dropdown. `WithdrawalMenu` takes a `renderTrigger` so the flow can supply its own button.
- **Web progress bar.** The flow reuses `components/system/ProgressBar.tsx`, which nothing else imported. It lost its right gutter and takes its fill's transition as `fillTransition`, which the flow sets from `flowMotion.progress`.
- **Green success chrome.** `useImmersiveNavbar` takes an `ImmersiveTone`. On the completion screen the flow passes `Success`, so the rail and the top band turn green, with white icons and logo and no strokes. The colours, item highlights and strokes all transition with `flowMotion.recolor`.
- **Withdraw menu outside click.** `WithdrawalMenu` puts its outside-click ref on the wrapper, trigger included. With the ref on the dropdown alone, the click that opened the menu also counted as an outside click and closed it again at once. This fixes the inline form's menu as well.
