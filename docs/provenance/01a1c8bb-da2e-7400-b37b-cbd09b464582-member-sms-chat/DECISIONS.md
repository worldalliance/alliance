# Decisions

- **Twilio Programmable Messaging, not Twilio Conversations.** The server already stores messages, polls status and handles STOP/START itself. Conversations would keep a second copy of each thread on Twilio's side and would stop the existing inbound webhook from firing for numbers in an active conversation. (agent decision; EVIDENCE.md §1)
- **A thread is every `mms` row whose `memberPhoneNumber` equals the member's current phone number.** `memberPhoneNumber` is a stored generated column, `from` for inbound rows and `to` otherwise, so existing rows get it with no backfill, it can't drift from `to` or `from`, and the release still running during the deploy's migration can insert rows that don't name it. `direction` defaults to outbound for the same reason, marked `BACKCOMPAT(mms-direction)` until no such release writes to `mms`; this release's writes all name it. Matching by phone, not by a user id, shows past broadcasts with no further backfill, and both members on a shared number see the thread. Consequences: a member who changes number loses the old number's history from view, and a recycled number shows its earlier owner's texts. (agent decision)
- **Inbound texts are recorded from launch onward. The `SmsInbound` event-log entries from before launch are not backfilled.** Backfilling them would put every member who ever replied to a broadcast on the Needs Reply list. Since `mms.body` now holds text members write, the staging anonymizer contact-scrubs it like other member-written text. (agent decision)
- **STOP/START replies are recorded in the thread too.** Keyword handling runs before the text is written, so a failed write can't lose an opt-out. The row records which keyword, STOP or START, the webhook acted on, so code reading the thread takes the webhook's decision instead of repeating its matching in SQL, where `upper()` and `\s` follow the database's locale and JavaScript's `toUpperCase()` and `trim()` don't. The webhook still writes the existing unhandled-text event-log entry. (agent decision)
- **Webhook retries are deduplicated by a partial unique index on `twilioSid` for inbound rows, with `INSERT … ON CONFLICT DO NOTHING`.** It's partial because existing outbound rows share placeholder SIDs such as `test-sid`. (agent decision; EVIDENCE.md §2) The index stays unique across deleted rows, so a retry can't revive a deleted text, and it is listed in `test/live-unique-rules.e2e-spec.ts`.
- **`GET /images/:key` serves only upload keys**, the slashless keys `POST /images/uploadImage` returns, as `GET /images/:key/download` already did. The route has no auth guard and reads the bucket with the production server's role, the one role the bucket policy lets into `mms-media/`, so without the check anyone could fetch a member's attachment as `/images/mms-media%2F<uuid>`. (agent decision implementing the private-storage requirement)
- **`mms-media/*` in the assets bucket stays private although the bucket also holds public assets.** The bucket policy denies the CloudFront distribution reads under that prefix, in production and staging, and in production denies every S3 action on objects there to every principal but the production server's role, so a principal granted the bucket later, like the local-development IAM user and staging's EC2 role today, stays out without anyone remembering to list it, and so do version, ACL and tagging actions nobody has granted yet. Outside the production server's own role, a presigned S3 URL is then the way to read a file. Listing the prefix's keys is a bucket action the deny doesn't cover, so principals granted the bucket can still see keys, sizes and dates; keys are random UUIDs, and denying listing would break the nightly copy's listing. The bucket is versioned, so a lifecycle rule on that prefix expires deleted versions after a day, which S3 rounds up to the next midnight UTC and runs asynchronously, so in practice a day or two; otherwise every attachment the server deletes would stay in the bucket. Staging's nightly copy of the production bucket skips `mms-media/`: staging's database is anonymized, and these are the first member files that aren't public. A separate private bucket would have needed a new env var and IAM grants. (agent decision implementing the private-storage requirement)
- **`mms_media` soft-deletes like the rest of the schema**, so `softDeleteCascade` follows a deleted text to its attachments. (agent decision; repo convention enforced by `test/soft-delete.e2e-spec.ts`)
- **Inbound media copy:**
  - The webhook stores one `mms_media` row per attachment and starts copying it to `ASSETS_BUCKET` under `mms-media/<uuid>` without waiting.
  - A cron job retries uncopied rows every minute while delivery is enabled. It runs under an advisory lock so its runs don't overlap, and takes the rows with the fewest failed copies first.
  - The cron leaves a row it has never tried alone for a minute after it's stored, as long as a first retry waits after a failure, so it doesn't copy a file the webhook is still copying and count one failure twice. A copy claims its row only if no other copy has. The webhook's copy and the cron's can still race on one row, such as when the webhook's copy runs past that minute; the copy that loses deletes its own upload. A claim that fails may still have committed, so its upload is deleted only once a re-read shows the row doesn't name it; when the re-read fails too, the upload is kept, since an orphaned file costs storage and a deleted one could lose the member's attachment. A copy that keeps an upload that way, or can't delete a losing upload, logs its key, so the file can be found and deleted by hand.
  - After a successful copy, the Twilio Media resource is deleted. The cron retries a deletion Twilio refused, until Twilio deletes the file or answers 404, and `twilioDeletedAt` records it. Refusals are counted and the rows with the fewest go first, so rows Twilio keeps refusing can't crowd out newer ones, and each retry waits 2^refusals minutes, capped at a day, as failed copies do, so a deletion Twilio keeps refusing costs a call a day rather than one a minute. Deletions are never given up on, since Twilio's copy has to go. (agent decision implementing the delete-from-Twilio requirement)
  - A failed copy is counted, and the next try waits 2^failures minutes, capped at a day, so an S3 or Twilio outage or a misconfigured deploy doesn't use up every row's tries. After 30 failures, about three weeks, the row is given up on; a 404 from Twilio gives it up at once, since Twilio no longer has the file. Twilio keeps the file until it is deleted (EVIDENCE.md §3), so the backoff loses nothing. (agent decision)
  - Media URLs must be `https://api.twilio.com`, because the copy sends Twilio credentials to them. An attachment that fails this is left out with an error log and the text is still recorded, since Twilio doesn't retry an inbound webhook that fails and the member's words would be lost. (agent decision)
  - Each Twilio and S3 call times out after 30 seconds and counts as a failed copy or refused deletion. That bounds each call, not the run: a run against a stalled endpoint can still hold the cron's lock for up to 50 copies' and 50 deletions' worth of timeouts, and the backoffs keep the runs after it short.
  - Staging's copy of the production bucket skips `mms-media/` (see the private-storage entry), so staging's copied `mms_media` rows name files staging doesn't have, and attachments don't load there. The anonymizer marks each of those rows given up on, by setting `copyAttempts` to `MAX_COPY_ATTEMPTS` (a unit test fails when the two differ), and deleted from Twilio, since staging's media cron would otherwise fetch production's Twilio media into staging's bucket and delete it from Twilio before production copied it. The terraform change has to be applied before this code is deployed.

  (agent decision; EVIDENCE.md §3)
- **Needs reply means the member has an inbound text that no later staff text answers; a later inbound text doesn't answer it.** A staff text is an outbound row with `sentById` set and a status other than the failure statuses REQUIREMENTS.md names. Texts with the same `createdAt` are ordered by id. A staff text is dated from when its send began, not when Twilio answered or a late send landed, so a member's text that arrives during the send sorts after it and stays listed. STOP and START texts are told apart by the `keyword` the webhook recorded on each inbound row, so the list and the opt-out or resubscribe always agree on which texts are keywords; an earlier SQL copy of the webhook's matching drifted from it where Postgres's `\s` and `upper()` follow the database's locale. Which staff text statuses count as a reply is a `Record` over Twilio's `MessageStatus`, so a status Twilio adds fails the build until someone decides; `partially_delivered`, `scheduled` and `read` count, as `queued`, `sent` and `delivered` do, and the inbound statuses `receiving` and `received` don't. Opted-out members are left off the list, since they can't be answered. Members who share a number are each listed for its unanswered text, as each of them sees the thread, so staff choose whose page to answer from, in member id order. A number is listed exactly when some counted inbound text has no staff reply after it, so the server runs that one search, `DISTINCT ON` the number oldest-first for the wait and the sort, with a window function over the same rows taking the newest text's body for the preview, and sorts by the oldest text's `createdAt`, then id. One query costs about what one of the two earlier searches did, oldest-first and newest-first, and wait and preview come from one snapshot of the table (EVIDENCE.md §6). A partial index on `mms ("memberPhoneNumber", "createdAt", id)` covering inbound and staff texts serves the search for a later reply, which otherwise scans every broadcast ever sent on each poll (EVIDENCE.md §6). (agent decision implementing the requirement)
- **Staff send through `MmsService.sendStaffText`, which returns its failure instead of swallowing it as `sendMms` does.** A Twilio rejection, a 400 from Twilio's API, becomes a 422 that carries Twilio's reason, with the member's number replaced; a 400 without Twilio's JSON error body, such as a proxy's HTML page, or with no reason counts as any other failure. The admin client shows 4xx messages and hides 5xx ones. Any other failure, such as a Twilio outage, rate limit or bad credentials, becomes a 502 with no reason, since its text says nothing about the member and could quote the number. Every failure, a timeout and a rejection included, also raises the Slack SMS-failure alert a failed broadcast raises, as `sendMms` does: an outage, a hung Twilio API or bad credentials need ops and not only the staff member who saw the error, and Twilio answers 400 for problems with our account, such as a sender number that can't text a region, as well as for a member's number (agent judgement from Twilio's error reference, not rechecked for this task). A timeout becomes a 504, and the composer's fallback tells staff to check the thread before retrying. A send that lands after the timeout is still recorded, with its sender. A text Twilio accepted that the database then fails to record is logged with its SID and fails the request; staff see the composer's fallback, since the admin client hides 5xx text. (agent decision)
- **The server refuses sends to opted-out members, to members with no phone number, and to members whose number isn't valid E.164, as well as the UI hiding the composer.** The number check uses `isCanonicalE164`, as `textReachable` does, so a legacy invalid number gets a clear refusal instead of Twilio's; it is its own helper in `mms-thread.service.ts`, since it returns a refusal for each reason and lets staging's numbers through, so changing `textReachable` leaves it alone. Outside production, staging's anonymized `+1555` numbers are let through, since `sendStaffText` records them without sending, so staff texting can be tried on staging. In production the same prefixes can only be legacy numbers no text reaches, and `sendStaffText` would record a text to one as sent, so they get the invalid-number refusal. (agent decision; fail loudly)
- **A staff text's 1,600-character limit counts UTF-16 code units, as `String.length` does, on the server and in the composer.** Twilio counts characters outside GSM-7, such as emoji, as more than one toward its limit (EVIDENCE.md, "Staff text length limit"), so `@Length`, which counts a surrogate pair as one, let through emoji texts Twilio rejects with a 422 and an SMS-failure alert. Counting code units counts an emoji as two or more; Twilio doesn't document its exact count, so a text near the limit may still be refused by Twilio or refused here when Twilio would take it. (agent decision; researched: Twilio's error 21617 page)
- **"Mark opted out" calls the existing `MmsUnsubService.unsubFromMms` with reason `marked_by_staff:<adminId>` and an empty raw body.** The event-log message now names the reason instead of always saying "keyword". Marking a member who has already opted out is refused with the same 409 as a send, so a stale tab doesn't record a second opt-out. A member whose number fails the send path's number check is refused the same way, with a 400: `unsubFromMms` looks members up by the normalized number, so a legacy unnormalized one would opt out whichever member holds its normalized form, or no one, and still report success. Two marks landing at the same moment can both pass that check and record the opt-out twice; the member's state is still right, the button is disabled while a mark is pending, and preventing it would mean reshaping the shared STOP path, so the duplicate audit row and Slack line are accepted. (agent decision)
- **`Mms.sentBy` names its target entity by string (`"User"`)**, unlike the `() => User` thunks other entities use. A value import of `User` into `mms.entity.ts` makes the app fail to load: the import cycle through `user.entity.ts` reaches `action-event-notif.entity.ts`'s eager `@ApiPropertyOptional({ type: Mms })` before `Mms` is defined. Its type is `Pick<User, "name">`, the fields read, not `User`: a full `User` closes the type cycle `User.optInMms` → `Mms`, and tsc then rejects TypeORM's `_QueryDeepPartialEntity` for an update that sets an `Mms`, such as `record-delivery.ts`'s, depending on the order it checks files (EVIDENCE.md, "`Mms.sentBy` type cycle"). (agent decision)
- **A staff text keeps its sender when the staff account is soft-deleted.** `Mms.sentBy` is listed in `softDeleteCascade`'s kept references, so deleting an account doesn't make that person's texts look automated. A hard delete still nulls `sentById` through the foreign key. (agent decision)
- **Thread paging:** `before` is the id of the oldest text the page shows, and the server returns the texts ordered before it by `createdAt` then id, so texts sent at the same moment page without gaps or repeats. A `before` that isn't a text on the member's current number is refused with a 400 rather than answered with an empty page, which would read as "no older texts". Ids in the path go through `ParseIntPipe`, as across the server, so one past `int4`'s maximum answers 500 where `before` answers 400; ALL-2171 bounds them server-wide. (agent decision implementing the requirement)
- **Viewing inbound media:**
  - The admin page points at `GET /mms-threads/media/:id`, behind the admin guard, which redirects to a 5-minute presigned S3 URL. The page's URL stays stable across polls while the signed link stays short-lived.
  - Only JPEG, PNG, GIF and WebP render inline, matched on the media type without its parameters, and `image/jpg`, an unregistered alias Twilio's accepted MMS types list, is served as `image/jpeg` (agent judgement from Twilio's media-type list, not rechecked for this task). Every other type is served as an attachment, so a member-supplied file never renders in an admin's browser.
  - The content type is taken from Twilio, not sniffed. Signed URLs are served from S3's origin, not the admin's.
  - An attachment shows "Attachment still loading…" until it is copied, and "Attachment unavailable" once the copy is given up on.

  (agent decision; EVIDENCE.md §3)
- **The member's own refresh error uses the sections' shared `SectionRefreshError`**, so it reads "Could not refresh this member. Reload to see the latest." like every section, and later changes to the shared line, such as its colour or how it is announced, reach it too. (agent decision)
