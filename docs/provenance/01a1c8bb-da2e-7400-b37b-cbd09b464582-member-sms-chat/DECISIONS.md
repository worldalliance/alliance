# Decisions

- **Twilio Programmable Messaging, not Twilio Conversations.** The server already stores messages, polls status and handles STOP/START itself. Conversations would keep a second copy of each thread on Twilio's side and would stop the existing inbound webhook from firing for numbers in an active conversation. (agent decision; EVIDENCE.md §1)
- **A thread is every `mms` row whose `memberPhoneNumber` equals the member's current phone number.** `memberPhoneNumber` is a stored generated column, `from` for inbound rows and `to` otherwise, so existing rows get it with no backfill, it can't drift from `to` or `from`, and the release still running during the deploy's migration can insert rows that don't name it. `direction` defaults to outbound for the same reason, marked `BACKCOMPAT(mms-direction)` until no such release writes to `mms`; this release's writes all name it. Matching by phone, not by a user id, shows past broadcasts with no further backfill, and both members on a shared number see the thread. Consequences: a member who changes number loses the old number's history from view, and a recycled number shows its earlier owner's texts. (agent decision)
- **Inbound texts are recorded from launch onward. The `SmsInbound` event-log entries from before launch are not backfilled.** Backfilling them would put every member who ever replied to a broadcast on the Needs Reply list. Since `mms.body` now holds text members write, the staging anonymizer contact-scrubs it like other member-written text. (agent decision)
- **STOP/START replies are recorded in the thread too.** Keyword handling runs before the text is written, so a failed write can't lose an opt-out. The row records which keyword, STOP or START, the webhook acted on, so code reading the thread takes the webhook's decision instead of repeating its matching in SQL, where `upper()` and `\s` follow the database's locale and JavaScript's `toUpperCase()` and `trim()` don't. The webhook still writes the existing unhandled-text event-log entry. (agent decision)
- **Webhook retries are deduplicated by a partial unique index on `twilioSid` for inbound rows, with `INSERT … ON CONFLICT DO NOTHING`.** It's partial because existing outbound rows share placeholder SIDs such as `test-sid`. (agent decision; EVIDENCE.md §2) The index stays unique across deleted rows, so a retry can't revive a deleted text, and it is listed in `test/live-unique-rules.e2e-spec.ts`.
- **`GET /images/:key` serves only upload keys**, the slashless keys `POST /images/uploadImage` returns, as `GET /images/:key/download` already did. The route has no auth guard and reads the bucket with the production server's role, the one role the bucket policy lets into `mms-media/`, so without the check anyone could fetch a member's attachment as `/images/mms-media%2F<uuid>`. (agent decision implementing the private-storage requirement)
- **`mms-media/*` in the assets bucket stays private although the bucket also holds public assets.** The bucket policy denies the CloudFront distribution reads under that prefix, in production and staging, and in production denies every S3 action on objects there to every principal but the production server's role, so a principal granted the bucket later, like the local-development IAM user and staging's EC2 role today, stays out without anyone remembering to list it, and so do version, ACL and tagging actions nobody has granted yet. Outside the production server's own role, a presigned S3 URL is then the way to read a file. Listing the prefix's keys is a bucket action the deny doesn't cover, so principals granted the bucket can still see keys, sizes and dates; keys are random UUIDs, and denying listing would break the nightly copy's listing. The bucket is versioned, so a lifecycle rule on that prefix expires deleted versions after a day, which S3 rounds up to the next midnight UTC and runs asynchronously, so in practice a day or two; otherwise every attachment the server deletes would stay in the bucket. Staging's nightly copy of the production bucket skips `mms-media/`: staging's database is anonymized, and these are the first member files that aren't public. A separate private bucket would have needed a new env var and IAM grants. (agent decision implementing the private-storage requirement)
