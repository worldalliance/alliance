# Decisions

All agent decisions. Decisions 1–3 of `docs/provenance/01a1dd1c-671e-76d3-8697-d491bf5e870e-cron-lease-locks/DECISIONS.md` hold the design. These are the choices made while implementing it.

## 1. Keep `@nestjs/locks`; no fallback helper

The store passes the package's whole contract suite, concurrency cases included, against Postgres. Two bun processes racing for one key leave exactly one winner per round. Under bun, the server boots with the ESM-only package loaded and logs `LocksStorage: PgLockStore` (EVIDENCE.md, "Runs"). So the fallback REQUIREMENTS.md 5 allows isn't needed.

## 2. Fencing tokens count per row, not from a sequence

The NestJS recipe draws tokens from a sequence (EVIDENCE.md, "`LockStore` contract and recipe"). Here `release` clears `owner` and never deletes the row, so the row's own `fencingToken + 1`, set in the same `ON CONFLICT DO UPDATE` that takes the lease, grows with every acquisition of its key. The contract asks only for tokens that grow per key. This leaves the schema fully generated by `migration:generate`, with no hand-written sequence to keep apart from the entity. Rows are never deleted, so the table holds one row per lease key the code has ever used: about 16 for the planned cron keys.

## 3. One `UPDATE`/`INSERT` per call, on `clock_timestamp()`

`acquire` is `INSERT ... ON CONFLICT (key) DO UPDATE ... WHERE owner IS NULL OR expired`. Postgres re-checks that condition on the locked row, so of many concurrent callers only one takes a free or expired key. `renew` and `release` are compare-and-set `UPDATE`s on key, owner and liveness. `clock_timestamp()` rather than `now()`, because `now()` is the transaction's start time. TTLs travel as `bigint` milliseconds, since 30 days is past a 32-bit integer.

## 4. `LeaseModule` is wired into `AppModule` now

No job takes a lease yet, but registering the module boots the package in every environment ahead of the cutover (ALL-2368). The production guard against the in-memory store then runs in production, where an incompatibility with this NestJS 11 / bun setup would show up before any job depends on the package. The package's scheduled-job and leader-election scanners find no decorated providers, so nothing runs.

## 5. The dependency is declared in `server/package.json` only

ALL-2367's text also named `apps/frontend/package.json`. The root `AGENTS.md` **Dependencies** rule covers the web packages, and `server` is its own workspace with its own `package.json`. Adding it bumped bun's hoisting of `ajv-keywords` and `@expo/ws-tunnel` in `bun.lock`, with no version changed.

## 6. `@nestjs/locks/testing` is mapped in `server/tsconfig.json` `paths`

The server compiles with `module: commonjs`, whose resolution ignores `package.json` `exports`, the only place this subpath is declared. bun resolves it at runtime. A `paths` entry for the one subpath is narrower than changing the whole server's `moduleResolution`.
