# Collective result groups, update preview, and copy as written

Status: implemented. [REQUIREMENTS.md](./REQUIREMENTS.md) defines the behavior, with origins distinguished. The choices below are agent-authored.

## Data

- `ActionUpdate` has `splitCollectiveResult boolean NOT NULL DEFAULT false`, `nonCompleterResult text NULL`, and `uninvolvedResult text NULL` (migration `ActionUpdateSplitCollectiveResult`). `shortNotifString` is the completed group's text. The default lets a server that predates the columns keep inserting, the same reasoning as `notificationMode`'s default.
- The admin no longer offers a split checkbox. Sending uses two texts: completed (`shortNotifString`) and didn't-complete (`nonCompleterResult`). Away/uninvolved members read `nonCompleterResult`. The server, not the admin, writes `splitCollectiveResult: true` on create and on an edit of a non-legacy row that sets `nonCompleterResult`, and mirrors `nonCompleterResult` into `uninvolvedResult` on every write, so a server from before the result always split still sends the same texts. Origin: agent decision, review round 1. The flag on edit, set whenever the edit sends `nonCompleterResult`, even `null`, keeps a row stored unsplit from being read or backfilled as unsplit: review round 13. No schema migration; the extra columns stay as they are.
- Migration `UnsplitCollectiveResultToNonCompleters` gives every non-legacy row saved unsplit the split shape with all three texts equal to `shortNotifString` (an empty one becomes `NULL`), so those updates keep notifying every group with the collective result. Prepared rows are included so the editor shows what was sent. Its `down` is a no-op: split with equal texts reads the same under the old rule. It lands after the guard and the server's create-time flag, so a stale admin bundle cannot save a new unsplit row once it has run; only the seconds between `migrate()` and the restart remain (ALL-2020). Origin: agent decision, review rounds 1 and 12. It does not cover a row stored unsplit and edited since cfec099: the edit saved it split with a `NULL` didn't-complete text, which can't be told from one an admin emptied on purpose, so whether to restore those is left for ALL-2047 to settle against real rows. Origin: agent decision, review round 14; the user deferred the choice ("I don't know").
- Rows already saved split keep their texts as they are: nothing copies `uninvolvedResult` into a `NULL` `nonCompleterResult`. On such a row, uninvolved members are now skipped, and where the two texts differed they read `nonCompleterResult`. A backfill would send didn't-complete members a text the admin wrote for a different group and chose not to send to them, and skipping someone does less harm than sending them unintended copy. Origin: agent decision, review round 1; the user deferred how this is done ("I don't know"), so a later agent may backfill instead if real rows show this skips members the admins meant to reach.
- `shortNotifString` is not `@IsNotEmpty()`; a send with both texts empty is blocked by `readGroupResults` ("Write at least one group's result.").
- The create and update DTOs take `nonCompleterResult` as optional, and `AdminActionUpdateDto` returns it, never a member-facing DTO. They take `splitCollectiveResult` only as `true`, and `uninvolvedResult` only equal to `nonCompleterResult`: an admin bundle from before the result always split sends `false` for an unsplit save, or a separate uninvolved text for a split one, and gets a 400 reading "Reload the admin to save this update." instead of a save that skips every non-completer or drops the text it typed. Such a bundle shows that text when creating an update, but its edit page replaces any error with "Failed to save update"; the server cannot change what a deployed bundle renders. Bundles from cfec099 on send the two texts equal and are accepted. Origin: agent decision, review round 6; a request failing both reports the flag's refusal alone, round 10. Those inputs are only guards: a `null` flag gets a 400 too, only the server writes either to the row, and the OpenAPI client leaves it out so new admin code doesn't send it. `AdminActionUpdateDto` still returns `splitCollectiveResult` and `uninvolvedResult`, both left out of the OpenAPI client, because an old bundle seeds its edit form from them. Without the flag the bundle saves with no flag, so the guard never fires and non-completers silently keep the stale text. Without `uninvolvedResult` its preview shows uninvolved members getting nothing. `uninvolvedResult` returns `nonCompleterResult`, what uninvolved members are sent, not the stored column, which on a row saved split before this change can hold other text and would get an older bundle's unedited save refused. Origin: agent decision, review rounds 1 to 5.
- The guard does not catch an admin bundle from before the split fields existed (#665, 2026-10-15), which sends neither the flag nor `nonCompleterResult`: its create saves with `nonCompleterResult` null, so every non-completer is skipped, and the whitelist drops its other fields without an error. Neither field can be required on create: bundles from cfec099 on omit `nonCompleterResult` when no didn't-complete text is typed, and the admin no longer sends the flag. Catching such a bundle needs a version marker the admin sends, and the tab would have to have stayed open three weeks, so it is left for ALL-2024. Origin: agent decision, review round 10; the user deferred the choice ("I don't know").
- The create and update DTOs no longer take `notificationMode` or any formula. `createActionUpdate` sets `notificationMode` to `normal` itself, because the column's default stays `legacy` for servers that predate it.

## Shared copy code (`common/src/action-update-copy.ts`)

- `recognitionCopy({ allianceResult, recipientName, link })` builds every recipient's copy: the text as written in-app, "Update: " before it in push and text, its first sentence as the email subject, and a "Hi <first name>" email body. `RecognitionBranch`, `recognitionBody`, `weeksAgoLead`, and `common/src/forms/contribution-formula.ts` are gone, along with `parseContributionFormula` in `shared/parsed-dtos.ts`.
- `RecognitionGroup` and `readGroupResults` are the one implementation of "which text each group reads, and what blocks a send". The server's `readRecognitionConfig`, the preview, and the create dialog's submit check all call it. Completed reads trimmed `shortNotifString`; DidNotComplete and Uninvolved both read trimmed `nonCompleterResult`. Each empty text becomes `null` (skip); both empty fails with "Write at least one group's result." `RecognitionGroup.Uninvolved` stays as a classification for counts; it is not a separately authored text.
- `firstSentence`'s tests live in `common/src/action-update-copy.test.ts`. `sentence-splitter` was added to `common/package.json` and `apps/frontend/package.json` at `^5.0.1`, matching the server's version.

## Planning

- `usesRecognition(mode)` is a `Record<ActionUpdateNotificationMode, boolean>`, false only for legacy. `readRecognitionConfig` returns the group results, or a single message for what blocks a send.
- `recognitionGroupOf({ completed, participant })`: completed → `Completed`; on the participant roster → `DidNotComplete`; otherwise `Uninvolved`. The roster is the existing `findParticipantIdsForActions` rule (assigned − away − withdrawn + completed), so withdrawn members land in `Uninvolved`.
- The roster moved out of `ActionsService` into `ActionParticipantsService` (`findParticipantAction`, `findParticipantIdsForAction[ById]`, `findParticipantIdsForActions`) with no change to the code. The recognition service needs the roster, and `ActionsService` already depends on the recognition service, so the move avoids a circular dependency.
- `prepare` reads the roster before opening its transaction, because the roster takes its own pool connections. Completion comes from the latest terminal activity alone; no form responses or snapshots are loaded.
- `planRecognition` can no longer fail per member. It leaves out every recipient whose group text is `null`. `recordAudience` already created those recipients' exposure rows at send, so at freeze `prepare` soft-deletes them in one `id = ANY(...)` statement. The delivery query skips deleted rows, so no channel reaches them, and the deleted row records that they were in the audience but skipped.
- `prepare` still holds an update whose texts turned invalid after sending, with `readGroupResults`' message as `notificationHeldReason`.
- Sending checks `readRecognitionConfig` directly. The admin "Check recipients" button, `POST /actions/updates/:id/recognition-check`, `RecognitionCheckDto`, and `RecognitionMemberIssueDto` are removed: their job was resolving each member's contribution, and the preview already shows the config problems and the email subject live.
- The `ActionCohort` audience is the roster itself, so `Uninvolved` is always empty for it. Only the `AllMembers` and `Tag` audiences reach that group.

## Preview (admin)

- `apps/admin/src/lib/updatePreview.ts` builds the variations as pure data from the unsaved texts. `components/UpdatePreview.tsx` renders them, and both screens use it. The preview runs the shared copy function on every render, so copy updates on each keystroke with no debounce. If `readGroupResults` fails, its message replaces the cards.
- The placeholders are the sentinel strings `[name]` and `[link]`, highlighted with `<mark>` by splitting the output on them. `[name]` has no space, so `nameParts` keeps it whole.
- `PreviewVariation` is `Completed` and `DidNotComplete`. The didn't-complete card's count is `didNotComplete + uninvolved`. A skipped group's card says "Not notified: this group's result is empty."
- The two inputs live in `components/CollectiveResultFields.tsx` on both screens. Once copy is frozen, the editor page keeps the fields and adds a note that edits no longer reach anyone, and hides the preview. Legacy updates get neither.
- `components/ActionUpdateRecognition.tsx` keeps only `NotificationHeldBanner`. The editor no longer loads the action's form or its variants, which only fed the formula editor.

## Counts

- `POST /actions/updates/:id/recognition-preview-counts` (admin), with body `{ notifyType, tagId }`, returns `RecognitionPreviewCountsDto`: `completed`, `didNotComplete`, and `uninvolved`. The server-side tally, `RecognitionPreviewCounts`, is a `Record<RecognitionGroup, number>`.
- `ActionsService.findActionUpdateAudience` resolves both the send and the preview. Its `decideCohort` flag is false for the preview, so the preview skips `decideOpenAction` and reads only saved cohort decisions.
- `ActionUpdateRecognitionPreviewService` holds the counting (in its own file, because the recognition service was already past 500 lines). The pure tally is `countRecognitionPreview`.
- The editor page refetches through react-query whenever the unsaved audience type or tag changes. These are select inputs, so there's no debounce. A `None` audience shows zeros without a request. "Tag" with no tag picked shows "Pick a tag to count recipients." A failed request shows "Couldn't count the recipients."

## Migrations

- `RemoveActionUpdateRecognitionExperiment` starts from `migration:generate`, with two hand edits. The generator emitted `DROP TYPE "ExperimentArm"` (and a matching `CREATE TYPE` in `down`), but that type is shared with `experiment_assignment.arm`, so both lines were removed. A `DELETE FROM "experiment_assignment" WHERE "experiment" = 'action_update_recognition'` was added before the enum swap, because the cast would fail on those rows. `down` restores the enum value and a nullable `assignedArm` column, but not the deleted rows.
- The admin's pre-send check used to draw arms, so assignment rows can exist even though no update went out; the local db had 196. The migration deletes them regardless.
- `RemoveRecognitionTemplating` starts from `migration:generate`, with two hand edits. The generator emitted `DROP TYPE "ActionUpdateNotificationMode"` after dropping the exposure's `mode` column, but `action_update.notificationMode` still uses that type, so the line was removed, along with its `CREATE TYPE` in `down`. An `UPDATE` moving `retrospective` rows to `normal` was added before the enum swap. `down` restores the columns empty and the `retrospective` value, but not which updates used it.
- `readExperimentArms` lost its last outside caller and is no longer exported. `ExperimentArm` stays because other experiments use it.
