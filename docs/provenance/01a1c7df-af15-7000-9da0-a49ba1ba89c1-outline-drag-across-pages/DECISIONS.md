- Dropping elements on a page's row in the outline, or on the "No elements" note of an open empty page, appends them to the end of that page; dropping between element rows of any page inserts them there, and dropping on a shared-visibility group's header row, or on an open list's or accordion's row, puts them before it, since a line after it would sit below its contents, perhaps off screen, while the page's row takes drops at the page's end; only in a display-only builder, which has no page row, does the last entry on its page keep its after side, the page's end. A collapsed or empty page otherwise has no row to drop on, nor, in a display-only builder, does the end of a page ending in a collapsed group, whose header row takes drops only before it. Appending follows the drop-into-folder convention of file managers. (agent decision)
- "Selected" means the builder's existing selection: a range made with Shift-click or the row checkboxes, or a shared-visibility group. Grabbing an element inside it, or the header row of a shared-visibility group inside it, drags the whole selection; grabbing one outside it drags that element or group alone, so a collapsed group still drags by its header. Those selections are contiguous runs on the open page, so a multi-drag moves a contiguous run from one page. (agent decision)
- When the moved elements hold the selection and land on another page, the builder opens that page with them still selected and scrolls the canvas to them. A selection elsewhere follows the elements' new positions as it did for same-page moves. Undo and redo follow the element the selection starts at onto another page, so undoing such a move reopens the page the elements came from with them selected; within a page they keep the address, as on main. As undo does on one page, a range narrows to its anchor and an id-less block gives way to the page on screen. (agent decision)
- Visibility groups need no special handling. The draft already re-derives groups after each schema change, so a group moved whole keeps its key, and a member separated from its group leaves it, as for same-page moves. (agent decision, reconstructed from `normalizeVisibilityGroups` in `apps/admin/src/lib/visibilityGroups.ts`)
- The scope is the sidebar outline, as asked. Dragging on the canvas still reorders one element within the open page. (agent decision)
- The "Move to page" menu sits in the settings heading beside the move arrows, for an element, a range selection and a shared-visibility group. Sidebar actions otherwise appear only under Advanced, which range and group selections lack. The menu is absent on a one-page form and in a display-only builder, which has no pages to move between. (agent decision)
- On a form that repeats ids (ALL-2007), where two pages share an id or two top-level elements do, a move between pages is refused before it changes the draft, with an error toast naming the repeated ids, quoted, that stays until dismissed. The builder finds a selected element and its unfinished expression text by page id and element id, so on such a form a move between pages could carry them, or a selection the move shifts, to the wrong element. Refusing on any repeat, not only on ids the move involves, keeps the rule to one check, and since moves between pages then happen only on forms without repeats, undo needs no repeated-id case. On such forms the selection keeps main's rules within a page, so the branch brings them no regression, and their pre-existing bugs, such as a reorder or deletion showing the selected element's twin, stay with ALL-2007. Following such an element by reference, and narrower refusals, tried in earlier review rounds, kept drawing cases main doesn't have. The user left how to handle repeated ids to the agent. (agent decision)
