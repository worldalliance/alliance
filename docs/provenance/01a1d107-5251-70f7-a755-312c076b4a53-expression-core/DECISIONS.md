# Decisions

All entries are agent decisions unless they say otherwise. Spec references are to `docs/provenance/01a1c8da-8f1b-7459-9652-87f613c8693c-variable-framework-spec`.

## Layout

- **Module.** The core lives in `common/src/expression/`. `tree.ts`, `catalog.ts`, `failure.ts`, `print.ts`, `evaluate.ts`, `evaluate-operators.ts` and `evaluate-methods.ts` import no TypeScript compiler, so web and mobile can run and print expressions; `common/src/forms/render-path-imports.test.ts` enforces this for the interpreter and printer. `parse.ts`, which parses text, and `convert.ts`, which turns TypeScript's syntax tree into the tree, import `typescript` and run on the server and in the admin editor, as the save check of a later PR will.
- **Parser.** Text is parsed with TypeScript's own parser, not jsep as the old formulas are, so the syntax the parser accepts is exactly the syntax `tsc` checks, and diagnostics from both share one source text.
- **Allowlist reuse.** The methods and `Math` functions an expression may call, and the library declarations `tsc` checks them against, are the old formula system's (`common/src/forms/formula-allowlist.ts`, `formula-lib.ts`). One list of what a formula may call keeps the old and new systems from drifting while forms move over (spec change 14); the new system's strictness comes from its compiler options, not a different library.

## Tree

- **Names.** An input is stored by its stable id, which is also its name in text, so the spec's "rename is a label change" holds with no lookup. A named expression is stored by its id and printed under its current name, so renaming one reprints its dependents. Lambda parameters are stored by name, and the parser rejects one called `eval`, `arguments` or a word strict mode reserves, such as `let`, since the later save check's strict `tsc` rejects it, or `await`, since `(await) ** 2` prints as `await ** 2`, which doesn't parse. Function names, input ids and named-expression names read back as names, which `true`, `class`, `my-name` or a strict-mode reserved word or `await` don't, and differ from each other and from `Math`, `isUnknown` and `undefined`, since otherwise a parsed tree wouldn't print back as text that parses to it; the parser throws on a scope that breaks this, as a host's bug.
- **What the tree can't hold.** `==`, `!=`, `undefined`, `!` after a value, spread, bitwise operators, `typeof`, `as`, assignment and statements have no node kind, so the parser rejects them with a message; `== null` and `undefined` point at `isUnknown(…)` as the spec asks. A function (`x => …`) is accepted only as a method's first argument, where every method that takes one takes it; native methods ignore one in a later place, such as `some`'s `thisArg`. Text TypeScript reads as a call with type arguments, such as `f(a < b, c > (d))`, gets a message saying to write the `<` comparison the other way round, with `>`, as does text whose print TypeScript would read so, and text that fails to parse only because TypeScript read type arguments, which it finds by parsing the text again with each `<` replaced by another operator (`count < [count > (1)].length`). `<`, `>`, `<=` or `>=` with another of them as an operand is rejected: the inner one gives yes/no, which they can't order, and once printed TypeScript can read the pair as type arguments (`count < (-1 > `` `x` ``)`). Text whose printed form TypeScript would read as type arguments is rejected too, saying to write the `<` the other way round: whether it does turns on parentheses the printer drops, as in `count < ({ a: (items).filter(x => x > (count ?? 0)).length }).a`, which parses where its printed form doesn't, so the parser tries the printed text. A function parameter called `this` is rejected, since its printed form `this => 1` doesn't parse, and so is a repeated parameter, which JavaScript rejects. A parenthesized `?.` chain read further, as in `(a?.b).c`, is rejected, since the tree has no parentheses and would print it as `a?.b.c`, which TypeScript reads differently. A `?`, `!` or modifier on a record key or a parameter is rejected rather than dropped, since only `tsc`'s checker reports it. A number literal above `Number.MAX_SAFE_INTEGER` is rejected, since a double past it skips integers, so `9007199254740993` would be stored as `9007199254740992`, and JSON would store one that isn't finite (`1e999`) as `null`. So is a decimal literal with more digits than a double holds, such as `1.00000000000000001`, which would be stored as `1`. A comment is rejected, since the tree has nowhere to keep it and saving would drop it unseen ("Fail loudly", root `AGENTS.md`); that also keeps out a `tsc` directive such as `@ts-ignore`, which would hide type errors.
- **No tree validator yet.** Nothing in this slice reads a tree from storage or the network, so it has no validator; ALL-2195, which stores trees, adds one at the boundary it guards, where it can match what that boundary needs. Text can't give every tree the type allows: a function outside a method's first argument, a read of a forbidden property, `<`, `>`, `<=` or `>=` with another of them as an operand, or a tree whose printed text TypeScript reads as type arguments, such as `a < !(b > (c ?? d))`. The parser produces none of them, so a tree that came from text prints text that parses back to it, and the round-trip test generates only such trees, leaving out any `>` right of a `<`. The printer throws on a reference whose id `refName` has no name for, since printing the id would read back as another name or not parse, on a field read whose name isn't an identifier, which only text in brackets can write and which would parse back as an index, and on a number literal that is negative, `-0` or not finite, which text writes as `-` applied to a number or can't write at all.

## Interpreter

- **Results.** `evaluate` returns `Result<Value, EvalFailure>`, where the failure is an error (with a message) or pending (with the keys it waits on, such as earlier actions). An error outranks pending when both occur, since waiting can't remove the error. An error for a value that doesn't match its declared type names the value's kind (`got text`, `got a number`), not the value, since inputs hold member data that would reach wherever errors are logged or shown (agent judgement, from AGENTS.md's personal-information rule; review round 23). For the same reason a failed read by a key that comes from a value, such as `table[state]`, and a record field its type doesn't declare leave the key out of their error; a dot read and a missing declared field name the field, which the expression's text or the catalog wrote.
- **Unknown propagates.** Only `&&` and `||` (three-valued), `??`, `isUnknown` and function parameters declared nullable absorb an unknown, and a list's `concat` keeps one as an item, as native `concat` does and `tsc` types it, so `names.concat(state)` and `names.concat([state])` agree; every other operation on one, including `!`, member reads, method calls, arithmetic, relational comparisons, templates and a ternary test, gives unknown. A method that takes a function runs it whatever its other arguments hold: `reduce` passes an unknown starting value to it, which `tsc` makes the function handle, and native methods ignore `thisArg`, so the function's errors count, as the requirement that an error anywhere makes the condition an error asks. An unknown inside a list or record passed to a host function, where the parameter's type doesn't allow one, is an error, not unknown, since the function can't take it; the later PR's save check asks for a fallback there first. Both sides of `&&` and `||` are always evaluated, which the requirement that an error anywhere makes the whole condition an error asks for, so the guard idiom the spec prints, `!isUnknown(count) && count > 5`, also evaluates `count > 5` for an unknown `count`; it has to give unknown there, not an error, for the guard to work. `includes`, `indexOf` and `lastIndexOf` give unknown when a missing item could be the one sought and no match comes first, since native lookups would count it a non-match and `tags.includes("vip")` would then decide what `tags.some(t => t === "vip")` leaves undecided. `join`, and `sort` without a function, give unknown for a list with a missing item, since native `join` prints it as empty text and native `sort` orders it as the text "null". The later PR's save check keeps unknowns from reaching a position where propagation would hide them.
- **Selection is lazy.** A ternary evaluates only the branch its test picks, and `??` evaluates its right side only when the left is unknown, as the user's requirement on untaken branches asks; a failed or pending left side of `??` stays failed or pending.
- **Predicates.** `filter`, `find`, `some`, `every` and the other predicate methods run their function on every item before deciding, so an error on any item fails the call, as with `&&`. `some` and `every` then follow three-valued OR and AND over the items. `find`, `findIndex`, `findLast` and `findLastIndex` give unknown when the predicate is undecided for an item before the first match in their search order, as `indexOf` does for a missing item, and `filter` when it is undecided for any item. Native `some` short-circuits, which would make the result depend on item order. `map` and `flatMap` also run their function on every item first, so an error on a later item outranks pending on an earlier one; `sort` with a function runs the interpreter's own merge sort, since engines differ in which pairs native `sort` compares (V8 and Bun differ on a 23-item list) and a comparison can fail or be unknown for one pair alone; it makes every comparison the merge sort asks for, counting an unknown or failed one as equal, then fails with every failure it met, or gives unknown if a comparison was unknown; `reduce` stops at the first failure, since each call takes the previous one's result.
- **Strictness.** `&&`, `||`, `!` and a ternary test take yes/no values only, with no JavaScript truthiness. `===` and `!==` compare text, numbers and yes/no only; `includes`, `indexOf` and `lastIndexOf` seek only those, since native lookups match a list or record by identity, `join` joins only those and `sort` without a function sorts only those, since native `sort` orders a list or record by its text; methods take only those as arguments, since native ones would turn a list or record into text, except a list's `concat` and `reduce`'s starting value, which native ones keep as they are. A text key reads a field or `length` as a dot does, and a number key on a record reads the field its text names, as `tsc` allows. Each operand's type is checked before an unknown one decides the result, so a rejected operand is an error whatever the other operand is, for every member alike. A result that isn't a finite number (division by zero, `Math.log(-1)`) is an error. An input value or function result that doesn't match its declared type is an error naming it, and so is a record carrying a field its type doesn't declare, so a host passing a wider object can't expose undeclared fields. An argument passed to a host function is cut to the fields its parameter declares, since `tsc` lets a wider record pass for a narrower one and the expression couldn't otherwise call it. Methods run on a copy, so `sort` and `reverse` can't change an input.

## Printer

- **Canonical layout.** A small Wadler-style printer breaks a group onto separate lines when it exceeds 80 columns: a chain of one operator puts each operand on its own line, a ternary puts `?` and `:` on their own lines, and argument lists, lists and records put one item per line. A record key is written bare only when it is an ASCII identifier, since a key can be any text and the engine's Unicode tables can be newer than the parser's. A different logical operator nested in `&&`, `||` or `??` gets parentheses: mixing `??` with the others is a syntax error, and Prettier parenthesizes mixed `&&`/`||` for readability.
