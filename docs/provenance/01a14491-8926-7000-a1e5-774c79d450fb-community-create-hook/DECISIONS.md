- `useMyCommunities` owns the `queryKeys.myCommunities()` cache and already holds every other write to it (leave, join a public group, upsert, remove), so creating a group becomes its `createCommunity` mutation rather than a new hook.
- A created group goes into the cache at once, then `refreshMemberships` refetches the user's groups and the public groups, as leaving does. A public group the user creates belongs in the public list too, which web didn't refetch before. The upsert lets callers place an invite into the new group without waiting on a refetch, so the forms' own `refreshCommunities()` after a create goes, along with web `InviteForm`'s "Failed to refresh groups" toast and mobile manage's `refreshAll()` after a create. Mobile manage still refreshes the user afterwards, as before.
- The mutation runs with `networkMode: "always"`, as `useCommentThread`'s writes do, so a create made offline fails its form at once, as the raw SDK call did, rather than pausing until the device reconnects. Leave and join keep the default.
- A failed create's message comes from `thrownRefusalMessage`, which reads the status `registerErrorStatus` puts on the thrown error: a 4xx shows the server's message, a 401 asks the user to sign in again, and a 5xx or a request that never reached the server shows the form's fallback. Passing the thrown error to `errorMessage` instead would show framework or browser text such as "Internal server error" or "Failed to fetch". The create keeps throwing, like leave and join, rather than resolving to a `sendOrExplain` result, since each form already reports through its own error slot or alert.
- The mobile `InviteForm` and `InviteShareLink` create-group handlers were already near copies and now match exactly. Merging them is tracked separately, in ALL-1734.
