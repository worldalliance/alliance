- `useTaskFormSubmission` in `shared/lib/useTaskFormSubmission.ts` owns the viewer's writes of a response to an action's task form: `submit` (`tasksSubmitForm` for a member, `tasksSubmitPublicForm` for a guest) and `optOut` (`tasksOptout`). These calls write no cache entry of their own. They qualify for a named hook because each success moves caches other hooks own: the actions list (`useRecordActionRelation`), the visibility context (`useInvalidateVisibilityContext`) and the form's aggregate views (`useInvalidateTaskFormAggregateViews`). Before, every caller repeated those updates after its call, so web and mobile drifted: mobile left the aggregate views alone after a submit.
- It sits in `shared/` because web and mobile both submit, and `useTaskFormHandlers` (shared) withdraws.
- The cache updates run inside the hook only when the server accepts. The hook hands the client's result back, refusals included, so each platform keeps its own handling of refusals (reload, deadline, formula sources) and mobile's guest-token rotation, which reads the response header.
- Plain callbacks rather than `useMutation`: callers branch on the refusal's status and message, and nothing reads a pending or error state off the mutation.
- Every call passes `throwOnError: false`. Mobile configures the client to throw on a refusal, so a refused withdrawal there now resolves with the refusal instead of rejecting unhandled. Mobile's `ActionTaskPanel` does not render `actionError`, so it still shows nothing; that gap predates this change.
- The relation recorded on submit and withdrawal is keyed by `body.actionId`, the action the server records the response against.
- A guest's submission invalidates the form's aggregate views (the guest's answers count toward them), and touches neither the visibility context nor the actions list, which are the member's. Mobile renders no aggregate views, so invalidating them there does nothing.
