# Decisions

Agent decisions unless marked otherwise. Sources are in `EVIDENCE.md`.

## File layout

- `mms.service.ts` would pass 500 lines once its saves announce thread changes, so Twilio status refresh (`refreshMmsData`) moved to `TwilioStatusWorker`, its only production caller, which fetches through `MmsService.fetchMessage`. The three send paths stay together, since they share dispatch, timeout, late-send recording and alerting. A Claude subagent's split suggestion stood in for Codex's, which was out of usage.
- `mms-thread.service.ts` would pass 500 lines once staff sends check what the sender saw, so recording inbound texts moved to `MmsInboundService`, which only the Twilio webhook calls and which shares nothing with reading, sending or marking a thread. A Claude subagent asked for splits, standing in for Codex, which was out of usage, also proposed moving the rules for which numbers staff may text; that larger move wasn't needed to stay under the limit.

## Session refresh

- `refreshSession` signs the user out only when the server refuses the refresh with 401, the only refusal its refresh route sends. Any other answer, a 403 from a proxy in between included, or a refresh that couldn't be sent, fails the request instead, since signing out over a server error or a dropped connection discards the page for a session that may be fine.

## Transport

- One admin-only Socket.IO namespace, `/mms-threads`, carries both thread changes and composing state; the admin client opens one socket per tab from the sidebar layout, which wraps every page that shows a thread or the Needs reply badge. The repo already runs Socket.IO gateways, and server-sent events can't carry the client's composing reports upstream (EVIDENCE: typing and presence protocols).
- The admin client opens the socket only once the admin is signed in, after the sign-in bootstrap has refreshed a lapsed access cookie. A handshake refused as unauthorized, such as a reconnect after the 30-minute cookie lapsed, refreshes the session through the HTTP client's shared refresh and reconnects, as the token-based messaging sockets do. A refresh answered with anything but success or 401 says nothing about the session, so the socket retries it rather than giving up.
- The handshake is refused in `io.use` middleware unless the token's session is current and its account is an admin, and it fails closed when that check errors. The event-log gateway instead checks admin after connecting, and the shared `socketAuthMiddleware` accepts a verified token when the session check errors; neither suits a feed of every member's thread activity. A check that errors refuses with "Unavailable" and logs an error, so clients retry instead of refreshing a session that is fine, and an outage doesn't read as expired tokens. Revoking a member's admin role disconnects their open sockets, as deleting an account does, and drops a handshake that passed its check before the revocation but connected after it; nothing else ends a session early.
- `MessagingConnectionConfig` accepts `onRefreshToken` without `getAuthToken`, so a socket that authenticates with the session cookie can refresh the cookie and reconnect after a refused handshake. This supersedes the decision in `01a0a70c-f48e-7000-9a50-d85aa6870b39-mobile-oauth-login/DECISIONS.md` that the config requires `getAuthToken` whenever a refresh callback is supplied; the refresh contract is otherwise unchanged. A socket without `getAuthToken` that has `onRefreshToken` opens its own connection rather than sharing one with the tab's other sockets on that origin, since Socket.IO sends cookies only with a connection's opening request and a shared one would retry a refused handshake with the old cookie. A cookie socket that never refreshes, such as the frontend's, keeps sharing, so it costs no extra connection.
- Every messaging socket retries a handshake refused as "Unavailable", backing off from one second to thirty as the token refresh does, with each delay jittered by up to half either way so sockets refused by one outage don't retry in lockstep, because Socket.IO doesn't retry a refusal from middleware and a database blip would otherwise leave the socket down until the page reloads.
- Every thread change is broadcast to all admin sockets as `{ phoneNumber, needsReplyChanged }`, and each client refetches only the cached threads whose `phoneNumber` matches. Per-thread rooms would need join and leave bookkeeping across reconnects, for an admin audience small enough that a broadcast costs little.
- `needsReplyChanged` is false for automated outbound texts, their status changes, attachment copies, and a staff text's status changes other than into or out of failed, undelivered or canceled, so each text of a broadcast or each delivery report doesn't make every admin refetch Needs reply.
- Events are emitted after the write commits, from each writer: inbound texts, outbound saves (staff, automated, and late-recorded sends), Twilio status changes, handled and needs-reply marks that change a text, opt-outs and resubscribes, including those of a number no member holds, and attachment copies that finish or give up. A TypeORM subscriber was rejected because entity events fire before commit and query-builder updates carry no entity. Phone-number changes, such as a verification moving a number between accounts, and account deletions emit nothing: they are rare, and the 60-second poll picks up a member page's new number, after which pushes match it, and the members a thread, Needs reply row or Texts row names. A listener's error is logged rather than thrown into the writer, whose change has already committed; the poll still picks the change up.
- While connected, the member and number thread queries and Needs reply poll every 60 seconds (user-approved fallback); while disconnected they keep their earlier 10- and 30-second intervals. The Texts list keeps not polling, as `01a1e6f9-f8e9-770e-b299-a69524ccbfde-sms-threads-by-number` decided, since the requirement makes pushes its refresh. Every `connect` refetches all thread queries, Needs reply and the Texts list, since Socket.IO doesn't guarantee delivery across a disconnect.
- A push also refetches thread queries with no data yet, whose number is unknown: a first load in flight, or one that failed, which would otherwise wait for the 60-second poll, unless the server refused it, since a change to some other thread can't change that answer. A push or `connect` joins any fetch in flight, whose response may predate the change, and fetches again once it settles, once however many pushes arrive meanwhile: cancelling and restarting it on each push would apply no response until a stream of pushes ended, keeping a thread opened during a broadcast loading. Pushes refetch Needs reply at most once every 5 seconds per tab, first and last of a burst included, besides the refetch on each `connect`, since that list's query scans every unanswered text and a burst of replies to a broadcast would otherwise refetch it once per text in every open tab. The Texts list, whose query sorts every inbound and staff text, refetches on every push under the same 5-second throttle, `needsReplyChanged` or not, as the requirement says; filtering on that flag would skip only changes that leave the list as it was, but would tie the list to a flag named for Needs reply. In a hidden tab a push only marks the queries stale, and they refetch when the tab is shown, as TanStack Query's polling already pauses there.

## Composing

- The server keeps composing reports in memory per socket and phone number, expiring each 10 seconds after its last refresh; the client refreshes at most every second while the draft has text and changes, so the notice lasts nine to ten seconds after the last edit without a timer to report skipped edits later, and sends a stop when the draft empties or the composer unmounts. These follow the start, refresh and expire pattern of Matrix and Twilio (EVIDENCE: typing and presence protocols). Disconnecting drops a socket's reports, and an admin with several tabs is listed once.
- In-memory state assumes one backend process (EVIDENCE: repository measurements); running several would need a shared adapter and shared composing state.
- Composing is keyed by phone number, the thread's `phoneNumber` as the member and number thread endpoints return it: `mms_thread.phoneNumber` on a number's page, and on a member's page the member's `phoneNumber`, which is the `Mms.memberPhoneNumber` that page's texts are matched by. Both are the raw string the texts were recorded under, never normalised, so a composer and a list row always name a thread by the same string its texts and thread-changed pushes carry, and a mismatch would show first as a member page listing no texts. Not by `mms_thread.id`: a number with no texts may have no row yet, and thread-changed pushes already name numbers. The server refuses a composing report whose `phoneNumber` is missing or empty, logging it as malformed. The protocol is new in this unmerged branch, so the change from member ids needed no backward compatibility.
- Composing reports use volatile emits, so a report made while disconnected isn't replayed late on reconnect. Stops don't, since Socket.IO also drops a volatile packet whenever the transport is busy, which would leave the notice up until it expires; a stop replayed on reconnect is harmless, as the server dropped the old socket's reports on disconnect. A reconnect reports a draft only if it was edited within the 10-second expiry, which `common/` shares between server and client, so a deploy that reconnects every tab doesn't show idle drafts as replying. The server starts a draft's expiry afresh from that report, so around a reconnect the notice can outlast the last edit by up to twice the expiry; reconnects are rare, so the report doesn't carry how long the draft has left.
- The notice reads "<name> is replying…" (names joined with "and" for several), beside the composer's label on both thread views and on the Needs reply and Texts rows. Beside the composer it is a `role="status"` region that stays mounted so screen readers announce it; on a list row it is plain text beside the contact's name, since an announcement there wouldn't say which thread it is about, and on the name's line, which it truncates to fit, so a row doesn't change height and move the rows below under the pointer.

## Sending over newer texts

- `afterId` is the record REQUIREMENTS defines: the last-saved text, by id, in the thread's latest page when it was taken, or null for an empty thread. Newer means saved later, by id on both sides, not dated later: a staff text's `createdAt` is taken before its Twilio call, so another admin's reply saved after the text the sender saw can be dated before it. The composer reads it from the query cache rather than its props, so the record taken on a refusal sees the refetch that landed before the warning renders. A send doesn't move it, since that would take in texts that arrived during the send; instead the sender's own texts don't count as newer, so a draft typed while their send was in flight isn't refused over it. The server refuses with 409 and `error: "newer_texts"` when any other text, inbound or outbound, is newer, on a member's thread and a number's thread alike, since both send through `MmsThreadService`'s one staff-text path. When `afterId` isn't in the thread, a member's send is refused with `error: "number_changed"`, as after their number changed, since the sender hasn't seen that thread and no text may have arrived; a send by thread id is refused with 400 "That text isn't in this thread.", since that thread's number can't change and such an `afterId` is a client bug. A 409 already means "opted out" on this endpoint, so the client tells them apart by `error`, as the OTP refusals do. The composer treats a 409 whose `error` it doesn't recognise like any other failure, showing the server's message, so a tab loaded before a later conflict value still shows a readable refusal.
- A refusal whose refetch failed shows an error saying the new texts couldn't be loaded instead of a warning with nothing to read. The composer asks the query whether the refetch failed rather than comparing text ids, since the cache counts the sender's own texts, which the server ignores. That refetch makes one attempt, without the query's retries, so the sender doesn't wait on a send the server has already refused.
- The warning and "Send anyway" appear once the refetch has landed, and "Send anyway" resends with the refreshed thread's newest id. It skips the quiet-hours check only when the refused send had passed it as confirmed by staff; otherwise it checks again, since quiet hours can begin while staff read the new texts.
- The warning scrolls the thread to its end, which brings the new texts into view when staff had scrolled up to read history; marking which texts are new was not added, since the warning says they arrived while staff wrote and they sit at the end.
- `afterId` is optional on the server, on both send endpoints, marked `BACKCOMPAT(staff-text-after-id)`, because admin tabs opened before this release send no `afterId` and would otherwise be refused. The server logs each send without `afterId`, and the contract step follows a week with none, since an admin tab can stay open for days.
