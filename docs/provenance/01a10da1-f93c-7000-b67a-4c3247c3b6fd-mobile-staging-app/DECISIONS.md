# Agent decisions

- **Variant record in app.config.js.** The `IS_DEV` ternaries became a `VARIANTS` record keyed by `APP_VARIANT` (development, staging, production). Unset still means production. Unknown values and a variant without a Google iOS client ID throw at config time. Production and development resolve to the same config as before; their fingerprints were compared before and after the record and matched.
- **Staging identity.** Bundle ID `com.alliancefoundation.alliancemobile.staging` and package `com.alliance.alliancemobile.staging`, following the `.dev` pattern. Hosts `staging.worldalliance.org` and `staging.thealliance.org` for associated domains and the Android App Link, because the server returns mobile OAuth on staging's `APP_URL`.
- **Runtime target from the application ID.** The bundle picks the API URL, PostHog project and feature-flag environment from `expo-application`'s `applicationId`. An `EXPO_PUBLIC_APP_VARIANT` that app.config.js sets was tried first: a staging export without `--clear` after a production export still carried `"production"`, because Metro's transform cache ignored the change. The installed binary can't be stale that way.
- **Dev builds running a published update talk to production**, as every non-`__DEV__` bundle did before.
- **Staging analytics and flags.** The staging app uses the staging PostHog project and staging feature flags, matching what `apps/frontend/.env.staging` and `isEnabled` give staging web. The production PostHog host moved from `apps/mobile/.env.production` into `releaseTarget.ts`, which removed that file's only variable, so the file was deleted.
- **One OTA workflow.** `publish-mobile-ota.yaml` takes an `environment` input that names the EAS branch, the GitHub environment and `APP_VARIANT`, so staging and production share the publish step. Dispatch still defaults to production.
- **Rebuild warning.** Following the user's choice, the staging run posts a GitHub warning annotation when no finished staging build has the commit's runtime version for a platform. It still publishes, so the next rebuild gets the latest update. It loads the app config on its own first because `@expo/fingerprint` hashes a config it failed to load.
- **Deploy notify.** `publish-mobile-ota` now runs on both branches, so a skip means an upstream failed; it alerts on anything but success, like the other jobs.
- **OAuth return package.** The Android `intent:` fallback on the callback page names the staging package when the frontend is built in staging mode. The Play Store link in onboarding keeps the store package.
- **Apple association file.** The staging bundle ID was added to `webcredentials`. `assetlinks.json` waits for the staging signing certificate's SHA-256.
- **eas.json changes the production fingerprint.** `@expo/fingerprint` hashes `eas.json`, and every profile inherits `APP_VARIANT=production` from `base`, so the staging build needs its own profile. This moves the production runtime version once; it has to ship with a store build.
- **Android before the iOS client ID.** At the user's request ("unblock Android"), the missing-ID check fails only where `EAS_BUILD_PLATFORM` is `ios`. eas-cli leaves that variable unset on the machine that starts a build, so the check can't run any earlier there. Without an ID, the Google sign-in plugin is left out entirely: called without options it switches to its Firebase setup, which also changes the Android build. Adding the ID later changes the staging Android fingerprint once.
