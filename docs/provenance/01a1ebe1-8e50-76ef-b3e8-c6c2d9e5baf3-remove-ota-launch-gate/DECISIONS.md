# Decisions

- **The splash hides by itself.** The gate held the native splash with `preventAutoHideAsync`, plus a 30 s watchdog, and hid it once it opened. With the gate gone nothing needs the splash past the first render, so both go and expo-splash-screen hides it when the root view mounts. Agent decision.
- **Gate-only code is deleted, not kept for later.** `ota_gate_resolved`, `OtaGateOutcome` and `ota_gate_crashed` in `common/src/analytics.ts`, `flushAnalytics` in `shared/lib/analytics.ts` (only the gate flushed before reloading), the backend's optional `flush`, and the splash-stand-in constants only the progress screen read. Builds still running the gate keep sending `ota_gate_resolved`; PostHog accepts events the code no longer names. Agent decision.
- **Update identity goes in through PostHog's `customAppProperties`, at init.** `register()` runs after init, and its super properties persist across launches, so the lifecycle events PostHog captures during init would carry nothing, or the previous launch's update. `customAppProperties` is read once per JS runtime, which matches the `Updates` constants: a reload starts a new runtime. PostHog types the object as a closed set of `$app_*`/`$device_*` keys, but spreads all of it into every event, so the extra keys arrive as properties. Field set follows Sentry's Expo integration (EVIDENCE.md) plus `ota_updates_enabled` and `ota_update_created_at`. Agent decision, from a codex second opinion.
- **The identity properties go on release builds only.** Development builds run with expo-updates disabled and PostHog opted out. Agent decision.
- **One PR.** The researcher pointed to Google's and GitHub's guidance on one purpose per PR; the codex second opinion read that guidance as asking for focused changes rather than separating telemetry, and the identity data is what shows whether updates land. Agent decision, announced to the user without objection.
- **No OTA debugging doc in this PR.** It was proposed alongside an alert; the user dropped the alert, and most of what the doc would have explained (gate outcomes, `applied` logged before the reload, the iOS/Android difference in the gate's inputs) no longer exists. Reading the fleet's update is a PostHog breakdown by `ota_update_id` and `$os`. Agent decision.
- **Verification on a release build is left to production data.** Exercising "an update downloaded at launch surfaces the restart banner and runs on the next cold start" needs a release build pointed at a published update. After this ships, `ota_update_id` per `$os` in PostHog shows whether iOS and Android pick up updates alike. Agent decision.
