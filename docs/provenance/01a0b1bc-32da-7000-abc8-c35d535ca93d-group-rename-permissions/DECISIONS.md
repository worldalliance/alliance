- `ParticipantRole` moved from the participant entity to `common/src/participantRole.ts`. The client helper in `shared/` kept its own copy of the admin rule keyed on the generated client's union, so server and client could disagree about who is an admin and the client could offer a control the server refuses.
- The rule is a `Record<ParticipantRole, boolean>` rather than an array or a predicate, so a fourth role fails the build in every package until someone opts it in or out. The old server form, `[Admin, Owner].includes(role)`, would have made it non-admin without a word.
- The Postgres enum keeps the name `ParticipantRole` and its three values, so there is no migration and no change to the generated client.
- `ParticipantState` stays on the entity. Nothing outside the server reads it as an enum.
- `getParticipantState` takes a missing conversation and returns null, like `isConversationAdmin`, so the mobile screen drops its own null check. Web's conversation panel keeps its `mode === "new"` check, which is about the mode rather than null: the new-mode props allow a conversation, and the new-message view is never an invite.
- `updateConversation` calls `ensureConversationAdmin` itself, like `addParticipantToConversation` and `removeParticipantFromConversation`, and the controller drops its `ensureParticipantAndRun` wrapper. `ensureConversationAdmin` goes through `getParticipantOrFail`, which refuses an outsider with the same 403, so the wrapper only added a query.
- The admin check runs before `updateConversation` looks at the chat's type, so it covers every type. In a community chat only leaders, who sync in as `Admin`, can update it. In a direct chat both people are `Member`, so an update returns 403 where it used to return 201 and save nothing. Neither client offers the editor in those cases.
- Outside edit mode, the mobile group photo shows the server's photo, not the form's, like web. A pick that comes back after edit mode ended would otherwise show as the group photo with no Save button.
- Web loads the group edit form from `selectedConvo` when the pencil is clicked, not once when the info panel mounts. A rename pushed from another admin updates the header while the panel is open, and a form filled at mount would still hold the old name and save it back.
- A failed group save on mobile is sent with `throwOnError: false`, like the comment hooks, so the alert can go through `refusalMessage`. `sendOrExplain` takes the client function and its options and sets the flag itself. When the flag was the caller's job, a caller that left it off still typechecked, and mobile then showed every refusal as "Please try again." The server's own refusal shows its message, a 401 asks the user to sign in again, and a 5xx or a dropped connection says to try again. `errorMessage` alone put framework text like "Internal server error" in front of the user.
- The save's handling lives in `sendOrExplain` in `shared/lib`, which sends a request and returns what to tell the user when it fails: a title ("Couldn't save the group") and a message. It returns words instead of showing them, so bun test can run it without react-native. `action` fills in both the title and the sign-in line, so the caller names only what it was doing.
- Web's group save calls `sendOrExplain` too, so it gets the same words as mobile, and a save that never reaches the server ends the spinner and says so. Web shows the title and message as one line, "Couldn't save the group. Please try again.", in the panel's existing error slot.
- Mobile leaves edit mode when the user stops being able to edit the group. Save and Cancel only render while they can edit, so otherwise the title input would stay up with no way to save or leave. Nothing takes the right away mid-edit yet: only a named group's creator can edit it, no endpoint changes roles, and a removed member gets no live update. The check is for the first change that does.
- Web closes the group editor when the viewer stops being able to edit the group, like mobile. Otherwise the name input and Save stay up and saving gets a 403.
- Mobile loads the group edit form from the server when "Edit group" is tapped, not from an effect that runs whenever edit mode is off. Each edit starts from the server's title and photo, so a pick that lands after edit mode ended can't carry into the next edit and get saved.
- Who can add and remove members is its own `Record<ConversationType, boolean>` in `common/src/conversationType.ts`, not the editable-info one. The two agree today, but they're separate rules. Both clients ask `canEditConversationMembers`, and web's info panel drops its `isAdmin` prop, since that check now happens inside the helper.
- The server refuses adding or removing members outside a group chat with a 403, checked after the admin check like `updateConversation`. Before, community leaders sync in as `Admin` and could add anyone to a community chat, or kick a member, over the API. The community decides who's in its chat: `syncCommunityConversationMembers` removes anyone added by hand and re-adds anyone removed the next time it runs. A direct chat already refused, because both people are `Member`. Neither client offered these controls outside groups. Leaving a chat goes through `leaveConversation`, which doesn't change.
- Mobile's add, remove, and leave ignore a tap while any of them is still out. Leave greys out and the search results dim. A double tap otherwise sent two requests, and the second came back refused, "You are not part of this conversation.", on top of a leave that worked. The X dims to half opacity and uses `disabled` to expose its unavailable state to screen readers. Its profile link is a sibling, so disabling removal cannot pass the tap to profile navigation. The guard is `useOneAtATime` in `shared/lib`, which drops a task handed to it while one is running. It checks a ref, not state, so a second tap that lands before the re-render is still dropped, and its test covers the double tap, which the mobile screen has no component test for. Add is guarded too. The server returns the group unchanged for someone already in it, but two adds sent at once both get past that check, and the second insert breaks the one-row-per-member constraint and comes back a 500. The search rows aren't inside another tappable, so they take `disabled` as well as dimming.
- Adding a member who gets added by another request at the same moment returns the group unchanged, the same answer as adding someone already in it, instead of a 500. Both requests pass the 'already in it?' check, and the second insert breaks the one-row-per-member constraint. The service catches that unique violation, as `forum.service.ts` does for likes. A client guard can't cover two devices, or a retry.
- The remove-member X is labeled "Remove <name>" on both clients. Web sets it through the shared `Button`'s `title`, which is both the tooltip and the accessible name, so `Button` doesn't grow an `aria-label` prop. Mobile sets `accessibilityLabel` and `accessibilityRole`. The profile and remove controls are siblings on both clients. Nesting them adds the remove label to the web link's name and can hide the mobile remove control from screen readers.
- Web's add, remove, and leave go through `sendOrExplain` like the save, and share the panel's one error slot. The title in front of each message says which action failed. The slot is `role="alert"`, so a screen reader reads the message out when it appears, the way mobile's `Alert` is read. Every action that writes the slot, the save included, clears it as it starts, so the message names the attempt in flight, not one two clicks ago that the round trip would leave on screen.
- Web's add, remove, and leave go through `useOneAtATime` like mobile's, so a click while any of them is still out does nothing, Leave group greys out, and the search results dim. The X takes the shared `Button`'s `disabled`, which dims it and shows the not-allowed cursor. The search results are clickable `div`s with no `disabled` to set, so they dim and take `pointer-events-none`, which also stops the hover highlight from claiming the row is still live. The guard drops a click that gets through anyway, from a keyboard or a second device.
- Web's one error slot sits above the panel's scrolling area rather than inside it, so a failure from the remove X or Leave group, which both sit below the member list, stays in view instead of rendering off the top of a scrolled panel. On a ten-member group it was 600px above the fold, and the click looked like it did nothing. A `sticky` slot inside the scroll would have been two classes instead of a wrapper, but the slot is opaque, so it hid whichever member row it came to rest on, which after a failed removal is usually the one the user was trying to remove. Outside the scroll it covers nothing and needs no `z-index` of its own. `px-14` keeps a long message clear of the back chevron, which is absolute over the whole panel. Mobile puts the same words in an `Alert`, which is always in front.
- `sendOrExplain` reports every failure it explains through `captureException`, as `ExceptionEvent.RequestFailed` with the `action` and, for a refusal, the status, like the comment hooks. Otherwise a dropped connection or a proxy's 5xx on a group change left no trace beyond the device's console. One event for every caller, told apart by `action`, so no caller has to pick one. Refusals the user can act on, like a 401 or a 403, are reported too, like the comment hooks do.
- The group name field in both clients' info panels stops at 500 characters, the server's limit, with a `CharacterLimitNotice` under it, like the community name fields. Before, a longer name reached the server and came back as class-validator text in the failure alert. The limit is `CONVERSATION_TITLE_MAX_LENGTH` in `common/src/conversation.ts`, which the three conversation title validators in the server DTOs read too, so the clients and the server can't drift apart.
- Which chats show "Leave group" is its own `Record<ConversationType, boolean>`, `conversationTypesUsersCanLeave`, next to the member and info ones, and both clients ask `canLeaveConversation`. It's a separate rule from editing members: any member can leave, admin or not. A direct chat has no one to leave, and a community chat gets its members from the community, so neither offers it.
- The server refuses leaving anything but a group with a 403, using `conversationTypesUsersCanLeave`. Before, a community member could leave the community's chat over the API and the next `syncCommunityConversationMembers` put them back, and either person could leave a direct chat and strand it with one participant.
- `declineInvite` refuses with a 403 unless the caller's participant state is `Invited`. Before, it removed any participant, so a joined community member could call decline to leave the community chat, getting around the leave rule. Both clients show Decline only while the user is invited. A 403 matches the leave refusal.
