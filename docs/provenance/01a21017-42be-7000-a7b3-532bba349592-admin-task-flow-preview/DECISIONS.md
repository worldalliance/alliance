# Decisions

## Moving the task flow into sharedweb

- The flow lives in `sharedweb/forms/taskflow/`, inside a directory `sharedweb`'s tsconfigs already include, so no build config changes. `ProgressBar` and `Timeline`, which it needs, move from `apps/frontend/src/components/system/` to `sharedweb/ui/`, and their frontend callers import them from there. (agent decision)
- The host interface is `TaskFlowHost` in `sharedweb/forms/taskflow/host.ts`, plus a `TaskFlowViewer` prop. The host supplies what differs between apps: how the app's chrome reacts while the panel is up (the member nav's immersive mode), resuming a flow the member left mid-task, what the completion screen's buttons do, where the panel sits, and what renders under a profile phone question (the members' code confirmation, which `main` added to the flow while this branch was open; the flow still offers it only when it records a signed-in member who isn't being impersonated). Its hooks are module-level functions, so the flow calls the same ones on every render. The viewer prop carries the user, sign-in and impersonation state, because the admin's preview member is runtime data. The members' wiring is `apps/frontend/src/components/taskflow/memberTaskFlowHost.tsx`, which holds the code that `TaskFlow.tsx` used to run inline. (agent decision)
- `ImmersiveTone` moves to the host module, because the shared completion screen picks the tone and the frontend nav reads it. (agent decision)
- The moved files keep the React hooks lint rules the frontend's ESLint config gave them: the root config, which lints sharedweb, applies them to `sharedweb/forms/taskflow/` and the components moved to `sharedweb/ui/`, and the flow destructures the host's hooks so the rules see their calls. Widening the rules to the rest of sharedweb, which never had them, is ALL-2492. (agent decision)
- The flow's integration tests (`TaskFlow*.test.tsx`, `TaskFlow.testing.tsx`) stay in `apps/frontend/src/components/taskflow/`, with only their imports changed. They render the members' `ActionTaskPanelForm` with the frontend's auth, nav and router, so they test the members' wiring through the host interface, and passing unchanged is the evidence that the members' flow didn't change. Only the unit tests of moved modules (`flowMotion`, `useExpandingPanel`) moved with them. This departs from the approved "tests moved alongside", because moving the integration tests would mean moving `ActionTaskPanelForm` and the frontend's auth context with them. (agent decision)
- The task panel's card and its completed header are extracted to `sharedweb/forms/taskflow/TaskPanelCard.tsx`, so the members' panel and the admin preview render one implementation. `StackedCard`, which it renders, moves with it from `apps/frontend/src/components/system/` to `sharedweb/ui/`. The members' `ActionPageTaskPanel` passes its Share button in as the header's trailing content. (agent decision)

## The admin's task flow preview

- The admin form endpoint (`GET /tasks/adminForm/:id`) answers with `AdminFormDto`, which adds `usedInAction`, the action resolved by the existing `ActionFormLinksService.findActionsByFormIds` (task form first, then variant), as the forms index already reports. `FormDto` itself is left alone, because members' form endpoints serve it too. (agent decision)
- `TaskFlowViewer.previewUserId` marks a staff preview. The flow then passes it to the form state as `adminPreviewUserId`, which is what the admin's existing preview passed to `FormRenderer`. It also stops the flow from loading the signed-in viewer's own city: `TaskAnswersCard`'s `showsOwnLocation` is false, so it shows the previewed member's stored city string, not the staff member's location. The flow throws when a staff preview or an unsaved schema runs in a mode that records answers, so a preview can never save or submit under the staff member's account. (agent decision)
- The completed card's response is built in the browser (`previewFormResponse`) from the preview's answers, public-answer choices and the formula options offered, as `selectedFormulaChoices` computes them. It keeps the visibility validator verdicts and device type the preview's form ran with, as a submit does, so output blocks gated on them show on the completed card as they would on the member's. (agent decision)
- The builder treats a form with `usedInAction` as a task form wherever it opens, including `/forms/:id` and the suite launch's `previewAs` links. The builders that edit an action's task form (the action dashboard and the project action page) also say so directly, because the builder doesn't reload a form it has just created, so `usedInAction` is unset until the next load. (agent decision)
- The owner deferred which header the preview panel shows ("I don't care"). The agent's pick: "Preview" over "Nothing you enter here is saved.", styled like the members' staff preview header. The members' "Staff preview" copy is not reused, because it says the action hasn't gone out to members, which isn't true of every form previewed from the admin. (agent decision, owner-deferred)
- The task flow preview applies to forms members fill through the task flow: an action's task form or one of its variants, which the builder recognises as task forms. The stand-in action's name falls back to the name of the action `usedInAction` names. Follow-up, update and standalone forms keep the existing paged preview. (agent decision)
- "Below the admin's top bar" is read as the area below the form builder's header bar, the one holding Edit and Preview. The panel portals into a wrapper around the builder's content area and fills it (`absolute inset-0`), so it sits right of the admin sidebar and below the builder header, and Edit stays in reach. (agent interpretation)
- In preview the flow runs in `TaskFlowMode.Preview`, which already never calls `submit` and saves no draft or position. The admin also passes a `submitTaskForm` that throws, so a future path that tried to submit would fail loudly instead of writing. `TaskFlowPreview.test.tsx` records every non-GET request and asserts none was sent through submit, the completion screen and the completed card. (agent decision)
- The completed card reuses the members' read-only flow ("View task") and `CompletedTaskHeader`, and puts "Start over" where the members' Share button sits. "Start over" remounts the flow, which clears the answers. Changing the previewed member or row also remounts it. (agent decision)
- The preview starts on the flow's first step, as a member does, instead of on the page selected in the builder, which the old paged preview opened on. (agent decision)
- Where neither the form builder nor the form names an action, the stand-in action is named "Task preview". The name shows only as the title of a blocked form's screen. A blocked form shows the staff detail the old preview showed (`showDetail`, plus `draft`, since the preview always renders the builder's in-browser schema, as the old preview did). (agent decision)
- The admin theme gains the frontend's `--color-grey-0`, `--color-grey-1` and `--color-navy`, which the shared task panel's cards, the flow's outline dots and its completion buttons use. Without them those backgrounds didn't render in the admin. (agent decision)
- The preview sends no member analytics. The admin never calls `registerAnalytics`, so the shared `captureEvent` the form and flow use only buffers there and never sends. The form's page-tracking hooks are also off whenever the form has no `onSubmit`, which is true in preview, and the admin passes a no-op `onFormStarted`. The admin's own PostHog, which records staff sessions, is unchanged. (reconstructed from existing code)
