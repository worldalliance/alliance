# Decisions

Decisions carried from `docs/provenance/01a1ce4b-16f7-713d-9845-fe08e3ffa147-ci-deploy-speed/DECISIONS.md` and implemented here: the lock sits on the job that calls a reusable deploy workflow, with a hard-coded group name; that workflow takes the deployed commit as an input; live state is recorded as GitHub deployments, which the staging guard reads; "newest for production" is the `production` branch's tip when the lock is acquired; the hosts roles pin the reusable workflow, rolled out by expand and contract.

## Shape

- **The reusable workflow is `.github/workflows/deploy-environment.yaml`.** It holds the guard, the backend, frontend and admin deploys, the three `verify-*` smoke checks, the production OTA publish and the job recording the result. `deploy.yaml` keeps the checks, builds, `deployed-config`, `upload-react-sourcemaps`, `mobile-fingerprint-check` and `notify`, and calls it from one `deploy` job holding `concurrency: {group: deploy-<environment>, queue: max}`. This extracts one stage of ALL-2012's split of `deploy.yaml` and leaves the rest of that issue open. Origin: agent decision.
- **`publish-mobile-ota` moved under the lock.** Outside it, an older run's OTA publish could land after a newer run's. It still isn't part of the recorded result, matching the spec's list of jobs that "fully green" excludes. Origin: agent decision.
- **The deployed commit reaches every checkout in the called workflow, `publish-mobile-ota.yaml`'s release checkout included**, which takes it as a `commit` input when called, as ci-deploy-speed's DECISIONS has a call pass the commit. `VITE_APP_GIT_SHA` stays where the frontend is built, in `deploy.yaml`, which this PR doesn't move. Origin: agent decision.
- **`publish-mobile-ota.yaml` still tells a dispatch from a call by `github.event_name`; ci-deploy-speed's inputs-based gate is deferred to ALL-2166.** The only caller today, `deploy.yaml`, runs on push, so the two agree. The override, the first dispatched caller, arrives with ALL-2166 and changes the gate with it. Origin: agent decision.
- **The production freeze check stays where it is** (`dirty-check` in `deploy.yaml`, outside the lock). Moving it into the called workflow is part of the promotion work, ALL-2166. Origin: agent decision.
- **`notify` names the failed jobs from the run attempt's job list**, as `build-staging-mobile.yaml`'s alert does. A called workflow reports a single result to its caller, so `needs` would name only `deploy`, hiding whether a deploy, a smoke check or the OTA publish failed. When the job list can't be read, the alert still posts, saying the failed jobs are unknown. Origin: agent decision.

## Guard and deployment record

- **The guard is a composite action, `.github/actions/deploy-guard`, whose script has unit tests** with a stand-in `gh`, following `run-on-host`. Origin: agent decision.
- **Records go in their own environments, `staging-live` and `production-live`.** Actions opens a deployment in an environment for every job naming it, several per run (EVIDENCE.md, "Deployments Actions creates"). Those would read as live for runs that never finished deploying, and on a non-production environment each success marks earlier deployments there inactive, ours included. Origin: agent decision.
- **The guard opens the record (`in_progress`) once it decides to deploy, and a final `record` job sets `success` only when the guard, all three deploys and all three smoke checks succeeded, else `failure`.** It runs under `always()`, so a cancelled or failed run doesn't stay `in_progress`, and tries the post three times, since a partial re-run can't retry it. Both status posts pass `auto_inactive=false`: GitHub's docs can be read as marking the previous successful record in a non-production environment inactive on any new status, which would leave `staging-live` with no live commit after a deploy starts or fails, so the flag keeps live-commit.sh's reading true however GitHub applies it. Origin: agent decision.
- **Every job in `deploy-environment.yaml` after `guard` fails in any attempt other than the one that ran the guard.** A partial re-run keeps the guard's outputs from the earlier attempt, so its deploy jobs and OTA publish would otherwise land the commit without judging whether it is stale, and its smoke checks and `record` would mark that attempt's deployment successful on checks run later, against whatever the hosts serve by then. The guard outputs its `github.run_attempt`. A step shared through a YAML anchor (supported since 2025-09-18, https://github.blog/changelog/2025-09-18-actions-yaml-anchors-and-non-public-workflow-templates/) fails each deploy, smoke-check and `record` job when that differs, pointing at **Re-run all jobs**; `record` fails before posting, so the record keeps the guarded attempt's result. `publish-mobile-ota`, a called workflow that can't take the step, gets the attempt as a required `guard-attempt` input and runs the same check first. Origin: agent decision.
- **A live commit is the newest record whose newest status is `success`, among the newest 100 records** (`live-commit.sh`). With none, nothing is treated as live. Origin: agent decision.
- **Staging's guard compares against the newest `staging-live` record whatever its state, not the live commit**, so a newer deploy that started and failed still counts as already deployed. Checks now finish out of order, so an older run can take the lock after a newer one whose deploy reached the hosts and then failed a later step; deploying the older commit then would roll staging back onto the newer commit's migrated schema. The user deferred this choice, how the work is done rather than whether ("I don't care", review loop round 9); this is the agent's recommendation. With no record, the deploy goes ahead. Origin: agent decision.
- **Staging skips when the compare API says that record's commit is `ahead` of this one.** Equal commits redeploy, `behind` or `diverged` deploy, and any other status fails the run. Origin: agent decision.
- **`publish-mobile-ota`'s dispatch gate reads production's live commit from `production-live`**, through the guard action's `live-commit.sh`. A production run whose guard skips concludes success, where the old concurrency group cancelled it, so the newest successful Deploy run no longer names the commit production runs. With no recorded success, which holds until production first deploys through `deploy-environment.yaml`, the gate refuses every dispatch rather than guess. Origin: agent decision.
- **`deploy-environment.yaml` grants `contents: read` at its top level**, so its jobs that declare no permissions, the smoke checks, don't inherit the calling job's `id-token` and `deployments` grants. Origin: agent decision.
- **The record sets `required_contexts: []`.** The run's own checks gated the deploy, and GitHub would otherwise require every commit status to pass before it accepts the deployment. Origin: agent decision.
- **The production record sets `production_environment: true`**, so a newer success doesn't mark earlier production records inactive. Origin: agent decision.

## Compatibility

- **The hosts roles trust both `deploy.yaml` and `deploy-environment.yaml` (the expand step).** The user applies that plan before this merges. A later plan removes `deploy.yaml` 30 days after production first deploys a commit with the new workflow, when no earlier Deploy run can be re-run (`BACKCOMPAT(deploy-lock)` in `terraform/ci-oidc.tf`). `production-hosts` doesn't accept `main` yet: only the override and reconcile step need that, and they arrive with ALL-2166. Each role's `workflows` entry became a list, `parameter-drift`'s included. Origin: agent decision.
- **The expand step follows only the no-op change making each role's `workflows` entry a list**, ahead of the guard action's commits and the workflow move, so its plan can be applied from that commit alone. Origin: agent decision.
- **Pre-merge Deploy runs aren't re-run**, as `docs/ci-secrets.md` says: one deploys with no guard and no record, so the record would name a commit the hosts no longer run. The old workflow-level group, `Deploy-<environment>`, and the new `deploy-<environment>` are one group, since GitHub compares group names case-insensitively, so a pre-merge run still in flight holds the same lock. Origin: agent decision.
- **`build-staging-mobile.yaml` accepts the backend deploy's old and new job names** (`deploy-nest-backend`, `deploy / deploy-nest-backend`), and the calling job's own name, `deploy`, which the jobs API lists on its own when that job was skipped (EVIDENCE.md, "Job names of a called workflow"). The old name is `BACKCOMPAT(deploy-lock)`, kept for Deploy runs that started before the change. Origin: agent decision.
- **actionlint ignores its "unexpected key `queue`" error in `deploy.yaml` only** (`.github/actionlint.yaml`), because no release knows the key yet (EVIDENCE.md, "`queue` support"). Origin: agent decision.

## Verification

- **Nothing runs the new workflow before it merges.** A push to `main` is the first staging run of it. Local checks cover syntax (actionlint, shellcheck, `terraform validate`) and the guard's decisions (unit tests). Origin: agent decision.
