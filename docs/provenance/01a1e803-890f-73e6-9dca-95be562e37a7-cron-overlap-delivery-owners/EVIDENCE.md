## Detecting abandoned in-flight work

- Job systems re-run work that looks abandoned and expect handlers to be idempotent; none stops the old worker. pg-boss: `expireInSeconds` set to the worst-case run time, optional heartbeat, and a worker that only looked dead "can run twice" ([pg-boss queues](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md), vendor). SQS: visibility timeout at the longest processing time, or extend it from a heartbeat ([SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), vendor). Oban's Lifeline rescues "purely based on time" ([Oban.Lifeline](https://hexdocs.pm/oban/Oban.Lifeline.html), vendor). River's rescuer may run a job "alongside an existing execution attempt" ([River maintenance services](https://riverqueue.com/docs/maintenance-services), vendor). Kubernetes client-go leader election "does not guarantee that only one client is acting as a leader" ([leaderelection](https://pkg.go.dev/k8s.io/client-go/tools/leaderelection), vendor).
- A paused holder can resume after its lease expired; only a token checked where the write lands (a fencing token) prevents its stale write ([Kleppmann 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html), common practice).

## Waitlist: telling a dead send from a slow one

- Per-message cancellation arrives in nodemailer 10.5.0, whose guide warns cancelling doesn't establish non-delivery ([cancelling a send](https://nodemailer.com/guides/cancelling-a-send), vendor). The installed 7.0.13's timeouts are under "Measurements".
- Cancelling after the message data is sent leaves the outcome unknown; see "Unknown send outcomes".
- Node runs timer callbacks "as early as they can be scheduled after" the delay, so a deadline timer is late after an event-loop pause ([Node event loop, timers and nextTick](https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick), vendor).

## Unknown send outcomes

Checked 2026-11-17 by research, second-opinion and brainstorming subagents. No formal standard says what a sender should do when it doesn't know whether a provider accepted a message.

- A timeout doesn't mean nothing happened. SMTP names the gap: a link failing after the server accepted the message but before the sender got the reply duplicates it ([RFC 1047](https://www.rfc-editor.org/rfc/rfc1047.html), an early memo, not standards track), and a spurious timeout after the message body "would typically result in delivery of multiple copies" ([RFC 5321 §4.5.3.2.6](https://www.rfc-editor.org/rfc/rfc5321#section-4.5.3.2.6), formal standard). SMTP's answer is for the receiver to keep that gap short (RFC 5321 §6.1, RFC 1047); neither RFC says duplicates are better than losses. "APIs with side effects aren't safe to retry unless they provide idempotency" ([AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/), vendor engineering guidance, common practice). Stripe's idempotency keys make a retry safe only because Stripe stores the keys ([Stripe](https://docs.stripe.com/api/idempotent_requests), vendor).
- No provider used here offers a deduplication key for sends. Twilio's Message create documents none; `I-Twilio-Idempotency-Token` applies to Twilio's webhook calls ([Message resource](https://www.twilio.com/docs/messaging/api/message-resource), [webhook overrides](https://www.twilio.com/docs/usage/webhooks/webhooks-connection-overrides), vendor). Mailgun has none; a request for one is marked "planned" ([feedback](https://feedback.mailgun.com/forums/156243-feature-requests/suggestions/18429739-add-support-for-idempotent-requests-to-the-api), vendor). Nor do SES, which says retrying a request that timed out may send "a second email with a different message ID" ([SES troubleshooting](https://docs.aws.amazon.com/ses/latest/dg/troubleshoot-error-messages.html), vendor), or Postmark ([Postmark](https://postmarkapp.com/support/article/what-is-an-idempotency-key), vendor). Expo has none and says a push is "more likely" delivered more than once than not at all ([Expo sending notifications](https://docs.expo.dev/push-notifications/sending-notifications/), vendor). OneSignal does, and says "Always include `idempotency_key` when implementing retries" ([OneSignal](https://documentation.onesignal.com/reference/idempotent-notification-requests), vendor).
- Past sends can be looked up. Twilio recommends reconciling at least daily: list the message SIDs Twilio created in a time frame and match them by timestamp and `To` to find messages created when no SID came back ([outbound message logging](https://www.twilio.com/docs/messaging/guides/outbound-message-logging), vendor); the list endpoint filters by `To`, `From` and `DateSent` ([Message resource](https://www.twilio.com/docs/messaging/api/message-resource), vendor). Neither page says an empty result proves a send never happened. Mailgun's Logs API filters on `user_variables` and `message_id` without documenting the matching rules ([Logs API](https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/logs/post-v1-analytics-logs.md), vendor), keeps events "at least 3 days" ([Events](https://documentation.mailgun.com/docs/mailgun/api-reference/send/mailgun/events/get-v3-domain_name-events.md), vendor), and says events may still be "on their way to the storage engine", so the last half hour should be treated as incomplete ([event polling](https://documentation.mailgun.com/docs/mailgun/user-manual/events/event-polling), vendor). Not verified: whether a Mailgun `X-Mailgun-Variables` header or a Message-ID we set can be used to look a message up.
- No standard or provider sets a different unknown-outcome policy by how important a message is. Sending unknown outcomes to a human rather than retrying: [brandur.org on idempotency keys](https://brandur.org/idempotency-keys) (common practice). No study compares the cost of a duplicate message with a missed one; a notification alone measurably disrupts attention ([Stothart et al. 2015](https://doi.org/10.1037/xhp0000100), research-backed, not about duplicates).
- The research subagent recommended reserving before sending, tagging the message, waiting at least 15 minutes, then checking with the provider: found means sent, provably absent means resend, inconclusive means no resend and a loud log (agent judgement). The second opinion agreed with suppressing automatic retries but not with invisible suppression: staff need to see unresolved sends, close them without resending or deliberately accept the duplicate risk, and a local record that a send was never handed over should count as evidence, since a run can reserve a send and crash before calling the provider (agent judgement; the crash window checked in `server/src/actions/action-update-recognition.service.ts`). The brainstorm's 30 ideas added per-channel policies, a digest backstop and duplicate-tolerant copy, none of them researched.

## Provider errors that prove a send didn't go out

Checked 2026-11-17 by research, second-opinion and brainstorming subagents.

- Email: an SMTP 4xx or 5xx reply, or a connection lost before the final "." of the message data was sent, means the message wasn't sent; a connection lost after the final "." and before the reply leaves it unknown ([RFC 5321 §4.2.5, §4.1.1.4](https://www.rfc-editor.org/rfc/rfc5321.html), formal standard). RFC 1047's duplicate risk is under "Unknown send outcomes".
- Twilio documents only a 429 as not processed ([error 20429](https://www.twilio.com/docs/api/errors/20429), vendor). Reading another 4xx carrying a Twilio error body as not sent is common practice; timeouts, connection resets and 5xx replies leave the outcome unknown ([AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/), common practice). A failure before any request bytes leave, such as DNS, a refused connect or TLS, sent nothing (research agent's judgement).
- For messages that aren't critical, record unknown outcomes as unknown and surface them; automatic reconciliation with the provider isn't worth building for them (research agent's judgement).

## Ordering recomputations of a cached count

- Under READ COMMITTED a blocked UPDATE re-evaluates its WHERE against the newly committed row, so a single-statement guarded write is an atomic compare-and-set; it sees no fresher state of other tables ([PostgreSQL 17 transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html), vendor).
- `FOR UPDATE` on the action row conflicts with the `FOR KEY SHARE` foreign-key checks of rows referencing it, and row locks last until transaction end ([PostgreSQL 17 explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html), vendor).
- A version checked at write time is Optimistic Offline Lock ([Fowler](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html), common practice). Comparing a value instead of a version is fooled when the value returns to the one read.
- `now()` is the transaction's start time and `clock_timestamp()` the current time ([date/time functions](https://www.postgresql.org/docs/17/functions-datetime.html), vendor); node-postgres turns timestamptz into a millisecond JavaScript `Date` and bigint into a string ([node-postgres types](https://node-postgres.com/features/types), vendor). `pg_current_xact_id()` returns the current transaction's ID, assigning one if it has none ([transaction ID functions](https://www.postgresql.org/docs/17/functions-info.html), vendor).
- With `CACHE 1`, the default, "it is safe to assume that nextval values are generated sequentially"; with a larger cache, sessions' values "might be generated out of sequence" ([CREATE SEQUENCE](https://www.postgresql.org/docs/17/sql-createsequence.html), vendor). `nextval` is never rolled back ([sequence functions](https://www.postgresql.org/docs/17/functions-sequence.html), vendor). `bigserial` is a bigint column defaulting to `nextval` of a sequence the column owns ([serial types](https://www.postgresql.org/docs/17/datatype-numeric.html#DATATYPE-SERIAL), vendor). Checked 2026-11-17.

## Measurements

- nodemailer 7.0.13, read from the installed source (`node_modules/nodemailer/lib/smtp-connection/index.js`, `lib/smtp-transport/index.js`) on 2026-11-16: `connectionTimeout` 2 minutes, `greetingTimeout` 30 seconds, `socketTimeout` 10 minutes of inactivity (`socket.setTimeout`, reset by any traffic), so a send has no total cap. `sendMail` takes no AbortSignal, and the SMTP transport's `close()` does not touch a send in flight.
- A heartbeat stops during an event-loop pause and fails when the pool is exhausted, and keeps beating for a send hung in a live process. Agent analysis on 2026-11-16 of `server/src/notifs/lock-utils.ts` at the branch's base and of the 2026-11-14 production incident, in `docs/provenance/01a1dcda-00fe-72c8-833d-6d724a5377c9-raise-db-pool-size/EVIDENCE.md`, "Incident", where ten jobs each holding one pooled connection filled the pool.
- TypeORM 0.3.28, read from the installed source on 2026-11-16: `save` reloads the row and writes every column that differs (`SubjectChangedColumnsComputer.js`); `UpdateQueryBuilder` skips columns whose `isUpdate` is false (`UpdateQueryBuilder.js:310`), which `repository.update` and `save` both use.
- `pg_dump --data-only -t action` (pg_dump 18.3 against a local PostgreSQL 18.3 database migrated to this branch, 2026-11-17) emits `SELECT pg_catalog.setval('public."action_usersJoinedComputation_seq"', …, true)` beside the table's rows, and the sequence's `seqcache` is 1.
