- `findActiveUsersForRoster` loads users, contract events and away ranges as three column-only queries joined in JS instead of TypeORM relation loading, which cost several times the CPU for the same rows (about 4x for 690 users locally). Contract events load as raw rows with their `userId` column, since selecting the `user` relation joins and hydrates a `User` per event, most of the remaining CPU. Its other callers (cohort decision pass, `decideOpenAction`, cohort divergence, action relations) read only `id`, `date` and `type` of contract events (`isSettled`, the contract predicates) and `startDate`/`endDate` of away ranges. Both loaders exclude soft-deleted rows: TypeORM's query-strategy relation load passes `withDeleted` from the find options, false by default. A comparison on the staging snapshot found identical users, contract events and away ranges for all 690 users. (agent decision)
- Saved cohort decisions for every action that reads them load in one query (`CohortAdmissionService.prefetchAdmittedMemberIds`) instead of one per action. Actions reading the live cohort are not prefetched, so their decisions aren't loaded for nothing. (agent decision)
- `findParticipantIdsForActions` stays the only implementation of the participant formula; the batched sweep and the single-action reload both go through it. Called without a `session`, it primes the session with `findActiveUsersForRoster` instead of the full `findActiveUsersWithTags` load. Its users never leave the method, and the predicates it runs (`computeIsAssignedAndPresent`, `computeIsAwayDuringWindow`, `computeMissedActionDeadline`, the NOT universe) read only what the roster carries. `findUserActionRelations` already ran it on a roster-primed session. A caller passing its own session keeps whatever that session loads. (agent decision)
- Terminal activities load only the columns `findLatestTerminalActivities` reads, and the action loads drop the unused `activities` relation (`findParticipantAction`, `findIncompleteUsersForAction`). (agent decision)
- The sweep writes changed counts with one `update` per distinct pair of the count it read and the new count, matching the read count in the `WHERE`, so TypeORM still bumps `updatedAt` and a count a request-path recompute changed while the sweep computed stays until the next sweep instead of being overwritten by the sweep's older one. A request that wrote back the count the sweep read is not detected and is overwritten until the next sweep or recompute; closing that needs a row lock or version column, more machinery than a window that self-heals within 10 minutes warrants. One `UPDATE … FROM unnest(...)` would be a single query but bypasses the `updatedAt` bump. Unchanged actions no longer get `updatedAt` bumped every 10 minutes. (agent decision)
- `reloadUsersJoinedForAction` on the request path still writes unconditionally. Skipping an unchanged count there would compare against a value read before a concurrent request's write, and could leave that request's stale count in place until the next sweep. (agent decision)
