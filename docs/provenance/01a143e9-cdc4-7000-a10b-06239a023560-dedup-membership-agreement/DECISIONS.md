- The rules live in `shared/lib/contract.ts` (`WEEKLY_COMMITMENT_CONFIRMATION`, `canSignAgreement`, `signedContractId`, `signedContractEvent`, `suspendedContractEvent`), beside the existing `isConfirmationCloseEnough`, `getSignedMessage` and `getSuspensionMessage`.
- The sign and suspend flows are shared too, in `shared/lib/useMembershipAgreement.ts`: the form state, the submitting flag, the derived status (which contract was signed before, whether the latest is signed, whether to announce an update), the request, the event recorded locally, clearing the typed statement, invalidating the visibility context, and refreshing the member. What happens after signing has changed in both apps at once before (46a5e2209 added the visibility invalidation to both), so it is one rule. Each screen passes its own error display and confirms a suspension in its own UI before calling `suspend`.
- Both screens refresh the member through their auth context's `refreshUser`, which reloads `authMe` into the signed-in user and from there into the page. Mobile used to call `authMe` itself and update only the page's state, which left the rest of the app holding the pre-signing user. Mobile's `refreshUser` used to clear the signed-in user when `/auth/me` returned an empty response; signing now calls it, so it gets fixed first, in its own commit, to update the user only when the response carries one.
- The hook reads the current contract itself, and both screens show the agreement only once it has loaded. Web no longer shows its placeholder contract (id 1) on this page: it used to compare against the placeholder and could sign it (ALL-1239 tracks the same problem in onboarding). While the contract loads, nothing is reported about a previous contract or an update, and Sign stays disabled. If the load fails, the member still sees the contract they signed, with the Suspend button, and both screens say "The membership agreement couldn't be loaded." through each app's `LoadFailed` component, which offers "Try again" and shows the retry in progress (`membershipAgreementLoadFailed` in `shared/lib/copy.ts`). Mobile's query client doesn't refetch on focus, so without the retry the message could stay up for minutes. Onboarding's own "The membership agreement is unavailable. Please try again." is left alone: it answers a Join attempt, and web's `OnboardingPage.tsx` is at the 500-line limit. `useCurrentContract` maps an HTTP error to `null` (ALL-1218), and web's API client returns HTTP errors rather than throwing them, so the hook treats an empty current contract as a failed load too; the server always has one (`ContractService.getCurrent` uses `findOneOrFail`).
- A refused sign or suspend request (an HTTP error) shows the error message, through `thrownRefusalMessage`, so the server's reason comes through and an expired session says to sign in again. Web's API client returns HTTP errors rather than throwing them, so web used to do nothing; mobile's client already throws (`throwOnError: true` in `apps/mobile/app/_layout.tsx`), so mobile showed its generic error. The requests now pass `throwOnError: true` themselves, so the shared hook behaves the same under either client. This fixes a gap rather than settling a disagreement, so it has its own commit.
- `isConfirmationCloseEnough` is no longer exported and checks against `WEEKLY_COMMITMENT_CONFIRMATION` directly; `canSignAgreement` is its only caller.
- The suspended event builder is shared alongside the signed one: both pages built it identically, and the two events change together when `ContractEventState` does.
- The updated-contract notice shows only once the previously signed contract has loaded, as web did. Mobile showed it whenever the signed contract id differed from the latest, so it appeared on its own, with nothing above it to be an update of, while the previous contract was loading or if it failed to load. The latest contract's signing form is shown either way, so the member still sees they need to sign.
- Only a signed event points at a previously signed contract. Suspended events carry no contract id (server `ContractService.suspendContract`), so this matches both apps' existing behaviour and lets the previous contract's section always show the signed actions without re-checking the event type.
- The Sign and Suspend buttons are disabled while a request is submitting on both platforms, as mobile did. Web had no such guard, so a double click could send two requests.
- Left per platform: error display (`alert` vs `Alert.alert`), suspend confirmation UI, and layout.
- The membership page's agreement copy lives in `shared/lib/copy.ts` as `membershipAgreement` (heading, suspend button and alert title, updated notice, sign and suspend error messages, and the away-period form's hint for the "Other" reason, which points at the agreement above it) and `membershipFaq` (the questions about membership and their heading). Both platforms render from them, so the mobile screen takes web's wording, including web's longer answer to "Why is there an agreement?".
- "Use agreement" applies to the page's remaining "contract" wording on web too: "An updated agreement is available.", the sign and suspend error messages, and `suspendContractConfirmation` ("Are you sure you want to suspend your agreement? ..."), which both platforms show.
- `suspendContractConfirmation` keeps its name; only its text changes.
- Console log messages ("Error signing contract:") are developer-facing and stay as they are.
