# Decisions

## What counts as the repository

A folder counts as the Alliance repository when its git history contains the repository's root commit, `08337694b991…` (EVIDENCE.md, Measurements), so a copy whose remotes are named differently, or point at a fork, still counts (agent decision, following the brainstormer's proposal). A folder inside a copy, or a worktree, resolves to its main checkout, the parent of git's common dir, because `scripts/new-worktree.sh` runs from and creates worktrees beside the main checkout (EVIDENCE.md, Measurements). A shallow copy without the root commit reads as incomplete rather than foreign, and a bare repository isn't usable (agent decision, following the second opinion).

"Scripts that support what the app needs" (REQUIREMENTS.md) is read as HEAD containing the commit that added `scripts/list-worktrees.ts`, `99c38cf0e4…`, which the task sidebar (ALL-2035) runs; a later task that needs newer scripts raises `minimumCommit` in `src/main/repository/source.ts` (agent decision). A copy that has never fetched that commit counts as outdated, not broken. The fast-forward fetches `main` through the copy's remote whose URL has the repository's host and path, so the SSH and HTTPS forms both count, which moves that remote's tracking ref too, so `git status` doesn't then show main ahead; when every remote is another repository, such as a fork, it fetches from the repository's URL, so that copy still updates to the Alliance's main. It then runs `git merge --ff-only FETCH_HEAD`, which refuses rather than merges when the copy's main has commits of its own (agent decision). The fast-forward runs without the 10-second limit on quick git checks, and quitting waits for it rather than stopping it, since git stopped partway leaves the files it wrote with main unmoved (agent decision). git sets no transfer timeout, so "Updating" has a "Cancel" that stops the fetch and leaves the copy outdated, since an SSH download can stall indefinitely; a Cancel once the fast-forward has started lets it finish. The fetch, and the clone, also set `http.lowSpeedLimit=1000` and `http.lowSpeedTime=60`, so a stalled HTTPS download fails by itself after a minute (agent decision). "Uncommitted changes" ignores untracked files, which a fast-forward leaves in place unless they collide. The update checks again, after its fetch, that the copy is on `main` with nothing uncommitted, since the user can switch branch or edit between the check and confirming. A failed fast-forward says only that it failed, with git's output behind "Details", since diverged commits, colliding untracked files and a held lock all fail it alike (agent decision).

## Where it looks, in order

The saved choice, then the main checkout of the copy an unpackaged app runs from (`app.getAppPath()`), then the default folder (REQUIREMENTS.md). A saved copy that has gone stops the search with "The Alliance repository at … is gone", rather than silently falling back to another copy, and doesn't start a clone (agent decision). The default folder counts only when it is the top folder of a copy, since a folder inside some other checkout would otherwise identify as that checkout. The automatic clone starts at launch, or at "Check again" out of "Needs Git", which kept launch from cloning; any other "Check again" and the end of a cancelled clone never start one by themselves (agent decision). Cancelling a clone or changing its folder saves that folder as the user's clone folder, so later launches and "Check again" show it with "Clone" rather than cloning anywhere by themselves; otherwise a cancelled clone restarted at every launch. A saved clone folder that holds a copy counts as the saved choice, so a finished clone whose save failed, or was cut short by a crash, is still found (agent decision). "Not cloned" with a problem, such as a saved copy that is gone or couldn't be checked, offers "Check again", so the saved copy is looked for again without relaunching (agent decision). A found copy isn't saved; only a copy the user chose or the app cloned is, so a development build keeps following the checkout it runs from (agent decision).

## Cloning

A full clone over HTTPS: the repository is public, about 225 MiB packed (EVIDENCE.md, Measurements), and a blobless clone would make agents' `git blame` and offline history reads fetch on demand (EVIDENCE.md, git) (agent decision). git runs with `GIT_TERMINAL_PROMPT=0` so a clone that needs credentials fails rather than waits on a prompt nobody sees, `LC_ALL=C` so its progress parses, and `GIT_OPTIONAL_LOCKS=0` so status checks never contend with the user's own git, and without inherited `GIT_*` variables, so a `GIT_DIR` from a git hook or rebase can't point it, or the tests' fixtures, at another repository.

The clone goes into a dotted sibling, `.<folder>.cloning-<uuid>`, renamed into place only on success, so a failed or cancelled clone never leaves something that looks like a copy, and the name can't match a worktree's `alliance-<name>` folder (agent decision, following the second opinion; EVIDENCE.md notes no documented app practice). The next clone sweeps partial siblings a crash left. A folder with files is never cloned into (EVIDENCE.md, GitHub Desktop and git). "Change folder…" picks the clone's destination: an empty or new folder is used as is, and a folder with files gets an `alliance` folder inside it, so picking `~/code` clones to `~/code/alliance`, and when that is already a copy, points to "Use existing copy" (agent decision). A folder in a copy of the repository, empty or missing ones included, is refused with a pointer to "Use existing copy", since cloning there would nest a second copy inside the user's checkout (agent decision). Changing it mid-clone restarts the clone there, unless git has already finished, when the finished clone is kept as a cancel keeps it. The user's repository actions, and the lookups at launch and "Check again", run one after another, so a cancel pressed while a folder change restarts the clone stops the restarted clone and saves its folder, and a lookup can't start a clone while "Use existing copy" saves (agent decision). Quitting cancels a clone in progress, waits for git to exit and removes the partial folder. A cancel or quit that lands once git has finished is too late: the clone is kept, saved and shown like any other, rather than leaving a full copy the app calls "Not cloned" (agent decision).

## Git missing

On macOS, `/usr/bin/git` without Apple's command line developer tools is a stub that opens their installer, so the app runs it only when `xcode-select -p` succeeds and names a folder that holds `usr/bin/git`, since xcode-select still names a folder whose tools were deleted, and, when the tools are missing, says how to install them with a "Check again" button, rather than letting macOS pop an installer up unasked. Setup's repair of it stays with ALL-2034 (agent decision, following the second opinion).

## Where it shows

An "Alliance repository" entry at the top of the sidebar shows the state in a few words and opens a view with the folder, progress and actions; it sits where ALL-2034's Setup group will go, and chat never waits for it (agent decision; REQUIREMENTS.md has chat stay usable while it clones). Failures show their message with git's output behind "Details", per the repository's UX guidelines. The update's confirmation is inline, with "Cancel" focused, rather than a native dialog, which the e2e tests can't drive (agent decision). The sidebar entry carries no live region, since the conversation views already use `role="status"`; the repository view announces each clone phase, leaving the percentage to its progress bar so a screen reader isn't read every percent step (agent judgement).

A new conversation's folder now resets to the default after each start, rather than keeping the last folder picked, so it defaults to the repository (REQUIREMENTS.md); with no repository it falls back to the last conversation's folder, as before. The picked folder is stored under a new key, so a pick saved by an earlier build doesn't override the repository on the first new conversation after the upgrade (agent decision).

## Tests

The e2e tests set `ALLIANCE_AGENT_REPOSITORY_SOURCE` in `playwright.config.ts`, as they already stub the CLIs, so no test clones from GitHub or finds the checkout it runs in, whose root commit CI's depth-1 checkout lacks (EVIDENCE.md, Measurements). By default it names a default folder with files and no copy, so existing tests start with no repository; the repository tests build a fixture source with real git. The variable is read only by an unpackaged app and, when set, also skips the app's own checkout.
