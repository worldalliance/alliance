# Decisions

Agent decisions unless labeled otherwise. Facts cited here are in `EVIDENCE.md`.

- **Supersedes "`restart` the timer on each deploy" in `01a1c193-c5d8-7000-8a5b-cc1cba80460c-sync-systemd-timer/DECISIONS.md`.** On the staging host's systemd, a restart computes the next run from the timer's previous start, so the first deploy after each 10:30 sync started another one (**Incident** and **systemd source**). `daemon-reload` reloads edited unit files and keeps the timer's last trigger across the reload, so the next run is computed from that trigger, and `enable --now` starts the timer only when it isn't running.
- **Changing `OnCalendar=` makes systemd start the service once, on the deploy that ships it,** if the new time falls between the last run and the deploy. This is upstream's catch-up on reload (systemd/systemd#16732), which has no off switch in the host's version (**systemd source**). The run-window guard below skips that run unless the deploy lands within 5 minutes of the new time on a day whose run hasn't started, where it is that day's run, and the comment above `OnCalendar=` says so.
- **A timer someone stopped by hand gets started by the next deploy, and the host's systemd may start the service right then** if a scheduled time passed since its earlier start (#31231, unfixed in AL2023's systemd, **systemd source**). The guard skips that run too, except within 5 minutes of the scheduled time on a day whose run hasn't started. A `stop` or `disable` holds only until the next staging deploy, whose `enable --now` starts the timer again, and `mask` fails on the host because the deploy installs the timer as a regular file in `/etc/systemd/system` (**Guarding the sync against off-schedule runs**), so `docs/legacy/monitoring.md` says a pause lasts until the next deploy. A pause that survives deploys is ALL-2111.
- **How the requirement that a staging deploy never causes an extra sync is met: a run-window guard in the script.** The user deferred how it is met, not whether (they answered "I don't care" to the choice). The service unit sets `SYNC_SCHEDULED_AT=10:30`, and `scripts/sync_prod_to_staging.sh` skips a run it marks that starts outside the 5 minutes from that time, or on a day whose run already started, before the lock and any healthcheck ping: it logs, posts a `:no_entry:` Slack line naming the time systemd started it, and exits 0. Neither systemd nor the deploy tools surveyed offer a way to keep these starts from happening, and failing closed on a skipped run is the published practice for scheduled jobs (**Guarding the sync against off-schedule runs**). The window is 5 minutes, wide enough for the timer's default `AccuracySec=` of a minute and the unit setting no `RandomizedDelaySec=` (**Guarding the sync against off-schedule runs**), and narrow so few deploys land in it.
  - A guarded run that passes the window writes the UTC day of its scheduled time to `~/sync_prod_to_staging.slot`, and a guarded run on a day already recorded skips. Keying on the day rather than the scheduled minute keeps the deploy that moves `OnCalendar=` later in the day from adding a second run that day. A slot file that can't be written fails like the other startup checks.
  - What still runs: a deploy that starts the service within 5 minutes of the scheduled time, on a day whose run hasn't started. That run stands in for the day's scheduled one, so staging still syncs once that day.
  - Only the service unit sets the variable, so a run outside it, such as through `systemd-run`, is never guarded.
  - A skip sends no healthcheck ping, so the day's real run still counts and a guard skipping every run shows up as a missed ping.
  - `OnCalendar=` and `SYNC_SCHEDULED_AT` are kept in step by a test in `scripts/sync_prod_to_staging.test.ts` that reads both unit files, rather than derived, since a unit file can't read the other's value and generating one at deploy time adds deploy logic for a value that rarely changes. A mismatch that reached the host would skip every run, which fails loudly: a Slack line daily and a dead man's switch alert.
  - A skip's Slack line and `docs/legacy/monitoring.md` give the off-schedule route as `systemd-run` starting the script in a transient service, since `systemctl start` on the service is guarded too. Unlike running the script in an SSH session, whose hangup aborts the sync partway, the transient service runs detached and logs to the journal, and it gets a clean environment without `SYNC_SCHEDULED_AT` (**Guarding the sync against off-schedule runs**).
  - A malformed `SYNC_SCHEDULED_AT`, or a `date -u +%s` that prints no number, fails like the script's other startup checks: an `:x:` on Slack, a `/fail` ping and exit 1.
  - The cost: a run systemd starts late for another reason, such as after host downtime, also skips, which `Persistent=false` already does.
- **Supersedes "The deploy removes the old crontab line" in `01a1c193-c5d8-7000-8a5b-cc1cba80460c-sync-systemd-timer/DECISIONS.md`: remove the cleanup outright.** The removal condition it carried, staging's crontab no longer listing the sync, now holds (**Staging crontab**), and staging is a single host.
