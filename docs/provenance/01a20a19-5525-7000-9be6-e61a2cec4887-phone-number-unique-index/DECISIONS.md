# Decisions

- **The "shared number" suite the issue placed in `server/test/mms.e2e-spec.ts` had since moved to its own file, `server/test/mms-shared-number.e2e-spec.ts`, so the whole file is deleted.** Every test in it sets up two live accounts on one number, which the index now refuses at setup. (agent decision)
- **The mocked-violation tests in `server/test/phone-number-unique.e2e-spec.ts` are replaced by the real-index ones, not kept beside them.** They stubbed `EntityManager.save` to throw what the missing index would have, and once the index exists the real-index tests cover the same paths. (agent decision)
- **`PhoneVerificationService.start` looks up the number's one live holder instead of taking two holders and requiring exactly one.** That two-row check existed only because several live accounts could hold one number until this index, as its comment said. `find` skips deleted accounts, so a deleted holder still doesn't count as holding the number. (agent decision)
- **Code that handles a list of holders stays as it is:** `setUnsubscribed`, `PhoneVerificationService.verify`'s `others`, and the inbound text log's `members`. Deleted accounts still keep their numbers, so the first two can still meet several rows, and the third is correct with one member. Narrowing their types would change the `SmsInbound` event payload without changing behaviour. Only their docs are reworded. (agent decision)
- **The migration is the generated one, unedited:** `CREATE UNIQUE INDEX "UQ_user_phone_number_live" ON "user" ("phoneNumber") WHERE "deletedAt" IS NULL`, and a `down` that drops it. It isn't created `CONCURRENTLY`. TypeORM runs each migration in a transaction, which `CONCURRENTLY` can't run in, and the build takes milliseconds at the local database's size (EVIDENCE.md, **Measurements**). (agent decision)
- **Three more tests the issue didn't list put two live accounts on one number, and failed at setup once the index existed.** "lists a number two members share once, naming both" (`server/test/mms-number-thread.e2e-spec.ts`) is deleted, since the index rules its state out. "keeps accounts sharing a number under its limit" (`server/test/phone-code-per-account.e2e-spec.ts`) is deleted, since "sends a number five codes an hour, except to the account holding it" in the same file already covers the limit for accounts that don't hold the number. "records one event when members sharing a number are marked at once" (`server/test/mms-needs-reply.e2e-spec.ts`) tests concurrent marks on one number's thread, so it is kept, with one member sending all four marks at once. (agent decision)
- **The production duplicate count was checked when the PR was opened, in a read-only session (EVIDENCE.md, **Measurements**), and returned 0. That is the first of two checks: the profile update saves any number unrefused until the index exists, so the PR description asks whoever pushes `production` to rerun the query just before.** A duplicate saved in between fails the migration, and `scripts/deploy_backend.sh` keeps the old release, so the miss is loud. (agent decision)
- **This index ships without waiting for ALL-2280 (#1053) to reach installed mobile apps.** The settings-phone-refusal task left that choice to this PR. #1053 is on `main` ahead of this commit, so the production push that runs this migration also deploys it to web and, once the backend is live, publishes it to mobile as an OTA update (`.github/workflows/deploy-environment.yaml`, `publish-mobile-ota`). Until an installed app picks that update up, a member who enters a number another live account holds fails every settings save while it stays entered, and production had no such shared number (EVIDENCE.md, **Measurements**). (agent decision, left to this PR by the settings-phone-refusal task)
