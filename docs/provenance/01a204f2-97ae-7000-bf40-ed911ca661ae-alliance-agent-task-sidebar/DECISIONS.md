# Decisions

## From ALL-2035 and earlier plans

These points come from ALL-2035, or restate agent decisions the user deferred in `docs/provenance/01a1eacc-f2ab-7181-b7d9-f8bf93c89797-alliance-agent-ui-worktrees-setup-plan/DECISIONS.md` (A new task's base) and `docs/provenance/01a1a949-c8f1-7000-9631-5610045dff02-alliance-agent-desktop-app/DECISIONS.md` (Worktree records). They weren't asked again (agent decision, following the second opinion: asking again reopens choices the user declined to make).

- A new task's worktree is a sibling made from the main checkout by its own `scripts/new-worktree.sh`, branched from `main` freshly fetched from the repository's remote. Creation starts when the user sends the request, not while it is typed, and no spare worktree is kept in reserve (ALL-2035; the plan's agent decisions).
- The sidebar lists tasks from the checkout's own `bun scripts/list-worktrees.ts`, version 1, never parsing the scripts' records; another version shows a problem naming both versions (desktop plan's agent decision).
- The first message waits in the main process until the worktree is ready, then starts the task's first conversation, so a window reload during creation loses neither (ALL-2035; brainstormer), and a reloaded window left on the creation shows the task it became once it is ready (agent decision). A creation that fails stays listed, with the problem, the request, what it left behind, "Try again" and "Edit request", until retried or dismissed; failed creations live only while the app runs (agent decision: a crash or quit leaves the scripts' half-created record, which lists as "Not finished being created"). What a failed run of the script left behind is saved under the request's title, so once the creation is retried or dismissed it lists as the app's, not as made outside it.
- Worktrees the app didn't create show as tasks marked "Made outside Alliance agent". A worktree made from inside a task, as `AGENTS.md` tells agents to, nests under that task through the record's `parent` (agent decision, following the brainstormer and second opinion), so it isn't clutter. A task whose parents loop, which only hand-edited records produce, shows at the top level as broken rather than nowhere (agent decision). So does a worktree whose folder is gone, which git lists until `git worktree prune`, rather than as ready (agent decision).
- The task's state is shown in words: the creation stage, "Couldn't be created", "Ready", "Needs attention", "Not finished being created", "Not finished being removed", and an archived task keeps showing its state under the Archived group (ALL-2035; wording is agent judgement). Agent working, finished and failed states are ALL-2036's.

## Creating

- The worktree's name, which is also its branch, is the request's first words in lowercase ASCII, joined by dashes and cut at a whole word to at most 37 characters, then numbered (`-2`, `-3`) past every name the worktree list or a local branch already uses, or a local branch's folder (`fix` beside `fix/login`), or an earlier attempt of the same creation tried, with `task` for a request with no letters or digits (agent decision). 40 characters at most keeps the test database's name, `alliance_<name>_test`, inside Postgres's 63-byte limit. A local branch counts as taken because `new-worktree.sh` checks out an existing branch rather than starting a new one from main, and a branch's folder because git can't create `fix` beside `fix/login`, which the script finds only after copying the databases. A tried name counts because the script refuses a name whose folder or database exists before it leaves a record or branch, so Try again would otherwise repeat the refusal. The research found products generate names, and name the branch after the workspace (EVIDENCE.md).
- The app fetches `main` through the copy's remote for the repository, as the repository update does, and passes the fetched commit to `--from`, not `origin/main`, so a remote with another name or a fork still works and the branch gets no upstream to push to by accident (agent decision). The update and the task creation share this fetch (`src/main/repository/fetch.ts`), which runs one fetch at a time across both, since fetches race on `FETCH_HEAD`. A creation reads the names other creations have chosen and records its own with no await between, so two creations at once can't choose the same name.
- Progress maps the script's `==>` stage lines to plain words, keeping the last stage for any other output (agent decision). The list of stage lines lives beside the script's call in `src/main/tasks/create.ts`; a stage line it doesn't know keeps the previous stage showing rather than failing.
- Quitting aborts creations in progress. `runCli` sends the script SIGTERM, then SIGKILL; a child it started, such as `bun install`, can outlive it, as ALL-2118 records for the CLIs. The script's record then lists as "Not finished being created" (agent decision: waiting for a database copy and `bun install` would hold the quit for minutes). Stopping the script's whole process group is ALL-2391.
- A creation whose worktree `new-worktree.sh` made but the listing after it couldn't find, or whose title the app couldn't save in `tasks.json`, fails saying it was created, and Try again lists again rather than running the script under a new name, so it never makes a second copy (agent decision). It offers Try again alone, without Edit request or dismissal, since only Try again saves its worktree as the app's and a dismissed one would list as made outside it; a quit before then still leaves it listed that way (agent decision). Once a listing of the checkout it was made in no longer shows its worktree, the worktree was removed, so the creation counts as having made nothing: Try again makes another under a new name, and Edit request and dismissal come back (agent decision).
- A worktree whose creation succeeded but whose first conversation couldn't start is kept, with the request moved into its "New conversation in this task" box and the problem shown there (agent decision).

## Archive

- Archive stops the task's agents by closing every live session whose folder is the task's worktree, without asking first, and its hint says so; Restore undoes it (agent decision, following the second opinion: the action keeps everything, so a confirmation adds friction to a reversible step). None of the products researched documents what archiving does to a running agent (EVIDENCE.md). Dev servers don't exist yet; ALL-2038 adds stopping them.
- Archive waits at most the opening wait for sessions still starting anywhere, so a stalled start in another task can't hold it, and a session that began starting in the archived task's folder before Archive, or that opens there before Archive finishes, closes as it opens; one begun after Archive finished is left alone. A Resume of a session Archive is closing, or one Archive closes as it opens, fails with "This conversation is closing. Try again in a moment.", since the backend would hand back the session about to close. So does any Resume in that folder asked for while Archive is still closing, since the backend holds it until the closing CLI exits and then reopens the session after Archive has stopped closing what opens. A Start in that folder asked for while Archive is still closing fails with "Conversations in this folder are closing. Try again in a moment." rather than reporting success for a session that closes as it opens. Archive saves the task as archived before stopping its agents, so a save that fails stops nothing. From that save until Restore, the main process refuses every Resume in the task's folder with "This task is archived. Restore it to open this conversation.", checking before the backend resumes, and a Resume already past that check when Archive begins closes as it opens, since it began before Archive, so no Resume reaches an archived task whatever its timing; Archive saves the task's folder with the flag, so the main process refuses Resume there after a relaunch before the worktrees are listed, and once the app points at another checkout that doesn't list the folder; the listing decides for a folder it lists; this rule, not the timing of the hide, keeps its agents stopped. Archive hides the task as soon as the closing ends, without waiting for another listing, and not before, even when a listing reads the saved flag first. Archive is unavailable while the task's own form starts a conversation, since the window moves to that conversation once it starts, which archiving would hide (agent decision).
- What the app knows about tasks that the scripts don't record, the title of a task it created and whether a task is archived, is kept in the app's own `tasks.json` in its user data folder, keyed by the worktree record's id, or by the folder for a worktree without one (agent decision; the second opinion preferred the scripts' records, but the app-only flag needs no script change and no other tool reads it yet). Its entries outlive their worktrees, so a worktree remade at the path of an archived one without a record starts archived; pruning them waits on giving each repository its own entries, since one file serves every repository the app is pointed at (ALL-2393, agent decision).
- Archived tasks sit in a collapsed "Archived (n)" group at the end of the task list, and their conversations are hidden with them; opening one restores nothing until "Restore". A conversation of the task still shown when Archive finishes gives way to the archived task, since showing it would start its agent again (agent decision; the researched products keep archived items in the same list behind a filter or tab).

## Conversations outside a task

- "Ask without a task" starts in the main checkout the repository view found, with the hint that new tasks copy its database and local settings, so changes belong in a new task, which branches from freshly fetched `main` rather than from the main checkout's code (REQUIREMENTS.md; the second opinion). The folder picker for conversations, and its IPC channel, are removed; the repository view keeps its own picker for "Use existing copy".
- A conversation belongs to the task whose worktree folder equals the conversation's folder; every other saved conversation lists under "Other conversations" (agent decision).
- The window lists tasks again whenever the app's window gains focus, so a worktree made in a terminal shows up when the user comes back (agent decision), and when the repository's folder changes.

## Tests

The e2e tests give every launch its own fixture repository, cloned into the test's work folder, with fake `scripts/list-worktrees.ts` and `scripts/new-worktree.sh` (`src/main/tasks/testing/fixture.ts`) that need no Postgres or `bun install`, and that files in the git directory steer: `fake-hold` pauses creation, `fake-fail` fails it after creating the folder (agent decision). Tests that used the folder picker now use "Ask without a task", which runs in that work folder. A launch with that repository waits until the app has checked it and finished cloning it, since the clone replaces the work folder, which tests start conversations in directly.
