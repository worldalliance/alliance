# TypeORM soft-delete specification

The interview is settled. This document defines implementation choices and verification for [the recorded requests and approvals](REQUIREMENTS.md). Agent choices below derive from those requirements; existing code alone is not evidence of user intent.

## Scope and storage

Apply TypeORM's delete-date metadata to every currently registered application entity except the exceptions below, including entities that currently have no deletion endpoint. Convert existing application row-deletion paths, internal replacement/removal paths, and cascaded deletions. Existing endpoint availability and permissions remain the boundary for who can delete.

| Exception                                      | Treatment and rationale                                                                                                                                                                                               |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SpentToken                                     | Keep expiry cleanup permanent; this is an anti-replay record with a bounded useful lifetime.                                                                                                                          |
| WaitlistBrowser                                | Keep explicit forgetting and expiry cleanup permanent; this is temporary browser access state.                                                                                                                        |
| AiDetectionResult                              | Keep removal of obsolete computed results permanent.                                                                                                                                                                  |
| RecentSearch                                   | Keep replacement/removal of disposable search history entries permanent.                                                                                                                                              |
| Cluster                                        | Keep permanent replacement of computed clusters and its existing reference cleanup.                                                                                                                                   |
| Simple relationship rows                       | Keep physical unlinking of ORM junction tables and the explicit WaitlistEntryTag join entity. Friend, Participant, and ActionFormAssignment carry lifecycle or assignment data and remain in scope for soft deletion. |
| Migration bookkeeping and unused legacy tables | Keep their current schemas and lifecycle. Staging's extra tables are not a reason to introduce entities for obsolete code.                                                                                            |

The named transient exceptions apply to those records' existing lifecycle and cleanup operations; they do not exempt business records merely because an internal job deletes them. Form drafts, user devices, notifications, reviewers, and reminders remain in scope.

Each in-scope entity stores a nullable timestamptz deletedAt using @DeleteDateColumn. Preserve existing invitation/message timestamp values; add null deletion dates for other existing live rows. Keep Action.archived and WaitlistLink.archivedAt as independent, reversible archive states.

Move the forum's stored deleted booleans to deletedAt, backfilling old true values with one migration-time timestamp. The booleans stay one deploy longer as write-only columns for rollback (see Rollback below) and are dropped in a later deploy. Preserve the public deleted boolean by deriving it from the timestamp in response construction. Preserve createdAt and updatedAt during the backfill. The migration marker represents prior deletion state, not a recovered historical time.

Default entity reads use TypeORM filtering. Include deleted rows deliberately for the approved history, thread placeholders, and internal deletion traversal, with active-parent and authorization checks applied independently. Use the existing TypeORM dependency; no new delete or restore endpoints are needed.

## Deletion transitions and integrity

Mirror each deletion path's existing effects. Existing custom soft deletes of posts, comments, and invitations retain related rows; preserve that behavior. In particular, deleting a comment keeps its replies. Only converted physical-deletion paths need the cascade and reference changes below.

TypeORM softDelete is an UPDATE and does not execute PostgreSQL foreign-key ON DELETE actions. For converted physical-deletion paths, make those transitions explicit within the deletion transaction:

- CASCADE marks in-scope descendants deleted, removes permitted simple relationship rows, and physically removes affected transient exceptions.
- SET NULL detaches references as the existing operation does. Shared referenced records remain intact.
- RESTRICT and application dependency checks reject deletion under the same conditions as today, counting references that remain logically present. Already deleted dependents do not create new restrictions merely because their rows are retained. A retained physical parent row must not bypass a previous deletion restriction.
- The deletion root, affected descendants, reference changes, session invalidation, and required audit record commit together. A failure leaves the operation unapplied.

Infer ownership from the existing deletion path and foreign-key direction; a parent deletion does not delete shared targets just because a relation can load them. Traverse descendants even when ordinary entity loading would hide them. Preserve prior deletion timestamps when rows are already deleted.

Convert internal row replacement too: replacing action reviewers, clearing drafts after submission, replacing reminders, removing variants/assignments, removing obsolete post tags, unlinking OAuth accounts, and rejecting or leaving conversations. A new record for a later lifecycle stays distinct from retained history; normal app flows do not undelete a previous lifecycle.

Preserve endpoint-specific repeat-deletion behavior, status codes, and authorization checks except for the explicitly approved forum mutation failures. Concurrent delete/edit/create operations must not produce visible children of deleted parents or partially applied cascades, on the creation paths the Locking decision below lists; the paths it names as unlocked are a known gap. Side effects after commit, including notifications and socket updates, use the existing transaction/dispatch discipline.

Existing account deletion hides the account's currently cascaded posts, comments and their descendants, action activity, messages, notifications, and associated history. Retention changes storage, not their visibility or contribution to current counts. The detached account-deletion audit survives; failure to persist it still rolls back deletion.

Simple unlinking and SET NULL transitions remain destructive to the relationship itself. Manual restoration is an operator action, not a promise that clearing one parent's timestamp reconstructs all prior relationships or restores all descendants.

## Query and uniqueness audit

Audit ORM repository calls, joins, relation loading, relation mutations, existence checks, counts, raw SQL, shared SQL predicates, upserts, insert-on-conflict paths, workers, notifications, sockets, and analytics against the new lifecycle.

TypeORM filtering does not make arbitrary raw SQL or update/upsert statements respect deletion. Explicitly exclude deleted actors/targets in raw reads and mutation predicates. Historical inclusion on one alias must not unintentionally include deleted users or parents on another alias.

Preserve reuse of deleted names/emails and logical relationship keys. Adjust the relevant uniqueness rules to cover active rows, retaining existing case sensitivity, partial conditions, and concurrent-insert behavior. Primary keys and identities referenced by foreign keys continue to identify the retained record.

Audit conflict targets when replacing global uniqueness with active-row uniqueness. A draft saved after a previous draft's deletion, a repeated friendship, conversation rejoining, OAuth relinking, and newly created names/emails must succeed as before without reviving the old row.

Manual restoration may fail a uniqueness constraint when a replacement active record already owns the value; keep that failure explicit. No application restoration workflow resolves these conflicts.

Current/live metrics exclude rows that physical deletion previously removed. Saved historical metrics keep their existing semantics. The approved invitation history is a deliberate inclusion: creation/signup totals and retained referral/group-assignment references survive invitation deletion, while active lists, claimability, and invitation-management mutations exclude it.

## Forum behavior

Retain deleted-comment ancestors where the existing thread presentation needs a placeholder and live replies. Thread construction must distinguish these visible placeholders from whole subtrees removed through account/activity/parent deletion; including deleted rows must not resurrect a cascaded subtree.

Apply the same presentation rules to web, mobile, admin responses, activity/action threads, feeds, and exports. Preserve the existing API's deleted boolean and field shape. Return empty original-body and attachment values for a deleted-comment placeholder rather than serializing its retained content. Keep author/thread identifiers and other currently exposed metadata where the placeholder remains visible.

Reject editing, liking, and pinning deleted forum content with the agreed 404 response. Remove those controls wherever a deleted-comment placeholder is rendered. Existing descendants and discussion below the placeholder remain usable.

Accept a reply to a deleted-comment placeholder only in an otherwise available parent discussion and under existing reply permissions. Save it successfully and preserve normal notifications to eligible other recipients; skip the deleted-parent-author notification instead of failing after persistence. Enforce existing visibility rules for the owning post/action/activity.

Deletion of a comment still removes its currently removed notifications from normal visibility through the applicable soft-deletion transition. Notification previews, feeds, searches, and exports must not leak its retained text.

## Accounts and authentication

Retain account fields privately in the database, and use the deleted state to deny sign-in, refresh, authorization, impersonation of the deleted subject, token-mediated session recovery, and messaging participation. Normal member/admin lookup and mutation paths cannot reach the deleted account.

Use a persistent per-account session generation: initialize current accounts to generation zero, increment on deletion in the transaction, and bind newly issued access/refresh credentials to that generation. Treat a pre-migration credential with no generation as zero so existing sessions for active unchanged accounts keep working until ordinary expiry.

Check account identity by the token subject and validate its current active state and generation at authentication boundaries, including admin authorization and sockets. Email reuse must not let a previous account's token authorize as its replacement.

Clearing deletedAt in the database does not reset the generation. Old credentials remain invalid after manual restoration; fresh sign-in issues the current generation. Any user-bound credential that can mint a session must respect this boundary.

At deletion commit, disconnect the affected subject's active sockets and stop later authenticated events. Check deletion again before queued notifications/messages or background work act on a retained account or target. Already completed external deliveries are not reversible.

## Messaging

Migrate Message.deletedAt to delete-date metadata even though no message deletion endpoint exists. Direct database-marked deletion and existing parent/account/conversation deletion become consistent with normal reads.

Exclude deleted messages from member and admin message lists, reply quotes, latest-message previews, and unread calculations. Preserve the last-read boundary when its referenced message becomes hidden; deletion must not make older already-read messages unread again.

Preserve live replies as ordinary messages when their quoted target is unavailable; omit the unavailable quote. A new send to a deleted reply target fails through the existing invalid-target behavior. Conversation/participant deletion retains its current effects on access and visibility.

## Video files and playback

Deleting a video marks its row and retains its existing storage objects. Lists/details and official manifest/segment endpoints treat the row as unavailable. Failed-upload cleanup and replacement of a live video's old files keep their existing behavior; this migration is not storage versioning.

Web and mobile route uploaded-video sources through the video API even when the saved source is a direct storage URL, using the block's recorded videoId. An owned upload source without a videoId is unavailable rather than played from storage: the staging snapshot has no such block with a key (all 48 bare keys and all 254 storage URLs carry a matching id; the 47 id-less URLs are the bare storage origin, which never played), so a lookup by key would serve no data. Do not rewrite immutable form snapshots to change their playback source. The server stops rewriting a block's key into a storage URL when it serves a form, and serves a saved storage URL for an upload as its key, so client bundles that predate the API routing play it through the API too.

Keep arbitrary externally hosted video sources on their existing playback path. Uploaded-source recognition must validate ownership/origin and key structure so an unrelated URL does not get interpreted as an Alliance upload.

The retained object remains subject to its existing storage access policy. Previously copied direct storage URLs may still work; changing bucket/CDN access or invalidating those links is outside this migration.

## Migration and verification

Implementation is complete only when the schema and behavioral checks below pass for all in-scope entities and every identified permanent-deletion path has an explicit soft-delete transition or an approved exception.

1. Run the relevant suites green before implementation. Add reproductions for the approved forum/filtering bugs before changing their behavior.
2. Apply migrations to a disposable local copy. Verify new live markers, preserved invitation/message timestamps, forum migration-time markers, unchanged unrelated fields, constraints, and schema consistency using the repository's migration workflow.
3. For each affected deletion root, test hidden-but-retained rows, its descendant/reference transitions, existing restrictions and permissions, repeat-deletion behavior, and rollback on audit/reference/descendant failure. Include account, community, action, form, conversation, tag, project, and variant deletion.
4. Test reuse and concurrent creation for changed uniqueness rules, including email/name recreation, friendships, participant rejoining, OAuth relinking, drafts, and assignment/reminder replacement.
5. Test deleted-account access and refresh credentials, open sockets, admin authorization after email reuse, queued work, and manual restoration followed by fresh sign-in. Verify old sessions remain invalid while unaffected pre-migration sessions remain valid.
6. Test forum placeholders with replies, account-cascaded subtree removal, redacted API content, mutation 404s and controls, reply success, and skipped deleted-parent notifications across the affected clients and export paths.
7. Test deleted-message filtering with synthetic deleted rows, reply quotes, latest previews, unread counts, deleted read cursors, and concurrent reply-target deletion.
8. Compare invitation history and live acquisition counts using synthetic deleted/claimed records. Verify referral and contract/group assignment after a previously valid invitation is deleted.
9. Test retained video objects, playback/details/list denial after deletion, API routing for saved owned URLs with and without an id, unchanged external sources, and database restoration followed by playback.
10. Run package typechecks, required coverage review, duplication review, formatting, and relevant browser/mobile checks through repository workflows. Use synthetic fixtures and record any uncovered gaps.

New tests establish observable behavior rather than mirroring the deletion helper. A clean duplication or coverage report alone does not establish the query/cascade audit.

## Implementation decisions

Choices made while implementing, each with the reason a later agent needs before changing it.

- **One cascade helper.** `softDeleteCascade` in `server/src/datasources/soft-delete.ts` reads every foreign key's `ON DELETE` from TypeORM metadata and applies it as updates: CASCADE marks rows (including already-deleted ones, whose timestamps stay), SET NULL detaches rows outside the deletion, RESTRICT and NO ACTION throw `SoftDeleteRestrictedError` (a 500, as the FK violation was) while a surviving live row references the deletion. Join tables and the exempt entities are physically deleted; the helper throws if an exempt table is itself referenced, since a physical delete there would cascade past it. Every converted path calls it, so a new foreign key needs no per-path code. The custom soft deletes of posts, comments, and invitations stay plain non-cascading updates.
- **Locking.** The helper locks every row it marks `FOR UPDATE`. A writer that attaches a row to a parent a deletion could mark locks that parent in the insert's transaction and checks it is live, so a concurrent deletion either waits for the child (and then cascades it) or makes the write fail. `lockLive`, beside the helper, takes `FOR KEY SHARE`, the lock the foreign-key check it replaces took, so it adds no wait to callers that already hold other locks; action activities (action and account), reminder notices (group and member), friendships (both accounts, plus the stored friendship itself `FOR UPDATE`), posts, comments, and messages (their author), form-variant assignments (the chosen variant), and new conversation participants (their accounts) use it. It only waits on the helper's `FOR UPDATE`, which is why writers whose parent a plain update deletes lock it `FOR SHARE` instead. Posts, comments, and messages lock their author before anything else, the order an account deletion locks in, and a reply locks its ancestor comments root first, as a deletion's cascade does. Comment creation locks a post parent and message creation locks its conversation and participant `FOR UPDATE`: both rows are written afterwards, and two share locks would deadlock on upgrade. A form variant locks its action `FOR UPDATE`. `FOR SHARE` covers a comment's action or activity parent and ancestor comments, reply targets, share-link targets, a post's action and added experts or authors, the group a signup's invite places it in, the account an OAuth link is written for, the response a partnership note is added to, the project an action is assigned to, the group `CampaignService.update` points a campaign at, and a tagged waitlist tag. Other creation paths, form submissions and drafts among them, do not lock their parent, so one racing its parent's deletion can leave a live row under a deleted parent (ALL-1426). Several of these locks and the raw-SQL `deletedAt` filters have no test yet (ALL-1433). Writes to a loaded account or participant are updates filtered to live rows, and a profile update locks the account `FOR UPDATE` before its save, because a `save` of the loaded entity would clear a `deletedAt` committed since the load; `updateCommunity` writes the group's editable columns the same way, and the remaining by-id account writes (roles, admin flag, staff directory, welcome mail, SMS opt-in, domain switch, OAuth email verification) filter to live rows. Message creation saves its participant whole, under the `FOR UPDATE` lock it checked it live with. Other load-then-save paths, the group-leader saves among them, still can (ALL-1425).
- **Join rows.** Every junction or other undated CASCADE row of a deleted parent (e.g. form snapshot history, group members and leaders, action authors, general-update suites and tags, reminder-group members) is physically deleted with it, so restoring the parent from the database brings it back without those links.
- **Kept reference.** `Participant.lastReadMessage` is the one SET NULL the helper leaves in place (`KEPT_REFERENCES`), so a read cursor keeps its position when its message is hidden. Unread queries read the cursor's time from the raw row; the participant DTO omits a hidden cursor message rather than serializing its body.
- **Active-row uniqueness.** Names, emails, and relationship keys a deletion used to free are unique among live rows only: user email, tag, project, waitlist tag/template/cohort names, form draft, OAuth account (both keys), friend pair, participant, community conversation, form assignment, variant form, action task form, device push token, share-url keys, and the one member-action event per action. Post tags use a deferrable exclusion constraint, because the deferred uniqueness their renames rely on cannot be a partial index. Codes, tokens, hashes, idempotency keys, and tables with no deletion path stay globally unique. `ON CONFLICT` targets on partial indexes pass `indexPredicate`.
- **Invites.** An invite whose claimant's account is deleted is claimable again, as physical deletion left it. The deleted account keeps its `referredByInviteId` until another signup claims the invite; that claim detaches it, because the one-to-one column's full unique constraint allows one holder. History reads that must count deleted invites (daily stats, invite funnel, contract-signing group placement, admin referral detail) load them `withDeleted`; ambassador invite stats keep excluding deleted invites, as they did before.
- **Forum threads.** Thread loaders read `withDeleted` and drop comments whose author is deleted; a reply under a dropped comment drops with it because the hierarchy discards orphans. A deleted comment with a live author is the placeholder. A reply is accepted under a placeholder but not under a comment the thread drops, so creating one walks the parent chain and refuses when any ancestor's author is deleted. Deleting a comment unpins it, since a deleted comment cannot be unpinned; `UnpinDeletedComments1791238815100` unpins comments deleted while pinned before that. Placeholders keep their likes count and author; the web and mobile like toggle and like summary are hidden on them. `findCommentsForPostRaw`, the flat list the replied-to-post validator and the forum completer read, drops the same orphans the hierarchy does, so a reply removed with its parent's account no longer counts as a reply. `findPostsByAction` reply counts now exclude deleted comments, matching the forum list's comment count. Creating a comment now requires its post to be visible to the commenter, or its action or activity to be live. The pre-existing update of `post.updatedAt` by the comment's `parentObjectId`, which also touches a post when the parent is an action or activity, is unchanged (ALL-1416). Admin export and settings of a single post load posts without `withDeleted`, so a deleted post answers 404 there, and a member's comment list leaves out comments whose post or action is deleted rather than show them without a title; loading it `withDeleted` would also surface posts an account deletion removed, which the previous physical cascade made unreachable.
- **Sessions.** `SessionService` (global) checks the account by token subject and generation on every authenticated request, socket handshake, refresh, and admin or leader check; admin and leader checks no longer look the account up by email. The access, optional, and refresh guards and `getAuthenticatedSession` answer 401 only for a token that fails to verify or names an ended session; a failed lookup propagates as a 500, because both clients drop the session on a 401 from refresh. The admin and leader guards still answer 401 for any failure (ALL-1421). A socket handshake refuses a token that fails to verify or names an ended session, and accepts a verified token when the lookup itself fails, since clients never retry a refused handshake. Callers that only gate access use `assertCurrent`, one existence query; admin, leader, and event-log checks load the account with `currentUser`. `generationOf` reads a missing generation as 0. The OAuth handoff token carries the generation. Password-reset and email-verification tokens mint no session and are unchanged. Sockets disconnect through an in-process `user.account.deleted` event; the server runs no socket adapter, so one instance holds every socket. The event sweeps the sockets connected when it fires, so a handshake that checked the account just before the deletion committed can join after the sweep and stay connected until it disconnects (ALL-1428); the event-log gateway's window is wider, since it names a socket's account only after accepting it (ALL-1418).
- **Videos.** `uploadedVideoKey` in `common/src/video-src.ts` recognizes an uploaded source as `videos/<digits>`, optionally on any `https://<distribution>.cloudfront.net/` origin whose distribution is a single hostname label, since each environment saves its own distribution's host. Clients play such a source through `/videos/:id`, and the server serves the bare key in place of such a URL, so a player that still plays any absolute URL from storage reaches the API as well. Only `getForm` rewrites; schema snapshots sent with completed responses and response history keep the saved source, so bundles that predate the API routing play those from storage. A form update answers with `getForm`, and an admin re-save stores the key the editor loaded. A pre-cutover client that posts back the schema it was served is matched against what `getForm` serves for the current version, then against each version in the form's history with the media rewrites rebuilt, since the rewrite makes it differ from the stored snapshots; the history match does not rebuild filled-in contracts (ALL-1429). Video files go out with a one-minute `max-age` instead of the immutable header, because replacing a video rewrites its files under the same names and a deleted video must stop playing; a replaced or deleted video stays playable from a cache for at most that minute. They leave out S3's ETag, so nothing revalidates and an expired copy is fetched in full, because iOS hands the app a 304's `Content-Length: 0` (the reason `configureApp` turns Express's ETags off) and whether AVPlayer is affected was not verifiable here. Images keep the immutable header. Any other URL keeps its existing path. A foreign CloudFront URL of exactly that shape would also be treated as an upload; it plays through its block's videoId, or not at all without one.
- **Smaller calls.** AI detection skips deleted comments and form responses rather than sending retained text to the detector. SMS STOP/START updates every account with the number, deleted ones included, even when no live account has it, since an opt-out belongs to the number; only live accounts get an opt-out audit row and a log entry. A request body cannot set `deletedAt`: the whitelisting ValidationPipe strips it, and entities whose `deletedAt` has a decorator mark it `@IsOptional() @IsEmpty()`. The action "users invited" stat counts deleted invites, as it did when deletion only set a plain column. The city import leaves `deletedAt` alone, so re-running it keeps an operator's deletions. Replacing the invite message template clears its `deletedAt`, and the waitlist mail limit counts only live allowance rows. A deleted member's existing experiment assignment is read `withDeleted`, so assigning an arm does not abort a reminder run.
- **Migration hand edits.** The session-generation column was moved from the generated migration into `SessionGeneration1791238815000`, so the commit that checks sessions stands without the soft-delete schema. Added by hand: the forum backfill (add the column, then set it to `now()` where the old flag is true) and the drop-and-recreate of the share-url and action-event partial indexes, whose predicate changes `migration:generate` does not detect. `down` notes that its full unique constraints fail once a deleted value has been reused, and leaves deleting those rows to the operator; it restores `post_tag`'s unique constraint as `DEFERRABLE INITIALLY DEFERRED`, which the previous release's tag reordering relies on. A drop and re-add of `friend`'s generated columns was removed: it comes from `typeorm_metadata` naming the main checkout's database, and predates this change.
- **Rollback.** The migration keeps `post.deleted` and `comment.deleted`, mapped as `legacyDeleted` with `select: false`, and deleting a post or comment directly still sets them, so the previous release, which selects and filters on them, keeps working and keeps those deletions hidden. Drop them in a later deploy. Rolling back still makes every other record soft-deleted since the deploy visible again, accounts included, which can then sign in, because the previous release does not read `deletedAt`; pair a code rollback with `migration:revert` or with physically deleting those rows. The previous release also cannot save form drafts or link OAuth accounts against the migrated schema, during the deploy's migration window or after a rollback: its upserts' `ON CONFLICT (userId, formId)` and `(userId, provider)` name full unique constraints this migration replaces with partial indexes. Keeping both constraints for a deploy would make a later draft or link conflict with the deleted row, so the gap is accepted.
- **Left as found.** `UserService.remove`, which physically deletes a user, has no caller.
