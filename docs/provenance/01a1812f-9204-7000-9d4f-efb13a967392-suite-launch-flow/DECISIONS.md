## Actions page

- "Draft or active" uses the existing status buckets (`actionStatusBucket`): Draft and Active. Onboarding and archived actions don't count. Each suite links to its suite page and shows its active and draft counts.

## Where the flow lives

- "Begin launch process" shows only while the suite has no members-taking-action event, so a launched suite never offers a second launch. The launch itself reloads the suite right before creating anything and refuses when one exists, so a launch from another tab or person since the page loaded creates no second announcement and reminder set. The server accepts a second members-taking-action event, so two launches confirmed in the same second could still both go through; a server-side guard would close that.
- Everything runs on the client against existing endpoints: `evaluate-cohort`, the admin action and task-form queries, the suite event endpoint, and reminder group creation. No server change was needed.

## Schedule

- "PST" is read as Pacific time (`America/Los_Angeles`), so the defaults follow daylight saving. Both dates stay editable, with the Pacific time shown under each picker.
- The office event is 11:59pm Pacific, seven days after the day members start. When the member start rolls past midnight, the office event moves with it.
- The office event uses the `office_action` status ("Office taking action"), matching `CreateEventForm`'s deadline default.

## Sanity checks

- A member's actions are the suite actions whose cohort expression includes them, evaluated with `evaluate-cohort`, which counts active users only. For a regular (non-onboarding) action, only members with an active contract count, since the server admits a member only while they hold one; contract status is read as of now, not as of the launch time. Prerequisites are ignored, so the totals are an upper bound: someone who would only unlock a later action still counts it. Optional actions count too.
- Contract violations show in a red banner at the top of the panel and block launch until staff tick "Launch anyway, breaking the contract". Two contract terms are checkable at launch: a member assigned more than 15 minutes (the contract's 15-minute blocks), and office taking action less than 7 days after members start (its 7-day completion period). Its non-overlap term needs other suites' periods per member, left out with the cross-suite load. Its exceptions depend on a member's circumstances, which no launch check can see.
- Readiness reuses the action dashboard's checklist, now extracted to `actionReadiness.ts`, so both screens apply the same rules. It reads each action through the admin action query, because suite payloads don't load authors or the suite relation.
- Member preview lists each picked member's assigned actions, their total minutes, preview and edit links, and a "Log in as this member" impersonation link (the same endpoint the user detail page uses). Impersonating replaces this browser's auth cookies with the member's and nothing switches back, so the preview says in words that it signs the browser out of admin, and that launch progress survives signing back in.
- The launch flow is its own page, `/suites/:suiteId/launch`. The schedule, "Ready to launch" boxes, dismissals, and the contract acknowledgment are saved in this browser's localStorage per suite, so a refresh or leaving and coming back keeps them; a successful launch clears them. They are per browser, not shared between staff.
- Saved progress can't vouch for what nobody reviewed. A "Ready to launch" box is saved with the version it approved (the action's `updatedAt` and its task form's `formSnapshotId`), and clears with an "Edited since it was marked ready" note once either changes. The contract acknowledgment is saved with the exact violations it accepted, so a new or different violation asks again. A saved schedule whose member start has passed falls back to the default schedule.
- n in "I am going to notify {n} real members" is the size of the union of the suite's action cohorts.
- The launch confirmation restates the member start and office deadline in Pacific time, the window between them, and how many reminders it creates, so an AM/PM or wrong-week pick shows at the last step, where the pickers show local time.
- The typed confirmation is required in every environment, unlike the reminders tab's, which skips it in development.

- Each blocker above the launch button names the section that resolves it (`LaunchSection`, whose values are the sections' DOM ids), and clicking it scrolls there. Blockers with nowhere to go (already launched, still loading, a check that failed to load) stay plain text.

## Spelling and grammar

- Rule checks: double spaces between words (a markdown hard break, two trailing spaces, is allowed), back-to-back repeated words, a space before punctuation, and a missing space after sentence punctuation.
- Spelling counts a word as known when either `typo-js`'s bundled en_US Hunspell dictionary (which handles inflections) or `an-array-of-english-words`, a 275k-word list with newer and compound words, has it. On the 114 local actions this cut misspelling flags from 67 (29 distinct words) to 29 (13), and every typo in a sample of 23 common misspellings is still caught except "wich", "calender", and "publically", which the long list has as real words. A larger Hunspell dictionary (`dictionary-en`) didn't help: it is the same word list. Treating a word that splits into two known words as known let real typos through ("arguement"). Both dictionaries load lazily, only when the launch panel opens (about 190 KB and 730 KB gzipped). Only lowercase words of three or more letters are checked, so names and acronyms aren't flagged. Curly apostrophes count as straight ones, so `isn’t` is checked whole. URLs (including bare `www.` ones and bare domains), link targets, inline code, code fence labels, file names, HTML tags, and email addresses are skipped.
- Capitalized words stay unchecked even at the start of a sentence, line, or heading. Checking them there (known if either case is in a dictionary) took the local actions from 67 misspelling flags to 266, nearly all brand names opening form option labels, and found no new typo.
- A short list of Alliance terms (`grantmaking`, `grantmaker`, `grantmakers`) always counts as spelled right. A rule accepting any known word plus "making" was the alternative, but compound rules let real typos through.
- Dismissing a misspelling dismisses that word everywhere in the suite, like "ignore word" in a spellchecker; other findings are dismissed one at a time. So findings are listed by what one dismissal covers: a misspelling is one row naming how many places it's in, each place with its context and edit link, and the launch blocker counts those rows. "Show dismissed" lists each dismissal once, greyed, with a button to restore it, since a dismissal is saved until launch and one stray click could otherwise hide a real typo for good.
- Checked text: the action's name, short description, body, and every member-facing text in its task form and in each variant's form, since members split across variants each see one. A form finding links to the form it's in. A variant form's saved version is part of the action's "Ready to launch" version too, so editing a variant clears the box.
- Fixing means editing the action (an edit link opens it in a new tab) and re-running the checks. There is no in-place auto-fix. A dismissal is keyed by the finding's surrounding text, so it survives edits elsewhere in the same field. Findings with identical surrounding text, as when a form repeats a sentence, are numbered in order so each is dismissed on its own.

## Launch

- The sequence is: create the member event, then the office event, then the default reminder groups on the new member event. The default reminders come from the same list the reminders tab's "Populate default reminders" uses, now `defaultReminderBodies` in `presets.ts`.
- The steps aren't atomic. When one fails, the panel stays open and says exactly what was created and what's left to add by hand.

## Launch review additions

- Distribution: members are grouped by the exact set of suite actions they get, most common first, with each group's minutes. A button per group adds one of its members to the preview, so each distinct experience is one click from "Log in as this member".
- Reminder preview: the default reminders are listed by send time in Pacific time, computed with the office action event as the deadline. A reminder that would send before members start blocks launch, which happens when the window is shorter than three days.
- Each reminder opens to its email subject, email, text, and push as a member receives them at its send time, rendered by `renderReminderKeywords`, which moved from the server's `processKeywordReplacements` into `common/src/reminderKeywords.ts` with `formatActionList` and `getTimeLeftString`, so the launch page renders exactly what the worker sends. The server keeps `processKeywordReplacements` as a wrapper that supplies its own links. "Preview as" picks a group of members by the actions they get, most common first, and renders for that group's first member, since the actions change the task names and counts. Group leads reminders render for a sample group with 3 members still to finish. A member's uncompleted tasks at launch are all their assigned suite actions, less optional ones where the reminder excludes them.
- A reminder sent at one instant for everyone (the launch announcement and the `from_deadline` reminders) notes how many recipients it reaches between 10pm and 8am in their saved zone, Pacific when unset. Range reminders already send at each member's preferred time, so they're never noted. The note doesn't block. The default schedule trips it: "Missed deadline message" sends at 11:59pm Pacific, 2:59am Eastern.
- Each action row shows its cohort's member count and description, an edit link for its task form, and notes to weigh before "Ready to launch": archived and an empty cohort. The notes don't block, because a cohort that depends on an earlier action can be empty at launch. A missing cover image isn't noted, at staff's request.
- An action that already has its own members taking action event (the action list's `memberActionStart`, which before launch can only come from the action's own events) is noted with that start, since launching adds a second start and a second announcement. It doesn't block, as staff may mean to re-run it.
- Each action row shows the action editor's `OpenReferenceWarning`: a cohort that reads an action still open at launch, and not awaited as a prerequisite, freezes members' placement at launch, so someone who finishes the referenced action later never gets this one. It's evaluated against the launch schedule, with this suite's own actions given the office deadline the launch creates. Like the editor, it doesn't block.
- An action whose description and task form take longer to read than its time estimate gets a note, since member load and the 15-minute contract check sum time estimates. Reading time is the action dashboard's estimate (0.462 seconds a word), now `readingTime` in `actionReadiness.ts`. With variant forms, it's the longest read any member gets. The note doesn't block: an estimate can fairly assume skimming.
- A link members can't open is a text finding: an `http(s)://` link to `localhost` or a loopback address, an `example.*` placeholder domain, or an `admin.` or `staging.` host, as when a URL is copied from the admin panel or a test site. Only links with a scheme count, to keep false positives down; of the 70 local actions whose bodies have links, none is flagged.
- Placeholder text (TODO, TBD, TKTK, FIXME, lorem ipsum, `[insert …]`, `[add …]`, `[tbd …]`) is a text finding like the rest.
