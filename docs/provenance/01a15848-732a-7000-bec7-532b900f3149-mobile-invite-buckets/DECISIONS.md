## Decisions

- **Mobile drops `request_pending` group invites by accident, not design.** The hand filter came in with the first mobile group page (`11ede5329`, "basic group main page mobile") with no recorded requirement, and community invite requests already existed then (`017064827`). The shared rule puts a request someone else made under "needs approval" and the leader's own request under "no action needed"; mobile now shows both.
- **Mobile shows the pending buckets only.** It lists needs-approval, to-be-sent and no-action-needed, and leaves out past invites as it did before, so the tab stays a to-do list on a small screen.
- **Status labels come from `shared/styles/inviteStatus.ts`.** The invite-status-colors task requires every site that shows an invite status's label and color to read that record. Its decision to keep this tab's "Pending"/"Link sent" separate described a summary of two statuses; the tab now shows every non-settled status of both invite kinds, including community requests, which a local map would have to label anew. An unused link reads "Pending" and a request "Request pending", as everywhere else.
- **`bucketCommunityInvitesByActionability` accepts an unknown user.** Like the one-time helper, it returns empty buckets while the user is loading, so neither caller writes that fallback.
- **The fix for missing request approvals is in the server.** `GET /user/onetimeInvites/:communityId` returned invites without their community, so the shared rule could not tell a request was for the viewed group and the web leader tab never offered Approve or Reject. Loading the relation, as the overview list does, fixes both apps at the source instead of having community-scoped callers patch the community in.
- **One-time invite mutations patch the other cached lists before invalidating them.** The overview includes every invite in the groups the user leads, so the same invite can sit in a group's list and in the overview. Invalidating the other lists (#740) only marks an unmounted list stale, which on the web it already is, so the next screen still rendered the old copy first. Each mutation now patches the others to match what the server returns, then invalidates them, skipping its own key: an approved or edited invite is merged into the cached copy, since approve answers without the invite's group; a rejected request is marked `request_rejected`, which the server keeps and both screens list as settled; a deleted invite is removed. A group's cached list keeps only that group's invites, so an edit that moves an invite drops it from the list it left. The invalidation covers what a patch cannot know: a created invite, and the list a moved invite joins.
- **The tab refetches both lists when it gains focus or the app returns to the foreground.** Mobile's query client keeps a list fresh for five minutes and does not refetch on focus, so without it a leader returning to the tab or the app, or arriving from a notification about a new request, would see the list as it was up to five minutes earlier. The tab is keyed by group, so switching groups remounts it and refetches the new group's lists too. The refetch joins a fetch already in flight rather than cancelling it. Pull-to-refresh uses the same refetch. Wiring react-query's focus manager to the app state would do this for every query, a broader change left alone here.
