# Decisions

Each draws on `EVIDENCE.md`. ALL-2013's own proposals were set aside per `REQUIREMENTS.md`; where a decision matches one, it is because the evidence led there.

- **Keep 500 lines for hand-written source and call it the repo's own threshold.** No standards body sets a file-length limit, and linter defaults spread from 300 to 2,000. 500 traces to _Clean Code_ as a non-absolute upper bound. The research recommends treating it as an operational choice rather than a defect boundary. Naming it as ours, with the whole-file-reading reason, lets an agent judge the edge cases the rule doesn't list.
- **Trigger only when a change grows a file past 500 or past its waiver; drop "a file past 500 is already overdue for a split".** The research recommends preventing unexplained growth over demanding wholesale splitting of existing files; the dropped sentence pushed toward the latter.
- **Keeping a file whole is decided after the codex consult.** That keeps the second opinion on the case where self-judgment is weakest, and splitting only reduces context when an agent can read one piece without the rest.
- **The waiver is a comment the lint rule parses, `/* alliance/max-lines <ceiling> -- <reason> */`, rather than an `eslint-disable`.** An `eslint-disable` switches the rule off, so it can't hold a ceiling, and ESLint's bulk suppressions count one finding per file, which lets a suppressed file grow. A comment in the file is what the next change to it reads, where a commit message would go unseen. `alliance/no-max-lines-disable` reports any `eslint-disable` or inline-config directive naming `alliance/max-lines`, so the old waiver form can't come back; a directive that also switches off that rule, or a bare `eslint-disable`, still escapes it, but is a visible act against lint as a whole. It is hand-rolled because `@eslint-community/eslint-plugin-eslint-comments` would be a new dependency for one check, and it finds directives through `SourceCode` and parses their rule lists with ESLint's own `ConfigCommentParser` from `@eslint/plugin-kit`, so it flags the directives ESLint honors, quoted rule names included. In a language where `/* */` isn't a comment, the waiver takes that language's comment syntax.
- **`alliance/max-lines` is its own rule, not a wrapper around core `max-lines`.** The core rule takes no per-file ceiling. The new rule keeps the old counting (non-blank lines, comments included) so existing counts carry over. It looks for the waiver anywhere among the file's comments, so a waiver below a header comment still counts, and treats a `/** alliance/max-lines … */` or `// alliance/max-lines …` as a malformed waiver, naming the `/* */` form, rather than missing it; it reports any waiver after the first, so a stale duplicate can't sit unchecked. The waiver it offers a file past the limit counts its own line, so pasting it passes; whether a file is back within the limit is judged without the waiver, so a waiver only its own line keeps past 500 is reported for removal. Ceilings in multiples of 50 (`REQUIREMENTS.md`) mean two branches that each add or remove a few lines rarely both edit the waiver line, which with exact counts conflicted or, merged cleanly with the same delta, left `main` past its ceiling. Waivers apply to the TypeScript files the rule lints. For other hand-written source, the `AGENTS.md` rule applies without lint.
- **No new CI job.** Every package's `typecheck` script ends in `eslint`, and CI runs typecheck for every package, so `error` severity alone makes CI block.
- **Baseline waivers say `baseline:` rather than claiming cohesion.** 53 files (50 tests, type tests included, 3 source) were past the limit when the rule became an error. Their reasons say they were never judged one unit, so the next change growing one goes through the split step with no reason to defer to.
- **Agent instructions stay under the line limit; other docs have none.** Agent instructions are the one category where the research found vendor numbers (Anthropic: under 200 lines per `CLAUDE.md`; Cursor: rule files under 500).
- **Cite _Clean Code_ through its publisher listing only.** The research's page scan was hosted on a user-upload site, likely an unauthorized copy; the listing carries the same citation.
- **No line limit for generated files, migrations, lockfiles, snapshots, fixture data, data, workflow YAML and config.** Every linter surveyed supports such exclusions; GitHub's only workflow limit is 500 KB and its splitting guidance (composite actions, reusable workflows) carries no line trigger; yamllint and markdownlint limit characters per line, not lines per file. Fixture helpers (builders, seeders, mocks) are executable code and stay under the limit, as `EVIDENCE.md` advises ("Keep executable helpers within it"); every TypeScript file named for fixtures in the repo is such a helper, so `alliance/max-lines` exempts none by name. Generated TypeScript is named `*.gen.ts`, which the lint skips, since a generator rewriting the file would drop a hand-added waiver; `common/src/country-names.ts`, the one generated file named otherwise, becomes `country-names.gen.ts` so the repo shows one convention. The lint also skips `migrations/`, since a migration is generated or written once for one schema change and never grows. Any other exempt TypeScript file the lint still flags takes a waiver naming its category instead of an ignore glob, and its ceiling is raised as it grows without the codex step, since no limit applies to it: none exists today, and a glob written ahead of one would guess its name.
