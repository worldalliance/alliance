# Evidence: industry practice on file size limits

Three codex subagents (`codex exec`, web search, read-only) researched this on 2026-11-04, each from an open question that did not mention ALL-2013's proposals: file size in general, test files, and lint severity. The claude session spot-checked the Anthropic, Cursor and GitHub Actions figures against their pages. "Strong" means strong evidence for what a source says, not that its number improves outcomes. The severity question assumed ESLint ran nowhere automatically; each package's `typecheck` script runs it, so CI already gates on lint errors.

## File size in general

**Conclusions.** I found **no general industry standard prescribing a maximum number of lines per repository file**. The strongest relevant standards sources leave thresholds to the project; published tools and guides use substantially different numbers. ESLint itself says there is no objective maximum. [ISO/IEC 25023](https://www.iso.org/standard/35747.html), [MISRA Compliance:2020, §2.5](https://www.misra.org.uk/app/uploads/2021/06/MISRA-Compliance-2020.pdf), [ESLint](https://eslint.org/docs/latest/rules/max-lines).

**A few hundred lines is a documented convention, not an empirically established safety boundary.** Research supports considering size when assessing maintenance risk, but does not establish a universal 200/300/400/500/1,000-line file cutoff—or one validated for this TypeScript stack and coding agents. Studies also measure different units: files, classes, modules, and methods. [Gil and Lalouche](https://link.springer.com/article/10.1007/s10664-017-9513-5), [Koru et al.](https://link.springer.com/article/10.1007/s10664-008-9080-x), [Chowdhury et al.](https://www.cs.ubc.ca/~rtholmes/papers/msr_2022_chowdhury.pdf).

**My proposed local policy—not a discovered standard:**

| File category                                       | Defensible starting rule                                                                                                          |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Hand-maintained source and scripts                  | Aim below **500 physical lines**. Above 500, require a cohesion review and either a meaningful split or a documented exception.   |
| Tests                                               | Apply the same review trigger; allow exceptions for cohesive suites. Treat embedded fixture data separately.                      |
| Workflow YAML and configuration                     | Use length as a review signal, not an unconditional split requirement. Split at supported job, task, or configuration boundaries. |
| Generated code, lockfiles, snapshots, fixtures/data | Exempt from the source-length rule. Apply appropriate byte-size, generation, schema, and integrity checks instead.                |
| Ordinary Markdown docs                              | Organize by reader task and topic; no blanket LOC gate.                                                                           |
| Agent instructions                                  | Maintain a short always-loaded core and scoped supporting instructions; follow the relevant vendor’s guidance below.              |

For the stated whole-file-reading concern, I would count imports, comments, and blank lines, while retaining normal formatting. Separately measure tokens actually read, editing failures, and task completion time. Treat **500 as an initial operational choice to evaluate**, not a claim that line 501 causes defects. Baseline existing exceptions and prevent unexplained growth rather than demanding wholesale splitting.

**4. Empirical evidence: defects and maintenance.**

| Research                            | Finding and practical limit                                                                                                                                                                                                                                                                                                                                                                      | Evidence strength                                                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **Gil & Lalouche, 2017**            | Across 26 metrics, predictive validity was strongly related to correlation with code size; controlling for size tended to remove other metrics’ predictive value. Supports size as an informative variable, but supplies no universal file cutoff. [Paper](https://link.springer.com/article/10.1007/s10664-017-9513-5).                                                                         | **Research — moderate**: observational evidence, not a randomized file-splitting intervention.                        |
| **Koru et al., 2008**               | Replicated studies of ten open-source products found defect proneness increasing **more slowly than size**; smaller modules were proportionally more defect-prone. Applications were externally checked on two commercial systems. This cautions against equating more defects with higher defects-per-line. [Paper](https://link.springer.com/article/10.1007/s10664-008-9080-x).               | **Research — moderate**, replicated but observational and module-specific.                                            |
| **Hatton, 1997**                    | Analyses of earlier systems suggested medium-sized components, roughly **200–400 lines**, could have lower fault density than smaller or larger components. The paper calls for further experiments to test its conjectures. These are historical component results, not a validated TypeScript-file limit. [Original article, archived PDF](https://gwern.net/doc/dual-n-back/1997-hatton.pdf). | **Research — limited for this repository**: old datasets and substantial modeling assumptions.                        |
| **Chowdhury, Uddin & Holmes, 2022** | Studied approximately **785,000 Java methods across 49 projects**, recommending **24 SLOC or fewer**, excluding blank/comment lines. Maintenance was assessed through change- and bug-proneness proxies, not directly measured labor cost. The authors acknowledge confounding and measurement limitations. [Paper](https://www.cs.ubc.ca/~rtholmes/papers/msr_2022_chowdhury.pdf).              | **Research — substantial observational evidence for Java methods; limited transfer to files, TypeScript, or agents**. |

**What remains unverified:** a specific whole-file cutoff that reliably reduces maintenance cost across languages; and a controlled result showing that enforcing 500 lines improves Claude Code or Codex task outcomes. The studies above do not establish those claims.

**Inference for this repo:** reducing irrelevant text loaded into context is better supported than any particular source-file line limit. Splitting helps only insofar as agents can select the relevant pieces; loading every resulting piece preserves the context burden. This inference follows from Aider’s selective-context guidance and Anthropic’s explicit warning about imported instructions. [Aider](https://aider.chat/docs/faq.html#how-can-i-add-all-the-files-to-the-chat), [Anthropic](https://code.claude.com/docs/en/memory).

**7. Exemptions and escape hatches.**

All items here are **common practice with strong documentary evidence**, not evidence that every project should adopt every exemption.

- **ESLint:** configurable counting, per-file/glob rule overrides, file ignores, and inline disables with explanations. It can report unused disable directives. [Counting](https://eslint.org/docs/latest/rules/max-lines), [rule configuration](https://eslint.org/docs/latest/use/configure/rules), [ignores](https://eslint.org/docs/latest/use/configure/ignore).
- **SwiftLint:** configurable warning/error thresholds, excluded paths, nested configuration, and inline disabling. [Configuration](https://github.com/realm/SwiftLint#configuration).
- **Pylint:** message-level disabling, including module-scoped suppression. [Message control](https://pylint.pycqa.org/en/latest/user_guide/messages/message_control.html).
- **Checkstyle:** suppressions can target filenames and checks; `FileLength` can target selected extensions. [Suppressions](https://checkstyle.org/filters/suppressionfilter.html), [FileLength](https://checkstyle.org/checks/sizes/filelength.html).
- **RuboCop:** global and per-check exclusions; `CountAsOne` can count arrays, hashes, heredocs, or method calls as one unit. Its block-length rule exempts gemspecs; **rubocop-rspec explicitly exempts spec files from `Metrics/BlockLength`**. These are targeted exceptions, not blanket removal of test-quality checks. [Exclusions](https://docs.rubocop.org/rubocop/latest/configuration/include_exclude.html), [metrics](https://docs.rubocop.org/rubocop/latest/cops_metrics.html), [RSpec configuration](https://raw.githubusercontent.com/rubocop/rubocop-rspec/master/config/default.yml).

## Test files

**Conclusions**

**Keep hand-written tests under the same approximately 500-line target, with documented exceptions rather than a blanket exemption or an automatic higher test-only limit.** This is my recommendation for your whole-file-reading workflow—not an empirically established threshold. ESLint itself acknowledges that there is no objective maximum file length. [ESLint](https://eslint.org/docs/latest/rules/max-lines)

Recommended policy:

- **500 lines triggers review of the file’s boundaries.** Split by coherent feature, behavior, endpoint group, or fixture—not arbitrary line ranges. This follows documented approaches from Kent C. Dodds and Cypress. [Dodds](https://kentcdodds.com/blog/avoid-nesting-when-youre-testing#what-about-grouping-tests), [Cypress](https://docs.cypress.io/app/core-concepts/writing-and-organizing-tests#how-much-to-put-in-one-spec-file)
- **Permit specific exceptions** when splitting would fragment one coherent scenario or demonstrably worsen setup/runtime costs. Preserve readable, self-contained tests; do not hide assertions behind abstractions merely to meet the limit. [Google](https://abseil.io/resources/swe-book/html/ch12.html), [Cypress](https://docs.cypress.io/app/core-concepts/writing-and-organizing-tests#how-much-to-put-in-one-spec-file)
- **Handle existing oversized suites incrementally:** record a temporary baseline, prohibit unexplained growth, and extract cohesive groups when extending them. Prioritize files with unrelated setup, frequent concurrent edits, or disproportionate runtime. This migration policy is my synthesis; Cypress documents those splitting signals. [Cypress](https://docs.cypress.io/app/core-concepts/writing-and-organizing-tests#how-much-to-put-in-one-spec-file)
- **Keep generated snapshots and bulk fixture data outside the hand-written-code limit.** Keep executable helpers within it. This is a proposed local policy, not an external standard.

I found **no verified formal standard or controlled evidence establishing 500—or another particular number—as the correct test-file limit**. There is relevant research on test-class LOC, individual-test readability, and flakiness, but it does not establish that repartitioning unchanged tests into shorter files causes better outcomes.

Evidence labels below: **V — vendor recommendation**, including official tool behavior; **C — common practice**, meaning documented project/practitioner practice, not measured industry consensus; **R — research**. “Strong” means direct support for the stated behavior or recommendation, not proof that a numerical threshold is optimal.

**4. Why tests can deserve different treatment**

- **DAMP supports local clarity over aggressive deduplication.** Google permits duplication when it makes tests easier to understand; Playwright explicitly allows some duplication for the same reason. **V — strong recommendation.** [Google](https://abseil.io/resources/swe-book/html/ch12.html#tests_and_code_sharing_dampcomma_not_dr), [Playwright](https://playwright.dev/docs/best-practices#make-tests-as-isolated-as-possible)

- **That does not imply unlimited file length.** My inference: self-contained tests can remain self-contained after moving coherent groups into separate files. Dodds explicitly combines tolerance for duplication with splitting large files. **C — moderate support for this inference.** [Dodds](https://kentcdodds.com/blog/avoid-nesting-when-youre-testing)

- **There are real reasons to keep tests together:** shared fixture context, convenient navigation, and execution overhead. These support exceptions based on cohesion and measured cost, rather than exempting every test file. **C/V — strong documented considerations; case-dependent application.** [Checkstyle’s rationale](https://github.com/checkstyle/checkstyle/blob/master/config/pmd-test.xml), [Cypress’s tradeoffs](https://docs.cypress.io/app/core-concepts/writing-and-organizing-tests#how-much-to-put-in-one-spec-file)

Thus, DAMP primarily argues against **bad abstraction and excessive deduplication**. It does not independently justify a higher numerical file limit.

## Lint severity and CI gating

### Conclusions

**I recommend configuring the ratcheted file-length rule as `error` and making lint a required CI check.** This is a policy recommendation based on the evidence below, not a research finding that 500 lines is an optimal limit.

- **Use `error` for an agreed requirement; use `warn` for advice or evaluation.** Your waiver makes the requirement “stay within 500 lines or the explicitly accepted ceiling.” That fits ESLint’s recommendation to use errors for enforced compliance. Warnings remain appropriate when findings require discretionary review or the team is still evaluating a rule. [ESLint severity guidance](https://eslint.org/docs/latest/use/configure/rules#rule-severities)
- **Add enforcement, not just a severity change.** Given your stated setup, changing severity alone still depends on somebody running lint. Run the intended lint checks on PRs and configure their status as required. If existing lint debt prevents adoption, baseline it or start with a smaller enforced ruleset. [GitHub required checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [ESLint incremental adoption](https://eslint.org/docs/latest/use/suppressions)
- **Use `--max-warnings 0` only if every warning should block.** It is unnecessary for this rule once it is an error. Keeping the rule at `warn` with that flag also blocks CI, but ordinary local ESLint runs still succeed; `error` communicates the same requirement locally and in CI. [ESLint CLI](https://eslint.org/docs/latest/use/command-line-interface)
- **Keep the waiver reviewable.** I recommend requiring a reason for new or increased ceilings, lowering ceilings after reductions, and removing unnecessary waivers. Otherwise the mechanism is a fixed allowance rather than a continually tightening ratchet. This recommendation follows baseline tools’ distinction between checking against accepted debt and explicitly updating it. [Betterer workflow](https://phenomnomnominal.github.io/betterer/docs/running-betterer/)

**Evidence limits:** I did not verify a controlled comparison showing that coding agents fix ESLint errors more reliably than warnings, or evidence establishing 500 lines as the best threshold. ESLint itself says there is no objective maximum acceptable file length. [ESLint `max-lines`](https://eslint.org/docs/latest/rules/max-lines)

| **Detekt**                   | Baselines distinguish current findings from manually suppressed findings, allowing newly introduced issues to be reported. [Baseline documentation](https://detekt.dev/docs/introduction/baseline/)                                                                                                                                                    |
| **Android Lint**             | A baseline records existing issues so future checks can focus on newly introduced ones. [Official guidance](https://developer.android.com/studio/write/lint)                                                                                                                                                                                           |
| **SwiftLint**                | Supports reading a baseline and writing one through `baseline` and `write_baseline` configuration. **Important inference for your rule:** ESLint’s generic count baseline is insufficient for tracking file growth. Core `max-lines` emits one finding for an oversized file; increasing that file from 700 to 900 lines still produces one finding. A suppression count of one therefore permits that growth. Your proposed **numeric line ceiling** tracks something the generic suppression mechanism does not. [Core implementation](https://github.com/eslint/eslint/blob/main/lib/rules/max-lines.js), [suppression counting](https://eslint.org/blog/2025/04/introducing-bulk-suppressions/)

#### 4. Empirical research

“Warning” in static-analysis research often means a reported finding generally; it should not automatically be interpreted as ESLint severity `warn`.

| Study                                                  | Finding                                                                                                                                                                                                                                                                                                                                                                                                        | Classification / strength                                                                    |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Johnson et al., ICSE 2013**                          | Interviews with 20 developers identified false positives and the presentation of warnings as barriers to using static-analysis tools. This supports attention to noise and usability, rather than indiscriminately increasing severity. [Official publication page](https://research.google/pubs/why-dont-software-developers-use-static-analysis-tools-to-find-bugs/)                                         | Research · moderate; qualitative interviews                                                  |
| **Sadowski et al., Tricorder, ICSE 2015**              | Google reported that build warnings were often ignored. Build-breaking checks required essentially zero effective false positives; code-review analysis tolerated a small effective false-positive rate and generally focused on changed lines. Review visibility provided peer accountability. [Official paper](https://research.google.com/pubs/archive/43322.pdf)                                           | Research · moderate; substantial industrial experience, not a controlled severity experiment |
| **Distefano et al., Facebook, CACM 2019**              | An initial batch deployment of Infer saw approximately zero fixes; reporting during code review saw roughly 70% fixed. The comparison supports timely workflow integration, but does not isolate warning versus error severity. [Official author manuscript](https://discovery.ucl.ac.uk/id/eprint/10084236/), [publisher DOI](https://doi.org/10.1145/3338112)                                                | Research · moderate; observational before/after account                                      |
| **Tómasdóttir et al., ESLint adoption, IEEE TSE 2020** | Studied over 9,500 configurations, interviewed 15 developers, and surveyed 337. Most interviewees used only or mostly errors. Four said warnings were ignored or devalued; others used warnings for adoption periods or unfinished development. [Official university manuscript](https://pure.tudelft.nl/ws/portalfiles/portal/46810031/tse_js.pdf), [publisher DOI](https://doi.org/10.1109/TSE.2018.2871058) | Research · strong descriptive evidence; historical and not causal                            |
| **Heričko and Šumak, MIPRO 2022**                      | Across 15 npm packages and 16,562 commits, unresolved lint findings generally increased in absolute number, while their density slightly decreased. This does not establish that ESLint `warn` severity caused accumulation. [Conference-hosted paper](https://www.mipro.hr/LinkClick.aspx?fileticket=UyLwRusRy00%3D&language=hr-HR&tabid=108)                                                                 | Research · moderate; small longitudinal sample                                               |

**Synthesis:** These studies support reducing irrelevant backlog and delivering actionable feedback during active work. They do **not** establish that non-blocking findings never get fixed, or that changing every warning into an error improves outcomes.
