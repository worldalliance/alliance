# Decisions

The work is planned as separate PRs, each with its Linear issue. This directory covers the first, the server; each later PR gets its own directory naming this one.

1. ALL-2246, server: verified-at date, the code that handles the one-number-per-account constraint, send-code and verify-code endpoints.
2. ALL-2259, the unique index behind the one-number-per-account constraint, once the first is live and ALL-2280 (## Settings) has shipped.
3. ALL-2247, the Slack alert link for inbound texts (REQUIREMENTS.md), which needs only the constraint.
4. ALL-2248, web: the code step in settings and after a form's phone question, and the "Confirm your number" prompt.
5. ALL-2249, mobile: the same.
6. ALL-2250, stop saving numbers without a code, once no client older than the code step is in use.

## Server

- **`hasPassword`, `loadedUserTags` and `loadedUserCommunities` moved from `user.entity.ts` to `user.utils.ts`.** The entity would pass 500 non-blank lines with the verified-at column this task adds; of the three splits a codex subagent proposed, this one moves functions that don't touch the class and leaves every import of `User` alone. (agent decision under root `AGENTS.md` **File size**)
- **`otpRefusalException` takes the purpose**, because its delivery-failure copy told the caller to "use another sign-in method", which is wrong for confirming a phone number. (agent decision)
- **The one-account rule will be a unique index on `user.phoneNumber` over rows where `deletedAt IS NULL`, added by ALL-2259 once this PR's server is live**, the shape `user.email` already has, named `UQ_user_phone_number_live` so a write that loses a race to it can be told apart from other unique violations. This PR ships the code that handles a violation of it and names it in `PHONE_NUMBER_INDEX`; until ALL-2259 lands nothing stops two live accounts holding one number. Root `AGENTS.md` **Breaking changes** has a migration and the server deploy land at different times, and `scripts/deploy_backend.sh` migrates before it restarts the server and keeps migrations on rollback, so an index shipped with its handling code would meet a server that answers its violation with a 500. ALL-2259 rechecks the production duplicate count with the query in EVIDENCE.md before it migrates. Once the index exists, a restore of a deleted account whose number a live account has since taken fails at it; restores are done by hand by an operator, who then clears one of the two. The user deferred how the constraint ships, in one deploy or two. (agent decision, user deferred the choice)
- **Saving a number without a code still works, marked `BACKCOMPAT(phone-verification)`.** The profile update and a form's phone answer are what the released web and mobile clients call, so both keep saving a number, as unverified, until PR 6. A profile update that repeats the member's current number changes nothing and keeps it verified. The profile update refuses a number another live account holds with 409 "This phone number is already linked to an account. Enter a different number.", mapped from the unique index, so it takes effect once ALL-2259 adds the index, and two updates racing to one number get it too. A form's phone answer that another live account holds is skipped and logged, and its welcome text, which would go to the other account's phone, is not sent: the member finishes the form without a number, as REQUIREMENTS.md has a member who does not enter a code do, and can add one in settings. The form saves the number before sending the welcome text and treats its refusal as a taken number, so a number another account takes mid-submission is skipped the same way. (agent decision)
- **The refusal names the cause.** EVIDENCE.md records that the two research reports differed on explicit against neutral wording; the neutral form implies the same fact and says less about what to do. "Linked to an account" follows the second report: an unverified record doesn't show whose the number is. The user was asked and had not chosen when the design moved to verification, so this is open to change. (agent decision)
- **The profile update reads the member's row under its row lock.** It used to save a copy read before its write, and a save writes back every column that differs, so a STOP recorded meanwhile was undone. (agent decision)
- **Every write that sets a phone number, or acts on its holders, first takes an advisory lock on the number**: the profile update on the number it sets, and so a form's phone answer; STOP and START; and verify, so verify can read a number's holders and move it with no other write setting it or updating its holders landing in between. A member leaving the number takes only their row lock. Each takes the lock before any account row lock. (agent decision)
- **STOP and START record and announce the live members their update changed**, not those a read before it saw. A member can leave a number without its lock (the profile update and verify lock only the number they set), so a STOP to the old number can wait on that member's row and then find them gone. (agent decision)
- **The migration was written from a generated one.** A new enum value is added with `ALTER TYPE ... ADD VALUE` in place of the generator's recreate of the type, which rewrites `event_log` under an exclusive lock. The generator also emits drops and re-adds of `friend.lowUserId`, `friend.highUserId` and their index, and at times of `CHK_user_referral_fields`, none of which this change's entities touch; those statements are left out. With the migration applied, `migration:generate` emits only such statements. (agent decision)
- **Verified is recorded as `user.phoneNumberVerifiedAt`, null for a number no code has confirmed.** Nothing that sends a text reads it, which is how existing members keep receiving texts (REQUIREMENTS.md). Clients get it as `phoneNumberVerified` on the user they already load from `/auth/me`. (agent decision)
- **Codes reuse `OtpService` with a new purpose, `phone_verification`.** The endpoints are `POST /user/phone/code` and `POST /user/phone/code/verify`, for a signed-in member. The token naming the challenge is returned in the response body and sent back with the code, where the KORA sign-in keeps it in a cookie: the mobile app has no cookie jar for it, and the caller is already authenticated. A client that loses the token asks for a new code. (agent decision)
- **The verification text carries the WebOTP line only for a request from one of the Alliance's own sites.** The mobile app sends no `Origin`, and a request's `Origin` is otherwise the sender's to choose, so an unrecognised one is left out of the text. (agent decision)
- **On verify, the number moves in one transaction under the number's advisory lock**, so no write to the number lands between verify reading its holders and saving it. Verify then locks the verifier's row and the holders' rows in id order, so two members verifying each other's numbers at once can't deadlock. The account that loses the number has `phoneNumber`, `phoneNumberVerifiedAt` and `phoneNumberUnsubscribed` cleared, and a `phone_number_moved` event names it, which goes to Slack as the staff alert. The event is written in the move's transaction, since it is the only record of which number that account held, and goes to Slack once the move commits. (agent decision implementing the requirement)
- **An opt-out follows the number.** The verifying member's `phoneNumberUnsubscribed` becomes true when any account holding the number had it set, their own included, and deleted accounts too, since `MmsUnsubService` records a STOP on them; it is false otherwise. Twilio keeps refusing sends to a number that texted STOP whichever account holds it, so the flag stays accurate; a member changing to a number nobody held starts subscribed. Only live accounts lose the number. (agent decision)

## Settings

- **Web and mobile settings do not handle the profile update's refusal in this PR; ALL-2280 does, and ships before ALL-2259.** Settings autosave the whole profile, so once the index exists a refused number left in the field fails every later save. The user deferred whether that handling lands in this PR or a follow-up, which makes it optional here; a version built for this PR drew fix-now review findings in three rounds and was cut. No 409 reaches settings before ALL-2259 adds the index. (agent decision, user deferred whether the work happens in this PR)
