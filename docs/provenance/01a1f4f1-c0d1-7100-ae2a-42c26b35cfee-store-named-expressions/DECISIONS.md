# Decisions

Agent decisions unless labelled otherwise. The research and agent reports behind the questions asked are in `EVIDENCE.md`.

## Names

- **Code names.** The server, the database and the admin use "formula": `Formula` and `FormulaVersion` entities, `formula` and `formula_version` tables, `/formulas` endpoints. The expression core in `common/src/expression/` keeps "named expression" (`NamedExpression`, `checkNamedSave`) for now. `common/src/forms/variables.ts` already exports an old-system `Formula` type, and admin has an old-system `FormulaEditor`, so renaming the core would give one package two unrelated `Formula`s. Rename the core when the old form system is removed (ALL-2185); ALL-2384 tracks the rename.
- **Messages without "input".** Messages the core shows admins say "formula" where they said "named expression". Following the requirement that admins see no umbrella word for what a formula reads, they name the thing (``Nothing here is called `x`.``, `` `x` is already used by something formulas can read. ``) or say "something". A removed input stays unnamed ("This uses something that no longer exists."), since a formula may have taken its id as its name, and naming it would point at the formula.
- **Old builder relabel scope.** Every admin-visible string in the old form builder that names a form variable says "formula": the tab, its heading, its buttons, and the save gate and validation messages, plus the server's delete-refusal message. A new variable's default name (`variable1`) is data, not a label, so it stays.

## Storage

- **Versions.** A `formula` row holds the id, current name and soft-delete time; each save adds an immutable `formula_version` row with the name it was saved under, the tree, notes and who saved it. The current version is the latest by id. Consumers pin a version id (spec, "Fill session" and go-live pinning), so no snapshot object is needed. The research found immutable rows per version to be the shared pattern where consumers pin versions (`EVIDENCE.md`, "Storing versions").
- **Ids.** The client picks a formula's UUID, so one save can create formulas that read each other, and problems refer to entries by the same id the client sent. Ids are lower-cased on arrival, since Postgres compares and returns UUIDs in lower case; a new formula is inserted, never upserted, so it can't take an existing formula's id.
- **Delete.** Soft delete: the formula leaves the list and its name is free again, while its versions stay for whatever pinned them. A delete goes through the same check and is refused, naming each reader, when something still reads the formula, following LaunchDarkly, Unleash and Postgres `RESTRICT` (`EVIDENCE.md`, "Blocking deletes").
- **Unchanged saves add no version.** A save whose name, notes and tree match the current version writes nothing for it, so the history lists only real changes.
- **Renames.** Renaming changes the formula row and adds a version; readers store ids, so they reprint under the new name. Two formulas can swap names in one save: renamed rows pass through a `__renaming:<id>` placeholder, which no real name can take.
- **Notes** are per version, so the history shows what a note said at each save.

## Saves

- **One endpoint.** `POST /formulas/save` takes edits and deletions together, since fixing a dependent in the same save is a requirement and a delete can need the same. A refused save is a normal outcome the editor branches on, so it answers 200 with `problems`, empty on success, rather than an error status.
- **Two admins at once.** Each edit and deletion names the version it started from. A save based on an older version, a new formula whose id exists, or a formula deleted meanwhile is refused with 409 and a message saying to reload. Reload opens the formula's own page. For a new formula the editor hasn't saved, it first reloads the list: a save can commit and lose its answer, so the next save's 409 says it was already saved, and Reload opens its page; otherwise it opens a blank new formula, since the id isn't stored. This is optimistic concurrency as RFC 9110 `If-Match` and Google AIP-154 describe, carried in the body because a save spans several formulas (`EVIDENCE.md`, "Two admins at once").
- **Saves take turns.** The check reads every formula, so a save holds a transaction-scoped advisory lock (`formulas`) from its read to its commit; otherwise two saves could each pass against what the other is about to change. The e2e test holds the lock itself and shows a save waits; concurrent requests alone didn't overlap in tests, because the synchronous check runs each save to completion first.
- **Dependents.** No consumer stores expressions yet, so saves pass no dependents. Splits (ALL-2177) and forms (ALL-2184) add theirs to the save and to the re-check.
- **Catalog.** `server/src/formulas/formula-catalog.ts` is empty, per the requirement to ship with an empty input list; the changes that add inputs fill it.
- **Cost.** With an empty catalog, the formulas e2e tests run in about 2.6 s in total. Revisit with real inputs; `named-expression-saves` DECISIONS.md names checking several expressions in one program as the next step.

## Re-check before deploy

- **Where in the deploy.** `scripts/deploy_backend.sh` runs `server/scripts/check-stored-formulas.ts` after migrations, which create the table the first time, and before the new backend starts. On failure the old release keeps running (`keep_old_release`, or `recover_by_record` on the streak-removal path), and the log lists each broken formula with its text and problems, or each formula whose stored tree the release can't parse, by name and id. Migrations already ran by then; that is the state every deploy is in while the old backend serves, since migrations are expand steps.
- **Re-checking after the swap.** Where the old backend keeps serving through migrations, it takes saves until the swap, checked against the old release. The deploy runs the check a second time once the new backend passes its health check, while the rollback trap is still set, so a formula saved in those seconds that the release breaks rolls back to the old release, as the requirement that a failure keeps the old release running asks; the first run stays, so a release that breaks a formula already stored never starts. The streak-removal path stops the old backend before its check, so it takes one run. This is the review loop agent's judgement, not a user answer: the requirement settles it, so it wasn't put to the user. `rollback()`, and a manual redeploy of a commit from before the check, don't re-check formulas saved under the newer release: ALL-2376. A manual redeploy of a later commit runs its own check and refuses formulas it can't run, so `docs/deploying.md`'s rollback steps say to fix or delete them first.
- **The prod → staging sync isn't checked.** `scripts/sync_prod_to_staging.sh` copies production's formulas into staging without the check, and stays unchanged here, since the requirement covers deploys. The gap is narrow: a formula production saves after staging's release went out, which that release breaks, is caught by the next merge's staging deploy check. That check then holds every later staging deploy, and so production, at the old release until the formula or the release is fixed, which is correct, since production's own check would refuse the same release. Checking synced formulas, likely warning on ones synced from production and blocking on ones saved in staging, is ALL-2378, due before formulas are member-facing. This is the review loop agent's judgement, not a user answer: it isn't a product choice, so it wasn't put to the user.
- **What it checks.** `checkStored` in `common/src/expression/named.ts` runs the save check over every stored formula and, once they exist, every stored dependent, sharing `checkNamedSave`'s loop handling and reporting each problem once at its cause. Stored expressions are spared the needless-fallback check, as saves spare them.
- **TypeScript in production.** The check imports `typescript` at runtime. `common/package.json` lists it under `dependencies`, the deploy zip includes `common/`, and the deploy runs `bun install` on the workspace, so production has it; the server's own `typescript` dev dependency doesn't need moving.
- **Deploy test.** `scripts/deploy_backend.test.ts` stubs the formula check like the other deploy steps, and covers a failing check on both migration paths and a failing second run after the swap.

## Editor

- **Text only for now.** The editor edits text with notes, checks on save, and shows each problem at its place in the text. Autocomplete (the spec's deferred choice to load the TypeScript worker when a text editor opens) and the All/Any builder are left for follow-up issues ALL-2382 and ALL-2383: with an empty catalog, autocomplete would offer only other formulas' names and the builder would have nothing to pick.
- **Fixing in the same save.** A refused save lists problems in formulas not open in the editor under "Problems in other formulas", a heading that holds for a formula the edited one reads, which the check lists when it already fails, as well as one the save breaks; each with "Fix it in this save", which opens that formula's fields below the one being edited, its text printed with the names the save gives, so a fix after a rename reads the new name; the next save sends all of them. Focus moves to the opened fix's heading, and to Save when the admin presses "Stop fixing it", since each removes the button pressed. A delete sends the open fixes with it, so a reader can be fixed in the delete's save. A formula added since the editor opened has no fields to open, so it is listed by id with a link to its own page. A dependent's problem, which no save gives until splits (ALL-2177) and forms (ALL-2184) store expressions, is listed by id alone, for those issues to present.
- **After a save.** The editor works on the list as it opened it, which is the list fetched when the formula opens, a link from another formula included, not one cached from an earlier visit; when that fetch fails, the page shows the error rather than opening on the cached list. Only the editor's own save remounts it on the refreshed list. A refetch bringing someone else's version, or failing, keeps the admin's edits, and their save gets the 409, whose message offers Reload; other failed saves show only their message. A new formula's save moves straight to its page, whose own fetch finds it, so the page loads once and shows that fetch's error if it fails. Any other save remounts only on a list fetched after it, so the page shows what was saved; the fields stay read-only until that fetch settles, since the remount would drop edits made meanwhile. Either puts focus back on Save, which the remount would otherwise drop to the page. An admin who leaves while it loads stays where they went. When that fetch fails, the fields stay read-only, since a further save would carry stale versions and get a 409 for the admin's own save, and the editor says to reload. A delete drops the formula from the cached list before moving to it, so the list never shows it.
- **Leaving with unsaved changes** asks first, through `useUnsavedChangesPrompt`, extracted from the form builder's `useSavedForm` so both share it.
- **History** loads when opened, newest first, printed with the names formulas have now. Its cache is keyed on the formula's latest version, so after a save it loads afresh rather than showing the list without the saved version.
