- `shared/lib/useTaskFormAggregateViews.ts` owns `queryKeys.taskFormAggregateViews(formId)`: `useTaskFormAggregateViews` for one form, `useTaskFormsAggregateViews` for the sidebar's several, and `useInvalidateTaskFormAggregateViews` for writers. It sits in `shared/` because the opt-out writer, `useTaskFormHandlers` in `shared/lib/actionTaskPanel.ts`, is shared with mobile. Mobile renders no aggregate views, so it gains no reader.
- A form's views total the numeric answers of every response to it (`TasksService.findFormAggregateViews`), and change when a response is saved or the form's schema changes. From the member app the viewer saves a response in two places: submitting the task form (`ActionTaskPanelForm`, member or guest) and withdrawing, which saves the partial answers (`useTaskFormHandlers.handleAbandonAction`). Each invalidates the form's views on success. Schema edits happen in the admin app, which has its own query client.
- Responses from other members reach the views the way they reach the actions list: by refetching a stale query on mount and window focus, under the default `staleTime` of 0. The views have no polling interval of their own, so a page left open and focused keeps its totals until the next mount, focus or own write; they no longer ride the navbar's one-minute `actions` poll (`useTaskBadgeCount`), which the cache subscription turned into a refetch.
- A follow-up form submission saves a response to the follow-up form, whose views nothing renders, so it invalidates nothing.
- A failed load still reads as no views, as both fetchers did, since the views decorate the page.
- The action page skips the request for a signed-out viewer, whom the endpoint's `AuthGuard` refuses; the errored query would otherwise resend the doomed request on every window focus.
