## Sources

Checked 2026-11-23 by a research subagent and the implementing agent.

- Anthropic's setup page (https://code.claude.com/docs/en/setup), vendor recommendation: the npm package installs the same native binary through per-platform optional dependencies; each release publishes `manifest.json` with a SHA256 per platform and a GPG-signed `manifest.json.sig`; distributors set `DISABLE_UPDATES` when shipping Claude Code through their own channels.
- Anthropic's Agent SDK (https://code.claude.com/docs/en/agent-sdk/typescript), vendor practice: it bundles the native binary as per-platform optional npm packages.
- OpenAI's Codex CLI docs (https://learn.chatgpt.com/docs/codex/cli), vendor documentation: cover `install.sh`, npm and Homebrew only, nothing on pinning or verifying a download. The `rust-v0.167.0` GitHub release publishes per-triple tarballs with `codex-package_SHA256SUMS`.
- electron-builder's contents page (https://www.electron.build/docs/contents), vendor recommendation: `extraResources` for native binaries and CLI tools needed at runtime, landing in `Contents/Resources` on macOS and read through `process.resourcesPath`.
- Apple's "Placing content in a bundle" (https://developer.apple.com/documentation/bundleresources/placing-content-in-a-bundle), vendor recommendation: helper tools in `Contents/MacOS`, dynamic libraries in `Contents/Frameworks`; resources are everything that isn't code. It conflicts with electron-builder's `extraResources` for signed builds; `@electron/osx-sign` signs every binary it finds anywhere in the bundle (https://github.com/electron/osx-sign/blob/main/src/util.ts, source code).
- GitHub's Dependabot ecosystem table (https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories), vendor documentation: `bun` (Bun 1.1.39 and later, text `bun.lock`) supports version updates, not security updates; the options reference (https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference) has a per-entry `directory` and an `allow` list.
- VS Code's `shellEnv.ts` (https://github.com/microsoft/vscode/blob/main/src/vs/platform/shell/node/shellEnv.ts, source code) and FAQ (https://code.visualstudio.com/docs/supporting/faq), vendor practice: launched from the UI, VS Code runs the user's shell once, detached, as `$SHELL -i -l -c`, or `-ic` for csh and tcsh, with other forms for PowerShell, Nushell and xonsh, prints its environment between markers random to each run, waits up to 10 seconds by default, and on failure shows "Unable to resolve your shell environment in a reasonable time" and runs without it. Zed's environment docs (https://zed.dev/docs/environment), vendor practice: it loads a login shell's environment at startup too.
- Which launches skip that load, checked 2026-11-23 on each project's `main`, vendor practice from source code: VS Code's `getResolvedShellEnv` (`shellEnv.ts` above) skips it when `VSCODE_CLI=1`, which `isLaunchedFromCli` (https://github.com/microsoft/vscode/blob/main/src/vs/platform/environment/node/argvHelper.ts) reads and both its `code` command and its developer launcher `scripts/code.sh` (https://github.com/microsoft/vscode/blob/main/scripts/code.sh) set, and traces "skipped (VSCODE_CLI is set)"; Zed's `main.rs` (https://github.com/zed-industries/zed/blob/main/crates/zed/src/main.rs) loads it only when stdout isn't a terminal; `shell-env`, `shell-path` and `fix-path` never skip it outside Windows. POSIX (https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html, formal standard) defines `TERM` only as the terminal type, not as a launch signal. On the implementing developer's Mac: launchd's GUI environment (`launchctl print gui/$UID`) held only `SSH_AUTH_SOCK`, and an app started with `open` from a terminal received that terminal's environment, `TERM` included, with stdout not a terminal; electron-vite 6.0.0's `dev` starts Electron with the inherited environment and `stdio: 'inherit'`.
- `shell-env` 4.0.3 (https://github.com/sindresorhus/shell-env, source read from its npm tarball), common practice: runs `-ilc` with oh-my-zsh's auto-update and tmux autostart turned off, with no timeout, and splits `env`'s output on newlines; when the default shell fails it tries `/bin/zsh` and `/bin/bash`, then returns `process.env`, and when a shell the caller named fails it rethrows (`index.js` at tag `v4.0.3`, checked 2026-11-23). `fix-path` (https://github.com/sindresorhus/fix-path) builds on it and warns that packaged Electron apps opened from the Finder may not quit properly.

## Shell environment timeouts

Checked 2026-11-24. JetBrains IDEs, vendor practice from source code: `DEFAULT_SHELL_ENV_READING_TIMEOUT_MILLIS = 20_000L` in `EnvironmentUtil.java` (https://github.com/JetBrains/intellij-community/blob/idea/243.22562.145/platform/util/src/com/intellij/util/EnvironmentUtil.java), changeable with `-Dij.load.shell.env.timeout`; on timeout it kills the shell, logs and falls back to its own environment without telling the user. VS Code, vendor practice: the 10-second default predates `application.shellEnvironmentResolutionTimeout`, limited to 1 to 120 seconds, which the 1.75 release notes (https://code.visualstudio.com/updates/v1_75) add because some shell configurations need longer. Cursor, a VS Code fork with the same default and setting, common practice: its forum thread on "Unable to resolve your shell environment in a reasonable time" (https://forum.cursor.com/t/unable-to-resolve-your-shell-environment-in-a-reasonable-time-please-review-your-shell-configuration-and-restart/161024) advises raising the setting to 30 seconds or more. Zed, `shell-env` and Emacs's exec-path-from-shell set no timeout; none of the six retries.

## Codex's npm launcher

`@openai/codex@0.167.0`'s `bin/codex.js` maps the platform to a target triple (Linux to `*-unknown-linux-musl`), finds `vendor/<triple>/bin/codex` in the platform package, sets `CODEX_MANAGED_PACKAGE_ROOT` and one `CODEX_MANAGED_BY_<package manager>` variable, and execs the binary with its arguments. It changes no other environment, PATH included.

## Login-shell environment

On the implementing developer's Mac (macOS 27, zsh, a profile loading nvm), 2026-11-23: `zsh -ilc exit` took 5.1 seconds and `zsh -lc exit` 0.01 seconds; `loadShellEnvironment` from `PATH=/usr/bin:/bin` took 8.4 seconds and returned a PATH starting with nvm's, `~/.local/bin`, `~/.bun/bin` and `/opt/homebrew/bin`. The same Mac, 2026-11-23: `/bin/tcsh -i -l -c 'echo hi'` failed with "Unknown option: `-l'", and `/bin/csh -ic` and `/bin/tcsh -ic` each wrote the environment to a file and printed the marker.
