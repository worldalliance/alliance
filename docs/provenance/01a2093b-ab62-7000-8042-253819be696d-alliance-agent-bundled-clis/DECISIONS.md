## Where the binaries come from

The CLIs are the vendors' npm packages, `@anthropic-ai/claude-code` and `@openai/codex`, pinned exactly as devDependencies of `agents/desktop` (agent decision; EVIDENCE.md, Sources). Each lists its per-platform binary packages as optional dependencies, and `bun.lock` records a sha512 for every platform's package, so the install verifies whichever it fetches. The meta packages are pinned rather than the platform packages, so each CLI is one entry a bump changes and a development build works on macOS and Linux, arm64 or x64, the platforms the app runs the CLIs on. They are devDependencies so electron-builder leaves them out of `app.asar`; its `extraResources` copies the host platform's binaries instead. Anthropic also publishes a GPG-signed manifest of SHA256 hashes, which would add provenance on top of the registry's integrity check; it was left out as a second mechanism no bump bot understands.

The app runs Codex's native binary, not the npm package's `bin/codex.js`, which only finds that binary and sets `CODEX_MANAGED_BY_*` for Codex's update hints, which the app turns off (EVIDENCE.md, Codex's npm launcher).

## Development builds run the bundled copies

A development build runs the CLIs from `node_modules`, so a developer's own auto-updating `claude` never meets the version check again, which blocked every message once it updated (agent decision, stated to the user beside the task's questions). The PATH lookup is gone. `ALLIANCE_AGENT_CLAUDE_EXECUTABLE` and `ALLIANCE_AGENT_CODEX_EXECUTABLE` still name an executable to run instead, for the tests' stubs and the capture runs, and now fail when they name no executable file rather than resolving to a path that fails at spawn. The tests that had found a CLI installed on PATH while the app ran now name a missing file that then appears, since leaving the variable unset would run the real bundled CLI in a test. The exact-version check stays, since a variable can name any version; its failure tells a development build to run `bun install`, the fix once a bump is pulled. When a CLI can't be checked, the sign-in panel's summary no longer says to install the CLI, which wouldn't change the one the app runs; its wording is in REQUIREMENTS.md, Sign-in panel.

`CLAUDE_CODE_VERSION` and `CODEX_VERSION` are read from `package.json`, which a zod check holds to exact versions, so a bump changes one place.

## One environment for both CLIs

Each CLI's environment used to drop the other vendor's namespaces and set only its own private folder, so a `claude -p` that a Codex session starts ran with the user's own `~/.claude`, and a `codex` that a Claude session starts with the user's `~/.codex`. So every CLI the app runs gets one environment, `agentEnvironment` in `src/main/agent/agent-environment.ts`: it drops both vendors' namespaces (`CLAUDE*`, `ANTHROPIC_*`, `CODEX*` but `CODEX_CA_CERTIFICATE`, `OPENAI_*`), sets `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and Claude's three traffic variables, and puts the app's launcher folder first on PATH (agent decision). Claude processes therefore now drop Codex's non-credential settings too, such as `CODEX_REFRESH_TOKEN_URL_OVERRIDE`, which a Codex they start would read.

## Launchers

The app writes `claude` and `codex` shell launchers into `bin/` in its user data, exec'ing the bundled executables, or failing with exit 127 and the reason when the app has none, so a bare name never falls through to a CLI the user installed (agent decision). Codex's passes `codexConfigArgs`, the overrides the app's own Codex runs take, so its analytics, feedback and update check stay off however an agent starts it. A launcher was chosen over writing those keys into the private `config.toml`: the app writes that file only through app-server's `config/batchWrite`, and a Claude session can start `codex` before any Codex session has run. Writing them also creates `CODEX_HOME`, since Codex refuses every command but `--version` without it. Each lookup of an agent the app hasn't found yet rewrites both launchers from the executables found then, so a CLI that appears while the app runs, such as after `bun install` in a development build, reaches agents' bare names once its own agent is looked up.

## Codex's command shell

`codexConfigArgs` sets `allow_login_shell=false`, per the requirement, so Codex runs each command as `<shell> -c`, which reads only `~/.zshenv`, and skips the login-shell snapshot that /etc/zprofile's path_helper and `~/.zprofile` reorder (EVIDENCE.md, Codex's command shell). A user who prepends their own `claude` or `codex` in `~/.zshenv` still shadows the launchers; that is rare and left alone. `src/main/agent/codex/shell-path.test.ts` is the CI test the requirement names: it runs the bundled Codex's `exec` through the launcher against a local mock of the Responses API, as Codex's own tests do, with a home whose `.zprofile`, `.bash_profile` and `.profile` put another `claude` and `codex` first, and expects `command -v claude codex` to print the launchers. It fails with the login shell on. It ends once the command's output arrives, since Codex syncs its plugin catalogue from the network before exiting.

## Login-shell environment

`src/main/shell-environment.ts` loads the user's login-shell environment: it runs `$SHELL -i -l -c`, or `-ic` for csh and tcsh, which take `-l` only alone, falling back to the passwd entry's shell, the shape of VS Code's `shellEnv.ts` (agent decision; EVIDENCE.md, Sources and Login-shell environment). The command writes `/usr/bin/env -0` to a file in a fresh temporary folder, whose path reaches it in an environment variable so no shell quoting is needed, then prints a marker random to each run, so profile output and the processes a profile starts, which share stdout, can't corrupt the environment, and the app keeps only stdout's last few bytes. The marker prints only when `env` succeeds, and `env` and `printf` are named by absolute path, so a profile that empties PATH or a failing `env` fails the load instead of returning an empty environment, and csh, which has no builtin `printf`, prints the marker whatever PATH its profile sets. A folder the loader can't remove afterwards fails the load, naming it, since it holds the environment. The shell runs detached, leading its own process group, as VS Code's does; once the environment arrives, the shell exits with an error, the 30-second timeout passes or the caller aborts, the loader kills that group, so neither what the profile is stuck on nor a process it left writing outlives the load. A job a startup file moves to a group of its own with `set -m` outlives it (ALL-2434). The command uses `>`, `"$VAR"` and `&&`, which sh-family shells, fish and csh/tcsh parse; a Nushell or PowerShell login shell, which VS Code gives commands of their own, fails the load and gets the error dialog (agent decision, YAGNI until someone uses one). A small loader was chosen over `shell-env` 4.0.3, which has no timeout, falls back silently to the app's own environment and splits values on newlines; `fix-path` builds on it.

The load waits 30 seconds, the user's round-5 answer (REQUIREMENTS.md), raised from 10 because the developer's own load took 8.4 seconds; VS Code defaults to 10 seconds but added a setting for 1 to 120 in 1.75 because some shells need longer, JetBrains IDEs wait 20 and Cursor's forum advises 30 or more (EVIDENCE.md, Shell environment timeouts and Login-shell environment). The cost: a hanging profile delays the error and the first agent, git or Bun call by 30 seconds. Rejected: keeping 10 seconds; giving up at 10 while the load runs on, since an agent session started on the launch PATH keeps it; retrying once, which no surveyed tool does and which doubles the wait for a shell that stays slow; caching the last good environment, which goes stale without the user seeing it.

The app loads it once at launch and merges it into its own environment, before any agent's CLI, git or Bun runs, per the requirement; the agents' environment applies its scrubbing, private folders and launchers after it, so a profile that sets `CODEX_HOME`, `CLAUDE_CONFIG_DIR` or a vendor credential doesn't undo them. git and Bun get it too, so an app opened from the Finder finds a Homebrew Bun. Quitting aborts a load still running. The window opens without waiting, and each command waits instead, since the developer's own shell took 5 to 8 seconds; on failure an error dialog, titled "Alliance agent couldn't load your shell environment", gives the reason and the PATH the app carries on with. The e2e tests set `SHELL` to `e2e/profile-free-shell`, which runs the command without a profile, so no test waits on the developer's shell; `e2e/shell-environment.e2e.ts` swaps in a shell whose profile sets a variable and a PATH entry, or fails, and checks what a CLI started at once runs with, and that git and Bun, which have their own waits, run from the PATH it loads.

Claude's "launchers stay first" measurement (EVIDENCE.md, Claude's command shell) ran from a terminal-launched app, whose PATH already held the user's profile entries. Loading the login environment gives a Finder launch that same PATH, launchers in front, so the measurement now stands for both launches (agent judgement, not re-measured).

`bun run dev` sets `ALLIANCE_AGENT_DEV_SCRIPT=1`, the marker the requirement names, after VS Code's `VSCODE_CLI=1` from its `code` command and `scripts/code.sh` (EVIDENCE.md, Which launches skip that load); a packaged app ignores it. The app deletes it from its environment at startup, so an app or test an agent starts from a dev build loads its own. Startup logs "Loaded the login-shell environment" or "Skipped loading the login-shell environment (ALLIANCE_AGENT_DEV_SCRIPT is set)", as VS Code traces its skip. Each load also logs how long it took, so a later change to the timeout has data (agent decision). The rejected alternatives were skipping when `TERM` is set, which POSIX defines only as a terminal type and which a desktop started from a text console passes to every app; skipping when stdout is a terminal, as Zed does, which still loads for a redirected dev run; and skipping in every unpackaged build, which would leave the e2e tests no launch that loads it without a switch of their own. `e2e/shell-environment.e2e.ts` launches with the marker and checks the CLI gets the launch environment without it.

## Linux libc

Claude's Linux binaries come in glibc and musl builds; the app runs the glibc one, and Codex's Linux build is statically linked against musl. On a musl distribution Claude fails to start, with the error the spawn reports; the app doesn't detect musl (agent decision, YAGNI while Linux targets Debian-based distributions).
