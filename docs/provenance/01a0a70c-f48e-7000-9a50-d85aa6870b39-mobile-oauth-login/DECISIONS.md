# Decisions

## Native provider UI

- Google on iOS and Android goes through `@react-native-google-signin/google-signin`. Its id token carries the web client id as audience, which `GoogleOAuthClient.verifyIdentityToken` already checks against `GOOGLE_CLIENT_ID`.
- Apple on iOS goes through `expo-apple-authentication`. `AppleOAuthClient.verifyIdentityToken` checks the token against `APPLE_BUNDLE_ID`, so the dev bundle id has to be in that comma-separated list.
- Android has no native Apple UI, so Apple there uses the browser session. Google also falls back to it when Google Play services are missing or out of date, since the native SDK can't run without them. The app doesn't ask Play services to show its update dialog, which would open on top of the browser session.
- On Android the browser session opens in Chrome's Auth Tab when the default browser supports it, through a local Expo module in `apps/mobile/modules/auth-tab`. A Custom Tab only returns to the app when Chrome hands the server's redirect to the verified App Link, and Chrome often keeps a redirect in the tab when no tap directly started it. Apple's web flow returns through a form that submits itself, so it's the likeliest to stay in the tab. The Auth Tab closes on the redirect itself and checks an https redirect against `assetlinks.json` for the calling app. Where it isn't available, `expo-web-browser`'s Custom Tab runs as before.
- An Auth Tab that closes because it couldn't verify the https redirect counts as `failed` and is logged. The member already went through consent, so reopening the flow in a Custom Tab would ask them again.
- A Custom Tab session counts as `cancelled` only when the member closed it (`cancel`, `dismiss`). `opened` and `locked` mean nothing waited on the redirect, so they count as `failed` and are logged.
- The module depends on `androidx.browser` 1.9.0, the first release with Auth Tab. `expo-web-browser` declares 1.6.0, and Gradle resolves both to 1.9.0.
- The module starts the Auth Tab with `startActivityForResult` and settles `openAsync` from `OnActivityResult`, which still arrives after Android recreates the activity (checked on a device with "Don't keep activities" on). Expo's `registerForActivityResult` would also settle it after recreation, through its fallback callback, but it takes a contract class and a `Serializable` input to get the same result.
- An Auth Tab result that arrives with nothing waiting on it, which is what a process death during the tab leaves behind, is logged and dropped. Picking that sign-in back up would take the redeem proof outliving the process, and the flow holds it in memory. The result may never reach the module at all, so the app doesn't rely on it: `whileAuthTabOpen` in `apps/mobile/lib/oauthResult.ts` writes a marker to AsyncStorage, tagged with the launch, while the tab is open, and the gate shows the retry message when it finds one an earlier launch left. It lives in JS so the login ships to builds that already have the module. A failed marker read or write is logged and the sign-in goes ahead, since the marker only adds a message.
- The result carries Android's raw result code next to the mapped type, so a code the module doesn't know shows up in the log rather than as a bare `unknown`.
- `openAsync` rejects with `ERR_AUTH_TAB_UNSUPPORTED` when the default browser has no Auth Tab by the time it runs. Launching the intent without a package would hand the consent URL to whatever opens it, which may never return the redirect.
- On Android, `modules/auth-tab` loads its native module with `requireNativeModule`, so a binary built without it fails at startup instead of silently opening a Custom Tab.
- The app requests only Apple's email scope. Mobile sign-in never creates an account, so a name has no use.
- A request that never gets a response counts as a network failure. Expo installs `expo/fetch` as the global fetch, and it rejects with a `FetchError` whose message starts with `fetch failed: `. The class isn't exported, so the prefix is what the app matches. Any other rejection, including a refusal the client throws on and a `TypeError` from a bug, is logged and counts as `failed`. The tests build the error from `expo/src/winter/fetch/FetchErrors`, so an Expo upgrade that changes the format fails them.
- The sign-in flow (native token or browser session, then the server) lives in `apps/mobile/lib/oauthSignIn.ts`, which takes the native steps as a `NativeSignIn` argument. `apps/mobile/lib/oauth.ts` holds only those steps and passes them in. Native modules don't load under bun, and the repo's lint bans `mock.module` because bun never restores it, so this split is what lets `oauthSignIn.test.ts` cover the flow against `serveApi`. The SDK calls in `oauth.ts` stay untested.
- The app signs out of the Google SDK after every attempt. Otherwise the SDK reuses the account it just picked, and a member told "no account found" can't choose a different Google account.

## Server

- A new `OAuthAuthService.signIn` holds the "existing provider identity, else matching verified email" half of `authenticate`. `authenticate` calls it and then creates an account when there is an invite. The mobile endpoints only call `signIn`, so no mobile path can reach account creation.
- `authenticate` creates an account whenever the state carries a referral code that resolves, which is a one-time invite, a campaign code, or a member's referral link. That is the web signup rule already, and REQUIREMENTS.md's "requires an invite" is read as "requires one of those" rather than as a narrowing of the web flow. The e2e test pins the one-time invite case, including that the invite is spent.
- `POST /auth/:provider/native` takes a native id token and answers with tokens or an `OAuthError` in a 200 body. No account, an unverified email, and a conflict are outcomes the app branches on, and the generated client throws on non-2xx.
- The browser fallback reuses the web callback:
  - `POST /auth/:provider/native/browser` mints the proof and returns it with the consent URL and the return link. The state records `origin: mobile` and that link.
  - The callback skips the cookie check for mobile flows, because a system browser session shares no cookies with the app. It signs in, then redirects to the state's return link with a short-lived signed handoff (user id, provider, outcome, proof hash) or an `error`.
  - `POST /auth/:provider/native/redeem` issues tokens only to the caller holding the matching proof. An app that registers the `alliance` scheme and catches the redirect gets a handoff it can't redeem. The proof does not cover an attacker who starts the flow themselves and holds it, which is why a deployed server returns on a verified App Link. The callback page's `intent:` link is the one way past that check, covered below.
- The server picks the return link and the app waits on the one the session response names. Deployed, it is `/mobile/oauth-callback` on `APP_URL`'s host. Against a local or test server it is `alliance://oauth-callback`, because a dev build can't claim the https path. There is no request parameter: the attacker is the caller, so letting the caller pick the scheme on a deployed server would reopen what the App Link closes. No shipped build uses the browser fallback yet, so nothing needs the scheme in production.
- `assetlinks.json` on the web app's hosts names `com.alliance.alliancemobile` alone, with the Play App Signing and upload certificates. The dev package is signed with Expo's template debug keystore, which ships inside `expo-template-bare-minimum` with the password `android`, so naming it would let any app built against that public key claim our links. Dev builds use the scheme instead, and `app.config.js` gives the intent filter to the production variant only. The filter lists both `worldalliance.org` and `thealliance.org`, so the app claims the link whichever of them `APP_URL` names. It matches on `path` rather than `pathPrefix`: the query carries the handoff and Android ignores it either way, so a prefix would only claim paths the web app may add later, which `isOAuthReturnLink` then hands to the router to 404 on.
- Only Android claims the https path. iOS reaches the browser fallback for neither provider, so the AASA file keeps to `webcredentials`.
- An app that opens the consent page in its own WebView reads the redirect itself, App Link or not. Google refuses sign-in inside a WebView and Apple doesn't. Closing that takes app attestation at redeem, which this task leaves out.
- `/mobile/oauth-callback` is a real page on the web app. It renders when the browser kept the redirect instead of handing it to the app, which a Custom Tab can do even for a verified link. With a query string, the page shows a "Return to the app" button that opens `intent://<host>/mobile/oauth-callback?<query>` naming `com.alliance.alliancemobile`. A tap is a user gesture, and an `intent:` link that names a package opens that app without depending on how Chrome treats App Links. The sign-in still waiting in the app reads the handoff or error from it. The prompt above the button promises only a return to the app, since the query may carry an error. The package name lives in `apps/frontend/src/lib/mobileApp.ts`, which the onboarding step's Play Store link also uses. If the member went back to the app first, `expo-web-browser` has already ended the session as dismissed and `+native-intent` drops the link, so the page still points to trying again or email and password. Without a query string there is nothing to return, and the page only says sign-in didn't finish.
- The `intent:` link checks the package name, not the signing certificate. An app installed from outside Play under `com.alliance.alliancemobile` that starts a flow itself would receive the handoff through the button, where the verified App Link and the Auth Tab would refuse it. The button is kept because that app has to replace the real one, which already takes a sideload the member agreed to. A member who signs in with Google or Apple never gives the app a password, so the button does give such an app a session it couldn't otherwise get. `mobileReturnUrl`'s comment says so. The stricter option, forwarding only an `error` and never a `handoff`, brings the dead end back.
- `/mobile/oauth-callback` doesn't start PostHog. The handoff arrives in the page's query string, and PostHog sends the full URL with the pageview.
- The SSR server mounts `/.well-known` on its own `express.static`. The catch-all one skips dot-directories, so it answered 404 for both association files. The deploy's HTTPS checks fetch `assetlinks.json` on both domains, because a missing file otherwise only shows up as a store build that never returns to the app.
- The handoff is good for 5 minutes and redeems once. It is spent only after the proof matches, so a handoff another app caught can't be burned out from under the app the flow belongs to.
- A `spent_token` row records the sha256 of each redeemed handoff, and the insert decides, so two requests racing one handoff can't both redeem it. A row keeps for the handoff's 5 minutes, and an hourly cron drops it once `expiresAt` passes.
- The browser flow's redirect URI is the web app's origin (`APP_URL`) under `/api` when deployed, which is already registered with both providers. In development it is the request origin, same as the web flow. Providers will refuse a LAN IP, so the browser fallback only works deployed or against localhost.
- A mobile-flow state that fails only on expiry sends the app `error=expired` rather than the web login page. Web flows keep their existing behavior.
- A mobile flow reports a provider's `error` on the callback as `cancelled` only for that provider's cancel code (Google `access_denied`, Apple `user_cancelled_authorize`). Any other error, or a callback with no code, is `failed`, so the app shows a retryable error rather than the neutral cancellation note. Web flows still read every provider error as a cancellation.
- `OAuthError.Expired` is new in `common/src/oauth.ts`. Web never emits it but its message record needs an entry.
- `OAuthOrigin` is `web` or `mobile`. The callback switches on it and runs a separate web or mobile flow, so a third origin is a compile error rather than a silent web flow, and a check added to one flow doesn't run in the other. Mobile states still carry `intent: authenticate`, which the mobile flow never reads. Dropping it would take a state type split by origin, and states are cast from the JWT rather than parsed, so the split wouldn't be checked.
- `verifyState` reads a missing `origin` as `web`. A state minted before this deploy has none, and some are still in flight while it rolls out.
- The handoff is parsed with a zod schema rather than cast. Every token this server signs shares one secret, and the app holds a state token too; without the shape check a state token redeems as a handoff, and because a mobile state has no `userId`, `findOneBy({ id: undefined })` returns an arbitrary user.
- The redeem endpoint answers `failed` when the handoff's user no longer exists.
- The server accepts a native id token more than once. On Android, `@react-native-google-signin/google-signin` 16.1.5 signs in through Play services' legacy `GoogleSignInClient`, which is expected to return the same cached id token until it expires (not yet checked on a device). Refusing a repeat would then fail a member who logs out and back in within the hour, and every retry after it. The replay it would prevent exposes nothing new: the same response carries a 1-day access token and a 30-day refresh token, and the server logs no request bodies.
- `/auth/login` and `/auth/register` set the auth cookies whatever `mode` asked for, and `extractAccessToken` falls back to the access cookie. The mobile app therefore held a second session it didn't track, which outlived its stored tokens whenever the logout request failed to reach the server, so cookies now follow the mode, as they already did on `/auth/refresh`. Header mode clears the pair rather than skipping it, because every install that signed in against the old server is carrying one. It clears before checking the credentials, so a rejected sign-in drops the pair too. Only the app and the e2e specs send header mode.
- Neither native id token carries a nonce, so anyone holding a token issued to the app can trade it for a session until it expires: 10 minutes for Apple, an hour for Google. `@react-native-google-signin/google-signin` has no nonce outside its paid tier, and binding only Apple's would leave Google's path open. Getting such a token takes a leak from the app's own sign-in, and the server logs no request bodies.

## Login surface

- `/onboarding` (the `WelcomeGate`) is the one login screen. The provider buttons are white, with Google's four-color mark and Apple's black logo, to match the gate's existing white "Log in" button on the photo. The unauthenticated redirect and logout already land there. `app/auth/login.tsx` is deleted, and the one link to it (the action page's "Log in to complete this task") points at `/onboarding`. `skills/playwright/MOBILE.md` named the old route and now names `/onboarding`.
- Provider buttons show only in `AccountMode.LogIn`. The dormant sign-up mode stays untouched.
- Apple's button sits above Google's, which its button guidelines ask for in a stacked layout. The order comes from a `Record<OAuthProvider, number>` rank, so a provider added later has to be given one. It holds on Android too, where nothing asks for it either way, rather than growing a platform branch. The web gate keeps declaration order.
- The email field no longer autofocuses. With provider buttons above it, an open keyboard would push them and the title off small screens.
- A provider failure writes to its own line under the provider buttons rather than the gate's shared `error` and `notice` lines below the password field, which is where the member's tap was. `FAILURE_TONE` in `apps/mobile/lib/oauthResult.ts` gives each failure a neutral or error tone and `AccountFields` keys the colour off the same enum, so a new `OAuthError` doesn't compile until it has one. The interrupted-return message uses that line too. The buttons come back enabled on a failure, so a retry is one tap, and stay disabled on success: the gate fades for 200ms before it routes, and a tap in that window would start a sign-in behind a screen on its way out.
- The session tokens reach secure storage only once the profile has loaded. Written before it, they outlive a sign-in the member was told had failed and sign them in on the next launch. Password login had the same hole, so the fix is its own commit ahead of this one.
- A failed token save drops the header and clears both stored tokens. The access token is written first, so a failure on the refresh token would otherwise leave it to sign the member in on the next launch. If clearing fails too, the error is an `AggregateError` holding both, since that access token may still be on disk and nothing else reports it.
- The half of `startSession` below React state lives in `apps/mobile/lib/session.ts`. `AuthContext` pulls in secure storage, the router and PostHog, none of which load under bun, so the split is what lets `session.test.ts` cover the order against `serveApi`.
- `setAuthHeader` drops the header by setting it to `null`. `client.setConfig` merges headers into the ones already set, so an empty object would leave the member's token on every later request.
- Logging out drops the header too. `clearSession` cleared the stored tokens and the user but left the token on the client, so every query the screens refired after it went out as the member who just left. `closeSession` in `apps/mobile/lib/session.ts` drops it after sending the logout request, because the server attributes the logout to the token on that request.
- The logout request stays fire-and-forget, since the server only uses it to attribute the event. Its failure is logged rather than left as an unhandled rejection.
- `closeSession` waits on the token delete and returns its failure. Tokens left in secure storage sign the member back in on the next launch, so `logout` shows an alert that says so, with a button that retries the delete. `clearTokensAndReport` in `AuthContext.tsx` sends every failed delete to `captureException` as `ClearSessionTokensFailed`, forwarded to Slack, since in a release build `console.error` only reaches the device log. Reporting it there covers logout, the launch, and login clearing tokens it failed to save, where the member sees only a login error. The alert's retries call `clearSessionTokens`, which skips the report, so one stuck logout sends one Slack message however many times the member taps "Try again". The launch, which clears the session when loading the profile fails, only reports a failed delete: the member there never asked to log out, and signing them back in on the next launch is what they'd want anyway. The retry loop lives in `retryClearTokens` in `session.ts`, which takes the alert as an `askToRetry` callback, so `session.test.ts` covers it. The browser can't, since react-native-web's `Alert.alert` does nothing. `clearStoredTokens` reads both keys back after deleting them and fails if either is left, because expo-secure-store's iOS delete ignores the keychain's result and never rejects. The screen still logs out at once rather than waiting on the keychain. The real fix is server logout revoking the tokens, but refresh tokens are stateless JWTs, so that takes server-side state and changes web logout too. It is left out of this task.
- The launch clears the session only when `/auth/me` still answers 401 after the 401 handler has tried a refresh. The handler used to call the refresh with the client's `throwOnError: true`, so a refresh token the server refused (it answers 401 for an expired or revoked one) threw instead of leaving the 401, and the launch would have read the most common logout as a network error and kept the dead tokens. `refreshingFetch` in `apps/mobile/lib/session.ts` now calls it with `throwOnError: false`: a refused refresh returns the original 401, and any other refresh failure throws. It lives in `session.ts` rather than `_layout.tsx` so `session.test.ts` can run `loadSessionUser` through the refresh, which the `serveApi` helper otherwise replaces. The mobile client throws on network errors and 5xx too, so clearing on any failure would delete the tokens of a member who opens the app offline or during an outage and log them out for good. Those failures keep the tokens for the next launch to try. `restoreSession` in `apps/mobile/lib/session.ts` holds that branch, so `session.test.ts` covers which failures drop the session. It sends a failure to `captureException` as `SessionLoadFailed`, since `console.error` never leaves a release build. A request that got no response is only logged: an offline launch is routine, and `isNetworkFailure` in `apps/mobile/lib/network.ts` spots one by `expo/fetch`'s `fetch failed: ` prefix. `SessionLoadFailed` isn't forwarded to Slack, because during an outage every member's launch would post one. `loadSessionUser` in `apps/mobile/lib/session.ts` makes the call with `throwOnError: false` so it can read the status, and returns `SessionRefusedError` for the 401. A launch that keeps the tokens this way shows a screen in the app layout, "We couldn't load your account" with a Try again button, in place of the app shell or onboarding. The retry runs the launch's load again, with no automatic retry when the connection comes back. A "Log in again" button beside it logs out and goes to onboarding, since a secure-storage read that keeps failing (expo-secure-store still throws `DecryptException` on Android for an item it can't decrypt) fails every retry the same way, and logging in again overwrites the stored tokens. The copy names no single cause for the same reason. Starting or clearing a session turns the screen off, so a login that lands while it is up goes home. The layout sends any launch that settles with no member to onboarding, with no separate health check. The retry screen covers every load that can't settle, and a health check that failed offline would hold a member with nothing stored, or a session the retry dropped, on an empty app shell. `AuthFailedToRefresh` fires only on a refusal. `restoreSession` also reads the stored tokens, so a secure-storage read that fails is reported as `SessionLoadFailed` and keeps the tokens like any other failure that isn't a refusal. The launch used to clear the session on it.
- A launch with neither token stored settles on no member without calling `/auth/me`. The call's 401 ran the refusal path, which recorded `AuthFailedToRefresh` and sent a logout request on every logged-out app open, and a 5xx reported `SessionLoadFailed` for a member with no session. A stored refresh token alone still makes the call, since `refreshingFetch` restores the session from it, and a refusal drops it so the dead token isn't retried on every launch. `restoreSession` reads the refresh token only when no access token is stored, so a failed read of a token the launch doesn't need can't keep a member with a good access token logged out.
- A launch load that a login or logout overtakes changes nothing. A member can log in from onboarding while it is still out, since an invite or OAuth return link opens the app there. `restoreSession` in `apps/mobile/lib/session.ts` notes the session it started under and fails with `SessionOvertakenError` once that session has moved. It checks after each stored-token read as well as after `/auth/me`: an access token read after the login would put the old session's token on the client in place of the new one, and a read that finds nothing would settle on no member over the new login. The check comes before `dropSession`, since a refusal of the old session would otherwise clear the new login's tokens.
- The 401 handler and the messaging socket refresh through one `refreshSession` in `apps/mobile/lib/session.ts`, so `session.test.ts` covers both. The messaging copy used to save only the new access token, dropping the new refresh token, and called the refresh with the client's `throwOnError: true`, so a refused refresh token threw where it meant to return nothing. `saveSessionTokens` moved from `AuthContext.tsx` to `SecureStorage.ts` beside the token getters, so `messages.ts` can save both tokens without importing the React provider. The `SessionTokens` type moved with it, so the keychain module doesn't reach back up into `session.ts` for the shape it writes. The socket's `getAuthToken` is `getAccessToken` rather than its own read of the same key, so every token read in the app goes through those getters. `refreshSession` returns a `Result`, so a refresh the server couldn't answer is in its type rather than only in its doc comment, and no token still means both "nothing stored" and "the server refused what is", which is one outcome to each caller. `refreshingFetch` unwraps it because it implements `fetch`. The messaging adapter maps the token to a boolean inside the `Result`, so `attachAuthRefresh` can log a failure without converting it to an exception. A keychain read that throws is a failure in that `Result` too, the way `restoreSession` already reads the same keys, so nothing rejects past the return type.
- A refresh the server answers with an access token and no refresh token fails, rather than saving the half it got. Header mode returns both or neither, so the pair should never arrive split, but `RefreshTokensResponseDto` marks each one optional for the cookie mode that returns neither. `saveSessionTokens` used to skip a missing refresh token and keep the stored one, which pairs the new access token with whoever was signed in before it. `SessionTokens` now requires both, so nothing can ask for a half save. `openSession` already takes a `SessionTokensDto` whose tokens are both required.
- After a refresh, `attachAuthRefresh` in `shared/lib/messages.ts` reconnects without writing the new token onto the socket. It used to set `socket.auth = { token }`, which replaced the callback `buildSocketOptions` installs to read the stored token on every connection attempt, so every reconnect after the first refresh sent that one token until the next refresh replaced it. `refreshSession` saves before it resolves, so the callback reads the refreshed token. `MessagingConnectionConfig` requires `getAuthToken` whenever a refresh callback is supplied. The callback returns `Result<boolean, Error>`: true means the refreshed token is saved, false means the session is absent or refused, and failure preserves the error. The socket reads the saved token rather than consuming a returned token. The web app passes neither callback and authenticates the socket with cookies, so this changes nothing there.
- Authentication rejection in Socket.IO middleware requires an explicit `socket.connect()` after refresh. Transient refresh failures retry through `es-toolkit` with delays starting at one second and doubling up to thirty seconds. A refused or absent session disconnects; a refreshed token that the socket still cannot authenticate logs the rejection and stops, preventing repeated refreshes against a server refusing its own token. A successful connection permits refresh at the next expiry. `connectMessagingSocket` returns `close`, which aborts retries, ignores a refresh still in flight, and disconnects, so a caller can't disconnect without stopping the refresh. The callback keeps `Result<boolean, Error>` because callers need only whether refresh established a session; an absent session is an expected outcome. Integration tests use a Socket.IO server so middleware rejection and reconnection run through the client's lifecycle.
- A token refresh that returns after logout is dropped. `apps/mobile/lib/session.ts` numbers each session: `openSession` opens the next one once the login's tokens are saved, `closeSession` closes it, and the app launches with one open so a stored session can refresh. `openSession` also closes the session before it loads the profile, since the login replaces it either way, so a login whose own access token is refused can't refresh with the tokens the last session left stored. Closing it there covers a login that follows a launch, not only one that follows a logout. The 401 refresh in `refreshingFetch` notes the session when its request goes out and skips the refresh when that session has closed or been replaced. The messaging socket goes through `refreshOpenSession`, which reads the open session and skips the call to the server while none is open. Both save and set the new token through `applyRefresh`, which skips the save and the header if the session moved. It checks again after the save, since logout and login close the session without waiting for the save, and the save runs on the same token-write queue as the logout's delete, so a logout that lands mid-save deletes after it. Without any of this, a refresh that was in flight at logout wrote the tokens back and put the header back on the client. The closed state, not the counter alone, covers a request sent between logout and the finished delete: its 401 would otherwise read the still-stored refresh token and reopen the session, and the same after a delete that failed. Skipping the refresh for requests sent without a token would have covered only the fetch wrapper, not the messaging socket. Sessions are numbered from one so that a later `if (!currentSession())` can't read the launch's session as a closed one; every check reads it against `undefined` today. `__resetSessionForTests` puts the counter back where the module starts, since `session.test.ts` shares one copy of the module across its tests. It throws unless `__DEV__`, which Metro sets, rather than reading `NODE_ENV`: a build made without `NODE_ENV` set reads as non-production and would let the app reopen a closed session through it.
- A logout's token delete, a login's token save, and a refresh's token save run one at a time, through a queue in `session.ts`. `closeSession` reads the session and deletes in one turn of it, `openSession` saves and opens the next session in another, and `applyRefresh` checks its session and saves in a third, so the delete either runs before the login's save or finds a session open and leaves the tokens alone, and a refresh save from the session a login replaces lands before the login's save. One queue carries all three, rather than a queue for the delete and the login's save beside a set of refresh saves they wait on, since both enforce the same rule and a write that never settles has to be bounded in both. The retry after a failed logout delete goes through the same queue and session check, since a delete queued behind a slow write leaves time for a login to land before the member taps "Try again". So does the delete after a login that failed to save its tokens: queued behind a second login's save, it would otherwise delete the tokens that login just saved. Reading the session without the queue left a window the width of the keychain delete, and a login that landed inside it finished, ran on a session the member kept using, and opened the next time logged out with nothing to explain it. Serialising logout and login in `AuthContext.tsx` instead would have left the same hole in `session.ts` for the next caller to fall into.
- Each queued token write gets five seconds, through the `withTimeout` from `common/src/timeout.ts`, before the next one starts. A keychain write that never settles would otherwise hold every write behind it forever: a logout's delete that never settled left the next login on its spinner until the app was killed. The clock starts when the write starts, not when it is queued, so a write waiting behind a slow one keeps its full five seconds. A write the deadline gives up on still lands later, so the last token write (a logout's delete, a login's save, or an open session's refresh save) runs again once it does. The member is past the retry alert at that point, so a silent second write is what's left; returning a failure on the deadline instead would alert a member whose tokens really are gone, which is the common case for a write that never settles.
- The app's API client asks for `credentials: "omit"`. `createClientConfig` is shared with the web apps, which need `include`, so it branches on `navigator.product`; `expo/fetch` reads the flag and skips the cookie store. Clearing the cookies server-side only reaches the requests the server sees, never a sign-in the member cancels at the provider or a launch where secure storage is empty and the cookie is not.
- The password form says "Invalid email or password" only when `/auth/login` answers 401 or 400 (a malformed email or an empty password). A request that gets no response, from the login or the profile load after it, shows the same "Check your connection" message as a provider sign-in and isn't reported, since every tap while offline would otherwise post to Slack. Anything else, like a failed token save, is logged, reported through `captureException` as `PasswordLoginFailed`, and shows "We couldn't log you in. Please try again." Reading every failure as a wrong password would send a member whose token save failed back to retry the same password, and drop the error `openSession` builds for that case. `requestTokens` in `apps/mobile/lib/session.ts` makes the call with `throwOnError: false` so it can read the status, and returns `CredentialsRefusedError` for a refusal; `passwordLoginFailure` beside it picks the message and whether to report. The web login form still reads every failure as a wrong password.
- `loginWithProvider` never rejects. Anything that throws during an attempt, like secure storage or a device with no browser, is logged and shows as `failed`. Otherwise the pending provider would stay set and keep every control on the gate disabled.
- `expo-router` would treat the return link as a route. `app/+native-intent.tsx` returns `null` for both the scheme and the https path, which leaves the login screen mounted while `expo-web-browser` reads the URL. The https path only matches on a host the web app answers on, by `isAllianceAppHostname`, so a link that merely ends in `/mobile/oauth-callback` still reaches the router rather than disappearing. A link that doesn't parse as a URL passes through to the router, which tolerates it; throwing there would crash an iOS cold start.
- A return link that arrives as the app's initial URL is the one Android killed the process for while the browser session ran. Nothing is waiting on it — the redeem proof was in memory — so dropping it leaves a tap that did nothing. It goes to the gate instead. A link carrying an error shows that error's message, so a member with no account isn't sent through the provider again to hear it; a link carrying a handoff asks for a retry. Neither names one provider ("Google or Apple"), because the flow that knew which one is gone. Redeeming it would take the proof outliving the process, which is the same thing the Auth Tab module declined to build. A stale link from the web page's button can also cold-start the app for a member who got in some other way; the gate sends a signed-in member home rather than showing them the login, and clears the param once read so a later login there still fades out.
- `+native-intent.tsx` is the export alone; the decision behind it is `oauthReturnRedirect` in `apps/mobile/lib/oauthResult.ts`, with its test. Metro bundles every file under `app/`, so a test there breaks the bundle on `bun:test`.
- `handoffFromReturnLink` parses the link through `R.fromThrowable`. A bare `new URL` would throw past the flow's `Result` type, to be caught in `loginWithProvider` and logged with the whole link, handoff token and all.

## Copy

Mobile-only wording, in `apps/mobile/lib/oauthResult.ts`:

- No account: names the other ways in on the same screen (another Google or Apple account, email and password). The web copy tells the member to ask for an invite link, which reads as a signup pointer.
- Provider already connected: the web copy says "Disconnect that one first", but mobile has no disconnect control. Mobile tells the member to use the connected account or their password.
- Network: "We couldn't reach the Alliance. Check your connection and try again."

The rest reuse `oauthErrorMessage`.

## Configuration

- The Google client ids the user supplied are constants, not env vars: the web one in `apps/mobile/lib/oauth.ts`, the iOS ones in `apps/mobile/app.config.js`. They ship inside the app binary anyway, and a missing env var would break every prebuild and dev server. The web one duplicates the server's `GOOGLE_CLIENT_ID`, which nothing checks and no test can see across both processes, so each side's comment names the other. Having the server hand the app the id instead would cost a round trip before every Google sign-in to guard a value that is public and effectively permanent.
- Dev and production builds have separate iOS clients. `app.config.js` picks one by `APP_VARIANT`, derives the URL scheme from it, and passes it to the app as `extra.googleIosClientId`, so the id lives in one place. A missing id fails the Google attempt on iOS with `failed` and logs it.
- The app never names the Android client ids. Google matches Android clients on package name and signing certificate.
- The deployed browser fallback redirects to `APP_URL`'s host. Both providers list that host's `/api/auth/<provider>/callback` for the production and staging domains, so `APP_URL` must stay one of the registered hosts.
- `app.config.js` sets `CFBundleAllowMixedLocalizations` to `false`. The `expo-apple-authentication` plugin turns it on when it's unset, so its `AppleAuthenticationButton` shows localized text. The app draws its own Apple button, and turning the flag on would put UIKit's own strings, like Cancel and Paste, in the device language across an otherwise English app.
