# Decisions

The user asked for ALL-2139 as filed and was not asked about each of its points. The issue's points come from `01a1ccef-8e76-75bb-9655-d39c48ef9c28-finish-thealliance-move` (its `DECISIONS.md`) and are recorded here as that source's proposals, followed in full unless an entry below says otherwise.

- Consumers no longer read which domain is new from which field holds it. `domainMove()` in `common/src/deployed-config.ts` takes the legacy domain to be whichever of the two `isLegacyAllianceHost` accepts, and the environment has cut over when that is `ALT_DOMAIN_NAME`. nginx's redirect direction, the server's `siteBaseUrl()` and the web's `getInviteBaseUrl()` follow it (the last two through `preferNewDomain()` in `common/src/url.ts`). This revises the earlier task's decision that each cutover must not simply swap the two values: after this change a swap is the whole config change, so ALL-2140 cannot reverse the redirects or links by doing only that. Deriving rather than adding a separate cutover flag leaves no state where the flag and the domains disagree. `domainMove()` throws unless exactly one of the two is legacy, and a test runs it over each deployed config. (agent decision)
- Symmetric consumers stay as they were: CORS origins, `siteUrlForHost`, link tagging, the admin panel's host matching and the Twilio signature check each treat both URLs alike. (agent decision, from reading each consumer)
- The admin deploy's certificate check moves to `deploy/nginx/check-cert.sh`, so the frontend deploy runs the same rule rather than a copy. It reports every missing name, and its printed certbot command names every name it was given, because certbot's `-d` list replaces a lineage's names (certbot user guide, "Changing a Certificate's Domains", from memory, not re-checked). (agent decision, from the round-3 review)
- The frontend deploy now checks that the `DOMAIN_NAME` certificate lineage covers the names the vhost serves, as the admin deploy already did, before it changes anything on the host. A new `DOMAIN_NAME` points nginx at a different lineage, and a missing one would otherwise fail every later `nginx -t`. The names are both domains plus, in production, their `www.` names: alliance.conf lists `www.` in both environments, but only production's DNS resolves them and only production's certificate covers them (live certificates read with `openssl s_client` in the round-3 review). Keying on the environment rather than on DNS lookups on the host keeps a failed lookup from silently skipping a name. (agent decision)
- `/.well-known/` gets its own location, because `location /` serves it and is where the cutover's redirect goes. It keeps that location's `Cache-Control` header. Deploy health checks require `/api/`, the PostHog proxy and both association files to answer `200` on both domains, because installed apps call the legacy domain and Apple and Android fetch association files without following redirects (`EVIDENCE.md`, "Vendor requirements"); `EVIDENCE.md` shows all of them answered `200` on every host before the change. (agent decision, implementing the forwarded source's "update the health checks")
- On cutover, nginx answers each document navigation on a legacy host with a `302` to the same path and query on the new host, except under `/api/`, `/events/`, `/socket.io/`, `/.well-known/` and `/assets/`. The first four are the forwarded source's. `/assets/` is added because a tab loaded before the cutover keeps fetching its hashed chunks there, and redirecting a module script cross-origin fails without CORS headers. The same holds for that tab's other fetches, such as React Router's `.data` requests and the `/build-version` check, so only requests whose `Sec-Fetch-Mode` is `navigate` move; the tab's next full page load then moves it. A request with no `Sec-Fetch-Mode`, from a browser older than Fetch Metadata (Safari before 16.4, per MDN, agent recall not re-checked), moves only when its `Accept` names `text/html`, which a page load's does and a script's `fetch()` default `*/*` doesn't, so those browsers' stale tabs keep working too (round-5 review). curl and other clients sending neither stay on the legacy domain and get its page. Keying on the header rather than exempting those paths keeps a same-origin fetch route added later working without an edit here. (agent decision; exempt list partly forwarded source; `Sec-Fetch-Mode` from the round-1 review)
- Whether a request moves is set by `map "__DOMAIN_MOVE__:$http_sec_fetch_mode:$http_accept" $moved_host`, a map over the constant the deploy substitutes, the request's fetch mode and its `Accept`, so one template serves both states and production's rendered config behaves as before (`EVIDENCE.md`). The map and the page-load health check spell out `cut-over` by hand, so `scripts/deployed-config.test.ts` ties both to `DomainMove.CutOver`, where a renamed value would otherwise leave the redirect silently off with green checks (round-3 review). (agent decision)
- The page-load health check expects the legacy domain to serve a page load before the cutover and, after it, to move a navigation (`Sec-Fetch-Mode: navigate`) and a request with no `Sec-Fetch-Mode` asking for `text/html` to the new domain while serving a fetch (`Sec-Fetch-Mode: cors`) and a request sending neither header. It expects the new domain to serve both without a redirect in either state, so a redirect that misfires there fails the deploy (round-4 review). (agent decision)
- The move carries no marker and the log-in screen shows no notice explaining it. Asked how the move should be announced, the user deferred: "whatever is easiest in the code. maybe even not show it at all?", noting the redirect is transient and that few people still arrive on worldalliance.org, mostly through old links. Showing nothing is the least code, so the notice the forwarded source proposed (title "We’ve moved to thealliance.org" on the log-in screen, from a `domain_moved=1` marker the redirect added) is dropped for this task, superseding that source's decision here. A member moved from a legacy page is signed out, since a session cookie doesn't cross domains, and logs in again without being told why. That includes a Google or Apple sign-in started from a tab loaded on the legacy domain before the cutover: its callback stays on the legacy domain and sets the session there, so the member lands on the new domain signed out after a sign-in that succeeded, and signs in again. A tab loaded on the legacy domain before the cutover is moved too, signed out, at its first page navigation after its next build check: the cutover deploy is a new build, so the stale-build hook turns that navigation into a document load, which nginx now redirects. A cookie never crosses domains, so this changes only when such a tab is signed out, not whether. Moving such a tab first, for example from the `/build-version` check, is more code than a transient redirect that few members meet needs. Bring the notice back if those sign-outs cause real friction, such as support requests or a drop in returning logins. (user deferred how the move is announced; agent decision, round-8 and round-10 reviews)
