# Decisions

The user asked for ALL-2139 as filed and was not asked about each of its points. The issue's points come from `01a1ccef-8e76-75bb-9655-d39c48ef9c28-finish-thealliance-move` (its `DECISIONS.md`) and are recorded here as that source's proposals, followed in full unless an entry below says otherwise.

- Consumers no longer read which domain is new from which field holds it. `domainMove()` in `common/src/deployed-config.ts` takes the legacy domain to be whichever of the two `isLegacyAllianceHost` accepts. nginx's redirect direction, the server's `siteBaseUrl()` and the web's `getInviteBaseUrl()` follow it (the last two through `preferNewDomain()` in `common/src/url.ts`). This revises the earlier task's decision that each cutover must not simply swap the two values: after this change a swap is the whole config change, so ALL-2140 cannot reverse the redirects or links by doing only that. Deriving rather than adding a separate cutover flag leaves no state where the flag and the domains disagree. `domainMove()` throws unless exactly one of the two is legacy, and a test runs it over each deployed config. (agent decision)
- Symmetric consumers stay as they were: CORS origins, `siteUrlForHost`, link tagging, the admin panel's host matching and the Twilio signature check each treat both URLs alike. (agent decision, from reading each consumer)
- The admin deploy's certificate check moves to `deploy/nginx/check-cert.sh`, so the frontend deploy runs the same rule rather than a copy. It reports every missing name, and its printed certbot command names every name it was given, because certbot's `-d` list replaces a lineage's names (certbot user guide, "Changing a Certificate's Domains", from memory, not re-checked). (agent decision, from the round-3 review)
- The frontend deploy now checks that the `DOMAIN_NAME` certificate lineage covers the names the vhost serves, as the admin deploy already did, before it changes anything on the host. A new `DOMAIN_NAME` points nginx at a different lineage, and a missing one would otherwise fail every later `nginx -t`. The names are both domains plus, in production, their `www.` names: alliance.conf lists `www.` in both environments, but only production's DNS resolves them and only production's certificate covers them (live certificates read with `openssl s_client` in the round-3 review). Keying on the environment rather than on DNS lookups on the host keeps a failed lookup from silently skipping a name. (agent decision)
- `/.well-known/` gets its own location, because `location /` serves it and is where the cutover's redirect goes. It keeps that location's `Cache-Control` header. Deploy health checks require `/api/`, the PostHog proxy and both association files to answer `200` on both domains, because installed apps call the legacy domain and Apple and Android fetch association files without following redirects (`EVIDENCE.md`, "Vendor requirements"); `EVIDENCE.md` shows all of them answered `200` on every host before the change. (agent decision, implementing the forwarded source's "update the health checks")
